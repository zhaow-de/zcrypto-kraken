## Observations

**2. The account object reports a single figure keyed `EUR`** — `{'EUR': '99.35730000 EUR'}` under `spot_account_type=MARGIN`, not per-asset wallet balances. The same shape the two preceding versions gave.

**3. The fill's commission currency is still `EUR`, EUR 0.08 a side**, on both legs, reproducing the reading that contradicted this project's own test fixtures at rc4 and rc6.dev20260915. Unchanged, so nothing in that finding's disposition moves.

**4. Nothing was floored and no dust remains.** The closing sell carried the same `0.00014161` the buy filled, so the round trip left no sliver below the lot step; the harness recorded no dust note and probe 6 read the account flat.

**5. Probe 2 read an empty venue, where the two preceding passes did not.** Both earlier records carry a `REVIEW` on probes 2 and 6 for the SOL/EUR order this project left resting on purpose as the fixture T0160's in-flight REST-query check needs. That order is gone: probe 2, probe 6 and the operator's own read of Kraken → Trade → Open Orders all read zero before the run. **T0160's check 6 therefore has no fixture** and is owed a fresh resting order on one of the five two-way-spelled legs. **6. The engine was untouched by the run, measured as a rise rather than as an absolute.** `zcrypto_exec_external_events_total{disposition="unmatched"}` read **0** at 20 minutes before the run and **10** after, with `resets(...[30m])` **0**, so the +10 is real and not a counter reset; `{disposition="matched"}` stayed **0**. Those are INSTANT queries, so their offset and window are relative to the moment of reading: a later reader re-runs them and gets that later moment, never this one — which is why `resets` was read beside the two values rather than after them. The series stood at 15 when the 2026-09-15 pass ended and at 0 before this run; the engine was converged twice on 2026-09-16, the 13:05:20Z re-pin and the 13:39:05Z rollback, either of which restarts the process, so the gap is a restart and not a reading lost. The matched-at-zero reading is the scope property the sealed external observer exists to provide: the engine saw the probe orders, claimed none of them, and acted on none.

**7. The pass CANNOT SAY whether the fallback this version was taken for fired, and that is a property of the fallback rather than a gap in the run.** The harness's data client is built without credentials (`infra/scripts/kraken-order-semantics-probe.py:1625`), so its 1,627-instrument listing took the public path and signed nothing. A credentialed exec client is a different matter and was built on all four recorded invocations — `add_exec_client` runs whenever `--no-exec` is absent (`:1628`), and only the uncredentialed staging run passed that flag — so the possibility is not that no signed client existed but that nothing here reads whether such a client lists instruments on connect: the adapter is one stripped extension. **On this wheel a TradeVolume denial falls back silently instead of aborting, so nothing in the run distinguishes "never called" from "called, denied, and absorbed"**. On the predecessor wheel the same denial would have aborted the listing and been unmissable; the fix is exactly what removes that signal. What the pass proves about #5005 is that the wheel carrying it behaves as its predecessor did on all six probes. What reads the fallback itself is a credentialed listing whose TradeVolume call is made to fail, and it is owed below.
