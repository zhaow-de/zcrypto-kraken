## What this version changes that this repository reads

1. **Unscoped reads resolve both spellings, and fail whole on a row they cannot place.** `request_instruments` records each pair's altname beside its AssetPairs key (`record_pair_aliases` in `crates/adapters/kraken/src/http/spot/client.rs`), so once the listing is cached an unscoped OpenOrders read, in both `open_only` shapes, and an OpenPositions read resolve `XBTEUR` and `XXBTZEUR` alike to BTC/EUR. An open order or a position on a pair the cache cannot place fails the whole read, so a bare client with nothing cached raises on the first open row its read returns; a closed order there drops out of a read that otherwise succeeds. At node start that failure is `Failed to get mass status`.
2. **A scoped read still skips a two-way-spelled pair** (#5067): it keeps only the rows spelled by the pair's AssetPairs key, so scoped to BTC/EUR it returns no row for an order Kraken's row spells `XBTEUR`.
3. **Kraken's spot REST order reports carry no client order id.** `parse_order_status_report` (`crates/adapters/kraken/src/common/parse.rs`) builds each with `client_order_id` None, and startup reconciliation names such an order `ClientOrderId(<txid>)` (`crates/live/src/execution/manager.rs`). After a restart the engine's own id therefore finds none of its orders, which is what the row keying below answers.
4. **Client order ids are cut on the wire.** `truncate_cl_ord_id` (`common/parse.rs`) sends a free-text id of at most 18 characters as it is, a 36-character UUID and a 32-hex id whole, and any other longer id as `O` plus its last 17 characters, on every AddOrder, cancel and amend. The red button's `FLT<yymmddHHMMSS>-<n>` (17 characters through `n`=9, 18 through 99) and the fixture mint's 17-character ids reach Kraken as minted; the engine's `O-YYYYMMDD-HHMMSS-001-000-n` reaches it as `O-HHMMSS-001-000-n`.
5. **A node refuses to start over a Kraken margin position its reconciliation cannot rebuild.** The adapter's OpenPositions report carries no `avg_px_open`, and with `filter_position_reports` at its `False` default the start stops with `Unresolved positions during startup reconciliation ... missing avg_px_open for position recovery`. The operating rule below is the owner's answer.
6. **`LiveExecutionEngineConfig` gains `submission_recovery_policy`**, default `RESOLVE_LOCALLY`. The wheel reports 38 fields, and `tests/test_nautilus_interface_pin.py::test_every_exec_engine_default_is_the_one_we_measured` pins all 38.
7. **TradeVolume.** The credentialed listing takes the account's fee tier from `POST /0/private/TradeVolume`. An error, or an answer that does not deserialize, falls back to the public fees (#5005, logged as the WARN `Failed to request Kraken account fee rates, falling back to public rates`); a well-formed answer that omits a pair's fee fails the whole listing.

## The operating rule on this pin: no engine restart with a margin position open

The owner's ruling of 2026-09-23, binding until a pin carries upstream #5065: no engine converge or restart while a Kraken margin position is open. On this version such a restart either fails startup (`Unresolved positions during startup reconciliation ... missing avg_px_open`) and crash-loops, or boots with the position's entry price at 0, where only the realized-PnL gauge is wrong; which of the two depends on the pair's fill history. The red button clears a crash loop: its wrapper stops the unit, and it does not reconcile. So the window below has no step 6, the restart with the fixture's margin position open, and each restart in it follows a `kraken positions -o json` that prints no position.
