## Observations

**1. Post-only protection is unchanged, and the event stream still distinguishes it.** A crossing post-only is accepted and then venue-canceled, surfaced as `OrderCanceled` with no `OrderRejected` — as at 1.230.0, 1.231.0 and 2.0.0rc4.dev20260825. The distinguishing evidence is the cancel path: 4a/4c/4d each carry an `OrderPendingCancel` (our own cancel) and close `reason=User requested`, while 4b goes `OrderAccepted → OrderCanceled` **at the same millisecond (`.696`) with no `OrderPendingCancel`** and `reason=Post only order`. The engine's rule — treat `OrderCanceled` on a post-only as the "would cross" signal — remains correct and needs no change.

**2. The account object reports a single figure keyed `EUR`**, not per-asset wallet balances — `{'EUR': '99.51730000 EUR'}` under `spot_account_type=MARGIN`. The same shape the previous version gave.

**3. The fill's commission currency is still `EUR` at precision 2** — `Currency(code='EUR', precision=2, iso4217=978, name='Euro', currency_type=FIAT)` — on both legs, reproducing the `2.0.0rc4.dev20260825` reading that contradicted this project's own test fixtures. Unchanged at this version, so nothing in that finding's disposition moves.

**4. A SPOT buy under `spot_account_type=MARGIN` DOES open an OpenPositions row**, reproducing the `2.0.0rc4.dev20260825` reading the harness asks to re-take per build: the post-buy print read `open positions=1`. The balance at that same instant read `{'EUR': '99.51730000 EUR'}` — **unchanged from before the buy**, so neither the ~EUR 10 spend nor the buy's own EUR 0.08 commission had reached the account figure yet; both commissions appear only in the post-round-trip read. Recorded as the shape this build reports, not as an expectation for the next.

**5. Nothing was floored and no dust remains.** The closing sell carried the same `0.00015217` the buy filled, so the round trip left no sliver below the lot step — the harness recorded no dust note, and probe 6 read the account flat.

**6. An externally-placed order carries its quantity into the cache but not its price.** At node teardown the run logged `Residual LimitOrder(BUY 0.06000000 SOL/EUR.KRAKEN LIMIT @ 0.00 GTC, status=ACCEPTED, client_order_id=O76GEO-6CABP-OSH2K2, venue_order_id=O76GEO-6CABP-OSH2K2, tags=Some([u!("VENUE")]))`. Instrument, side, quantity, status, both ids and the `VENUE` tag are all correct; the venue holds that order at **37.54 EUR** and the cache renders it **`@ 0.00`**. This is the first attended pass able to see it at all — the `2.0.0rc4.dev20260825` run read `open orders 0, open positions 0`, so no externally-placed order was in its cache to render. **Nothing under `cli/` consumes it:** the two `.price` reads in `cli/engine/executor.py` are on `sized.price`, the engine's own sizing for orders it submits, and the paths that touch adopted external orders — `_cancel_resting`, `_adopt_resting_orders`, `_reconcile_adopted_rows` — cancel by id and classify by status, never by price. Recorded as an adapter reading with its blast radius measured, not as a defect this repo carries.

**7. The engine was untouched by the run.** Read by value from the workstation afterwards: `zcrypto_exec_kill_tripped` **0**; every `zcrypto_exec_position` series **0** across all twelve symbols; `zcrypto_exec_external_events_total{disposition="matched"}` **0** and `{disposition="unmatched"}` **5 → 15**, a rise of **+10 within one process** — `process_start_time_seconds{job="engine_app"}` read `1788542047.44` both before and after, so the delta is real and not a counter reset. The +10 reconciles as eight events from probe 4's four accept/cancel pairs and two from probe 5's fills. The matched-at-zero reading is the scope property the sealed external observer exists to provide: the engine saw the probe orders, claimed none of them, and acted on none.

**8. A pre-existing SOL/EUR order was resting throughout, deliberately.** Probes 2 and 6 both read `REVIEW` for it, and both are adjudicated rather than outstanding: it is the order this project left resting on purpose, named in `docs/open-topics/archive/T0160-nautilus-nightly-bump-and-flatten-contract-checks.md` as the fixture its in-flight REST-query check needs. Probe 6 reported it as `other 1` against `ours 0` — the harness never claimed it, and it cancels only its own orders by id, never `cancel_all_orders`, because the live engine shares this account. It is on SOL/EUR, not on the BTC/EUR the probes traded, and not on any of the five two-way-spelled legs where the reconciliation read is blind. The operator confirmed by eye at Kraken → Trade → Open Orders that it was the only order open after the run.

**9. The wheel carries this project's own upstream fix, and where it bites is the flatten path — not this pass's readings.** `2.0.0rc6.dev20260915` is past the `≥ dev20260906` floor, so it is the first pinned build to carry `nautechsystems/nautilus_trader` #4922, *Fix Kraken spot wallet balances to report venue-held amounts* — this project's own submission of the `locked`-always-zero defect found in August, merged upstream 2026-09-05 as `947685bd4`. The merged diff is a different shape from what was submitted, so it is what was triaged, read from upstream at that commit: the wheel is one stripped extension and cannot be read.

What it does: `request_account_state_with_metrics` fetches `POST /0/private/BalanceEx` in place of `/0/private/Balance`, and builds each wallet balance `from_total_and_locked(balance + credit - credit_used, hold_trade, …)` where it previously passed `Decimal::ZERO` for `locked`. `request_account_state` delegates to it, so both entrypoints take the fix.

- **The new private endpoint answered on this key.** Probe 1 returned an `AccountState` rather than an auth or parse failure, so the trade key's permissions cover `BalanceEx` and the response parses. Not a given — the account path moved onto an endpoint this project had never called.
- **None of the balance arithmetic above moves.** `credit` and `credit_used` are returned only for accounts holding a credit line, and `optional_credit_amount` reads an absent field as zero, so `total` here equals the `balance` the old path reported and every figure in the Summary means exactly what it meant at the previous version.
- **`locked` is still zero for EUR on the read the engine takes, by construction.** The merged builder sets `skip_margin_wallet = margin_entry.is_some()` and drops the wallet entry whose normalized code equals `target_code`. The probes and the engine both run `spot_account_type=MARGIN, margin_balance_asset="ZEUR"` (`infra/scripts/kraken-order-semantics-probe.py:1597`, `cli/engine/node.py:488`) and `normalize_currency_code("ZEUR")` is `EUR`, so the ZEUR wallet entry — the only one carrying `hold_trade` — is discarded, and the `EUR` the account reports is the TradeBalance-derived margin entry, built `from_total_and_free(equity, free_margin, …)`. Observation 2's single-`EUR` shape is that entry. On the engine's own account-state read the fix changes nothing, and `locked` there is a margin quantity, never a venue hold.
- **Where it changes something is `cli/engine/flatten.py`, and the reach is narrower than it first looks.** `read_balances` requests `account_type=AccountType.CASH` (`cli/engine/flatten.py:267`), so `margin_entry` is `None`, `skip_margin_wallet` is false, and every wallet entry survives carrying `locked = hold_trade`; `free` becomes `balance + credit - credit_used - hold_trade`, Kraken's own available figure, where before it was the whole wallet amount. **It does not fix the quantity a press sends.** `sweep` issues `cancel_all_orders` first and only then re-reads balances for each spot pass — `spot_legs(await read_balances(client, rec), listing)` — with `_sized_with_constraints` sizing each leg from that fresh row. So a hold behind a resting order is already released before the read that sizes the SELL, and under the old code the pre-fix `free` and the post-cancel available figure coincide. (Cited by symbol rather than line: this file outlives the line numbers, and two rounds of review caught them already stale.) What the fix actually reaches is the **pre-write plan the operator confirms**, the **cancel-failed path** (`sweep` continues deliberately when the cancel raises), and **holds an order cancel does not release**. Recorded that way rather than as a send-path fix, which the call ordering already prevented.
- **That last point is source-read, not measured.** No flatten ran this pass, and the harness could not have shown it in any case: it renders the account as `{str(c): str(b.total) …}` at all three of its sites (lines 1054, 1383, 1477), reading `.total` alone and never `.locked` or `.free`. So no reading of `locked` exists at any version, here or in the previous records. The resting SOL/EUR BUY of observation 8 held roughly 2.25 EUR and was the first attended pass with anything reserved at all, and it still could not have surfaced, because EUR takes the margin entry. Nothing at arming collects this; it belongs to the first flatten that runs on this version, which is [`T0160`](../../open-topics/archive/T0160-nautilus-nightly-bump-and-flatten-contract-checks.md)'s remaining leg.

## Version re-check rule

This pass binds to the exact string `2.0.0rc6.dev20260915` and to nothing else. Both arming guards do exact membership against `cli/engine/order-semantics-verified.json`: the engine Ansible role refuses a converge rendering `exec_armed=true` on a version absent from it, and `cli.engine.execgate` refuses the gate at runtime when the running interpreter's version is absent.

Any bump from here is a decision to re-run this pass at its full attended cost, or to revert the pin. A bump does not disarm a container that is already running — what it kills is the path forward, and nothing warns at the moment of the bump; the refusal arrives at the arming step.

The preceding pass is [`2.0.0rc4.dev20260825.md`](2.0.0rc4.dev20260825.md), which this one superseded as the current version while leaving that record's own readings and owed checks where they stand. **This record is no longer the current version**: [`2.0.0rc6.dev20260918.md`](2.0.0rc6.dev20260918.md) supersedes it from 2026-09-18, and the owed checks below stay where they stand — the two arming items were re-registered against that version, which is the one an arming window will be holding.
