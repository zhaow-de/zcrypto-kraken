## Harness

`infra/scripts/kraken-order-semantics-probe.py`, rebuilt for this version: the probes are the node's own callbacks driving an explicit step queue, with waits resolved by order events, quotes, or clock alerts. **This was its first live run** — every earlier exercise was `--selftest`, `--help`, or `--no-exec`.

Run in four staged invocations, per `infra/runbooks/order-semantics-verification.md`: a full dry run, the four zero-fill probes under `--apply`, the money round trip under `--apply --probe5`, and a fresh flat check. Evidence JSON for each is in `$HOME/probe-evidence/`, outside the repo tree.

Credentials were supplied by `infra/scripts/probe-with-vaulted-key.sh`, which decrypts the vaulted trade key into the harness's environment and executes a hardcoded target, so the operation can be permitted narrowly without granting a general secrets-reading capability.

## Observations

**1. Post-only protection arrives as `OrderCanceled`, not `OrderRejected`** — and via accept-then-cancel, with the venue assigning an order id before withdrawing it. The harness's expectation string for this probe was deliberately stripped of the previous version's answer and left as "RECORD which terminal event it arrives as", so this is a re-derivation against 2.x rather than a carried-forward observation that happens to agree. `_on_rejected`'s post-only marker path is therefore still unexercised by any live event at this venue.

**2. The account object reports a single figure keyed `EUR`**, not per-asset wallet balances — `{'EUR': '99.67730000 EUR'}` under `spot_account_type=MARGIN`. Recorded as the shape this build gives; wallet truth remains the Kraken UI or the raw `Balance` endpoint.

**3. A SPOT buy under `spot_account_type=MARGIN` DOES open an OpenPositions row.** The harness's note flagged that it may open none and asked for the reading; probe 5 reported `open positions=1` after the buy, and 0 after the closing sell.

**4. The fill's commission currency is `EUR` at precision 2** — `Currency(code='EUR', precision=2, iso4217=978, name='Euro', currency_type=FIAT)` — on both legs. This contradicts an assumption made in this project's own test fixtures, which were changed during the migration from `EUR` to `ZEUR` at precision 8 on the reasoning that "ZEUR is what production sees". That reasoning was correct about instrument *quote currencies* (546 live instruments carry `ZEUR`, zero carry `EUR`) and wrong about *commissions*. It is not a production defect — `cli/engine/instruments.EUR_CODES` accepts both spellings, so `_fee_eur` sums either — but a fixture fee of `0.012` is a value this venue cannot produce, since a real EUR `Money` quantizes to two decimals.

**5. The engine was untouched by the run.** Read by value from the workstation after the probes: `zcrypto_exec_kill_tripped` **0**; every `zcrypto_exec_position` series **0** across all twelve symbols; `zcrypto_exec_external_events_total{disposition="matched"}` **0** and `{disposition="unmatched"}` **24**. The matched-at-zero reading is the scope property the sealed external observer exists to provide: the engine saw the probe orders, claimed none of them, and acted on none.

## Version re-check rule

This pass binds to the exact string `2.0.0rc4.dev20260825` and to nothing else. Both arming guards do exact membership against `cli/engine/order-semantics-verified.json`: the engine Ansible role refuses a converge rendering `exec_armed=true` on a version absent from it, and `cli.engine.execgate` refuses the gate at runtime when the running interpreter's version is absent.

Any bump from here is a decision to re-run this pass at its full attended cost, or to revert the pin. A bump does not disarm a container that is already running — what it kills is the path forward, and the refusal surfaces at the arming step.
