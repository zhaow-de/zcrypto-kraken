## Summary<a name="summary"></a>

The §7 Phase-6 entry criterion — hands-on verification of the NautilusTrader official Kraken adapter for **margin/short/post-only order semantics and reconciliation** — was executed attended on **2026-07-10** (iter-079, spec `docs/specs/00039-phase6-kickoff-design.md`, protocol pre-registered). **Verdict: PASS on all six probes.** NautilusTrader **1.230.0** (exact pin, cp314) is confirmed as the Phase-6 execution engine; the thin-custom fallback stays dormant. ## Protocol amendment before any order (validate-only → zero-fill)<a name="protocol-amendment-before-any-order-validate-only-%E2%86%92-zero-fill"></a>

The ratified protocol ("validate-only sweep") was amended pre-run at spec self-review: the adapter at 1.230.0 exposes **no AddOrder `validate` parameter** at any layer (absent from the Python `KrakenExecutionClient` and the Rust `KrakenSpotAddOrderParams`), so validate-only requests cannot exercise the adapter — the very subject of the criterion. Substituted: **zero-fill real orders through the adapter** (far-from-market resting limits canceled after acknowledgment; a crossing post-only expecting the venue's post-only protection), preserving the zero-cost/no-fill intent. Human sign-off on the substitution at spec review and again immediately before the order probes ran (decisions log `[iter-079]`).

## Observations recorded for the shadow-engine build<a name="observations-recorded-for-the-shadow-engine-build"></a>

1. **Symbol normalization**: Kraken's raw `XBT` arrives as `BTC`; instrument IDs are `<BASE>/EUR.KRAKEN`. All 10 universe pairs resolve 1:1.
2. **Post-only rejection semantics**: a crossing post-only is **accepted then venue-canceled** (no `OrderRejected` event) — engine logic must treat `OrderCanceled` on a post-only as the "would cross" signal, not wait for a rejection.
3. **Balance semantics under `spot_account_type=MARGIN`**: the account object reports **TradeBalance-derived equity in the `margin_balance_asset` currency** (post-buy it read `EUR 100.00` = €90 cash + €10 BTC equity), not per-asset wallet balances. Wallet-level truth needs the raw `Balance` endpoint (or cash `AccountType`); the shadow engine's reconciliation must not confuse the two.
4. **Nonce high-water mark**: the adapter uses finer-grained nonces than millisecond — after a node run, millisecond-nonce REST scripts on the same key get `EAPI:Invalid nonce`. Any sidecar tooling sharing the key must use `time_ns()` nonces.
5. **First real-fill cost data point**: taker fee **€0.08000 on €9.99997 = 0.80 %/side** (exact, from `TradesHistory`), spread cost ≈ 0.018 %. Modeled cost is 0.6 %/side — observed is within the pre-registered 2× band for the 6b gate, but the tier should be understood before tiny-live (small-notional effects are unlikely: the fee is exactly 0.80 %). Registered in T0014's findings for the cost-calibration pass.

## Version re-check rule<a name="version-re-check-rule"></a>

This verification was **executed against nautilus-trader 1.230.0 exactly**, and that is the version its six probe results describe. Nothing here has been re-measured on any other version.

The consequence of a bump is unchanged in substance and moved in time: a fresh ~€0.20 zero-fill + round-trip pass must re-run the order-semantics probes **before the engine trades on the new version**. What changed is which act that gates. It was read as gating the *merge* of a bump PR; the binding condition is "before the engine trades", and nothing trades until the engine is armed — an act the owner performs separately and by hand. So the re-run is a precondition of **arming**, not of merging, and the repo may sit on a bumped version indefinitely while disarmed.

**The 1.231.0 re-run has since happened** — attended 2026-08-23, PASS on all six probes, recorded in [`1.231.0.md`](1.231.0.md), which supersedes this file for that version while this one stays the 1.230.0 record. The obligation is enforced by a machine rather than by this sentence: `cli/engine/order-semantics-verified.json` records the versions whose attended pass actually ran (`1.230.0`, `1.231.0`, and `2.0.0rc4.dev20260825` — the last of which is the deployable one, the engine having since crossed to nautilus 2.x), and two guards read that one file: the engine Ansible role refuses a converge rendering `exec_armed = true` on a version absent from it, and the execution gate refuses at runtime when the running `nautilus_trader` is absent from it (`reasons=…,nautilus_unverified`). The conscious stop is those two refusals, met at the arming checklist in `infra/runbooks/engine.md`, and not a red unit test: `tests/test_nautilus_adapter.py` no longer asserts a hardcoded version — it checks that the installed version matches the pin, and stays green across bumps by design, because the pin now tracks a nightly channel and an assertion that reddened on every routine move would have been repaired rather than read. Record a re-run in a **new** `docs/research/` verification doc for the version it covers and cross-link it here — this file stays readable as the 1.230.0 record.
