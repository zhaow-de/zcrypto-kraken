## 2026-09-16 — incident

window the 2026-09-15 13:44Z kernel oom-kill on zcrypto-ops, found by hand on 2026-09-16 · **not the product of a daily pass** — no pass ran between 09-08 and today, and this entry records one event rather than a window's verdict · alerts none fired, which is the finding · checks not run · deploys zcrypto-red re-pinned 09-16 09:34:57Z (capture bake) · actions a cap, a version bump and a new daily-pass read, all on an unmerged branch · follow-ups the converge that makes the cap live.

**A `grep` reached 58.4 GiB inside `zaccess-agentboard.service` and the kernel took a GLOBAL oom-kill on a 62 GiB host. Nothing alerted, and nobody noticed for a day.**

*What ran.* A probe of `infra/scripts/sweep.sh` passed `/dev/zero` as a pattern source: `sweep.sh -l -f /dev/zero --control NEEDLE`. `grep -f` treats each LINE of that file as one pattern, and `/dev/zero` never emits a newline, so it is one pattern that never ends. The kernel line records `anon-rss:61250304kB` (58.4 GiB) against `total-vm:119537880kB`, and `oom-kill:constraint=CONSTRAINT_NONE ... task_memcg=/system.slice/zaccess-agentboard.service`. The service restarted at 13:45:44Z.

*How fast.* Measured on this host afterwards, `grep -f` costs about **320 bytes of RAM per byte of pattern file**, linear across 2, 4 and 8 MB inputs (317x, 319x, 321x). Run backwards against the kernel's own figure that is **~187 MB of `/dev/zero` read — under a fifth of a second**. It did not creep up over the probe's 8-second timeout; it was there almost immediately and spent the rest of the time being killed. No operator could have caught it in the act, and the agent that ran it saw only `HUNG (8s timeout)`.

*NUL is not the cause.* A 2 MB single line of `a` blows up the same way (440 MB and still climbing when killed at 60 s). The fatal combination is an unbounded single line, an endless source, and the amplification — the byte value is irrelevant.

*The defect that let it in is fixed.* `sweep.sh` now refuses a pattern source that is not a regular file (`a pattern source is a regular file or it is refused`, merged the same day). That closes the device case and not the general one: a regular file with one enormous line reproduces it.

*Why the blast radius was the whole host.* `zaccess-agentboard.service` ran with `MemoryMax=infinity` and `MemoryHigh=infinity`; its cgroup peaked at 64.1 GB. With no limit to hit, a runaway child escalates to a global oom-kill rather than being contained — the kernel's own `constraint=CONSTRAINT_NONE` says so. The cgroup is not just agentboard: `KillMode=process` means a forked child inherits it for life, so the operator's tmux server and every session started through the web terminal are accounted there.

*Why no rule fired, established by reading the rules rather than assuming them.* `zcrypto-fleet-daemon-restarted` has exactly the right shape and its summary names this case — it failed only because agentboard publishes no `/metrics` and is scraped by nothing, so the series does not exist. `zcrypto-fleet-memory-headroom` names three host/job legs that exclude ops and is spike-blind at `for: 5m`. `zcrypto-fleet-memory-leak` subtracts hourly MINIMA a day apart, which a one-second excursion cannot move, and its 30 h age gate would have silenced it after the restart regardless. The kernel line has no route either: the journal keep-regex matches on `__journal__systemd_unit` and an oom-kill carries `_TRANSPORT=kernel` with no unit, so it is dropped at the relabel — **no host on this fleet ships kernel journal lines**.

*What is being done.* `MemoryAccounting=yes`, `MemoryHigh=12G`, `MemoryMax=24G` on the unit; agentboard bumped `0.4.23` to `0.5.3`; and a new daily-pass read of `systemctl show zaccess-agentboard.service -p MemoryMax -p MemoryHigh -p MemoryPeak -p NRestarts`, which answers uncapped, throttled and restarted in one read-only ssh — chosen over a new metric and rule because it needs no converge and no dashboard push, and because it reads the HOST rather than the repo, which is the gap this incident is actually about.

*Still open.* All of that is on an unmerged branch; `zcrypto-ops` runs the old version uncapped until an ops converge, and the new check reports attention saying exactly that until it lands. A size or line-length bound on `sweep.sh`'s pattern source is not written — the repo's own worst in-scope file is 0.24 MB, and the scope walk excludes `.venv` and `data/` by gitignore and skips binaries, so the remaining exposure needs a caller naming a large path deliberately.
