## 2026-07-20 — iter-110: gate-export incremental scoring — the cost stops growing with the journal ([[T0069]], spec 00060)

- **The structural fix for iter-109's finding.** `gate-export` re-replayed every journaled cycle every hour, each replay a full ~28k-bar, 12-year rebuild (81% of runtime). It now caches per-cycle outcomes and replays only what is new: **opt-in `--cache PATH`**, with no flag meaning today's behaviour byte-for-byte and `report` never cached (it is a human-facing *verification* tool and must genuinely re-verify).
- **Verified on real production evidence, not fixtures.** On the ops journal mirror (39 cycles): no-cache 63.11 s / cold 62.77 s (39 replayed) / **warm 0.30 s (0 replayed, 39 hits)** — and **the gate metrics were identical across all three runs**, which is the load-bearing property: a cache hit must be indistinguishable from a fresh replay. Cold matches no-cache, so enabling it costs nothing. Steady state (one new cycle/hour) is ~2 s here and ~13 s on the Atom vs ~510 s today; the point is that the cost is now **flat** rather than climbing toward the 3600 s pull interval — precisely, the *expensive* per-cycle rebuild is bounded to what's new, while `_journal_artifacts` and the evidence fingerprint still scan/hash every record each run, a small O(n) constant (the 0.30 s warm run over 39 cycles is that term) that stays seconds even at the projected 332-cycle horizon.
- **The safety property is the whole design, and the review found it broken twice before merge.** The cache invalidates wholesale whenever anything that could change a verdict changes. The first implementation hashed four modules; tracing `replay_cycle`'s actual call graph found two **live** gaps — `cli/risk/governor.py` (whose multipliers fold straight into `final_targets`) and `cli/engine/journal.py` (whose `validate_record`/`snapshot_content_hash` decide pass vs `validation_failed` vs `HashMismatchError`) — plus four latent verified-route modules and the unhashed replay *path*. Separately, the per-cycle key digested only `content_hash`, so tampering `n_bars` would make the real replay fail validation while the cache served the stale **pass**. Both closed; each fix pinned by a test the reviewer confirmed fails when the fix is reverted.
- **Deliberately over-sensitive.** A comment-only edit to any of the ten covered modules invalidates the whole cache and costs one full rebuild. Over-invalidation is cheap; under-invalidation silently corrupts the evidence that decides whether the strategy trades real money.
- **Fail open, never fail trusting.** Any cache problem — absent, unreadable, truncated, wrong schema, fingerprint mismatch — degrades to a full replay and rewrites; it never aborts and never serves a partially-trusted entry. The exception nets were narrowed to `(OSError, ValueError, KeyError, TypeError)` so a future refactor's `AttributeError` surfaces in tests instead of silently disabling the cache forever.
- **Observability so a dead cache can't look healthy:** `zcrypto_gate_cache_replayed_total`, `_hits_total`, `_invalidated` emit **always** (zero when caching is off), so a fingerprint that changes every run shows up as `hits 0 / replayed n` rather than as a working optimisation.
- **A counting trap avoided:** `JournalCounts` is now derived from each resulting `CycleOutcome` in one place rather than incremented inside the replay branches — otherwise cached cycles would stop being counted and a report would state "0 mismatches" because it never counted them, while the gate itself still looked right.
- **Closeout.** [[T0069]] updated (incremental scoring landed; the **attended** relocation and enabling `--cache` in the deployment remain, both needing a maintenance window — the code ships inert). [[T0074]] registered: the fingerprint covers the replay *code* but not the execution *environment*, so a numpy/Python bump could serve stale outcomes if the drift exceeds the 1e-6 `compare_targets` budget.

## 2026-07-20 — iter-112: the gate cache no longer trusts a cycle forever ([[T0077]], spec 00062)

- **The finding this fixes was not a bug report — it was a design gap nobody had modelled.** `gate-export --cache` (iter-110) skips `replay_cycle` on a fingerprint hit, and that replay is the **only** place the journal's parquet bytes are re-hashed (`concordance.py:116`). The NAS pull delegates to it explicitly (`--no-verify`: *"no .sha256 sidecars, Role B verifies it via replay"*), rsync has no `--checksum`, and `evidence_fingerprint` digests the `content_hash` **recorded in the record** rather than a fresh read. Enabling `--cache` would therefore have converted *"every parquet re-verified ~24×/day"* into *"verified once, then trusted forever"* — and a snapshot altered in place after its first replay would be served as a **PASS**, silently, with `mismatch_total` at 0 and the streak still climbing. Spec `00060` D2 had scoped its fingerprint to "everything a replay's verdict depends on **from the journal side**", so the parquet-bytes axis was never argued; the design's governing asymmetry (*over-invalidation is safe, under-invalidation silently corrupts*) was never applied to the axis that actually breaks.
- **This also reframes iter-109.** That iteration characterised the per-cycle full rebuild as pure waste — *"redoing work the previous run already did."* It is **also the continuous integrity monitor**. Any optimisation that removes redundancy must replace the monitoring the redundancy was silently providing; that is the transferable lesson, not the specific fix.
- **The mitigation: bounded rotating re-verification, always on when the cache is active** — not a flag, because a safety property that can be switched off will be. Each run force-replays a deterministic slice of otherwise cache-eligible cycles. Keyed on `sha256(cycle_ts) % 24` so a cycle's slice is a **fixed property of the cycle** — an index-keyed slice would move as the journal grows, making coverage neither uniform nor provable — and `sha256` rather than the builtin `hash()`, which is not guaranteed stable across processes. The current slice is `now.hour % 24`: stateless, no cursor to persist, corrupt, or reset.
- **A forced re-verification failure moves the gate** (D4): the same `CycleOutcome(mismatch=True)` any replay produces, into `JournalCounts`/`evaluate_gate` unchanged, counted as `replayed` and never `from_cache`. Detecting corruption must change the verdict, not merely log.
- **Verified on the real journal against the MODIFIED predicate** (57 cycles) — iter-110's "identical gate metrics" evidence covers the old eligibility rule and does not carry over: no-cache 94.52 s / cold 93.70 s / warm 2.45 s / warm-again 2.48 s, all exit 0, **gate metrics identical across all four**. Warm replays **1** with 56 hits — the counters, not the runtime, are what prove rotation engaged, since a fast warm run is exactly what a silently-disabled rotation would also produce. A 24-hour sweep re-verified **57/57 cycles, each in exactly one slice**; worst hour 5 replays ≈ 54 s on the NAS Atom, ~1.5% of the 3600 s interval against ~510 s for a full replay.
- **The guarantee was attacked, not merely tested.** Review confirmed eligibility depends only on `cycle_ts` and the run clock, reading nothing from the cache file — so an attacker with full control of that file can suppress the staleness metric but not the rotation replay, and a failed `save_cache` cannot stop it either.
- **Two latent traps closed on the way, both of the run's recurring shape.** The new metrics' *values* were unpinned end-to-end: hardcoding `oldest_verification_age` to `0.0` passed 72/72 until a test pinned the exact value — and that number is D5's own declared backstop, the sole way a stopped rotation is distinguishable from a healthy cache, so a constant `0.0` would have read as *"everything verified seconds ago, forever."* Separately, `_ROTATION_SLICES > 24` would have left high slices permanently unreachable (since `now.hour % N` only spans `[0,23]`) — **silently**, the exact failure class the iteration exists to prevent; now an assert.
- **Also corrects [[T0069]] on two counts**, established by reading the deployed loop rather than trusting its own projections: the *"loop can no longer keep up"* cliff **does not exist** (`pull-entrypoint.sh` sleeps *after* the work, so the period is `3600 + work` and the loop drifts rather than falling behind — the same file records it already running at ~103 min), and consequently **relocation is the safer remedy, not the redundant one**, since it preserves the integrity check `--cache` removes. The constraint that actually binds is the 18000 s lag alert, whose own comment concedes the value was copied from a CLI default rather than derived.
- **Closeout.** [[T0077]] → `resolved` and archived, but only after its residuals were actually worked down rather than filed away. It briefly stood at `partial` with three: the >3-day staleness alert rule, the cache-file siting decision, and the owner's threat-model judgement. All three closed in-iteration — the rule was written, committed and **pushed live** (read-back verified); siting was decided as spec `00062` D9 (ephemeral, never on a shared path, since the NAS and ops run different polars runtimes and `replay_fingerprint` digests neither); and the owner confirmed in-place alteration is worth defending against, so daily rotation stands. ## 2026-07-22 — iter-116: the app ships its own logs, and docker.sock leaves the fleet ([[T0089]], [[T0042]], spec 00068)

- **The CLI ships its own logs.** New `cli/logging/ship.py`: an opt-in `--ship-logs` sink that POSTs the existing `JsonLineFormatter` line straight to Grafana Cloud Loki with labels `{host, container, level}` — `level` from `record.levelname`, so **no regex exists anywhere in this path**, at ingest or at query. stdlib only (urllib/threading/collections), no new dependency on the capture image. Env: `ZCRYPTO_LOKI_URL`/`_USERNAME`/`_PASSWORD` + `ZCRYPTO_LOG_HOST`/`_SERVICE`; the flag with any of them unset **or empty** is a hard startup error naming every missing one.
- **stdout is untouched and remains the local ground truth.** The switch is additive: plain-text console exactly as before, docker's json-file driver still capturing it under the existing caps. A crash loses at most the in-memory ring; the last lines survive locally.
- **Bounded, non-blocking, self-announcing.** `emit()` is a deque append under an O(1) lock — all network I/O lives in a daemon worker. Ring 4096, drop **oldest** and count; batches ≤500 or 1 s; one in-flight batch; backoff 1 s → 30 s; exit flush with a 2 s hard deadline. A dead Loki costs one bounded ring and nothing else. **Non-429 4xx drops the batch rather than retrying** — after an outage longer than Loki's out-of-order window the held batch's honest timestamps are rejected forever, so retry-forever would wedge shipping permanently and silently.
- **docker.sock is mounted into nothing, fleet-wide.** All four Alloys lose the socket bind-mount, the docker-group `group_add`, and their `discovery.docker`/`loki.source.docker` components. Alloy's own logs now reach Loki through the **journald log driver** + each host's journal pipeline (a first-time build on the NAS). The T0042 socket residual closes; the T0089 wedge class becomes unrepresentable, because no *foreign* process reads docker's log files any more.
- **The parse stage survives where it is still fed.** Deleted on the capture hosts only; **kept on ops and the NAS**, where the oneshot units and the `archive-pull` wrapper still ship Python-shaped lines through the journal. The honest principle is `direct-ship path regex-free; journal path keeps its one ingest parse` — an earlier draft said "delete it everywhere" and would have permanently blinded `NAS · archive-pull ERROR logs`.
- **Label continuity, so no rule needed re-keying.** `ZCRYPTO_LOG_HOST` renders today's values: `{{ base_hostname }}` on the capture hosts, the literal `ops`/`nas` elsewhere (those Alloys apply static relabels, and the ops rules hardcode `host="ops"`).

Two rules added: `zcrypto-ops-poller-log-dead` (nothing watched the new direct-ship path) and `zcrypto-ops-unit-parse-dead` (restores T0060 level-regression coverage at 26 h). `zcrypto-alloy-docker-sd-wedged` retires with its subject, and its `prometheus_sd_*` series leave every keep-list — a keep-list entry for a series that cannot exist is the T0051 admitted-but-unpublished trap.

Spec D7's attended steps (vault token in place, per-host converges, the canary bake, the post-gate engine converge, per-step positive-trace verification in Loki, and the `grafana-push.sh` step — which prunes orphaned rules, so it must wait until ops and NAS are actually converged) are the remainder, and the T0089/T0042/T0020 topic updates land with them.

## 2026-07-26 — the engine journal stops growing forever, and the guard that matters is not about disk ([[T0021]], spec 00070)

- **A daily 01:23 UTC oneshot bounds the VPS engine journal at a 60-day tail** — `zcrypto-engine-journal-prune`, installed by the `engine` role with `ProtectSystem=strict` and `ReadWritePaths` limited to the journal dir (plus, since spec `00071`, the textfile dir it publishes into), so a bug in its own globs *structurally* cannot reach the trade key or the capture spool. Timer enabled, service left `static` (enabling it too would prune on every boot).
- **Retention was never a capacity problem, and saying so out loud changed the design.** 13 MB/day against 51 GB free is ~11 years of headroom. With no deadline forcing a cheap choice, the design could pay any amount of caution — which is how the real hazard got found instead of a `find -mtime +14 -delete` shipping.
- **The load-bearing guard protects order generation, not disk.** `cli/engine/cycle.py` derives each cycle's orders as a delta against the most recent journaled cycle; with no prior record `prev_targets is None`, every delta becomes the full target, and the engine emits orders to rebuild the entire book ("the shadow book starts flat"). An age-only prune reaches that state whenever the engine stops for longer than the retention window — every day ages out at once. So deletion requires **two** conditions: older than the cutoff **and** not among the newest N day-dirs. They coincide in healthy operation and come apart exactly when the floor is the only thing preventing a spurious whole-book rebuild. Recorded caveat: the floor counts day-*dirs*, so 60 consecutive days of all-failed cycles could still strand the lookup — not guarded, because any guard would key on the records the outage is failing to produce.
- **"Prune after verified pull" resolved to margin-plus-monitoring, not a handshake.** The architecture is pull-only (`rrsync -ro`, spec `00051` D10), so a NAS→VPS acknowledgement would mean opening a write-capable path *into the trade-key host*. Rejected: disk hygiene is not worth weakening that boundary. A day instead survives ~1,440 hourly pull opportunities under a 6 h lag alert — and the precondition was **verified rather than argued**: the oldest day on the host (`2026-07-11`) measured 127 files / 12,553,096 bytes on the VPS and byte-identically on the NAS.
- **The first review found the tests green and hollow.** Fixtures planted enough recent days that the keep-newest floor satisfied every assertion on its own — so the age cutoff could be *deleted outright* and all 21 tests still passed, as could either regex anchor and `-type d`. Four cases were added and the suite is now mutation-checked: all five mutations fail it. The lesson is the general one — a passing suite is evidence only about the fixtures it was given.
- **Observability was got wrong here, and is corrected in spec `00071` ([[T0100]]).** The reasoning recorded at the time — app metrics come from `/metrics` endpoints Alloy scrapes, a oneshot has no process to scrape, these hosts run no textfile collector, therefore publish nothing — was true at every step and did not follow. *The correct response to "no reader exists" is to add the reader.* The fallback claimed instead was false too: the journal keep-regex admitted only `zcrypto-capture-prune.service`, so the log line never reached Loki and the prune spent its first day observable through **nothing**. Superseded text follows, kept only because the reasoning is instructive: App metrics are now scraped from live `/metrics` endpoints; a oneshot that runs for a second has nothing to scrape. The fleet's mechanism for ephemeral timers is the textfile collector, which the ops node runs and the capture/engine hosts deliberately do not. Stated honestly rather than papered over: **nothing detects a timer that silently stops** — the spool-disk alert covers this filesystem but sits ~9 years away at 13 MB/day, so it backstops disk exhaustion, not the timer. Accepted because over-deletion is the dangerous failure and the keep-newest floor, not an alert, is what guards it. That alert's summary now names both prune timers.
- **Retention is 60 days.** The owner raised it from 14 during implementation, *between* the two converges — the first deploy ran at 14. The design is value-independent — the cutoff and the floor read the same parameter — so only numbers moved: steady state ~780 MB (1.5% of free space), ~1,440 pull opportunities of margin. A test now pins the deployed default against the spec, so the next drive-by edit has to change the ruling too.
- **Deployed attended and verified by outcome**, converged at 14 and re-converged at 60: `changed=4` then `changed=1`, with compose and the engine systemd unit `ok` in both, so no restart handler ever fired — confirmed by the container's `StartedAt` being byte-identical across both converges with `RestartCount` 0. The deployed command was read back from systemd's own resolved `argv[]`, not just the unit file.
- **The prune was proven on real data before the value changed**, which is the more informative record. At 14 a host `--dry-run` returned exactly the predicted `deleted=1 kept=15 cutoff="2026-07-12 UTC"` — one eligible day, the day sitting exactly *on* the cutoff correctly spared. At 60 it returns `deleted=0 kept=16 cutoff="2026-05-27 UTC"`, so **the timer is a verified no-op until ~2026-09-10**, when the oldest day first ages out.

- **The recorded guideline's transport did not exist.** T0027's 2026-07-23 design called for the detector to write to "the same `integrations/unix` transport that already carries the NAS `gate.prom` — no regex, no new plumbing". The two hosts it targets ran **no textfile collector**, and `integrations/unix` is static-mode Grafana Agent vocabulary this flow-mode fleet does not use. - **No compose edit and no volume change** — the material simplification. - **Three ways a `.prom` fails, and each defeats the rule that catches the others.** *Stale* — the collector serves the last values forever and `node_textfile_scrape_error` does not fire (it covers malformed input only). *Unreadable* — it does. *Absent entirely* — neither can, because a staleness rule cannot fire on a series that does not exist and `noDataState: OK` renders that silence green. It would have shipped inert, and the staleness rule could not have surfaced it: the collector skips an unreadable file *before* stamping its mtime, so there was no series to go stale. The allow-list was also admitting three of the prune's four series; `oldest_day_age_seconds` was being dropped at remote-write — the exact trap the spec claims to close. It is now derived from what the script actually emits, not a hand-kept list.

The producer/reader test passed with `"textfile"` removed from `set_collectors`. The timer-enable test split on the last of three occurrences and never inspected the task it named. The `.timer` file had no content coverage at all.
