## 2026-07-20 — iter-110: gate-export incremental scoring — the cost stops growing with the journal ([[T0069]], spec 00060)

- **The structural fix for iter-109's finding.** `gate-export` re-replayed every journaled cycle every hour, each replay a full ~28k-bar, 12-year rebuild (81% of runtime). It now caches per-cycle outcomes and replays only what is new: **opt-in `--cache PATH`**, with no flag meaning today's behaviour byte-for-byte and `report` never cached (it is a human-facing *verification* tool and must genuinely re-verify).
- **Verified on real production evidence, not fixtures.** On the ops journal mirror (39 cycles): no-cache 63.11 s / cold 62.77 s (39 replayed) / **warm 0.30 s (0 replayed, 39 hits)** — and **the gate metrics were identical across all three runs**, which is the load-bearing property: a cache hit must be indistinguishable from a fresh replay. Cold matches no-cache, so enabling it costs nothing. Steady state (one new cycle/hour) is ~2 s here and ~13 s on the Atom vs ~510 s today; the point is that the cost is now **flat** rather than climbing toward the 3600 s pull interval — precisely, the *expensive* per-cycle rebuild is bounded to what's new, while `_journal_artifacts` and the evidence fingerprint still scan/hash every record each run, a small O(n) constant (the 0.30 s warm run over 39 cycles is that term) that stays seconds even at the projected 332-cycle horizon.
- **The safety property is the whole design, and the review found it broken twice before merge.** The cache invalidates wholesale whenever anything that could change a verdict changes. The first implementation hashed four modules; tracing `replay_cycle`'s actual call graph found two **live** gaps — `cli/risk/governor.py` (whose multipliers fold straight into `final_targets`) and `cli/engine/journal.py` (whose `validate_record`/`snapshot_content_hash` decide pass vs `validation_failed` vs `HashMismatchError`) — plus four latent verified-route modules and the unhashed replay *path*. Separately, the per-cycle key digested only `content_hash`, so tampering `n_bars` would make the real replay fail validation while the cache served the stale **pass**. Both closed; each fix pinned by a test the reviewer confirmed fails when the fix is reverted.
- **Deliberately over-sensitive.** A comment-only edit to any of the ten covered modules invalidates the whole cache and costs one full rebuild. Over-invalidation is cheap; under-invalidation silently corrupts the evidence that decides whether the strategy trades real money.
- **Fail open, never fail trusting.** Any cache problem — absent, unreadable, truncated, wrong schema, fingerprint mismatch — degrades to a full replay and rewrites; it never aborts and never serves a partially-trusted entry. The exception nets were narrowed to `(OSError, ValueError, KeyError, TypeError)` so a future refactor's `AttributeError` surfaces in tests instead of silently disabling the cache forever.
- **Observability so a dead cache can't look healthy:** `zcrypto_gate_cache_replayed_total`, `_hits_total`, `_invalidated` emit **always** (zero when caching is off), so a fingerprint that changes every run shows up as `hits 0 / replayed n` rather than as a working optimisation.
- **A counting trap avoided:** `JournalCounts` is now derived from each resulting `CycleOutcome` in one place rather than incremented inside the replay branches — otherwise cached cycles would stop being counted and a report would state "0 mismatches" because it never counted them, while the gate itself still looked right.
- **Closeout.** [[T0069]] updated (incremental scoring landed; the **attended** relocation and enabling `--cache` in the deployment remain, both needing a maintenance window — the code ships inert). [[T0074]] registered: the fingerprint covers the replay *code* but not the execution *environment*, so a numpy/Python bump could serve stale outcomes if the drift exceeds the 1e-6 `compare_targets` budget.

## 2026-07-20 — iter-112: the gate cache no longer trusts a cycle forever ([[T0077]], spec 00062)

- **The finding this fixes was not a bug report — it was a design gap nobody had modelled.** `gate-export --cache` (iter-110) skips `replay_cycle` on a fingerprint hit, and that replay is the **only** place the journal's parquet bytes are re-hashed (`concordance.py:116`). The NAS pull delegates to it explicitly (`--no-verify`: *"no .sha256 sidecars, Role B verifies it via replay"*), rsync has no `--checksum`, and `evidence_fingerprint` digests the `content_hash` **recorded in the record** rather than a fresh read. Enabling `--cache` would therefore have converted *"every parquet re-verified ~24×/day"* into *"verified once, then trusted forever"* — and a snapshot altered in place after its first replay would be served as a **PASS**, silently, with `mismatch_total` at 0 and the streak still climbing. Spec `00060` D2 had scoped its fingerprint to "everything a replay's verdict depends on **from the journal side**", so the parquet-bytes axis was never argued; the design's governing asymmetry (*over-invalidation is safe, under-invalidation silently corrupts*) was never applied to the axis that actually breaks.
- **This also reframes iter-109.** That iteration characterised the per-cycle full rebuild as pure waste — *"redoing work the previous run already did."* It is **also the continuous integrity monitor**. Any optimisation that removes redundancy must replace the monitoring the redundancy was silently providing; that is the transferable lesson, not the specific fix.
- **The mitigation: bounded rotating re-verification, always on when the cache is active** — not a flag, because a safety property that can be switched off will be. Each run force-replays a deterministic slice of otherwise cache-eligible cycles. Keyed on `sha256(cycle_ts) % 24` so a cycle's slice is a **fixed property of the cycle** — an index-keyed slice would move as the journal grows, making coverage neither uniform nor provable — and `sha256` rather than the builtin `hash()`, which is not guaranteed stable across processes. The current slice is `now.hour % 24`: stateless, no cursor to persist, corrupt, or reset.
- **A forced re-verification failure moves the gate** (D4): the same `CycleOutcome(mismatch=True)` any replay produces, into `JournalCounts`/`evaluate_gate` unchanged, counted as `replayed` and never `from_cache`. Detecting corruption must change the verdict, not merely log.
- **Verified on the real journal against the MODIFIED predicate** (57 cycles) — iter-110's "identical gate metrics" evidence covers the old eligibility rule and does not carry over: no-cache 94.52 s / cold 93.70 s / warm 2.45 s / warm-again 2.48 s, all exit 0, **gate metrics identical across all four**. Warm replays **1** with 56 hits — the counters, not the runtime, are what prove rotation engaged, since a fast warm run is exactly what a silently-disabled rotation would also produce. A 24-hour sweep re-verified **57/57 cycles, each in exactly one slice**; worst hour 5 replays ≈ 54 s on the NAS Atom, ~1.5% of the 3600 s interval against ~510 s for a full replay.
- **The guarantee was attacked, not merely tested.** Review confirmed eligibility depends only on `cycle_ts` and the run clock, reading nothing from the cache file — so an attacker with full control of that file can suppress the staleness metric but not the rotation replay, and a failed `save_cache` cannot stop it either.
- **Two latent traps closed on the way, both of the run's recurring shape.** The new metrics' *values* were unpinned end-to-end: hardcoding `oldest_verification_age` to `0.0` passed 72/72 until a test pinned the exact value — and that number is D5's own declared backstop, the sole way a stopped rotation is distinguishable from a healthy cache, so a constant `0.0` would have read as *"everything verified seconds ago, forever."* Separately, `_ROTATION_SLICES > 24` would have left high slices permanently unreachable (since `now.hour % N` only spans `[0,23]`) — **silently**, the exact failure class the iteration exists to prevent; now an assert.
- **Also corrects [[T0069]] on two counts**, established by reading the deployed loop rather than trusting its own projections: the *"loop can no longer keep up"* cliff **does not exist** (`pull-entrypoint.sh` sleeps *after* the work, so the period is `3600 + work` and the loop drifts rather than falling behind — the same file records it already running at ~103 min), and consequently **relocation is the safer remedy, not the redundant one**, since it preserves the integrity check `--cache` removes. The constraint that actually binds is the 18000 s lag alert, whose own comment concedes the value was copied from a CLI default rather than derived.
- **Closeout.** [[T0077]] → `resolved` and archived, but only after its residuals were actually worked down rather than filed away. It briefly stood at `partial` with three: the >3-day staleness alert rule, the cache-file siting decision, and the owner's threat-model judgement. All three closed in-iteration — the rule was written, committed and **pushed live** (read-back verified); siting was decided as spec `00062` D9 (ephemeral, never on a shared path, since the NAS and ops run different polars runtimes and `replay_fingerprint` digests neither); and the owner confirmed in-place alteration is worth defending against, so daily rotation stands. ## 2026-07-27 — desync recovery survives its first attempt failing ([[T0008]], spec 00072)

## 2026-08-01 — verify-replay certifies the whole archive by replaying almost none of it (spec 00078, T0114 resolved)

- **The nightly canonical sweep is incremental, and its runtime no longer scales with the archive.** `zcrypto archive verify-replay --state-dir` caches each hour's raw verdict facts against the sha256 of the bytes **actually replayed** — not the sidecar's claim, since both writers publish sidecar-then-final and a crash mid-mint leaves a new sidecar over old bytes — and serves unchanged hours from one atomically-replaced `checkpoint.parquet`, ops-local at `/var/lib/zcrypto-ops/verify-replay-state/`, outside every NAS rrsync pin, with `/data` still mounted `:ro`. Steady state is the day's ~288 new hours (~23 min) rather than the whole archive (6,000 hours at 4.80–4.82 s/hour measured twice end to end = 8 h 00 m as of 2026-08-01, +288/day), so both of [[T0114]]'s dated cliffs are dissolved rather than pushed out: journald's `RateLimitBurst` (~2026-08-14 — per-run output collapses from one line per hour to four) and runtime meeting the 24 h cadence (~2026-09-11). Hours never seen before are always replayed; hours whose bytes changed drain oldest-first under a 7,200 s budget with the remainder announced as `pending`; a cached *failure* is never trusted, so a transient `ro,soft` NFS EIO still heals the next night instead of freezing into a permanently-failing hour. Three conditions exit 2 with the summary withheld so `run_ok=0` pages rather than the night reading green — an unwritable state dir, an enumeration that would evict more than a tenth of the checkpointed hours (an unmounted mirror, not a real shrink), and a sampled audit that caught the cache lying.
- **The property the whole design rests on was found at review, before a line of code existed.** The checkpoint stores only *raw* per-hour facts and the chain verdict is recomputed every run over cached and freshly-replayed rows alike. Caching the verdict instead would make anchoring **irrevocable**: `anchored = raw OR (contiguous AND prev_ok)` is a fold that can only widen, so an hour cached `anchored=True` stays true forever after the reconciler later rewrites its predecessor into a failure — and every successor stays green across a broken chain while `delta(failed_hours)` reads 0. A cold Fable review of the first draft caught it in the spec, along with four leaks in the invalidation argument. It is the same class of defect spec `00076` D7 shipped and reverted the same evening; the only difference is where it was caught, and here it cost a review round instead of a production night. Mutation confirms the pin bites and that it is a *single* pin: writing the chain verdict into the checkpoint rows makes an hour stay anchored after its predecessor breaks, and only the dedicated test catches it — the field-for-field equivalence test passes on a healthy tree, because there everything folds anchored anyway.
- **A sustainability reversal: the environment is recorded, it does not invalidate.** The first draft put `polars.__version__` in the invalidation key. Dependabot bumps polars roughly monthly (#218, merged 2026-07-28) while a full drain takes ~74 nights at year-one archive size, so the instrument would have sat permanently mid-drain, mixed-version, `pending` never reaching zero — the exact pathology at exactly the horizon this spec exists for. `polars_version` and `depth` are now recorded per row for forensics only, and environment drift is caught instead by the nightly sampled audit: 25 uniformly random **cache-trusted** hours re-replayed under current code and compared field-for-field, byte hash included. Constant cost, and strictly better detection than a year-long drain — it also covers overlay bit rot the NAS's hourly re-hash cannot see, checkpoint corruption, and a stale-predicate bug. The audit deliberately never samples *pending* rows: those are known-stale by construction, so auditing them would mismatch with certainty and false-page through every night of a legitimate drain.
- **The backlog alert's `for:` was wrong twice, and it is arithmetic rather than taste.** `pending` is a persistent textfile gauge scraped continuously between the daily runs, so on a *healthy* drain the condition (`pending > 0` **and** `delta(pending[26h]) >= 0`) goes true at the bump night's publish and cannot go false until the window's left edge passes it — a true run of exactly `max(24 h, window)` = 26.00 h, however much progress night two made. `for` must therefore **strictly** exceed that: `for: 25h` — the spec's own first number, faithfully implemented — fires on a healthy drain at the same instant it fires on a stuck one, and even `for: 26h` trips on the 26.00 h run, because equality is failure and not margin. Shipped `for: 27h` over `delta(…[26h])`, re-derived independently by two reviewers against the shipped values and pinned by a test that reads the window from the rule's own selector and `for` from the rule rather than from literals. The spec was corrected in place, since the wrong pairing had already reached operator-facing runbook prose. Stated precisely, because a looser version of this claim is easy to carry: a stall on the **first** drain night — the backlog never starts shrinking — holds true for 48 h and pages; a single stalled night **mid-drain**, after real progress, holds only 22 h and stays quiet; two consecutive mid-drain stalls page.
