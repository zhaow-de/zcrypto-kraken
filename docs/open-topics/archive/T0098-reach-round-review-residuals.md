# Reach-round review residuals: a stranded partial sibling, and duplicated seam logic

## Context — what

The pre-push review of the REST reach round ([[T0065]], `cli/ohlc/reach.py`) returned nine findings. Six were fixed in the same commit — REST call pacing, a manifest that folded detached content into the basket hash, missing per-series `sha256`, a factually wrong import comment, missing wiring tests, and dead test code. Three were deliberately **not** fixed there, because each would have widened the change beyond the component or touched code that must not move this week. They are registered here rather than left in a review transcript nobody re-reads.

## Why this matters

None of the three affects the data the round produces — the shipped set is correct and its continuity is verified. They are forward-looking: two are maintainability traps that get more expensive the longer two copies drift, and one is an operational papercut that will eventually cost someone a confusing manual cleanup.

## Findings so far

### 1. A mid-run failure strands a partial, unretriable sibling

`rebuild_sets` (`cli/data/rebuild.py`) cleans up a failed builder's output **only when the directory is still empty**. `reach_round` writes symbol-by-symbol and only writes `manifest.json` at the very end, so a failure at (say) fetch 7 of 30 leaves a non-empty sibling with no manifest — and because the sibling name is date-stamped, a same-day retry then trips the `sibling already exists` guard forever, requiring a manual `rm -rf`.

This is a **pre-existing** property of every `data rebuild` target, not something the reach round introduced, which is why it was not fixed inside the reach commit. But the reach round is the first target driven by many sequential network calls, so it is the first with a realistic chance of hitting it. The added REST pacing (3.0 s, the measured floor from T0053) materially reduces the most likely trigger.

This topic then asserted that a missing `manifest.json` is a reliable partial-run signature — every completed reach round writing one as its last act — and proposed building the fix on that signature: either clean up a manifest-less sibling on failure, or make the retry path recognise and replace one. **That premise was measured FALSE for 2 of the 5 rebuild targets and the fix rests on nothing like it — see `## Resolution`.**

### 2. Seam-reconciliation logic is duplicated between the reach round and the engine store

`cli/ohlc/reach.py::_drop_in_progress` is functionally identical to `cli/engine/store.py::_drop_in_progress`, and `_merge_or_detach`'s join/overlap/mismatch/merge block mirrors `_reconcile`'s `allow_replace=False` path closely. `MIN_SEAM_OVERLAP = 6` is hardcoded to match `_SEED_MIN_OVERLAP` rather than shared — the reach module's own comment admits the coupling.

Both copies are correct today. The risk is that a future safety fix to one has no path to the other, and this is seam logic guarding an unbackfillable-adjacent dataset. Extracting what is *identical* is a pure refactor, so it should ride an iteration already working in those files — with the caveat in sub-item 3 about *when* `cli/engine/store.py` may be touched. **Deleting both copies outright is NOT a pure refactor**, which this topic assumed and measurement refuted — see `## Resolution`.

### 3. `PAIR_KEYS` sits in the engine store, so `cli/ohlc/` imports upward to reach it

The asset → Kraken REST pair-key mapping lives in `cli/engine/store.py` only because that was its first consumer. `cli/engine/store.py` already imports `cli.ohlc.*`, so `cli/ohlc/reach.py` importing it back runs against the dependency direction. Two consequences, both currently benign and both documented at the import site:

- Importing the **submodule** does not dodge the package — Python runs `cli.engine.__init__` first, so the concordance/cycle/journal chain loads regardless. (An earlier comment claimed the opposite; that was measured false and corrected.) It costs nothing in practice because `cli/__main__.py` already imports `cli.engine.command` unconditionally.
- **`cli/ohlc/__init__.py` must never import `cli.ohlc.reach`**, or the package re-enters itself half-initialised via `cli.engine.store` → `cli.ohlc.dataset`. That is a live trap for anyone tidying the package exports.

The fix is to relocate `PAIR_KEYS` into `cli/ohlc/` (its natural home — it is OHLC REST reference data) and have the engine store import it from there, keeping `cli.engine`'s existing re-export intact.

**Why it was not done in the reach commit:** `cli/engine/store.py` feeds the shadow engine, which is mid-Stage-6a-gate with the clock running, and the owner is away 2026-07-29 → 2026-08-20. A no-behaviour-change refactor of gate-path code days before an unattended stretch is the change-freeze class this project rules against. It is safe and small **after** the gate call.

## Resolution

**Resolved 2026-08-02 by spec `00080`**, all three sub-items, on the owner's direction rather than on this topic's `ripe_when` triggers — sub-item 1's trigger (a sibling actually stranded) never fired, and the freeze that parked 2 and 3 had lifted: Stage 6a CLOSED 2026-07-30 with verdict PASS, and the engine runs pinned at `e5a44e1cb138` with its container unrestarted since 2026-07-26, so nothing merged to `develop` reaches production before an attended converge. **Two of this topic's own premises were corrected by measurement, and they are why the shipped fix differs from what is proposed above.**

**Sub-item 1 — the stranded sibling, commit `ed29d2ec`. The proposed manifest signature is FALSE for 2 of the 5 rebuild targets, so the fix uses no signature at all.** This topic asserted that a missing `manifest.json` reliably marks a partial run. Measured: true for `ohlc`, `funding`, and `oi` (each builder's last act writes `out_root/manifest.json`), **false for `snapshots`** (writes only `kraken-refdata-<UTC stamp>.json`) and **false for `universe`** (writes the single universe file, and only *reads* the OHLC set's manifest). Either proposed fix — cleaning up a manifest-less sibling, or making the retry replace one — would therefore have classified those two targets' **completed** output as partial garbage and deleted it. What shipped instead needs no signature: on any builder failure `rebuild_sets` deletes the **whole just-minted sibling** (`shutil.rmtree`), uniformly for all five targets. It is sound because the exists-guard raises *before* `mkdir` when the directory pre-exists, so every byte under `out_root` was written by the invocation that just raised — the "never delete builder output" caveat was protecting a directory this function does not mint, which is unreachable past that guard — and because every current builder fetches or derives repeatable input (the most expensive, a reach round, re-fetches ~90 s of paced REST). The handler catches `BaseException` and re-raises, so an operator's Ctrl-C mid-round cleans up exactly like a builder error; a test pins that, so nobody narrows it back. The strand was reproduced against unmodified code first — a builder that writes then raises left the sibling behind, and the same-day retry hit `sibling already exists` — then the fix flipped it.

**The hard-kill residual is accepted as a conscious drop, with the guard message as its remedy.** SIGKILL or power loss skips any handler, so a sibling can still strand. Rather than build a per-builder completion-witness protocol — machinery whose only consumer is a case the `rmtree` already handles — the `sibling already exists` refusal now tells the operator in plain language that the directory is either a completed sibling from earlier today or the leavings of a run killed mid-build, and to inspect and remove it to retry. Recorded here, in spec `00080` D2, and in the code comment beside the handler. **No successor topic exists and none is owed.**

**Sub-item 3 — `PAIR_KEYS`, commit `757c1449`.** The mapping now lives in `cli/ohlc/fetch.py`, its natural home: it is Kraken-REST reference data (display asset → REST pair key) consumed to call `fetch_ohlc`, and both users already import that module, so the move added no module and no import edge. `cli/engine/store.py` imports and re-exports it, so all four downstream import sites and `cli/engine/__init__.py`'s re-export were untouched and no test changed. `cli/ohlc/reach.py`'s upward import into `cli.engine` and the comment explaining the inversion are deleted; importing `cli.ohlc.reach` no longer loads `cli.engine` at all, which **dissolves** the half-initialised-package trap this topic registered rather than merely documenting it.

**Sub-item 2 — the seam duplication, commit `246bdfe0`. Full unification is NOT a pure refactor**, which is the second premise measurement corrected: this topic proposed extracting a shared helper and *deleting both duplicates*, but the two guard blocks measurably diverge and are test-pinned on both sides — different exception types (`OHLCError` vs `EngineError`); message prefixes asserted in `tests/test_ohlc_reach.py` (`seam too thin`, `seam mismatch`) and in `tests/test_engine_store.py` (`shortfall`, `mismatch`); reach's mismatch message carries both close values where store's carries neither; reach has a detached branch store lacks, store has an `allow_replace` poisoned-tail path reach lacks. Unifying them would have changed operator-visible, test-pinned messages or dropped the close-values diagnostic — a behaviour change wearing a refactor's clothes. What shipped is the identical part, once, in a new `cli/ohlc/seam.py`: `MIN_SEAM_OVERLAP = 6` (the single binding; `_SEED_MIN_OVERLAP` deleted), `drop_in_progress` (the two bodies were byte-identical), and `seam_overlap(left, right) -> (overlap_bars, mismatches)` — the **seam definition**, the join-on-`ts` and close-comparison both guards open with, which is precisely the surface a future safety fix must hit in both callers and therefore the drift risk this topic was opened for. The guard policies stay local, each carrying a docstring cross-pointer to its sibling so the deliberate divergence cannot be mistaken for an oversight. Mutation-proved rather than assumed: corrupting `seam_overlap`'s comparison fails the pinned mismatch tests in **both** test files, so both callers demonstrably route through the shared definition.

**Behaviour-neutrality was proven, not asserted** (spec `00080` D5): the full suite is green at **2755 passed, 0 failed, 0 skipped** with zero edits to existing test assertions, and `zcrypto engine soak-check` produces **byte-identical stdout and exit code** (exit 0) before and after the branch on the same local inputs — the probe that pins the CLI → soak → store wiring the refactor moves through. No deploy is owed by this branch; the change reaches production at the next attended engine converge (D6).
