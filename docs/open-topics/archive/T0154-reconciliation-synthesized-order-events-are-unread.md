# Reconciliation synthesizes order events on the live trade path, and nothing reads the flag that says so

## Context — what

The execution engine manufactures order events of its own and dispatches them to strategies exactly as it dispatches the venue's, distinguished only by a `reconciliation` bool the event carries. Nothing under `cli/` read that bool — `grep -n '\.reconciliation\b' cli/` was empty — so every synthesized event was handled as though the venue had said it.

Measured on the pinned wheel `2.0.0rc4.dev20260825` and against upstream source at `a52de0f914770b635701ae8961994e0f9b9067db` (`develop`, 2026-08-25T22:02:05Z, the day that nightly was cut):

- `LiveExecutionEngineConfig()` ships `inflight_check_interval_ms=2000`, `inflight_check_threshold_ms=5000`, `inflight_check_retries=5` and `generate_missing_orders=True`. `cli/engine/node.py`'s `_exec_engine_config()` sets only `reconciliation` and `filter_unclaimed_external_orders`, so all four defaults are live.
- **The in-flight check does not synthesize fills.** An order sitting `SUBMITTED`, `PENDING_UPDATE` or `PENDING_CANCEL` past the threshold is first *queried* — `QueryOrder` to the venue, once per retry — and at the fifth retry the manager (`crates/live/src/execution/manager.rs::check_inflight_orders`) manufactures a terminal event instead: `OrderRejected` with reason `INFLIGHT_TIMEOUT` for a `SUBMITTED` order, `OrderCanceled` for one pending a modify or cancel. Both are stamped `reconciliation=true`. Neither is a statement about what the venue did; both are the engine giving up on waiting.
- **`generate_missing_orders` is about positions, not in-flight orders.** It licenses reconciliation to synthesize a whole missing order, with its fill, to make the cache's position agree with a venue position report. Such an order is stamped `StrategyId("EXTERNAL")` with a reconciliation tag, so it arrives on `ExternalOrderObserver`, matches no ledgered row, and is counted `unmatched` and dropped — the one route of the three that is already contained, and contained by 00098 D3 rather than by anything aimed at this.
- **A synthesized fill's `TradeId` is synthetic.** `crates/execution/src/reconciliation/ids.rs` mints `S-{hex_ts}-{hash}` (FNV-1a over the fill fields) — deterministic across restarts so the engine's own duplicate-fill sanitizer dedupes *replays*, but by construction never equal to the venue's real trade id. So `is_duplicate_fill` cannot join a synthesized fill to the venue's later real one; what stops the pair being applied twice is `check_overfill`, with `allow_overfills` defaulting `False`, which refuses the second and does **not** publish it.

## Why this matters

This is the live trade path, and one of the three routes reaches an arm that spends money.

A cancel this engine requested sets `active.cancel_requested`. If the venue's ack does not arrive within roughly five retries, the manager manufactures the `OrderCanceled` itself. That landed in `_on_cancel_ack`, took the `cancel_requested` branch, wrote the row `canceled`, and proceeded to `_fallback(active)` or `_finish_revoked(active)` — the executor submitting its next order on the strength of a cancel **nobody at the venue confirmed**. The original may still be resting. This is the same class of ambiguity `_on_rejected` refuses to guess at, handled with a certainty the event does not carry.

The rejection route happened to land safely, and it is worth writing down that it was by accident rather than by decision: `INFLIGHT_TIMEOUT` contains none of `_POST_ONLY_MARKER` or `_KRAKEN_ERROR_MARKERS`, so `_on_rejected` fell through to the **ambiguous** arm — row `ambiguous`, remainder dropped, no resubmission, plan halted. That is exactly the right answer for an unanswered order, reached by a string not matching rather than by anything knowing the event was manufactured. A future marker list that grew a generic entry would silently turn it into a resubmission.

Failure direction across the three routes was not uniform, which is why "it fails safe" was never an available summary: the position route is contained, the rejection route halted, and the cancel route acted.

## Findings so far

- Nothing in `cli/` read `event.reconciliation`, on any path. The bool is first-class on `OrderFilled`, `OrderRejected` and `OrderCanceled` alike.
- Spec `00100` neither adopted nor rejected this machinery. It recorded `LiveExecEngineConfig` as "identical across all 33 shared fields" and names only `reconciliation` and `filter_unclaimed_external_orders`; the in-flight knobs and `generate_missing_orders` are not discussed anywhere in the design.
- The engine cannot arm on v2 yet (`exec_armed` renders `false`), so nothing here can fire against real capital before the decision is taken. It can fire on a **disarmed** engine only if orders are submitted, which they are not — so the rate is genuinely unmeasured, not merely unread.
- The `unmatched` half of `zcrypto_exec_external_events_total` is the family a synthesized position-reconciliation order would move, and `zcrypto_exec_orders_total{outcome="ambiguous"}` is the family a synthesized `INFLIGHT_TIMEOUT` rejection would move. Both are already deployed and already charted, so the reading needs no new instrumentation.


## Resolution

Fixed on `feat/nautilus-v2-migration`, and adjudicated in spec `00100` **D15** — "a terminal event the engine minted for itself is an unknown venue outcome, but a reconciled fill is a real one".

**The routing.** Candidate (1) adopted, in `cli/engine/executor.py`: `OrderRejected`, `OrderCanceled` and `OrderExpired` carrying `reconciliation=True` route to `_strand_ambiguous` from the top of `_on_order_event`, **above** the name dispatch, read as `getattr(event, "reconciliation", False)` in the file's existing defensive idiom — so the probe that opened this topic, `grep -n '\.reconciliation\b' cli/`, is STILL empty and must not be re-run as evidence that nothing reads the flag; grep the bare word, so no arm below can reach `_fallback`, `_reprice` or `_finish_revoked` on one. The row goes to `ambiguous` — an open state, so re-attach still sees an order that may still rest — the intent is journaled `ambiguous`, and the plan halts. Placing it above the dispatch is what turns the rejection route's accidental safety into a decision: a marker added to `_KRAKEN_ERROR_MARKERS` later cannot promote an in-flight timeout into a verdict. The check keys on the FLAG rather than on the mechanism, so the two sibling check loops in the same config (`open_check_*`, `position_check_*`, both with `interval=None` today) are covered by construction rather than by enumeration.

**Fills are excluded, deliberately.** A reconciled fill is the venue's own report transcribed late rather than an outcome invented — its quantity and price are the venue's, and only the trade id is minted because the report carries none. It is money that moved, so its row, its quantity credit and its published fill are all owed: no-fill-without-a-record has no exemption, and dropping the credit would additionally make the next resubmission over-ask by exactly that quantity. What covers a fill that did **not** happen is narrower than it reads, and D15 states the limit rather than glossing it: `create_incremental_inferred_fill` infers nothing unless the report's cumulative quantity exceeds the order's own, so a stale or replayed report cannot over-report; upstream's `check_overfill` with `allow_overfills=False` refuses an application past the order's quantity; and the executor's fill-time trips latch past the quantity the row was submitted for. `00100` D6's post-terminal reconciliation is **not** among them — a minted fill reaches the order and the Cache before dispatch, so it moves `active.filled` and the strategy-scoped position it is compared against by the same amount, and the check passes. A phantom *within* the remaining quantity, born of a venue misreport, is past every client-side guard there is.

**Candidate (2) as complement, never substitute.** `inflight_check_interval_ms`, `inflight_check_threshold_ms` and `inflight_check_retries` are now stated in `_exec_engine_config()` at the values they already hold (2000 / 5000 / 5) — the branch's idiom for a load-bearing default. No Kraken REST ack latency has been measured, so no different number was derivable; what the explicit statement buys is that an upstream default flip cannot move the live trade path silently. The interface pin keeps reading the library's own defaults so a bump that moved any of them is visible.

**Candidate (3) was not adopted and remains unestablished.** The config exposes no boolean that disables in-flight terminal generation — measured against the full field list on the pinned wheel — and no attempt was made to disable it by other means.

**The guard bites, on a fixture where the two sides differ.** Each routing test drives the same time-boxed intent to the same cancel and answers it with the same real library event class, differing only in the flag. Venue-sourced: 2 submissions, row `canceled`, plan runnable. Minted: 1 submission, row `ambiguous`, every later intent `refused`. The `reconciliation=False` arm is the true positive — an implementation that halted on every cancel ack would pass a one-sided fixture while breaking maker-first outright. Both directions proven by `infra/scripts/mutate-probe.sh`, each KILLED with its control proven and the tree restored byte-identically: reading the flag as constant `False` (the defect) fails the minted assertions, reading it as constant `True` fails the venue ones. Adding `OrderFilled` to the routed set fails the fill test at the dropped credit (`0.0 != 0.4`).

**The rate reading moved to an operating surface.** It genuinely cannot be taken until a v2 engine runs with a live exec client, so it now lives as a step in the engine runbook's pre-probe checklist (`infra/runbooks/engine.md`, §1 *Pre-probe*, step 5) — placed immediately after the healthy-boot `unmatched` baseline it must be read against, so an operator meets it at the moment it matters rather than in an archived file nobody reopens.
