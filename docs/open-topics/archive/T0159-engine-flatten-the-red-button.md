# `zcrypto engine flatten` — the red button

## Context — what

A market crash where everything must be converted to EUR within minutes has no primitive today: the kill switch cancels resting orders and refuses intents but **closes no position**; the only close path is a hand-signed probe plan through the 15-minute maker-first machine, with a 60-minute expiry and a pre-boundary blackout — built to be slow and careful, the opposite of a red button. The owner ruled the primitive on 2026-08-29: **whole account, market orders, kill file first.** Spec `00106` (this branch) is the design; this topic is its git-tracked residual holder.

## Why this matters

Scenario D (unattended open positions) and drill B in spec `00105` both end in "the operator's response is B" — and B does not exist. Rung 1 holds real margin positions across rollovers by design ([[T0018]]); a provider-level event ([[T0088]], accepted as-is with no standby) leaves the engine dead with positions open, and the master plan §10's "watchdog-triggered flatten-or-freeze runbook" was never built. The kill file plus a Kraken web UI is the entire emergency surface until this lands.

## Findings so far

- **The ruling, and what it overrides.** Whole account (pre-existing spot balances included — engine-owned-only is not "everything to EUR"); **market** orders, because in a crash the price is not the variable, time is; the kill file written first so nothing re-opens. Spec `00090` D6 records *"Rejected: MARKET as the fallback — unbounded price on the live path when a bounded marketable limit does the same job"* — that rejection stands for the probe machine; `00106` overrides it **for this command only**, and says so, because a bounded IOC in a fast market leaves residue and the residue is the exposure.
- **No market path exists in the engine**: `cli/engine/executor.py` builds only `order_factory.limit(...)` (GTC post-only, then IOC); nothing in `cli/engine/` constructs a market order. Margin closers today ride `_classify_margin_close` — sized from the Cache's live position with the venue's `reduce_only` flag — and spot disposals ride `_classify_spot_close` with an owner-supplied `qty`. `settle-position` is UI-only for the adapter (spec `00090` context).
- **The command must work while the engine is disarmed, kill-latched, or stopped** — that is the whole point. A hand-placed kill file on an idle engine cancels nothing until the next restart; while a plan rests, the 5-second poll revokes it. So the command's first act after the kill file is to wait for `level=none` (or the engine to be stopped), then cancel everything the venue still holds — never assuming the engine cancelled anything (what a `systemctl stop` does to a venue-resting GTC order is unverified in the repo).
- **The open design fork the spec settles**: out of process (a standalone invocation against the venue's REST surface, independent of the node and its state machine) versus inside the node (reusing the exec client but inheriting the plan machinery). The spec rules; the ruling's reasons are recorded there.
- **Fills raced by a cancel, dust below `ordermin`, and a leg the venue rejects** are the three ways "flat" fails to mean flat; the exit code must distinguish flat / partial / venue unreachable, and the journal must record what was attempted and what the venue answered, per action.

## Resolution

The build half is delivered on `feat/00106-engine-flatten`, every spec-`00106` commit on that branch, at the Fable review floor.

- **The command exists**: `zcrypto engine flatten --state-dir <PATH> [--execute]` (`cli/engine/flatten.py`, registered in `cli/engine/command.py`). The **default invocation is a dry run** — it reads the account, prints every leg with its side, quantity, pair and estimate at the taker rate, lists every dust balance and every balance no EUR or BTC pair can carry, and sends nothing; only `--execute` writes, and then only behind a `FLATTEN` typed at the controlling terminal, with no flag that skips it.
- **The exit-code contract is the whole verdict and never reads a leg's answer**, as `run_flatten`'s docstring states it on PR #599: 0 the final snapshot is flat (or the dry run completed), 1 refused with nothing sent, 2 something is still open (or the account-wide cancel failed, or a read failed after the first write, or a read before the cancel could not see every order or position — PR #599's clause, below), 3 the venue could not be reached or read **before** the first write, which is the cancel. A read that fails after `cancel_all_orders()` is 2 and never 3, because the account may already have moved.
- **The host wrapper** `/usr/local/sbin/zcrypto-flatten` is rendered from `infra/ansible/roles/engine/templates/zcrypto-flatten.sh.j2` and installed by the engine role — root-owned, not world-readable. It writes the kill file before it stops the unit, refuses to start the container while the unit is still active, and overrides the image entrypoint **before** the image, without which the container would start capture on a host whose engine was just stopped with positions open. The 2026-09-01 engine converge deployed it (below).
- **The unattended daily pass can never press it**: the `ops_daily` classifier is asserted to refuse `zcrypto-flatten` and `zcrypto engine flatten` under every wrapping the fleet actually spells — the wrapper, its absolute path, `docker exec` into the engine, an `ssh` that retargets the host, and the in-container form — each paired with a read command wearing the same wrapper, so a classifier broken into refusing everything fails too. The venue-mutating structural guard in `tests/test_engine_executor.py` admits `cli/engine/flatten.py` as a second such module by design, with the reason in its docstring.
- **A correction that ~1900 green tests could not see**, found by classifying the suite's test doubles: every `KrakenSpotHttpClient.request_*` needs a running event loop, and `OrderBook.bids`/`.asks` are methods, not attributes — so every invocation, `--execute` included, exited 3 on the first read and no request ever left the process. Fixed with `asyncio.run` at the CLI boundary, an awaiting recorder, fakes modelling the real library shapes, and three contract pins (one gated on `ZCRYPTO_LIVE_VENUE_TESTS=1`, which was `ZCRYPTO_VENUE_CONTRACT` until T0190 renamed it to the one opt-in the class uses). The doubles had been written to match our code rather than the venue; `tests/test_engine_stub_fidelity.py` now classifies all eight and guards the seven library ones in both directions.
- **What this branch deliberately did NOT prove.** No request has ever been made against the live account: the only request this code has issued left the process under a dummy key and came back `EAPI:Invalid key` — which proves a request signs, leaves and is answered, and nothing more. The five read shapes are unconfirmed against the real venue, and a reduce-only market close on a margin position remains **unsent from this repository on any order type**.
- [[T0160]] was registered from this work: the nautilus nightly bump and the contract checks that must ride with it, the side-enum `Option` change being the hazard that would make this command refuse to flatten rather than fail loudly.
- **The engine converge carrying `00106` + `rest-hold` is DONE — it was the 2026-09-01 converge**, and the wrapper reached the host with it: `/usr/local/sbin/zcrypto-flatten` is recorded in `docs/reference/fleet.md`'s services table (the red button's own row), which is the artifact this sub-item existed to place. It was listed as a next step until 2026-09-07 while already true; a next step that has happened reads as pending whatever its wording.
- **Four things this topic held open are disposed of, 2026-09-23.** `margin_legs`' docstring, left stale on purpose, was corrected with the listing cache (`7ff024973`): it names the enum's three members, FLAT, LONG and SHORT, and names `EXHAUSTIVE_MEMBERS` in `tests/test_nautilus_interface_pin.py` as what fails first if a later wheel adds a fourth. Whether the trade key's scope covers `TradeVolume` is moot: from `2.0.0rc6.dev20260918`, and on `2.0.0rc6.dev20260921`, a TradeVolume failure falls back to the public fee schedule (`nautechsystems/nautilus_trader#5005`). Whether the first read should degrade on a fee failure is answered by the wheel: the listing does not abort on a TradeVolume error or on an answer that does not parse, and the one fee failure still fatal — a well-formed answer that omits a pair's fee — fails the whole listing, which is exit 3 before any write; `tests/test_kraken_wheel_contract.py` pins all three. And a press between converge and dry run is accepted as a known gap; nothing gates it. Which fee path answered is visible only where a nautilus logger runs: the engine logs `Failed to request Kraken account fee rates, falling back to public rates`, which [[T0160]]'s step 2 reads, and the red button's bare client leaves no trace of it.
- **What the red button does on PR #599, on `2.0.0rc6.dev20260921`:**
  - **The listing is cached whole before any account read** — every row the listing returns, not one per symbol, in an order that keeps both spellings of every pair resolvable: the adapter's cache holds the last instrument cached for a symbol, so `read_listing` caches the rows spelled as their own symbol first and the other key last.
  - **One unreadable row no longer costs the cancel.** An open-order read that fails before the cancel is named in the plan, and the account-wide cancel and every leg still go out. A whole-account position read that fails is retried one basket pair at a time, scoped by instrument (`read_margin_positions`), and each pair it cannot read is named as a residual; when a scoped read fails before any has succeeded, or no basket pair is listed to ask, the original error is raised — exit 3 before the cancel, 2 after. A read left incomplete before the cancel ends an `--execute` run at exit 2, and the closing lines list each such read; a dry run prints the failure, says what an `--execute` run would end at, and exits 0. A scoped position read matches a row under the pair's AssetPairs key only.
  - **The plan names each resting order under the count:** `N resting order(s) seen -- the cancel is account-wide`, then `order <pair> <side> <qty> -- venue txid <txid>` for each.
  - **The five-leg caveat is gone** from the flat verdict, `--help` and the README row, and `BLIND_ORDER_READ_LEGS` with it. The exit-0 line says that the order, position and balance reads before the cancel and the final reads each came back whole, and that an open-order or balance row the adapter could not parse drops out of its read without failing it, so the operator confirms on Kraken's own pages.
  - **A spot sell goes out one 8-decimal unit under the reported balance where the floors allow.** The adapter rounds a balance's total and its held amount to 8 decimals each, so a reported free balance can exceed the venue's by up to one unit; `size_leg` takes one `_BALANCE_UNIT` off the floored quantity when the result still clears `ordermin` and `costmin`, and otherwise sends the quantity unshaved.
  - **Client order ids are `FLT<yymmddHHMMSS>-<n>`** — 17 characters through n=9 and 18 through n=99, so they reach the venue as minted — and the journal records `time_in_force` as `not sent (market order)`: the call still carries IOC, which the adapter maps for limit orders only.
  - **Its place under the owner's operating rule of 2026-09-23.** Until a pin carries upstream #5065, an engine started while a Kraken margin position is open can crash-loop at startup ([[T0160]]'s `2.0.0rc6.dev20260921` block). A crash-loop is cleared with the red button, which does not reconcile: its press stops the unit and closes the position.
