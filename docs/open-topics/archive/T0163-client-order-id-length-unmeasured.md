# Client order id length — the probe's 18-character truncation comment contradicts its own 27-character acceptance

## Context — what

`infra/scripts/kraken-order-semantics-probe.py` mints client order ids of the shape `O-<YYYYMMDD>-<HHMMSS>-901-P6V-<seq>` — 27 characters at a one-digit sequence — and the `1.230.0`, `1.231.0` and `2.0.0rc4.dev20260825` rows in `docs/reference/adapter-verification/` record those runs passing. When this topic was registered, a comment in the same file said the probe's recovery read matches on the `-901-P6V-` infix because that infix "survives Kraken's 18-char client-order-id truncation". The topic read that truncation as a cut keeping an id's first 18 characters: the infix starts at character 18, so such a cut ends exactly where it begins and keeps `O-20260823-120000-`, and the comment's two halves could not both be true. The wider question was unmeasured rather than merely inconsistent — acceptance at submit does not establish what the venue STORES, and no run in this repository had read a client order id back from the venue.

## Why this matters

Every id shape this repository sent was sized against a limit nobody had measured. `infra/scripts/kraken-fixture-mint.py` sent 29-, 31- and 32-character ids, all longer than the only length then believed accepted. If a truncation was real, two things followed silently: an id echoed back shortened no longer matches what was sent, and the probe's own crash-recovery read — keyed on an infix a cut would remove — finds nothing and reports a clean account where leftovers rest. Both failures read as success.

## Findings so far

- `infra/scripts/kraken-order-semantics-probe.py`, the `--probes 6` recovery read: the comment claiming the infix survives an 18-character truncation sat above the line that matched on `PROBE_ORDER_ID_INFIX`.
- `docs/reference/adapter-verification/2.0.0rc4.dev20260825.md` and the two `1.23x` rows: probe runs passing with 27-character ids. Every `--probes 6` row on record found zero open orders, so none of them exercised the recovery match against a real leftover.
- No row in `docs/reference/adapter-verification/` records a client order id as the venue returned it; the repository holds no other measurement of the venue's handling of id length.
- **The cut is the adapter's, and it keeps the tail** — read from upstream source on 2026-09-23. `truncate_cl_ord_id` (`crates/adapters/kraken/src/common/parse.rs` at `70d887545790`, the build commit of the pinned `2.0.0rc6.dev20260921`; the same rule is in that file at tag `v1.230.0`) sends a free-text id of at most 18 characters verbatim, a 36-character UUID and a 32-character hex id whole, and any other id as `O` plus its last 17 characters. So Kraken has never received an id over 18 characters from this repository, and every "acceptance at 27" on record was an 18-character id on the wire — `O-120000-901-P6V-1` for the 27-character shape. What the venue has accepted is 18 characters of uppercase letters, digits and hyphens. The topic's head-cut premise was wrong, and the comment's infix claim was true of the wire.
- **What was wrong instead.** The fixture mint's `FIXMINT-<kind>-<stamp>` ids shared their last 17 characters, so all three legs went out under one id, `O-<stamp>`, while Kraken documents `cl_ord_id` as unique among open orders and the resting leg was still open when the next leg went out. And the probe's recovery read could never fire: the spot order read carries `client_order_id=None`, and startup reconciliation names every order it adopts by its txid, so no read carries the id back, and an earlier run's leftover read as `other` — REVIEW, exit 0.
- **Pinned on the real client, offline.** `tests/test_kraken_wheel_contract.py::test_a_client_order_id_goes_out_verbatim_up_to_18_characters_and_as_o_plus_its_last_17_beyond` reads the `cl_ord_id` each id reaches a loopback venue with: 17- and 18-character ids and a 32-character hex id whole, `FIXMINT-spot-20260923T190000Z` as `O-20260923T190000Z`, and `O-20260823-120000-001-000-1` as `O-120000-001-000-1`. `test_an_order_report_carries_no_client_order_id` holds a report's `client_order_id` at `None` when the venue's row carries a `cl_ord_id`.

## Resolution

Resolved on PR #599, 2026-09-23, from the adapter's source and the wire rather than from a venue read — which the adapter cannot supply, because its reports carry no client order id.

- **The fixture mint** (`6d2fe352f`, `0b2736170`, `7e940fddb`). `mint_client_order_id` mints `FIXMINT-<R|M|S><ddHHMMSS>` — 17 characters, uppercase, one letter per leg — so each leg goes out verbatim under its own id, and the `FIXMINT-` tag reaches the venue. Each sent line prints the leg's id and the txid the venue answered (`sent <kind> as <id> -> venue txid <txid>`), and a leg that fails is caught on its own, the refusal naming the legs that were sent. `tests/test_kraken_fixture_mint.py::TestTheClientOrderIds` holds each id to at most 18 characters, unchanged by a replica of upstream `truncate_cl_ord_id` that is held to upstream's own test vectors, starting `FIXMINT-`, and the three distinct.
- **The probe** (`a94e8c6e0`). `OpenOrderSplit`'s docstring states the rule — the infix survives on the wire, but the spot order read carries `client_order_id=None` and reconciliation names every order it adopts by its txid — and `classify_open_orders` tells whose an open order is by its venue order id: `ours` for an id this invocation submitted or a txid an evidence file in `--evidence-dir` records, `known` for a txid named with `--known-order`, `unclaimed` for any other open order on `--pair` (probe 6 FAIL, exit 3), and `other` elsewhere.
- **The two other id shapes this repository sends.** The red button's `FLT<yymmddHHMMSS>-<n>` is 17 characters through n=9 and 18 through n=99, so it goes out verbatim (`43b4c9a94`). The engine's own `O-<YYYYMMDD>-<HHMMSS>-001-000-<n>` goes out as `O` plus its last 17 characters: `O-<HHMMSS>-001-000-<n>` while n is one digit, and each further digit of n takes one more character off the front; the row keying PR #599 carries matches ledger rows by the venue's txid, so that cut does not reach row matching.
- **Left as an observation, not an owed item:** whether Kraken's own pages show each id of 18 characters or fewer unchanged. It is read at the attended window's step 5c, the fixture mint's first `--execute` — workstation `kraken open-orders -o json` for the resting leg and `kraken closed-orders -o json` for the two market legs, the `cl_ord_id` field — and recorded as an observation in the `2.0.0rc6.dev20260921` adapter-verification record; [[T0159]]'s step-5 item carries the read.
