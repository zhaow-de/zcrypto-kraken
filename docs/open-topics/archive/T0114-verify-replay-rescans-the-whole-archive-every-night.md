# `verify-replay` re-verifies the entire archive every night, and cannot be windowed

## Context — what

`zcrypto archive verify-replay` replays every canonical book hour through `OrderBook` on every run. Measured end to end 2026-07-30/31: **5,724 canonical hours in 7 h 40 m = 4.82 s/hour**, and the archive grows **+288 hours/day** (12 pairs x 24 h, ~5 %/day at today's size).

**The runway is computable and short: runtime reaches the 24 h daily cadence at ~17,900 hours, about 42 days out (~2026-09-11).** Linear extrapolation, which is fair here because each hour is an independent parquet read plus replay.

The obvious mitigation — window the sweep with the CLI's existing `--since` — was tried that evening (spec `00076` D7) and **failed in production**: 1,870 of 2,218 hours reported `anchored=False`, every other check clean. The cause is structural, and `verify_replay`'s own docstring already stated it: *"a hole opened by `--pair`/`--since` counts as 'predecessor not present', same as a real archive gap."* An hour is chain-anchored iff it opens with a snapshot **or** its predecessor was present in the same enumeration and was itself anchored; a window cuts the chain.

Anchor-aware windowing (walk back to the last snapshot, replay from there, report only the window) was then measured and rejected too — see below.

## Why this matters

- **A 7 h 40 m nightly job on a daily timer has a ~42-day runway**, and it is not a cliff the instrument announces: `Type=oneshot` has no start timeout, so an over-running pass is simply skipped by the next tick rather than reported. The node also auto-reboots at 02:25 UTC, which a long run must clear.
- **The 2026-07-30 windowing incident under-measured this twice, and both errors are worth keeping.** First the hour count: the failing run's own output said "replayed 2218 hour(s)" and that number was taken as the archive size — it was the *windowed subset* (7 days x 12 pairs), while the archive is 5,724. Then the rate: 4.08 s/hour derived from that same subset understated the real 4.82 s/hour by 18 %, because a windowed sweep skips the per-pair setup the full one pays. Reading an instrument's output without asking what population it covers is the same class of mistake the whole T0097 thread was about — and it recurred within one evening, in the topic written to record the first instance.
- **The instrument cannot be scoped for investigation.** `--since`/`--pair` remain correct for *ad-hoc* narrow questions only if the operator accepts that `anchored` is meaningless in the narrowed view — a sharp edge on the tool the archive's integrity story depends on.
- Every hour of runtime is also an hour of the reconciled overlay being read under a `ro,soft` NFS mount.
- **A second, earlier cliff sits in front of the runtime one: journald's rate limit, around 2026-08-14.** Since spec `00077` the runner captures the sweep's output and replays it to the journal in one burst (`cat` of the temp file). journald drops anything past **`RateLimitBurst=10000` per 30 s per unit** *before Alloy sees it* — the fact `infra/ansible/roles/ops/files/config.alloy` already records. Today's sweep emits ~5,726 lines (one per hour plus two summaries) and grows +288/day, so at the nominal burst it crosses 10,000 around **2026-08-14** (5,726 + 288x15 = 10,046; +14 d is still under), ~28 days before the runtime cliff. Treat that date as approximate in **both** directions, for two independent reasons: journald scales the *effective* burst up with free journal disk space, which can only push the crossing **later**; while each failed hour emits a WARNING line on top of its per-hour line, which pulls it marginally **earlier**. Measure before relying on it (`systemd-analyze cat-config systemd/journald.conf` on the host) rather than trusting the nominal figure. What gets dropped is the **tail of a `(pair, hour)`-sorted stream** — the last pairs in sort order, *all* of their hours rather than only recent ones, plus both summary lines. So the trap is not 'recent findings vanish' but 'one pair's findings vanish entirely': an operator reading an early-sorting pair's complete record can conclude the sweep was clean while a late-sorting pair's failure was never printed. Both summary lines — what the new-breakage alert and the runbook tell an operator to read — go with it. Alerting itself is unaffected (the counts are parsed from the temp file, not the journal). The checkpointed-incremental fix below dissolves this too, by making the per-run output proportional to *new* hours; the alternative stopgap is `LogRateLimitBurst=` on the unit.

## Findings so far

- **Snapshot anchors are extremely rare, and rarer the healthier capture is.** Measured 2026-07-30 across the canonical tree: each of the 10 EUR pairs has **7 anchors in 537 hours, the most recent 2026-07-13** — 17 days stale. The two BTC-quoted pairs have exactly **1** (their 2026-07-23 genesis), which is the only reason they passed the 7-day windowed run. Anchors arrive on reconnect/resubscribe; since the T0035/T0008 recovery work landed, capture has not reconnected.
- **Therefore anchor-aware windowing does not converge**: anchoring a 7-day window today requires replaying back to 07-13 — effectively the whole archive — and the required lookback grows every day the stream stays healthy. A mitigation that gets more expensive the better the system behaves is not a mitigation.
- The paging half of the original problem is being solved separately and cheaply (alert on *newly*-failed hours rather than on exit code), which removes the schedule pressure but not the runtime.

## Resolution

**Resolved 2026-08-01 by spec + plan `00078`** (`docs/specs/00078-incremental-verify-replay-design.md`, `docs/plans/00078-incremental-verify-replay.md`), commits `f25128bf`..`523f8f25` on `feat/t0114-incremental-verify-replay`. `verify-replay` still certifies the **whole** archive every night, but replays only what changed, so its runtime is `(new hours) + (fixed budget)` forever and its journal output is flat — both dated cliffs above (journald `RateLimitBurst` ~2026-08-14, runtime meeting the 24 h cadence ~2026-09-11) are dissolved rather than pushed out. All three suggested next steps are disposed of:

- **Checkpoint the chain state — built, but not in the shape this topic proposed.** There is no cross-hour `OrderBook` state to persist: `replay_segment` builds a fresh book per hour, and the only cross-hour computation is `_chain_anchor`, a pure fold whose per-pair carry is `(prev_hour, prev_ok)`. So the checkpoint (`cli/archive/checkpoint.py`, one atomically-replaced parquet at `/var/lib/zcrypto-ops/verify-replay-state/`) caches **raw per-hour facts only**, and the chain verdict is recomputed every run over cached and freshly-replayed rows alike — caching the fold's *output* would make anchoring irrevocable (D1). The invalidation question this topic asked is answered by D2/D3: identity is the sha256 of the bytes **actually replayed** at a hand-bumped `VERIFIER_VERSION`, never the sidecar's claim (both writers publish sidecar-then-final, so a crash mid-mint leaves a new sidecar over old bytes), and a cached *failure* is never trusted — a transient `ro,soft` NFS EIO still heals the next night instead of freezing into a permanent failure. A corrupt, wrong-schema, or absent checkpoint is a loud full rebuild announced by `reused=0` (D9), a write failure is fatal with the summary withheld (D8), and an eviction that would drop >10 % of rows fails the run with the checkpoint unwritten (D7). The [[T0057]] lesson is honoured by construction: the state dir is ops-local and outside every NAS rrsync pin, and `/data` stays mounted `:ro`.
- **Windowing re-evaluation — decided, never build it** (D13). The runtime motive is gone, and windowing's structural defect is unchanged and unfixable: a window cuts the chain-anchoring predecessor set. `--since`/`--pair` remain ad-hoc tools with their documented sharp edge, and `--state-dir` refuses to combine with either (D10). Nothing is parked.
- **Duration + hour-count metrics — shipped as the run's census.** `ops_verify_replay_replayed_hours`, `_reused_hours`, `_pending_hours`, `_duration_seconds`, and `_audit_mismatches` join `00077`'s series, so the runway is a trended quantity rather than a hand-derived one, and a re-verification backlog that stops draining pages (`Ops · verify-replay backlog stuck`, `for: 27h` over `delta(...[26h])`).

The instrument's own honesty rests on a guard that can actually fail: every run re-replays 25 uniformly random **cache-trusted reused** hours under current code and compares the full raw-fact tuple, byte hash included (D6) — never pending ones, which are known-stale by construction and would false-page through every night of a legitimate drain. That, not an environment key, is what catches reader drift, overlay bit rot, and checkpoint corruption; `polars.__version__` was deliberately taken **out** of the invalidation key and left recorded-only (D5), because a monthly dependabot bump against a ~74-night full drain would leave the instrument permanently mid-drain.

The image rebuild, ops re-pin, converge, and rule push are an **attended tail this branch does not run**; the ordered checklist and its rollback caveat (digest **and** template together — the prior image rejects `--state-dir`) are in the iteration's `docs/iterations-history-phase6.md` entry and the memo's live rollout block, the same shape every previous ops re-pin took.
