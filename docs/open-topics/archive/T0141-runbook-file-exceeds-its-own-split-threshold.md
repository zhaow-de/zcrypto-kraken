# The runbook file exceeds its own stated split threshold

## Context — what

`infra/runbooks/README.md` states its own split rule in its Scope section: *"**Split when** this file exceeds ~12 sections, or gains a second subsystem's worth of material: move to `infra/runbooks/<subsystem>.md` and keep the explicit `<a name=…>` anchors byte-identical, because alert summaries and code comments cite them."* Measured 2026-08-18: **19 procedure sections** (20 `##` headings less the Scope section itself) across 743 lines, spanning at least four subsystems — capture, zaccess, ops/reconcile, and the engine's execution path. The threshold is exceeded by more than half again, and iter-140 added the largest single section in the file (`engine-probe-window`, a five-phase attended procedure).

The split was **not** done in iter-140, deliberately. Two reasons, both recorded here rather than left as a sentence in a task report:

- **It is a separate nameable component.** `branch-workflow.md`'s one-PR-one-component rule cuts both ways — a restructure of every runbook section is not "the rung-1 order path", and folding it into that branch would have made a safety-critical checklist commit also a file-move commit.
- **The anchors must stay byte-identical, and the checklist commit is the wrong place to risk them.** They are explicit `<a name=…>` tags precisely because the `— ALERT` / `— KNOWN LIMITATION` markers would otherwise become part of a heading-derived slug. Moving sections while an operator-facing probe checklist is the diff's subject mixes a reviewable procedure with a mechanical migration, and the procedure is the half a reviewer must actually read.

## Why this matters

The file's opening line is *"You are here because an alert fired in Slack"* — it is read at 03:00, on a phone, by a responder with nothing else open. Its own split rule exists because a runbook nobody can finish scanning is a runbook nobody reads, and that cost lands exactly when the responder is least able to absorb it.

The migration is also not free, which is why it needs its own change rather than a drive-by:

- **20 anchors, cited by 17 `infra/grafana/alerts.yaml`** alert summaries as `infra/runbooks/README.md#<anchor>` — a live page's only next step. (The count read 21 until the split re-measured it: the 21st `grep` hit is the Scope section's own prose mention of `<a name=…>`, not a tag. One section carries two anchors, not two.) Also cited from `infra/grafana/engine-dashboard.json`, `cli/archive/settle.py`, `tests/test_dashboards_cover_metrics.py` and `.pre-commit-config.yaml`.
- **`tests/test_infra_alert_rules.py` hardcodes the single-file assumption**: `RUNBOOK = REPO / "infra/runbooks/README.md"` and `_RUNBOOK_LINK = re.compile(r"infra/runbooks/README\.md#([A-Za-z0-9._-]+)")`, with `test_every_runbook_link_in_an_alert_summary_resolves` asserting every cited anchor exists. That test is the split's safety net **and** its blocker — it must learn about multiple files in the same change, or it goes green by resolving against a file the sections have left.
- A link that 404s is worse than a long file: the responder gets a fragment and no next step, which is the exact failure the test above was written to prevent.

## Findings so far

- Measured 2026-08-18 on the `feat/00090-rung-1-order-path` branch: 19 procedure sections, 20 `<a name=…>` anchors, 743 lines. Section families by prefix: `zcrypto-capture-*` (2), `cross-hour-straddle`, `zaccess-*` (4), `zcrypto-ops-*` (4), `zcrypto-engine-*` (4), `zcrypto-venue-*` (2), `refdata-sweep-due`, `engine-probe-window`.
- The split rule's second clause ("a second subsystem's worth of material") fired long before the count did — `zaccess` and `zcrypto-ops` are already distinct subsystems from capture, and the engine execution sections are a third.
- Two sections are not alert-triggered and split along a different seam than the rest: `refdata-sweep-due` (a scheduled reminder) and `engine-probe-window` (an attended procedure with human gates G1–G6). A subsystem-shaped split would separate them from the alert sections whether or not that is the intent.

## Resolution

**Resolved 2026-08-18** — split by **subsystem**, and the README reduced to a **pure index**.

- **The seam, and why.** Subsystem is what the file's own rule prescribed: `capture.md` (3), `zaccess.md` (4), `ops.md` (4), `engine.md` (7), `reference-data.md` (1). The open question this topic named — where `engine-probe-window` and `refdata-sweep-due` land under a subsystem seam — was answered by following that seam rather than inventing a second one: the probe window is engine material and sits last in `engine.md`, where the two exec-alert sections that reference it still read "below"; the reference-data sweep gets its own file, and that file's entry paragraph says a reminder came due rather than that an alert fired. The README keeps the Scope and holds **no** procedure sections, because an index that also holds the leftovers has no rule against gaining one more — which is exactly how one file reached nineteen.
- **The guard was widened and PROVEN before a section moved** (commit `a3bb29ec`). `tests/test_infra_alert_rules.py` now globs every `*.md` under `infra/runbooks/` and captures both halves of a citation, since a link resolves against the file it names; a second assertion pins each anchor to exactly one file. Proven through `infra/scripts/mutate-probe.sh` on a committed tree, reading which assertion fired each time: a cited anchor mutated to a non-existent one → `test_every_runbook_link_in_an_alert_summary_resolves`, reporting `no runbook file`; a correct anchor cited against the wrong file → the same assertion, reporting `actually defined in ['README.md']`; an anchor duplicated into a second file → `test_every_runbook_anchor_is_defined_in_exactly_one_file`. Baseline passed unmutated in every run and the tree restored byte-identically.
- **Byte-identity proven by set equality, not by eye** (commit `c88f3276`). The 19 chunks between thematic breaks and the 20 anchors are identical pre- and post-split — concatenated section bodies hash to `6a4f4c884fc1f8a750c3115036e42b40d7806aa46b777fa06d22ff6a65e0bcbe` on both sides — and relative order inside each file is preserved, so every "the sibling procedure above" / "the run-broken section above" still points where it says.
- **25 anchor citations updated in the same change**: 17 alert summaries, 3 engine-board panel descriptions, the clamp comment in `cli/archive/settle.py`, and 4 across three topic files (`T0103` ×2, `T0142`, and the archived `T0105`). A repo-wide sweep confirms all 25 resolve to the file that defines their anchor. Separately re-routed, as bare paths carrying no anchor: the root README's `probe-plan` Usage row, `T0018`, `T0049` ×4 and the index's `T0049` bullet. `tests/test_dashboards_cover_metrics.py`'s reference regex and `.pre-commit-config.yaml`'s mdformat allowlist both stop naming `README.md` and now cover the directory, so a new subsystem file is formatted and counted automatically.
- **One action is still OPEN at archive time, and it is owed at merge, not now: `infra/scripts/grafana-push.sh` must run once to re-ship the summaries and the Engine board.** Stated precisely in both directions, because the loose version misreads badly either way.
  - **Before this branch merges, nothing is degraded.** An alert summary carries a plain-text repo *path*, not a URL — a responder resolves it against `develop`, where `README.md` still holds every section. "The live summaries no longer resolve" is a statement about branch state, never about what a responder sees today.
  - **The window opens at merge and closes at the push, and inside it the link is degraded, not dead.** The path still names a file that exists; the responder lands at the top of the pure index, where every section is listed by its alert `uid` with a one-tap link. That is one extra hop on a phone — not the fragment-with-no-next-step failure this whole guard exists to prevent.
  - **The push is annotation-only.** Summary and description text, no rule added or removed, so **no `GRAFANA_PRUNE`**, no bake gate, no converge, nothing on any host. Order: **merge to `develop` first, then push** — pushing from an unmerged branch would ship summaries pointing at files `develop` does not yet have, which inverts the window instead of closing it.
- **The dashboard citations gained a guard they never had.** The panel descriptions cite sections exactly as the summaries do and are read at the same moment — the responder who followed the notification's panel link is already on the board — but nothing checked them, because the summaries' test reads `alerts.yaml` only. Found while updating them; closed in the same change rather than parked, since the next section that moves would otherwise break three unwatched links.
- **The index's own rows were the last unwatched citation surface, and they are now watched.** They link sideways — `](capture.md#anchor)`, relative, no `infra/runbooks/` prefix — so the path-aware pattern structurally cannot see them, which left the README the one surface no guard read *and* the surface that matters most: a summary's path resolves to the index, and the row is the responder's next tap. Both directions are pinned, because they fail differently — a row naming a file that does not define the anchor, and a section no row routes to at all (reachable only by someone who already knows which file to open). Proven with two more mutate-probe rounds reading which assertion fired: a mutated row and a wrong-file row both fired the link half; an anchor stripped from a row fired the unrouted half with `broken` still empty, so it really is the second assertion.
- **Deliberately not rewritten**: 4 `infra/runbooks/README.md#<anchor>` citations inside executed plans (`docs/plans/00075`, `docs/plans/00088`), which are point-in-time records of the alert YAML as authored then. They are not a page's next step, and rewriting them would falsify what was pushed.
