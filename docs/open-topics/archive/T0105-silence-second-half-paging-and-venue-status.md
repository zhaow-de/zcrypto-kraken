# Upstream silence: the paging half, and reacting to the venue's own status

## Context — what

The deliberately deferred second half of spec `00073` ([[T0101]]). That spec made a connected-but-silent book stream **observable** — booked as gap, exported as a gauge — and stopped there. Two things it consciously did not do:

1. **Nothing pages.** `gap_monitor.is_healthy()` does not consult the silence window, so the healthchecks.io dead-man still reports green through a total blackout. A repeat of 2026-07-27 is now correctly *counted* and still wakes nobody.
2. **Nothing reacted to Kraken's `status` channel** — corrected 2026-07-29. It was classified, logged with its `effectiveTime`, and counted by `system` value, with no behaviour and no rule keyed on any of it. The counter is now watched by `zcrypto-capture-venue-not-online` (`system != "online"`, a negative match so an unobserved payload shape cannot slip past it), with its procedure in `infra/runbooks/README.md`. **The observation armed first; the DECISION followed on 2026-08-06**, the day the first real non-`online` value arrived — see `## Resolution`.

Both omissions were recorded in the spec as decisions (D1, D3), not oversights. Both halves are built (see `## Done so far`), and the pre-drain **decision** — which this topic once believed no measurement could settle — was settled by exactly one: the measured zero lead of the first real event (`## Resolution`).

## Why this matters

**Half a fix that is mistaken for a whole one is worse than no fix**, because the metric now looks healthy-and-instrumented while the paging gap is unchanged. Anyone reading `zcrypto_capture_gap_seconds_total` after spec `00073` will see it move for the first time and could reasonably conclude the blind spot is closed. It was closed for *measurement* first, and stayed open for *alerting* until the paging half shipped 2026-08-05 (`## Done so far`) — this paragraph is the motivation as it stood while that gap was live.

The reason for deferring is real and should not be discarded on a later reading: `is_healthy()` gates the dead-man ping for **all 12 pairs at once**, on both hosts. A threshold fitted to ~4 days of thin-leg data could let one twitchy pair darken the fleet's last-resort liveness signal — trading a metric gap for a liveness outage, which is strictly the worse failure. That is the same reasoning spec `00072` D4 applied to the recovery ladder's wall-clock budget.

## Findings so far

- **The threshold's current basis is thin by construction.** 30 s was derived from the worst measured *natural* intra-hour book spacing: **12.196 s** (ETH/BTC, Fri 2026-07-24), **11.439 s** (ETH/BTC, Sun 07-26), with a largest natural hourly max of **12.299 s** across 104 segments. The `/BTC` legs bind because they are the newest and least liquid, and they had only ~4 days of history at measurement time. That is enough to set a conservative *booking* threshold and not enough to set a *paging* one.
- **The gauge is the instrument to fit against.** `zcrypto_capture_seconds_since_last_book_message{pair}` is fed by the same `last_seen` map the watchdog reads, so `max_over_time(...[24h])` on a healthy host gives the real natural-quiet distribution per pair, without injecting a fault into an unbackfillable pipeline.
- **Kraken's `status` channel is pushed automatically on connect and on every trading-engine state change**, carrying `system` ∈ {`online`, `cancel_only`, `maintenance`, `post_only`}. Its documented planned-downtime notification carries `type=maintenance`, `priority=high`, and an `effectiveTime` epoch.
- **Whether the 2026-07-27 outage was announced is unknown and unknowable retroactively** — `classify()` returned `"other"` for `status` and `_consume` dropped it unlogged, so nothing was ever recorded. Spec `00073` D1 fixes the recording; it deliberately builds no reaction, because a handler for a message this fleet has never once observed is the mechanism-nobody-proves-runs pattern.
- **An announcement cannot prevent loss** and should not be sold as if it could: if the venue publishes nothing, the data does not exist, and the secondary is fed by the same source. What it buys is *attribution* — separating "announced venue maintenance" from "our fleet broke", which is exactly what [[T0101]] got wrong for a day.
- **The counter this work will alert on is an UPPER BOUND, not a coverage fraction.** `GapMonitor` sums three window kinds independently — desync, disk watermark, upstream silence — so a pair desynced *through* a blackout books those seconds twice and `gap_ratio` can exceed 1.0. That is deliberate (each window answers a different question, and collapsing them would make two simultaneous faults look like one), but it means a rule reading `increase(zcrypto_capture_gap_seconds_total[...])` must be phrased as "how bad, roughly", never as "what fraction of the window was lost". Pinned by `test_gap_seconds_can_double_count_and_the_ratio_can_exceed_one`.
- **The booked duration over-reports by up to one 5 s check interval**, and always in that direction. The silence window closes at the pair's `last_seen` as of the closing tick rather than at the first message after the silence, so it absorbs a tick's worth of live traffic (≤ 2.4 % of a 209 s outage). Any threshold fitted from `gap_seconds_total` inherits that bias; fitting from the gauge does not.
- **The `1012` close frame is not an announcement.** Measured 2026-07-27: silence began 07:01:04.07, the `1012` arrived 07:04:49.35 — **225.28 s later**, at the end of the outage. Anything keyed on it recovers nothing.
- **The paging half needs two rules, not one, and the split is the finding.** A single per-pair bar cannot serve both shapes: the 2026-07-27 event was *every* pair going quiet at once, where the discriminator is the **minimum** across pairs — one thin leg being quiet is normal at any hour, all twelve simultaneously has no natural cause — while a single stuck stream is invisible to any cross-pair aggregate, because the aggregate reads its value off a healthy pair. The two need opposite bars (tight vs. loose) and opposite severities, so they are two rules.
- **On the blackout rule it is the PENDING PERIOD, not the bar, that decides whether the motivating event is caught.** The gauge is scraped every 60 s, so real silence at firing time is `bar + up to 60 s of scrape granularity + pending + the group's eval interval`. Phase sweep over scrape × eval alignments, at a 60 s bar: `for: 2m` catches the 209 s event in **12.1 %** of alignments and a 180 s blackout in **0 %**; `for: 1m` still misses 209 s in **12.9 %**; `for: 0s` catches every blackout ≥180 s in every alignment. Fitting the bar without fitting the pending period ships a rule that fails its own warrant — which is what `for: 2m` did until this was measured.

## Done so far

- **The venue-status observation is armed (2026-07-29).** `zcrypto-capture-venue-not-online` fires on `system != "online"` — a negative match, chosen because the payload shape for a real outage is unobserved and a rule enumerating known states would be a guess that silently misses whatever Kraken actually sends. The counting path is already validated for unseen values by synthetic `maintenance` / `cancel_only` frames in `tests/test_capture_upstream_silence.py`. Procedure in `infra/runbooks/README.md#zcrypto-capture-venue-not-online`, which at the time instructed the responder to record the value and its `effective_time` **here** — the input the then-parked decision needed; that obligation was discharged and retired when the decision landed (2026-08-06).
- **`zcrypto_capture_seconds_since_last_book_message` reaches Cloud** from both hosts as of 2026-07-29, after the capture roll and the Alloy config converge ([[T0107]], [[T0109]]). It had been emitted and dropped at remote-write since the day it was built, which is why this topic's paging half could not start its clock until now.
- **The paging half is built (2026-08-05)** — the dated item this topic carried, discharged as two rules in `infra/grafana/alerts.yaml`. `zcrypto-capture-all-streams-silent` (`min by (host) (…) > 120`, `for: 0s`, **critical**) covers the total-blackout shape 2026-07-27 proved nothing else sees; `zcrypto-capture-stream-silent` (per-pair, unaggregated so the page names the stuck stream, warning) covers the single-stuck-stream shape. Neither touches `gap_monitor.is_healthy()`, so the deferral's original hazard — an unfitted bar darkening the fleet-wide dead-man on both hosts for all 12 pairs — does not apply to either: a bad bar here costs a false page, not a liveness outage. `tests/test_infra_alert_rules.py` pins the blackout rule by uid and by its `min by (host)` aggregation, because the family-level "is this metric watched" guard cannot see it — the per-pair rule queries the same metric and excuses it.
- **The per-pair bar is DERIVED (2026-08-05, `ade2c019`), and `PROVISIONAL_THRESHOLDS` is empty again.** `900` → **`300`**, `for: 10m` → `for: 0s`, with the summary's stated duration and `data-integrity-dashboard.json` panel 102 moved in the same commit. The binding **natural** per-pair maximum is the primary's **12.068981 s** (AVAX/EUR), above the secondary's worst of 11.125801 s (ETH/BTC) and matching the 12.196 s the daemon's own `BOOK_STALENESS_SECONDS` comment records; the twelve primary maxima of 30.26–31.59 s are one simultaneous fleet-wide event, proven by the min-by-host maximum equalling AVAX/EUR's per-pair maximum to the digit. 300 is ~25× that natural maximum. The `~2.4×` margin this topic prescribed was **superseded**: it lands at ~29 s, the daemon's own gap-booking threshold and *below* that event. The same measurement widened the fleet-wide bar 60 → 120.
- **The derivation's base is one week, not the thirty days `[30d]` reads as** — the gauge only started reaching Cloud with the 2026-07-29 converges, so the selector covered ~7.2 d (primary) / ~7.5 d (secondary) of samples. The bars stand; the re-derivation on a genuinely full window is split out as [[T0129]], with a measured trigger.

## Resolution

**Resolved 2026-08-06 — the decision the topic was parked on was made on the day its trigger fired, from measured data** (owner ruling, recorded in the phase-6 decisions log).

**The event — the first real non-`online` value this fleet has ever observed** (the record the runbook's procedure sent here while the decision was open):

- Kraken venue maintenance, 2026-08-06. The daemon's own log, primary: `system=maintenance` at **07:01:02Z**, `cancel_only` at 07:14:58 and 07:16:08, `post_only` at 07:16:15, `online` at **07:18:18Z**. **`effective_time=None` on all five transitions, both hosts** — zero advance notice.
- Book feed silence ran ~07:02–07:17Z, both hosts identically — venue-side, so nothing existed to capture and nothing was lost: the residual-gap counter read 5047.636732 before and after, and neither daemon restarted (`RestartCount` 0 on both).
- **The paging half this topic built proved itself end to end on its first live event**: `zcrypto-capture-all-streams-silent` fired at 07:04 (120 s bar), `zcrypto-capture-stream-silent` ×24 at 07:07 (300 s bar), `zcrypto-capture-venue-not-online` named the cause at 07:07, and both silence rules auto-resolved at 07:17–07:19 when the feed returned. No human action was needed, and none was taken — the venue rule's own "do not restart or converge on this signal alone" held.
- The status message led the feed silence by ~60 s — the earliest signal that exists for an unannounced event.

**The ruling: the pre-drain is consciously DROPPED.** The deciding number the topic named — the lead time in `effective_time` — is zero: Kraken supplied `None` on every transition of a real maintenance event, so there is nothing to key a *pre*-drain on, and building one against the still-unobserved planned-maintenance shape would be exactly the mechanism-nobody-proves-runs pattern this topic's own findings warn against. What survives, right-sized: **the 6b executor checks venue state at cycle entry** before placing orders — recorded as an input to [[T0018]]'s order-submission build item, where the order path is being designed anyway. If a future *planned* maintenance ever arrives with a real `effectiveTime`, that observation would be new evidence for a new topic, not a reason to hold this one open.

**Operational tail, done in the same change**: the runbook's `zcrypto-capture-venue-not-online` procedure rewritten per its own retire-when instruction (the record-here obligation is discharged; the alert stays); the rule silenced time-boxed to 2026-08-13 per the procedure's silence step (silence `b8a73b62`, matched on the rule uid — it is a counter-presence check and stays firing until the next capture daemon restart clears the counter; delete the silence early if the daemons restart sooner).
