# Final pre-go-live steps — arm64 re-enable, the OS upgrade + reboot round, the `nautilus_trader` bump, and the credential rotation round

## Context — what

Five things must happen in the run-up to the Stage-6b live-capital step that belong to no other iteration, and whose *timing* is most of the point: a build lane disabled for development speed has to come back; four Debian hosts take an attended upgrade-and-reboot round, two of which have been accumulating patches behind a disabled auto-reboot; the `nautilus_trader` bump — landed, at 1.231.0 — still owes the attended real-money re-verification, which now gates **arming** rather than the bump itself; the reference-data sweep runs one last time, its verdict read into the go/no-go; and every credential the fleet holds gets rotated once, after everything else has stopped changing. They are unrelated in subject and deliberately staggered in time; they are carried together because they share a trigger no other topic owns — the run-up to go-live — and an item with no owner at that moment is one nobody remembers.

## Why this matters

All four are silent until the moment they are not. A disabled build lane is invisible until something needs arm64 — the silent-drift shape the fleet's pins-and-labels discipline exists to prevent, and a first multi-arch build can surface QEMU/buildx issues that must not be debugged inside a go-live window. An unrebooted host is the same shape — the patches are installed, only the kernel/library switch is pending, so nothing looks wrong until an exploit lands or a reboot finally happens at the worst moment. The `nautilus_trader` bump is silent in the opposite way — it sits in an open PR looking like routine dependency housekeeping, when merging it without re-running the order-semantics probes would put the live engine on an unverified adapter; only a mechanical version pin makes that loud. Credentials are worse still, because exposure accumulates quietly across a whole development period — test runs, agent transcripts, terminal scrollback, screen shares — and no single incident justifies the disruption of a rekey. The clean line is one round, late: rotate everything after the last change that could leak something new. Rotating early and continuing to develop simply re-opens the same exposure with fresh secrets.

- **The two healthchecks.io keys are shaped differently, and that changes how each is rotated** (measured 2026-08-04, by hash comparison — values never printed):
  - The **admin/read-write key** (`hcw_…`) is `healthchecks_api_key` in `group_vars/capture_host/vault.yml` — **defined exactly once** and consumed by **no playbook, template or script**. It is held for hand-provisioning ping URLs, so rotating it is a vault edit with no converge behind it. (An earlier draft of this topic claimed two definitions; that was a bad grep — the second hit is a *comment* in `host_vars/zcrypto-red/vault.yml` naming the var and pointing at its real home.)
  - The **read-only key** (`hcr_…`) has **no variable of its own**: it is embedded in the last path segment of `hc_prometheus_metrics_path` (`group_vars/observed/vault.yml`), which renders into `HC_METRICS_PATH` in the ops Alloy secrets env and drives the healthchecks.io Prometheus scrape every 60 s. **It is load-bearing and must not be revoked**: that scrape is what publishes `hc_check_up` and `hc_checks_down_total`, which the `zcrypto-hcio-watchdog` alert rule and the capture-rollout gate both read. Rotating it therefore means re-issuing the key **and** rewriting the whole URL in the vault, then converging ops — **and then recreating the Alloy container**, which the converge does *not* do for you: the env-render task carries no `notify`, and the role's only handler is an HTTP `/-/reload` whose own comment records that a reload does **not** re-read `alloy-secrets.env`, because env is process-level. A vault rewrite plus a converge therefore leaves Alloy running on the **old** key while every file on disk shows the new one. Finish with `docker compose up -d --force-recreate` in `/etc/zcrypto-ops/alloy` and confirm the scrape still reports by value (`hc_checks_down_total` present, `count(hc_check_up)` back at its expected number) — not a key swap in place, and not a converge either.

- **OS/apt state, measured on all four hosts 2026-08-04** — every Linux host in the fleet runs **Debian 13 (trixie)**: `zcrypto` (capture primary + the trade engine), `zcrypto-red` (capture secondary), `zcrypto-ops` (compute tier), and `zaccess` (the internet bridgehead — probed with the single-identity agent its `MaxAuthTries 2` requires; note `IdentitiesOnly=yes` needs an `IdentityFile` naming the agent's public key, or ssh offers nothing and the login fails looking like a key problem). The NAS is Synology DSM and is not in this round. Unattended-upgrades **installs** patches on all four; what differs is rebooting:

  | host | `Automatic-Reboot` | time | notes |
  | --- | --- | --- | --- |
  | `zcrypto` | **false** | 21:25 (inert) | capture primary + trade engine — patches accumulate until an attended reboot |
  | `zcrypto-red` | **false** | 22:25 (inert) | capture secondary — same |
  | `zcrypto-ops` | **true** | 02:25 | reboots itself; also the deadline every long job on that host must finish clear of |
  | `zaccess` | **true** | 05:25 | reboots itself; up 11 days at the measurement |

  So "auto-reboot is off everywhere" is **not** the case — it is off on the capture pair only, which is exactly where the unpatched-reboot backlog builds. The retained 21:25 / 22:25 times on the capture hosts are deliberate dead config (`fleet.md` explains why they must not be deleted).
- **A reboot does NOT re-read `alloy-secrets.env`, so it cannot stand in for the container recreate** (measured 2026-08-04). No systemd unit runs `docker compose up` at boot on ops, and `grafana-alloy` carries `restart: unless-stopped` — so a reboot *restarts* the existing container, and a restart reuses the environment baked in at **create** time. Only `docker compose up -d` (which notices the changed `env_file`) or an explicit `--force-recreate` re-reads it. The reboot round therefore **does not** simplify the rotation's Alloy step; that step stays.

- **One known exposure this round subsumes**, from [[T0126]] — accepted rather than acted on: iter-125's vault-guard TDD red phase put the vault password into local subagent transcript(s) and terminal scrollback on the workstation. Nothing was committed, the branch was not on the remote, and the workstation already holds the sops key material, so the marginal risk did not warrant an immediate standalone rekey. **That judgement is sound only because this round is coming** — if the rotation sub-item is ever dropped or deferred past go-live, T0126's acceptance must be re-decided, not inherited.

- **(rotation — ripe as the VERY LAST step before go-live)** Rotate everything listed above in one round, once the final pre-live change has landed. **The 10 `*_healthcheck_url` ping endpoints ARE in scope** (owner, 2026-08-04 — reversing an earlier exclusion of mine that rested on a wrong cost estimate and a wrong risk description). They matter because a ping URL is write-only but accepts success, `/start`, `/fail` and `/log`, so whoever holds one can keep a **dead** client's check green — masking exactly what a dead-man exists to catch — or raise false alarms. There are **10** of them (the earlier count of 15 was variable *names*, including six `ops_*` Jinja aliases) across four hosts; the bridgehead carries none.

  **A ping URL cannot be edited — its UUID is immutable — so "rotate" here means DELETE the check and CREATE a replacement.** That is a different operation from every other item in this round, with consequences to plan for rather than discover:
  - **The check's history dies with it** — ping log, uptime record, downtime statistics. Accepted: none of it is load-bearing, but it is gone, so capture anything worth keeping first.
  - **`unique_key` changes**, because it derives from the check's identity. Queries keyed on the check **name** survive *only if each replacement reuses its predecessor's exact name* — so the delete/create loop must carry the old name forward deliberately, not regenerate one. Given that, — the rollout gate's `hc_check_up{name=~"zcrypto-capture.*"}` and the watchdog's `hc_checks_down_total` aggregate both do — but any dashboard or query keyed on `unique_key` breaks, and every per-check series shows a discontinuity at the cut.
  - **Integrations are NOT inherited.** The Management API creates a check with only the notification channels you name; omit them and the replacement pings happily and notifies **nobody** — a check that looks green and is deaf. Re-attach and verify them explicitly per check.
  - **Each check is blind between delete and its first new ping**, so do them one at a time and close each before starting the next.
  - **Sequence before the admin-key rotation**: the `hcw_` Management API key is what performs the delete/create, so either do this while it is still valid or do it with its replacement — not straddling the swap.

  **Marginal cost is near zero, which is why the earlier exclusion was wrong.** The URLs reach their consumers two ways, and both are already paid for by this round:
  - **Baked into container environments — five, not four**: `capture_healthcheck_url` **twice** (the group value plus `zcrypto-red`'s override — one per capture host), `engine_healthcheck_url` (`engine.env`, *alongside* `KRAKEN_SPOT_API_KEY`/`SECRET`), `ops_liquidations_healthcheck_url` (ops `compose.yaml`), `nas_gate_healthcheck_url` (NAS `env`). These need a container **recreate**, not a restart. Four of the five ride recreates the round already forces (trade key → engine; logship token → both capture hosts; Coinalyze key → the liquidations env block). **The NAS one rides nothing, and that is a trap of the same shape this branch fixed for Alloy**: the `nas` role is **render-only by default** — it runs `compose up -d` only under `-e nas_apply_compose=true` — so a NAS converge without that flag leaves `archive-pull` pinging the *deleted* check, taking the gate dead-man dark while every file on disk looks right.
  - **Read fresh from a rendered script each run** — the five ops runners (`archive-pull`, `panel-materialize`, `verify-replay`, `verified-replay`, `grafana-watchdog`). A converge alone suffices; the next timer tick picks them up.
