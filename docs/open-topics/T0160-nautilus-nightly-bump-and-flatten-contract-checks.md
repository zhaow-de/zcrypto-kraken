# T0160 — nautilus-trader nightly bump, and the flatten contract checks it must not skip

## Context — what

The repo pinned `nautilus-trader===2.0.0rc4.dev20260825` (`pyproject.toml`, index `nautechsystems`) when this topic was registered. On 2026-08-31 a scan of `nautechsystems/nautilus_trader` counted **154 commits merged since that nightly**. Three of them touch surfaces `cli/engine/flatten.py` depends on, and one of those is a latent behaviour change that would make the flatten command refuse to run rather than fail loudly.

The bump itself is trivial. This topic exists because the **checks that must ride with it** are not, and they are not derivable from the diff — they come from knowing which upstream changes intersect this repo's read path.

**It now holds a second subject, which the bump does not own.** Through `2.0.0rc6.dev20260918` the same adapter's order-report read dropped an order whose pair its instrument cache could not resolve — silently, with a successful empty return — and that blinded the engine's kill-switch cancel sweep **and its startup adopt pass** on five basket legs. Upstream #5034 fixes the read at its source and rides the current pin, `2.0.0rc6.dev20260921`, so what is left of that is the live re-read. The engine's row sweeps missed on every leg, for a different reason — a reconciled order is named by its Kraken txid, never by the id the engine sent — and PR #599's row keying is their repair. Both are read at step 2 of one attended window, and they are registered as sub-items below because a deferral whose only home is a PR body or an unmerged branch's prose is untracked.

**These are the surfaces corrected so far** — a list of what was checked, never a claim that nothing else claims otherwise, because every review round so far has found the scope of the previous one too narrow: the flatten command's reads, verdict, `--help` and README row and its runbook procedure; the kill-switch trip, the startup adopt pass, both of its row sweeps and the external-event filter, in code; the probe window's restart step, covering an order still resting at the start and one that closed while the engine was down alike, and the order-path drills that turn on that pass (A1, A2, F2, G), including which pair their plan may name; the go/no-go harness's open-order counts at both ends of a run — probe 6's post-run count and probe 2's read of what was already there — and their runbook steps; and the external-events counter's help text and dashboard panel. **Point-in-time records deliberately keep their original wording** — `docs/reference/adapter-verification/`, archived topics, and committed specs and plans. What remains here is the live reading.

## Why this matters

`zcrypto engine flatten` submits market orders against the live account. Its reads are deliberately defensive: `_required(obj, field, what)` raises `FlattenUnreachable` when a named field is absent or `None`, and that abort is correct **before** the first write because aborting is free there. That same strictness turns an upstream `Some/None` change into a refusal to flatten.

A bump that lands green on the unit suite therefore proves very little about this command: the whole reason the async defect below survived ten tasks and ~1900 green tests is that the test doubles were written to match our code rather than the venue.

## The bump is not cheap — it disarms trading until an attended live-money pass re-earns it

**This is the constraint that governs sequencing, and it is mechanical, not advisory.**

`cli/engine/order-semantics-verified.json` lists the nautilus versions whose attended ~EUR 0.20 order-semantics pass has actually happened. **Two independent guards read that one file:**

- `cli/engine/execgate.py` refuses the gate at runtime when the RUNNING interpreter's `nautilus_trader` is absent from the list.
- `infra/ansible/roles/engine/tasks/main.yml` refuses a converge rendering `exec_armed=true` on a version absent from the list.

The file's own note is explicit: *"The pin is FROZEN at this string until the engine is armed on it"*, and *"Never add a version without the `docs/reference/adapter-verification/<version>.md` record that carries its PASS."*

So bumping off `2.0.0rc4.dev20260825` **cannot** be a lockfile edit followed by a converge. Until a new attended six-probe pass runs against the new version on the live account and its record is committed, the engine cannot arm — and a converge that renders `exec_armed=true` is refused by the role. \[\[T0085\]\] holds that pass as one of its three legs and records the last one (2026-08-26, PASS on all six probes, EUR 0.16).

**Consequence for planning:** the bump belongs *with* its order-semantics pass, not before it, and neither belongs in a converge window shared with unrelated residuals.

**Why the bump was live work rather than a watch.** `904862a8` is this repo's own merge of the `00106` flatten branch (PR #364), 2026-09-01 — not an upstream nautilus PR — and its landing put the flatten fix these checks lean on into the running image before the trading library under it moved.

### The order-report read's instrument lookup, and the four engine-path readings around it

Measured 2026-09-03 against the pinned wheel, on a real `LiveNode` and against a loopback venue. **These readings were taken on the parked flatten-cache branch and are not re-checkable from `develop` alone** — the two live arms need the trade credential, and the wheel ships as one stripped compiled extension (`nautilus_trader/_libnautilus.cpython-314-x86_64-linux-gnu.so`), so no source read on this machine settles them either.

**The mechanism.** The Kraken spot HTTP client's instrument cache is keyed on the instrument id and scanned by `raw_symbol`, which is Kraken's `AssetPairs` **key** (`XXBTZEUR`); an open order is looked up by its own `descr.pair`, which is the **altname** (`XBTEUR`). The comparison is raw equality inside an `if let Some(...)` with no `else`, so an unresolved row is dropped with no warning and the call returns a successful, short list. **Five of the twelve `BASKET` legs are spelled both ways — BTC/EUR, ETH/EUR, XRP/EUR, LTC/EUR, ETH/BTC** — and that set is recomputable from repo state alone, from `cli/engine/store.py`'s `PAIR_KEYS` against `cli/backfill/read.py`'s `dump_pair_name` (`tests/test_kraken_fixture_mint.py::TestTheSameKeyGuard::test_the_blind_legs_are_the_two_way_spelled_basket_legs` and `tests/test_kraken_order_semantics_probe.py::test_the_reconcile_blind_legs_are_the_two_way_spelled_basket_legs` are that computation).

The four readings that decide what a repair may and may not assume:

1. **There is no local door, and both candidates are PROVEN CLOSED** — positively established, not merely unfound. No execution-client object exists in Python to hook: the factory's public surface is exactly `['name']`, a depth-4 walk of a built node found nothing exposing `cache_instrument`, and interposition was refused four ways. And the node's own instrument path is closed by a controlled A/B on a real `LiveNode` against **two loopback venues, one per client**: an instrument present in the data client's listing and absent from the exec client's own gives `Received 0 order(s)`, while the control arm gives `external=1, open=1`. Timing was ruled out by a 70–400 ms spread.
2. **The exec client's cache is populated KEY-ONLY, not cold.** It fetches its own `/0/public/AssetPairs` and logs `Loaded 2856 Spot instruments`. So the hazard is **spelling**, not population — and the stacked worry that "an empty adopted set is indistinguishable from a spelling miss" can be struck: the set is never empty for want of population.
3. **Flatten's twin shape is INVERTED for the engine, and this is the most expensive thing here to assume.** A **distinct-id** twin — the shape flatten's own cache priming *requires* — is parsed and then dropped by the execution manager (`WARN: 1 orders skipped (instrument not in cache)`, Cache empty). A **same-id alias** reconciles fully. **A plan that says "do for the engine what flatten does" ships an inert fix.**
4. **An altname-spelled open POSITION aborts startup loudly** — `RuntimeError: Failed to get mass status from KRAKEN`, exit 1 — rather than dropping silently. The order read is the asymmetric one; the position read fails closed.

**And the executions subscription is sent with `snap_orders:false, snap_trades:false`** — measured on this build. So "the WS execution stream delivers changes, not a snapshot" is no longer an inference corroborated by `_adopt_resting_orders` existing at all: a pre-existing resting order receives no WS event and therefore never self-heals into the Cache by any route other than the reconciliation read. That closes the one link in the argument below that was previously reasoning rather than measurement.

**The reading on `2.0.0rc6.dev20260918` is the HAZARD result: the blindness REPRODUCES on the engine path.** Two orders rested at the venue that the starting process did not place — one on `BTC/EUR` (key `XXBTZEUR`, altname `XBTEUR`) and one on `SOL/EUR` as the control, whose altname equals its key. The engine was restarted deliberately inside the inter-cycle gap. Its mass status returned `Received 1 order(s), 10 fill(s), 0 position(s)` and reconciliation read `external=1, open=1`: it adopted the `SOL/EUR` order, cancelled it, and the venue confirms it gone. **The `BTC/EUR` order appears nowhere in the boot — not under `BTC/EUR`, `XBT/EUR`, `XXBTZEUR` or `XBTEUR` — and it is still resting at the venue.** Every alternative is excluded by the same boot: the venue read succeeded (no `venue orders could not be read at startup`), the instrument cache was populated (the control resolved), the instrument load did not fail, no cancel raised, and the mass status request returned normally. So the order-report read looked the pair up by raw symbol, missed, and returned success with that order silently omitted. It is the defect this project's upstream issue #5033 reports and #5034 fixes.

**What `2.0.0rc6.dev20260921` changes, pinned offline on the real client.** #5034 records the altname index inside `request_instruments`, and the open-order, closed-order, fill and position readers resolve a pair spelled either way through it. They part on a row the listing cannot resolve: an open order or a position fails the whole read, while a closed order or a fill is skipped with a WARN — `ClosedOrders: instrument not in cache for pair <pair>, skipping order <txid>`, and its `TradesHistory` twin for a fill (upstream `crates/adapters/kraken/src/http/spot/client.rs` at `70d887545790`). So an unscoped `open_only=False` read, the shape PR #599's row keying issues in `read_venue_orders`, fails whole on an open order it cannot place and comes back short by any closed order it cannot. A read scoped to one instrument still keeps only the rows spelled by that instrument's AssetPairs key, so a scoped BTC/EUR read returns no rows (upstream #5067, open). `tests/test_kraken_wheel_contract.py` drives the real `KrakenSpotHttpClient` against a loopback venue and pins the open-order, closed-order and position clauses (the `2.0.0rc6.dev20260921` record names each test). The fill reader and the skip of an unresolvable fill are read from upstream's source, and no test here pins them. So the four readings above describe the adapter before #5034, and reading 1's closed door no longer matters: the fix is at the source.

### The row keying — the row sweeps' repair, on PR #599

The owner ruled the repair onto PR #599 on 2026-09-23. `cli/engine/executor.py` keys each ledger row to its Kraken txid as well as to the id the engine sent, and a restart resolves a row by the txid when the engine's own id misses:

- **Recorded at acceptance.** The `OrderAccepted` event in a row's `events` carries `venue_order_id`, on the in-flight path and on a superseded order's late acceptance alike, and so does every fill payload, as the backstop for an order that reaches FILLED with no acceptance in the ledger. The ledger's schema is unchanged — `execledger.validate_exec_record` checks `events` only as a list — so every reader of the exec record tolerates the new key and the engine converges alone. `_row_venue_order_id` reads a row's one distinct txid; none, or two that disagree, reads as none.
- **Resolved by the txid.** `_cached_order` looks a row's order up by the row's own id, then through the Cache's venue-order-id index. `_adopt_resting_orders` matches a resting order to an open row by client order id, then by venue order id; attachments are held by txid too (`_attached_by_venue`), `_attached_for` resolves an event by its client order id and then its venue order id, and every event-path ledger write names the row by its own id.
- **Closed orders read at the venue by txid.** The startup mass status is open-only, so `read_venue_orders` builds a bare `KrakenSpotHttpClient` on the engine's credentials, caches the whole listing, and reads with `open_only=False` from the earliest such row's boundary less one hour, under a 30 s bound — once per process, in the startup pass, before any cancel or pickup, and only when a row needs it. The closed-while-down arm takes a report found by txid through the arms a Cache order takes — the repair, the terminal state and both trips — and `_reconcile_finished_rows` compares each closed row with fills against its report for a withdrawn fill. A failed read leaves the rows as they are, logs one CRITICAL line and refuses every plan until the engine is restarted; it trips nothing. A plan is picked up only after the startup pass has run.
- **Ambiguous when unmatched.** An open row with no recorded txid, or whose txid the venue read does not return, takes the state and the event `ambiguous`, once. A finished row with fills, in either case, takes the event only and keeps its state — the coordinator's ruling, because the state would claim the order may still rest. The mark refuses nothing and trips nothing.
- **The adopt pass's cancel line names the gate's reasons**: `canceling adopted resting order <id> -- the gate reads none (<reasons>)`, where it printed "the kill switch is latched" whenever the gate read `none`, on a merely disarmed engine too.

It is proven offline on the pinned wheel — the venue-read tests drive real order status reports carrying `client_order_id=None` — and end to end on the production node assembly against a loopback venue: a reducer resting as `XBTEUR` was kept and re-attached, an order that filled while the engine was down was read by its txid and closed `filled`, and a legacy row was marked `ambiguous`.
