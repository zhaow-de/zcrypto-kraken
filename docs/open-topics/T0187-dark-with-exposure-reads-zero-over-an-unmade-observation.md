# The dark-with-exposure page reads no exposure over a position it never observed

## Context — what

`infra/grafana/alerts.yaml`'s `zcrypto-engine-dark-with-exposure` pairs *the engine is not reporting* with *money is exposed*, and fires on `$A > 0 && $B < 1`. Its exposure half is

```
max(abs(last_over_time(zcrypto_exec_position{host="zcrypto"}[24h]))) or on() vector(0)
```

With no `zcrypto_exec_position` sample anywhere in the window, `last_over_time` returns nothing, the fallback supplies 0, and `$A > 0` is false. 0 is a value the position genuinely takes — flat — and it is the quiet direction at the same time, so the rule reads *no exposure* over an observation that was never made, and the one page it exists for cannot fire.

## Why this matters

The series is not eagerly born, and it has two writers rather than one. `zcrypto_exec_position` is a labelled `Gauge` in `cli/engine/command.py`'s `_ExecutionMetrics`: `run()` seeds it at startup from the journal — `_seed_exec_positions` takes the newest `venue-*.json` that is both `"ok"` and `schema_version == 2` — and the executor's fill hook sets it per fill (`_metrics.set_position(...)` in `cli/engine/executor.py`). The seed publishes **every** symbol in that record's `state.positions`, and `cli/engine/venuestate.py`'s `venue_state_from_cache` writes an entry for every `INSTRUMENT_IDS` symbol, zeros included — so a restart that finds such a record publishes the whole basket at once, exposure and flat alike. It landed in `36ac083e`, before this topic was written, and `tests/test_engine_metrics.py`'s `test_run_builds_the_execution_metrics_seeds_positions_and_installs_the_executor_hooks` pins it.

So the blind window is narrower than a restart. `_seed_exec_positions` returns `None` when the journal holds no readable ok schema-2 record, and its call site then publishes no symbol at all; and when the seed itself raises, the `except Exception` around it logs and carries on with `exec_metrics` **already bound** — so fills still publish and the gauge is merely childless until the first one. Either way there is no series while it lasts, and no fill has come along to make one. If the engine then goes dark, node A reads 0 through the fallback and the page stays quiet with money at the venue: the state the rule was built for.

`_ExecutionMetrics`' own docstring states the principle the rule leans on and does not get: *a Counter's zero is a MEASURED fact where a Gauge's would be an unmeasured claim* — which is why `realized_pnl` is eager at 0 and a labelled position gauge is not, and why the seed gives it children from a measurement rather than from a claim. `T0018` records that nothing has been armed and no order has ever been submitted, so the fill hook has never fired — and the seed has. `docs/reference/adapter-verification/2.0.0rc4.dev20260825.md`, run 2026-08-26 and eight days after the seed landed, reads *every `zcrypto_exec_position` series 0 across all twelve symbols* by value; a labelled gauge with no children emits no samples at all and `get_sample_value` returns `None`, so twelve series present means twelve children, and with no fill ever the seed is what made them. The seed works in production, and this is the evidence a fix would be judged against.

The rule's own comment already names the neighbouring case: past the 24h lookback the page self-resolves while the engine may still be dark and the position still open, and the runbook says in those words that a resolve is not an all-clear. That is the same blindness with a clock in front of it, documented and accepted. The unseeded case has neither a clock nor a note.

## Findings so far

- **The ruling, to be recorded rather than re-derived: the fix is not an edit to node A's expression.** The same `or on() vector(0)` on node B is load-bearing — it is what makes the rule page on BOTH darkness routes (a dead exporter leaving `up` present at 0, and the primary's Alloy taking the series away entirely) and what lets `noDataState: Alerting` mean *the datasource is gone* rather than *the fleet is*. The rule's comment defends that at length. A fix at this layer, if one is ever taken, is therefore a separate presence check, so the blindness is itself visible instead of being folded into the quiet arm.
- `tests/test_infra_alert_rules.py`'s `_replay_dark_with_exposure` already models the fallback exactly — its `a(t)` returns `0.0` when the window holds no sample — and it exercises a genuinely flat position (`flat_then_dark`) as a quiet case. Nothing in it distinguished flat-and-observed from never-observed, so the work was a new history in that harness rather than a new harness — landed, and recorded below.
- An alert-rule change reaches Grafana only through `grafana-push.sh` run from merged `develop`, on the owner's word (`fleet-deploys.md`). That is why this is a topic and not a commit on the branch that found it; the rule carries `severity: critical` and sits on the live trade path.
- It is `T0183`'s family by shape, and is recorded there as *Excluded by transfer* to this topic — `T0183`'s arm (a) holds no earlier than this lands.
- **The replay's never-observed half has landed** (`tests/test_infra_alert_rules.py`): `_replay_dark_with_exposure` now takes a history that publishes no position sample at all, and `test_a_position_never_observed_is_as_quiet_as_a_flat_one_and_the_rule_cannot_tell_them_apart` pins it as reaching the same verdict as a genuinely flat book under today's node A, and that verdict as the quiet one. It is a characterisation written to go RED the day the gap closes — a reader finding it green must not read that as the rule being sound. Beside it, `test_the_replay_can_separate_an_unobserved_window_from_a_published_zero` exercises the `unobserved_reads` seam, which today's evaluation does not read.
- **The alert-layer fix is measurably harmful, which is why it is not taken.** Replayed: a blanket presence-aware node A — every empty window read as exposure — costs the rule both of its current properties. A dark engine holding a position stops self-resolving at the 24h horizon and keeps paging to the end of the replay, and a book the engine reported FLAT starts paging one `for:` past that same horizon. Both follow from every history being unobserved eventually. Trading the blindness for a page on a legitimately flat book is the worse of the two.
- **THE OWNER'S DECISION, 2026-09-09: the residual is ACCEPTED, not fixed** — the topic stays `open` carrying the `ripe_when` above, because the defect is judged tolerable at current stakes rather than solved. The grounds, recorded because an acceptance whose grounds are unwritten is indistinguishable from an unexamined gap: **darkness is independently guarded** — `zcrypto-engine-cycle-stale` reads `time() - zcrypto_engine_cycle_completed_at_seconds` at `for: 5m` and `severity: critical`, and references `zcrypto_exec_position` zero times, so a dark engine pages whatever this rule does; this rule's job is to add *and money is exposed* to a page that fires anyway, and its failure degrades urgency, never detection. The alert-layer fix is harmful (the bullet above). And what actually remains is **staleness, not absence**, which is not what this topic was opened for: the seed publishes the position as of the journal's newest record, not as of now, so a position opened while the engine was down, an engine restarting and seeding flat, and a death before its next cycle all read quiet. Reachable, since sanctioned hand settles happen; survivable, because *cycles have stopped* still pages critical. Nothing is armed, no order has ever been submitted, and rung 1 is ~€10–30 attended.
