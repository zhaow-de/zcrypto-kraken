## Why this matters

Tonight's iter-084 deployment ran on ad-hoc journalctl playbooks and dead-man pings alone — no ERROR alerting, no resource visibility on a 2 vCPU/4 GB host now running three workloads, no disk watch (the VPS journal grows ~1.4 GB/month). The disk-watermark alert this delivers is also the ripe trigger for the journal-retention topic, and the gap-ratio panel continuously watches the T0003 exit-bar quantity.

## Findings so far

- The adversarial pass caught and the spec now pins: per-rule no-data semantics (a blanket "no-data ⇒ alert" leaves the ERROR rule permanently firing when healthy), the §8 posture (non-root Alloy + GET-only proxy; the inspect-Env residual is a named waiver), capture-counter honesty (reconnect/resubscribe/segment counters must be added — additive state only), exporter failure isolation (telemetry may never kill a daemon or void a gate cycle), restart-safe staleness math (completed-at gauge + startup seeding), and the mechanical deploy embargo (`capture_metrics_enabled`/`engine_metrics_enabled` default `false`).
- Grafana Cloud IRM (OnCall) heartbeats offer dead-man semantics; the deliberate choice is to keep healthchecks.io as an independent failure domain. **Consolidation is an explicit open option, not a default** (see next steps).
- Series budget: keep-only relabeling seeded from the Docker integration's ~16-metric allowlist; target < 1 k active series on the free tier.

**The host-label asymmetry is deliberate and dashboard-relevant — do not "fix" it casually.** The ops node's metrics carry `host="ops"` (via `external_labels` on its `prometheus.remote_write`); **the NAS's carry no host label at all**. The `host` label the NAS's config sets is on the *Loki logs* pipeline only, never on metrics — a gap found the hard way in spec `00054`, when an alert selecting `node_load1{host="ops"}` matched nothing. The NAS was deliberately left unlabeled: adding a label to an existing live series changes its identity in Prometheus, and the `Reconciler · residual gap increased` rule pages for **permanent data loss** off `increase()`/`resets()` — not a series-identity change worth risking for symmetry. The consequences a dashboards package must handle:

- `node_load1{host=""}` selects the NAS (an empty matcher matches series where the label is **absent**); `node_load1{host="ops"}` selects ops. `NAS · load high` uses the former for exactly this reason — its Atom-sized threshold would misfire constantly against a 24-thread box.
- Both hosts' Alloy bind the same `--server.http.listen-addr=127.0.0.1:12345`, so **`instance` collides too** — it cannot distinguish hosts either.
- When the VPS `obs` role lands, decide the labelling scheme for the whole fleet **at once** rather than per host, and take the NAS's series-identity risk knowingly (ideally at a moment when a false permanent-loss page is cheap to dismiss). *\[Update 2026-07-19: the capture hosts shipped labeled from birth — `host="zcrypto"` / `host="zcrypto-red"` via `external_labels` (iter-105) — so the fleet is now 3-of-4 labeled and only the NAS's pre-existing series remain unlabeled; the "at once" decision reduces to the NAS's series-identity question alone.\]*
- Benign, recorded 2026-07-19 (explicit drop, no action): every fleet Alloy logs a `remotecfg` "noop client" line at startup — the unused remote-config service's normal idle message, not an error; do not chase it.
