# Grafana Cloud observability — execute spec 00043

## Context — what

The design and plan are done (authored attended, 2026-07-11, during iter-084's boundary wait; three-agent adversarial pass applied): both VPS containers ship docker logs and three metric levels (OS / container / application incl. trades+portfolio) to the **already-provisioned Grafana Cloud instance** via one non-root Alloy behind a GET-only docker-socket proxy; one committed dashboard; API-provisioned email alerts. This topic parks the **execution**.

- Spec: `docs/specs/00043-observability-design.md`
- Plan: `docs/plans/00043-observability.md` (Tasks 1–3 subagent TDD, Task 4 attended deployment/shakedown)

## Why this matters

Tonight's iter-084 deployment ran on ad-hoc journalctl playbooks and dead-man pings alone — no ERROR alerting, no resource visibility on a 2 vCPU/4 GB host now running three workloads, no disk watch (the VPS journal grows ~1.4 GB/month). The disk-watermark alert this delivers is also the ripe trigger for the journal-retention topic, and the gap-ratio panel continuously watches the T0003 exit-bar quantity.

## Findings so far

- The adversarial pass caught and the spec now pins: per-rule no-data semantics (a blanket "no-data ⇒ alert" leaves the ERROR rule permanently firing when healthy), the §8 posture (non-root Alloy + GET-only proxy; the inspect-Env residual is a named waiver), capture-counter honesty (reconnect/resubscribe/segment counters must be added — additive state only), exporter failure isolation (telemetry may never kill a daemon or void a gate cycle), restart-safe staleness math (completed-at gauge + startup seeding), and the mechanical deploy embargo (`capture_metrics_enabled`/`engine_metrics_enabled` default `false`).
- Grafana Cloud IRM (OnCall) heartbeats offer dead-man semantics; the deliberate choice is to keep healthchecks.io as an independent failure domain. **Consolidation is an explicit open option, not a default** (see next steps).
- Series budget: keep-only relabeling seeded from the Docker integration's ~16-metric allowlist; target < 1 k active series on the free tier.

**The host-label asymmetry is resolved — the whole fleet now labels uniformly.** All four hosts' metrics carry an explicit `host` label via `external_labels` on their `prometheus.remote_write`: `host="ops"`, `host="zcrypto"` / `host="zcrypto-red"` (since iter-105), and, since spec `00069` D7 (rollout Step 2, verified live 2026-07-26: `infra/nas/config.alloy` sets `external_labels = { host = "nas" }`), `host="nas"`. For most of this topic's life the NAS was the one holdout: the `host` label its config set was on the *Loki logs* pipeline only, never on metrics — a gap found the hard way in spec `00054`, when an alert selecting `node_load1{host="ops"}` matched nothing — and it was deliberately left that way, because adding a label to an existing live series changes its identity in Prometheus, and the `Reconciler · residual gap increased` rule pages for **permanent data loss** off `increase()`/`resets()`. The owner took that series-identity risk knowingly at the spec-`00069` rollout window (a window where a false permanent-loss page was cheap to dismiss), re-keying the exactly two `{host=""}` selectors that depended on the NAS's absence-matcher (`node_load1{host=""}` in `NAS · load high`, `count(up{host=""})` in the Alloy-dark NAS rule) to `{host="nas"}` in the same change (`infra/grafana/alerts.yaml`) — verified 2026-07-26: zero `host=""` matchers remain anywhere in that file. The consequences, now settled:

- `node_load1{host="nas"}` selects the NAS; `node_load1{host="ops"}` selects ops — no host any longer resolves via an absent-label matcher.
- Both hosts' Alloy still bind the same `--server.http.listen-addr=127.0.0.1:12345`, so **`instance` still collides** — `host` is the fleet's only per-host discriminator, not `instance`.
- Benign, recorded 2026-07-19 (explicit drop, no action): every fleet Alloy logs a `remotecfg` "noop client" line at startup — the unused remote-config service's normal idle message, not an error; do not chase it.

- **(autonomous, small — fold into the dashboards package)** **A monotonic counter panel cannot distinguish old damage from new, and ours currently does not try.** "Permanent loss (residual)" renders `zcrypto_reconcile_residual_gap_seconds_total` with red at ≥ 1 s. That threshold is right — the metric is unhealable, unbackfillable, and can only grow, so any nonzero value should be visible — but the consequence is that the panel is **red forever after the first loss ever recorded**, and a reader cannot tell a seven-day-old incident from one that happened this morning without leaving the dashboard and reading the reconcile ledger by hand. That happened on 2026-07-20: the owner asked whether a red 44.4 min was alright, and answering it required tracing the ledger to a single `both_streams_silent` entry at `2026-07-13T07:00Z` to establish the counter had been flat for a week.
  Fix generally, not just for this panel: **for every monotonic damage counter, pair the cumulative value with a recent-delta view** — e.g. `increase(<counter>[24h])` beside it, thresholded so *that* panel is green at zero — so the dashboard answers "is this getting worse?" rather than only "has this ever happened?". The same shape applies to any counter whose green state is unreachable once tripped. Cheap, dashboard-only, and idempotent to push. Applies to `residual_gap_seconds_total` today and to `healed_gap_seconds_total` / `healable_gap_seconds_total` for the same reason (a chronically gappy primary is a rate story, not a total story — the point `zcrypto-reconcile-healable-gap-rate` already makes in the alert layer but the dashboard does not).

- **(autonomous, verify-first — from the 2026-08-02 grooming)** **Capture-daemon JSON log lines render unparsed — VERIFIED STILL TRUE 2026-08-04, and the suspected cause was wrong.** Observed 2026-07-26: the capture daemon's structured-JSON lines (spec `00068` logship) displayed as raw JSON while the panel command's classic-format lines rendered cleanly. The grooming note blamed [[T0109]]'s single-file bind mount (`config.alloy` never reaching the running Alloy until PRs #226/#227) as "the likeliest cause". **It is not the cause, and the fix is not a pipeline stage.** Traced statically end to end:
  - The capture daemon **does not ship through Alloy at all** — spec `00068` D3/D6 gave it `--ship-logs`, pushing straight to Loki. The capture host's `loki.process "parse"` carries exactly one stage, a `stage.logfmt` for *Alloy's own* output, and its in-file comment says so explicitly: the docker log path that once carried the daemon's lines "is gone (D6)".
  - What the daemon pushes is a **JSON body by construction** — `JsonLineFormatter` emits one object per record (`ts`, `level`, `logger`, `file`, `line`, `message`) — with labels `{host, container, level}` only (`build_payload`, one stream per level).
  - So the lines bypass the only component that could parse them, and **no Alloy config change can reach them**. Adding a JSON stage to the pipeline would be building against the wrong layer.
  - **The fix is therefore dashboard-side, and cheap**: parse at query time in the panel's LogQL (`| json` plus a `line_format` promoting `message`), or accept the raw body. Note `level` is already a **stream label**, so level filtering and colouring work today without any parsing — only the rendered body is affected.
  - Design decision this leaves open for the package: query-time `| json` in the panels (cheapest, no fleet change) versus reversing D3/D6 to route the daemon through Alloy (heavier, re-opens a decision made deliberately). Recommendation: query-time.
