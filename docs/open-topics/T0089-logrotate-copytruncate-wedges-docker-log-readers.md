# `logrotate copytruncate` on docker's json logs wedges the log readers

## Context — what

The `base` role used to install `/etc/logrotate.d/zcrypto-capture-docker`, a **daily, `copytruncate`** policy over `/var/lib/docker/containers/*/*-json.log` (rotate 90, compress, `olddir /var/log/zcrypto-capture`). *(That install task is now a `state: absent` tombstone in the same file — see Done so far. The hosts still carry the file until they converge or are purged.)* `copytruncate` copies the file and then truncates the original **in place, while dockerd holds it open** — the one thing docker's own rename-based rotation never does. The observed effect: after the truncation the container ships no logs anywhere, and `docker logs <container>` hangs outright.

**Leading hypothesis for the mechanism** (the fix is the same either way, so this was not chased further): the json-file reader keeps its byte offset across the truncation and blocks until the file regrows past it. That cleanly explains the *follow* stream Alloy uses. It does **not** by itself explain a fresh, non-following `docker logs --tail 2` hanging — a new reader should not inherit the old offset — so there is a second dockerd-side effect in play (a read lock, or the decoder retrying on the truncated file). Treat the offset-strand as the leading account, not a settled one.

Found 2026-07-21 during the [[T0083]] attended window, from the `Capture · log pipeline dead` alerts (both hosts) that had been re-notifying every ~4h since ~06:07 UTC.

## Why this matters

It silently blinds the log plane of every **long-lived** container on any host carrying the `base` role — which is the capture hosts and ops (`site.yml`), the engine being co-located on the primary. That is both capture daemons, the engine, **and on ops the Alloy container plus the liquidations poller** (both `restart: unless-stopped` under the same glob); only the `--rm` ops jobs escape, because each new container gets a fresh log file and a fresh reader. The affected hosts' ERROR-log rules are blind for the duration, which is exactly the "green because we stopped looking" class. It is **not** data loss in the archive: capture itself is unaffected (both dead-men pinging, segments written), and metrics/SD are unaffected because they come from different components.

**The wedge does not self-clear on any near horizon** *(corrected 2026-07-21 — see the retraction note below; an earlier revision of this topic claimed it self-clears, and a first correction over-swung to "structurally permanent". Both were wrong.)* The stranded offset is a **high-water mark** — the file size at the last rotation the reader passed healthy — and it does **not** advance while the reader is stuck: each rotation truncates the live file back to 0 and leaves the mark where it was. So the reader clears only on a cycle whose own volume exceeds that mark. Measured on the primary 2026-07-21, refined as the day ran: mark 1,345,071 B (one full day), live file accruing 51,752 B/h at 21:19 UTC ≈ 1.24 MB/day — a **7.7 % shortfall** (the first estimate, taken over a shorter window, read 13.6 %; the gap is narrower than first thought but still a gap). It will not clear tonight — 293,033 B still to go at 21:19, i.e. ~5.7 h, against 3.5 h until the 00:49 rotation — and will not clear on any day resembling today. A ~8 %-busier day *would* clear it: treat that as possible, not as a plan. At exactly constant volume the race is a dead heat, lost only by the bytes written between logrotate's copy and its truncate.

Two corollaries the arithmetic forces, both opposite to the intuition:

- **Volume growth is the clearing mechanism, not the cause.** A container whose daily volume keeps rising clears its own strand every cycle; the long-dark case is volume that *flattens or dips*, which is exactly today (13.6 % under yesterday). So this stayed invisible for weeks because capture's log volume was still multiplying — the "4 KB day self-heals in minutes" case is a *fast-multiplying* container, not merely a small one.
- **A quiet day does not help** (the mark is frozen, so a quiet day is strictly neutral), while a fully *empty* cycle would: `notifempty` skips rotation entirely, letting growth carry across two cycles. Irrelevant for capture, but it shows the outcome is contingent on this host's traffic rather than on the mechanism.

**Confidence: medium.** This rests on the offset-strand model, which the Context section flags as the leading but *unsettled* account — it does not explain the fresh-`docker logs` hang. If the wedge does prove permanent, that unexplained dockerd-side effect is the likelier reason, not this arithmetic.

The policy is also **redundant**: docker rotates these itself by *renaming*, the reader-safe mechanism `copytruncate` exists to avoid, and **every long-lived container already sets its own caps** — 50m/5 on capture and the engine, 10m/3 on both Alloys and the liquidations poller, with 50m/3 daemon-wide for anything else. No container depended on the logrotate policy for bounded disk, and none is left unrotated by removing it.

## Findings so far — measured 2026-07-21 on the primary

- Loki's **last** capture line on both hosts: `2026-07-21 00:06:34 UTC` — identical to the second, i.e. a common cause, not two host-local faults.
- `logrotate.service` last ran `2026-07-21 00:49:52 UTC` — **43 minutes after** that last shipped line, which looks contradictory until the daemon's bursty logging is accounted for: 00:06:34 was simply the last line written before a quiet stretch, and the live file's own first post-truncation entry is `00:59:44`. Nothing shipped after the rotation.
- The rotated copy for the live capture container (`836397b183a5`) is **1,345,071 bytes** in `/var/log/zcrypto-capture/`; the live json.log has regrown only to **924,593 bytes**. So the file is roughly 420 KB short of the copy's size — and the reader's stranded offset is *at least* that copy size (under `copytruncate` anything written between copy and truncate is lost outright and pushes the offset higher), so that figure is a lower-bound estimate, not a measured offset.
- `docker logs zcrypto-capture --tail 2` **hangs (exit 124) on both hosts** — a fresh client wedges too, so the block is dockerd-side per container, not an Alloy bug.
- Alloy is healthy and shipping: the four `Fleet · Alloy dark` rules ([[T0079]]) all read Normal, `Alloy · docker service-discovery wedged` is inactive, and SD refresh is a flat 60/h on every host — so this is **not** the [[T0048]] defect-1 class. The two rule families together discriminate it: metrics up + logs dark ⇒ reader wedge, not agent death.
- Ops's `--rm` workload containers escape (each new container gets a fresh log file and a fresh reader), but its **long-lived** ones do not: the Alloy container and the liquidations poller are both `restart: unless-stopped` under the same glob. The ops Alloy happens to be clean right now only because it was recreated 2026-07-21 20:21 UTC during the [[T0083]] work.
- **The full blast radius, enumerated by testing every running container 2026-07-21 21:19 UTC — six wedged, one clean:** primary `zcrypto` → `zcrypto-capture` (1,052,038 B), `zcrypto-engine` (35,186 B), `grafana-alloy` (7,822 B); secondary `zcrypto-red` → `zcrypto-capture` (582,458 B), `grafana-alloy` (7,305 B); ops → `zcrypto-ops-liquidations` (101,420 B). The one healthy long-lived container is the **ops Alloy**, recreated hours earlier — an accidental control confirming that a fresh container clears the wedge. Note the engine container is `zcrypto-engine`, **not** the `zcrypto-engine-shadow` its healthchecks entry is named after; an earlier survey guessing the latter missed it entirely.
- **Spec `00043` §Logs foresaw this exactly** — it prescribed removing this policy "in the same rollout", naming the risk in its own words ("`copytruncate` truncating json-file logs behind dockerd's back risks clipped/lost lines under an API log-follower") and assigning the `state: absent` deletion to the `obs` role. That role was never built (Alloy shipped via the capture/ops roles instead), so a correctly-designed mitigation was stranded with its owner and the predicted failure arrived ~10 months later. Worth remembering whenever a mitigation is parked on a component that does not exist yet.

## Done so far

**Repo fix landed 2026-07-21** (branch `fix/t0089-drop-copytruncate-policy`): the `base` role's install task is replaced by a `state: absent` tombstone removing `/etc/logrotate.d/zcrypto-capture-docker`, and the now-orphaned `/var/log/zcrypto-capture` directory task goes with it (the archives already written there stay — spec `00043`'s call). This stops the policy being re-created on every converge; it does **not** by itself touch the hosts.

**Remaining: get the file off the three hosts** — `zcrypto`, `red`, `hp` — by hand-purge or an attended `--tags base` converge. That removal is also the recovery mechanism (below), so it is not merely hygiene.

## Suggested next steps

- **(Repo fix, autonomous)** Remove the logrotate policy from the `base` role — as `state: absent`, not merely deleted from the repo, or the existing `/etc/logrotate.d/zcrypto-capture-docker` persists on every host forever. Docker's own rotation already covers this correctly and reader-safely (rename-based): `max-size=50m`/`max-file=5` per capture container, 50m/3 daemon-wide. **Note the consequence to decide with it**: once the policy is gone, `/var/log/zcrypto-capture/`'s archived copies stop being pruned (and stop being produced) — decide whether to trim what is there. If a longer retention is genuinely wanted, change docker's `log-opts`, and be aware that **neither** alternative is free on the primary: container `log-opts` take effect only on container *recreate*, and daemon-wide `/etc/docker/daemon.json` is templated with `notify: restart docker` whose handler restarts dockerd **unconditionally, with no capture guard** — that would recreate every container including live L2 capture, i.e. an unbackfillable gap. Prefer leaving rotation as-is. Never `copytruncate` a live docker log.
- **(Attended deploy)** The capture primary needs `-e converge_primary=true`. Removing a logrotate file does not itself restart anything, but that flag's blast radius does — scope the run with `--tags base` so the capture role never executes (the `always`-tagged assert still demands the flag), which is a materially smaller blast radius than a full primary converge.
- **(Recovery — its own decision; removing the policy does NOT clear the existing wedge)** Ranked:
  - **(a′) — the default now that the policy is going away: just remove the file, in time.** With no nightly truncation the live log grows monotonically, passes its high-water mark, and the stranded reader resumes — no restart, no capture risk, and it needs no image rollout. **Timing is the whole game**: measured on the primary 2026-07-21 21:19 UTC, the capture log sits 293,033 B under the mark and is accruing 51,752 B/h, so it clears ~5.7 h after the purge — but only if the purge beats that night's ~00:49 UTC rotation. Purge afterwards and the file is truncated back to zero first, whereupon a ~1.24 MB/day stream cannot reach a 1.35 MB mark before the following rotation. Confidence is medium (see above), which makes this a free experiment: logs returning on schedule confirms the offset-strand model; logs staying dark means the unexplained dockerd-side effect dominates and only recreation will do.
  - **(b) — the fallback: wait for the next capture-image rollout.** It recreates the container (`zcrypto-capture.service` runs `docker compose down`/`up`, and the digest lands via the templated compose with a restart handler), so a new container ID means a new log file and a fresh reader. No *additional* risk — the restart happens for its own reasons anyway — but it is on someone else's schedule: `capture-deploys.md`'s canary rule needs a ≥ 24 h secondary bake first, so "the next rollout" can be weeks out.
  - **(a) — only if the blindness must end sooner, and test on `zcrypto-red` FIRST.** Pad the live json.log past the mark with well-formed records as root. The secondary is wedged identically and is the designated canary, so testing there is free. Caveats, all real: it may not work at all (padding addresses only the offset half, and the fresh-`docker logs` hang says something else is also blocking); external appends are invisible to dockerd's own byte accounting for `max-size`, so the container's rotation threshold drifts; without `O_APPEND` semantics a concurrent write could interleave mid-record, trading a known-fixable state for a corrupt stream; and it injects ~7,600 synthetic records into the capture log stream and into Loki. "No capture risk" holds only for the L2 data plane.
  - **(c) — rejected: restart dockerd or the capture container.** Both recreate the live L2 stream to fix a *logging* problem — an unbackfillable gap for no data benefit.
  - **Verification, whichever is chosen:** the dark window's lines are **skipped, not replayed** — they survive only in the on-host json.log. And do not accept "the `Capture · log pipeline dead` rules went Normal" as proof after option (a): synthetic padding would satisfy those rules by itself, which is the very "green because we stopped looking" failure this topic opens by naming. The honest check is **a known real capture line, emitted after the padding, appearing in Loki**.
- **(Check with it)** Whether the other long-lived containers are wedged the same way — the engine on the primary, and on ops the Alloy container and the liquidations poller (both `restart: unless-stopped`, both under the same glob). The ops Alloy was recreated 2026-07-21 20:21 UTC, so its reader is currently fresh.

## Retraction note — this topic has been wrong twice; read the current text, not the history

Recorded here because the open-topics tree is the project's persistent working memory across compaction windows, and a future session reading this file alone would otherwise see no sign that two contrary claims were published and withdrawn within hours of each other.

- **First revision (2026-07-21, commit `a85f7d0`)** claimed the wedge "clears by itself once the live file passes the stranded offset", and built the recovery advice on that. Wrong: at this host's volumes it does not clear.
- **First correction (`116fca2`)** over-swung to "structurally permanent — the reader can never win", reasoning that each rotation "re-strands the reader a day further on". Also wrong, and wrong in the more dangerous direction: the offset is a **high-water mark that does not advance while the reader is stuck**, so the deficit never compounds. The pre-push review caught it by simulating successive cycles.
- **Current text** states the defensible middle: a marginal race, lost today by 13.6 %, decided by day-to-day volume variance rather than by structure, at medium confidence because the underlying mechanism is itself unsettled.

The lesson worth keeping: both errors came from reasoning about a mechanism instead of simulating it. The second was produced *while correcting the first*, which is exactly why a correction gets the same scrutiny as the claim it replaces.
