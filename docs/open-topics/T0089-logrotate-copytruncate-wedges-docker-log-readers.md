# `logrotate copytruncate` on docker's json logs wedges the log readers

## Context — what

The `base` role used to install `/etc/logrotate.d/zcrypto-capture-docker`, a **daily, `copytruncate`** policy over `/var/lib/docker/containers/*/*-json.log` (rotate 90, compress, `olddir /var/log/zcrypto-capture`). *(That install task is now a `state: absent` tombstone in the same file, and the file itself was purged from all three hosts on 2026-07-21 — see Done so far.)* `copytruncate` copies the file and then truncates the original **in place, while dockerd holds it open** — the one thing docker's own rename-based rotation never does. The observed effect: after the truncation the container ships no logs anywhere, and `docker logs <container>` hangs outright.

**The offset-strand hypothesis is FALSIFIED — measured 2026-07-21 21:27 UTC, see Findings.** The idea was that the json-file reader keeps its byte offset across the truncation and resumes once the file regrows past it. The secondary's own capture log refutes it: that file crossed its 525,068 B mark at ~15:54 UTC and is now 34 % beyond it, yet the container is still wedged and Loki has received nothing since 00:06:34 UTC. Whatever blocks dockerd here is **not** a byte offset waiting to be passed — consistent with the datum the hypothesis never explained, that a fresh, non-following `docker logs --tail 2` hangs too.

**What this means operationally**: removing the logrotate policy prevents *future* wedges, but nothing about growth clears an *existing* one. The only remedy demonstrated to work is **recreating the container** — evidenced by the ops Alloy, which is the sole healthy long-lived container precisely because it was recreated at 20:21 UTC. A `restart` may or may not suffice (untested; it keeps the same log file but rebuilds dockerd's logger), and for the capture containers that distinction is moot since any stop is an unbackfillable gap.

Found 2026-07-21 during the [[T0083]] attended window, from the `Capture · log pipeline dead` alerts (both hosts) that had been re-notifying every ~4h since ~06:07 UTC.

## Why this matters

It silently blinds the log plane of every **long-lived** container on any host carrying the `base` role — which is the capture hosts and ops (`site.yml`), the engine being co-located on the primary. That is both capture daemons, the engine, **and on ops the Alloy container plus the liquidations poller** (both `restart: unless-stopped` under the same glob); only the `--rm` ops jobs escape, because each new container gets a fresh log file and a fresh reader. The affected hosts' ERROR-log rules are blind for the duration, which is exactly the "green because we stopped looking" class. It is **not** data loss in the archive: capture itself is unaffected (both dead-men pinging, segments written), and metrics/SD are unaffected because they come from different components.

**An existing wedge does not clear on its own.** Two earlier revisions argued about *when* growth would clear it — "it self-heals", then "structurally permanent", then a marginal race — all inside a model the secondary has now falsified. Growth is not the variable.

**Confidence: high for the negative claim, across all six containers.** It rests on two independent legs, not on the secondary's arithmetic alone: that container crossed its mark and did not resume (above), and a **fresh, non-following `docker logs --tail 1` hangs on every one of the six** — which no byte-offset model can produce, since a new reader inherits no offset. What remains genuinely unknown is the positive mechanism (a dockerd read lock, a decoder stuck on the truncated file, something else); that gap is why the remedy below is stated as "recreation is the only *demonstrated* fix" rather than as a theory.

The policy is also **redundant**: docker rotates these itself by *renaming*, the reader-safe mechanism `copytruncate` exists to avoid, and **every long-lived container already sets its own caps** — 50m/5 on capture and the engine, 10m/3 on both Alloys and the liquidations poller, with 50m/3 daemon-wide for anything else. No container depended on the logrotate policy for bounded disk, and none is left unrotated by removing it.

## Findings so far — measured 2026-07-21 across the fleet

- Loki's **last** capture line on both hosts: `2026-07-21 00:06:34 UTC` — identical to the second, i.e. a common cause, not two host-local faults.
- `logrotate.service` last ran `2026-07-21 00:49:52 UTC` — **43 minutes after** that last shipped line, which looks contradictory until the daemon's bursty logging is accounted for: 00:06:34 was simply the last line written before a quiet stretch, and the live file's own first post-truncation entry is `00:59:44`. Nothing shipped after the rotation.
- The rotated copy for the live capture container (`836397b183a5`) is **1,345,071 bytes** in `/var/log/zcrypto-capture/`; the live json.log has regrown only to **924,593 bytes**. So the file is roughly 420 KB short of the copy's size — and the reader's stranded offset is *at least* that copy size (under `copytruncate` anything written between copy and truncate is lost outright and pushes the offset higher), so that figure is a lower-bound estimate, not a measured offset.
- `docker logs zcrypto-capture --tail 2` **hangs (exit 124) on both hosts** — a fresh client wedges too, so the block is dockerd-side per container, not an Alloy bug.
- Alloy is healthy and shipping: the four `Fleet · Alloy dark` rules ([[T0079]]) all read Normal, `Alloy · docker service-discovery wedged` is inactive, and SD refresh is a flat 60/h on every host — so this is **not** the [[T0048]] defect-1 class. The two rule families together discriminate it: metrics up + logs dark ⇒ reader wedge, not agent death.
- Ops's `--rm` workload containers escape (each new container gets a fresh log file and a fresh reader), but its **long-lived** ones do not: the Alloy container and the liquidations poller are both `restart: unless-stopped` under the same glob. The ops Alloy happens to be clean right now only because it was recreated 2026-07-21 20:21 UTC during the [[T0083]] work.
- **The full blast radius, enumerated by testing every running container 2026-07-21 21:19 UTC — six wedged, one clean:** primary `zcrypto` → `zcrypto-capture` (1,052,038 B), `zcrypto-engine` (35,186 B), `grafana-alloy` (7,822 B); secondary `zcrypto-red` → `zcrypto-capture` (582,458 B), `grafana-alloy` (7,305 B); ops → `zcrypto-ops-liquidations` (101,420 B). The one healthy long-lived container is the **ops Alloy**, recreated hours earlier — an accidental control confirming that a fresh container clears the wedge. Note the engine container is `zcrypto-engine`, **not** the `zcrypto-engine-shadow` its healthchecks entry is named after; an earlier survey guessing the latter missed it entirely.
- **The falsification, measured 2026-07-21 on `zcrypto-red`.** Its capture container has one rotated copy — **525,068 B, plain NDJSON** (verified by file magic, *not* gzipped, which was the escape that would have saved the model: a compressed copy would imply a 4–6 MB mark) — written at the 00:15 UTC rotation, and whose **first line is the container's own startup** (`2026-07-19 13:59:47 … starting capture`), so it is the *entire* pre-rotation file and the mark is exactly its size. The live json.log is **704,731 B — 179,663 B (34 %) beyond that mark** — and the container is **still wedged** (`docker logs` exit 124) with Loki's last line still `00:06:34 UTC`, 21 h earlier. A follower resumes within seconds of crossing its offset; this one crossed and did not.
  - *Two escapes, both closed.* **(i) Could the true mark exceed the copy?** Only by the bytes written between logrotate's copy and its truncate — 179,663 B of them, ≈5.4 h of this stream's output, inside a window of milliseconds. Dead by ~6 orders of magnitude. **(ii) Could an earlier, larger rotation have set the mark?** No: Loki carries lines up to `00:06:34`, i.e. the reader was demonstrably healthy right up to the 00:15 rotation, so the strand dates from *that* rotation and *that* copy.
  - *Deliberately not claimed:* a precise crossing time. This stream is bursty — 122,273 B landed in a single burst around 21:16, ~27× the hourly average — so back-extrapolating at a constant rate is invalid. What is solid: the file was **already past the mark at an earlier reading in the same session** (582,458 B) and is further past it now, with no resumption at any point.
- **Spec `00043` §Logs foresaw this exactly** — it prescribed removing this policy "in the same rollout", naming the risk in its own words ("`copytruncate` truncating json-file logs behind dockerd's back risks clipped/lost lines under an API log-follower") and assigning the `state: absent` deletion to the `obs` role. That role was never built (Alloy shipped via the capture/ops roles instead), so a correctly-designed mitigation was stranded with its owner and the predicted failure arrived ~10 months later. Worth remembering whenever a mitigation is parked on a component that does not exist yet.

## Done so far

**Repo fix landed 2026-07-21** (branch `fix/t0089-drop-copytruncate-policy`): the `base` role's install task is replaced by a `state: absent` tombstone removing `/etc/logrotate.d/zcrypto-capture-docker`, and the now-orphaned `/var/log/zcrypto-capture` directory task goes with it (the archives already written there stay — spec `00043`'s call). This stops the policy being re-created on every converge; it does **not** by itself touch the hosts.

**Policy purged from all three hosts 2026-07-21** (owner, by hand; verified — no other logrotate config matches docker's json logs). So no *new* wedge can form on any container. This is **prevention only**: measurement then showed it clears none of the six existing wedges.

## Retraction note — this topic has been corrected three times; read the current text, not the history

Recorded here because the open-topics tree is the project's persistent working memory across compaction windows, and a future session reading this file alone would otherwise see no sign that two contrary claims were published and withdrawn within hours of each other.

- **First revision (2026-07-21, commit `a85f7d0`)** claimed the wedge "clears by itself once the live file passes the stranded offset", and built the recovery advice on that. Wrong: at this host's volumes it does not clear.
- **First correction (`116fca2`)** over-swung to "structurally permanent — the reader can never win", reasoning that each rotation "re-strands the reader a day further on". Also wrong, and wrong in the more dangerous direction: the offset is a **high-water mark that does not advance while the reader is stuck**, so the deficit never compounds. The pre-push review caught it by simulating successive cycles.
- **Second correction (superseded within hours)** settled on a marginal race — "lost today by 13.6 %, decided by volume variance" — at medium confidence. That framing is gone too: it still assumed growth was the variable.
- **Current text** makes no timing claim at all. An existing wedge does not clear on its own; only recreation is demonstrated to fix one.

The lesson worth keeping: the first two errors came from reasoning about a mechanism instead of measuring it. The second was produced *while correcting the first*, which is exactly why a correction gets the same scrutiny as the claim it replaces.

**Third correction (2026-07-21 21:27 UTC, measured):** the two entries above argued about *when* growth clears a wedge. The secondary settled it — its capture log crossed its mark 5.4 h earlier, sits 34 % beyond it, and is still wedged with nothing in Loki since 00:06:34. The offset-strand model is falsified; growth is not the variable, and the purge is prevention rather than recovery. Unlike the first two, this correction came from a measurement rather than from reasoning about the mechanism — which is the whole lesson of the previous two.
