# 91. Kraken CLI paper trading — capability assessment against the shadow + tiny-live decision

**Question put (2026-09-05):** the master plan's Phase-6 design rests on *"Kraken has no spot testnet — shadow mode plus tiny-live replaces it"* (§12, Stage 6a). Kraken has since shipped an official CLI whose announcement advertises a paper-trading suite. If that suite is as capable as advertised, the substitution decision — and the design that hangs off it — would be worth reopening. This report measures the suite against what Phase 6 actually needs, and asks what use it has after go-live, with the engine armed and alpha research running beside it.

**Verdict: the substitution decision stands, and nothing in Phase 6 changes.** The CLI's spot paper engine cannot represent the deployable's positions at all — it is a long-only cash simulator with no margin and no shorts — and its cost model is cheaper than the best execution the real venue allows. It is not a testnet, does not claim to be one, and Kraken's own promotion gate refuses to accept paper evidence without a live pass. Two narrow post-go-live uses survive, plus one finding about this repo's own configuration that is worth acting on regardless of everything else here.

## 1. The measured basis

Every claim below was produced by reading the shipped source or running the shipped binary, on 2026-09-05. Nothing rests on the announcement post or on secondary reporting.

- **Binary:** `kraken 0.4.1`, installed at `~/.cargo/bin/kraken`, the same binary this repo's MCP server runs.
- **Source:** `github.com/krakenfx/kraken-cli`, MIT, © Payward, Inc., cloned at `v0.4.1` and read directly. The paper engine is `crates/kraken-paper/`; futures paper is `src/futures_paper.rs`; the promotion gate is `crates/kraken-workspace/src/promote.rs`.
- **Empirical probes:** an isolated throwaway paper workspace (`kraken workspace create zcprobe --capital 100000 --mode paper`), removed after the probes. The real account was never addressed; `kraken workspace list` showed only the `default` live workspace before and after.
- **Venue reference:** `kraken pairs -o json` for `BTC/USD` minimums, and this repo's own `docs/reference/kraken-fee-schedule.md` for the account-confirmed fee ladder.

A deep-research fan-out was launched for this question and **failed**: 75 of its 97 agents died on an API session limit and not one claim reached verification. Its raw claim list is not used here. That failure is recorded so nobody mistakes this report's evidence for having come from it.

## 2. What the announcement actually claimed

The post's whole technical statement of the paper suite is one sentence: the suite *"runs a local state engine that tracks simulated balances, executes limit/market orders against the live public ticker, and calculates unrealized P&L offline."*

Read carefully, that claim is **accurate and modest**, and the source confirms it line for line. It describes a local simulator priced off the public ticker. It does not claim depth, queueing, partial fills, margin, or venue-side matching, and it never uses the word testnet. The post also predates the research features — workspaces, sessions, the lab and replay arrived in `0.4.0` (2026-07-27) and go unmentioned in the announcement. So the premise "if it is as capable as the blog post stated" resolves against reopening the decision: what the post states is a good deal narrower than what a testnet substitute would need to be.

## 3. The disqualifying findings

### 3.1 There are no shorts, and therefore no deployable

`crates/kraken-paper/src/lib.rs` gates a sell on inventory held:

```rust
OrderSide::Sell => {
    let available = self.available_balance(&base);
    if available < volume {
        return Err(PaperError::Rejected(format!(
            "Insufficient {base} balance. Available: {available:.8}, Required: {volume:.8}"
        )));
    }
```

Confirmed empirically, with a control beside it so the refusal is not mistaken for an always-refusing stub:

| Probe | Result |
| -- | -- |
| `paper sell BTCUSD 0.01` holding zero BTC | rejected — `Insufficient BTC balance. Available: 0.00000000, Required: 0.01000000` |
| `paper buy BTCUSD 0.01` (control) | filled at 79664.1, cost 796.641, fee 2.0712666 |

`kraken paper buy` and `kraken paper sell` accept only `--type market|limit` and `--price`. The real order path (`kraken order buy`) carries `--leverage`, `--reduce-only`, `--oflags`, `--timeinforce`, `--trigger`, `--close-ordertype`, `--stptype` and `--validate`; the paper path carries none of them.

The deployable is a long/short spot-margin book whose short side the master plan costs explicitly, and whose short-BTC-only rule exists because alt shorts carry ~44–88%/yr. A simulator that mechanically refuses every short cannot run it, cannot shadow it, and cannot produce one number the go/no-go reads. This finding alone ends the substitution question for Stage 6b.

### 3.2 The cost model is cheaper than the venue's best case

Paper charges one flat rate on every fill, market and limit alike — `DEFAULT_FEE_RATE = 0.0026`, with no maker/taker distinction anywhere in the engine. Against this repo's account-confirmed ladder (Tier 1, 30-day volume $0.00, confirmed on the logged-in Kraken Pro fee tab):

| Cost, one round trip | Rate |
| -- | -- |
| CLI paper default (0.26% × 2) | 0.52% |
| Real, all-maker (0.40% × 2) | 0.80% |
| Real, all-taker (0.80% × 2) | 1.60% |

Paper's default sits **below the best round trip the venue allows**, by 28 bps against all-maker and 108 bps against all-taker. The ruled execution style is maker-first with a taker fallback, so the realized blend lands between those two — and paper is under the whole range, in every achievable style.

The rate is configurable via `--fee-rate`, so the level is fixable. The *shape* is not: a single scalar cannot express a maker/taker split, and that split is exactly what Phase 6 sends rung 1 to measure. The margin costs are not modelled at all, because margin does not exist here: the real book pays an opening fee of 0.01–0.04% plus the same rate **every 4 hours** a position is open, the standard spot fee on both the open and the close, and 3% at index on forced liquidation. A short held one week accrues 42 rollovers.

For scale: Stage 6b's superseded weekly band was 10 bps, and it was replaced for being 5–12× below the floor the venue minimums impose. The paper engine's default cost error on a single round trip is an order of magnitude above that band.

### 3.3 Fills ignore size, and ignore the venue's minimums

The market fill is `fill_price = ask * (1 + slippage_rate)` for a buy and `bid * (1 - slippage_rate)` for a sell. Order volume never enters the price. Slippage is a constant fraction, defaulting to zero, and quotes come from a single REST ticker snapshot — top of book only, no depth. Measured:

| Order | Fill price |
| -- | -- |
| 0.0001 BTC (≈ $8) | 79664.1 |
| 1.0 BTC (≈ $80,000) | 79664.1 |

A $8 order and an $80,000 order clear at the same price. Nor are venue constraints enforced: `BTC/USD` carries `ordermin` 0.00005 and `costmin` $0.50, and paper filled an order of 0.00000001 BTC — one satoshi, a five-thousandth of the minimum, costing $0.0008.

That last gap is precisely inverted from the problem Stage 6b was rebuilt around. The 6b rungs exist because **0 of 801 intended orders cleared `ordermin` at €500 quarter-size** — the binding constraint on this book is the venue's minimums, and this simulator is blind to them. It would have reported a clean fill on all 801 and told us nothing. This project already models what the simulator ignores, in `cli/engine/instruments.py`: the `ordermin` check runs on the *floored* quantity, with `lot_step` and `tick_size` quantization and a committed `COSTMIN`, guarded by `tests/test_costmin_drift.py`.

### 3.4 Limit fills are optimistic

A resting order fills when `ask <= price` (buy) or `bid >= price` (sell), for its **full volume, at its limit price**, charged the same flat rate. There is no queue position, no partial fill, and no maker rate. A real limit order at the touch frequently does not fill when the market trades there, because size ahead of it in the queue does. Here it always fills.

## 4. Kraken's own position agrees with ours

The strongest corroboration is the vendor's, in `crates/kraken-workspace/src/promote.rs`. Its gate requires a frozen experiment, at least two passing sessions, and — decisively — at least one pass whose source is the **live** market:

```
"no experiment pairs 2 passes with a live pass — replay alone never promotes"
```

The shipped skill states the reasoning plainly: *"replay screens and live confirms; two replay passes must never promote on their own."* The vendor's own gap list names flat fees, taker rates charged on maker fills, flat slippage, and no partial fills or latency.

And the gate cannot pass at all today. One criterion is hardcoded unsatisfiable, with an unconditional blocker beside it:

```rust
criterion: "live credentials scoped to this workspace",
satisfied: false,
...
blockers: vec!["live execution needs scoped credentials; until then promotion is
                evaluated but never performed"]
```

`workspace create --mode` says the same in its help text: *"named live workspaces are not yet available."* The changelog calls the project *"still alpha software."*

So Kraken ships a paper suite that refuses to promote on paper evidence, cannot perform a promotion at all, and describes itself as alpha. The design decision this report was asked to re-examine — that simulation screens and live capital confirms — is the same one the vendor encoded in its own gate.

## 5. Futures paper: the only shorting path, and why it is not ours

`kraken futures paper` is a materially better engine than spot paper: it has `sell` as a genuine short, positions, leverage to 200×, maintenance margin at 2%, liquidation, funding accrual on an 8-hour interval, IOC partial fills, and post-only, stop, take-profit, trailing-stop and FOK order types.

It is nonetheless the wrong instrument, and not by a technicality:

- **Different carry.** Futures funding accrues every 8 hours at a market-determined rate; spot-margin rollover is charged every 4 hours at Kraken's published per-currency rate. Neither substitutes for the other in a cost model whose honesty the plan calls load-bearing.
- **Different tax.** German treatment splits these — §20 *Termingeschäft* at 26.375% versus §23 on delivery — and §11's go/no-go economics must hold under the worse scenario. The T2 tax-probe set is specified as margin long plus margin short across rollovers, which futures cannot supply.
- **Different fee schedule, and different instruments** from the EUR spot-margin pairs the book actually trades.
- **Lower precision:** the futures engine computes in `f64` where the spot engine uses `Decimal`.

Substituting futures paper for spot-margin research would replace a missing simulation with a *misleading* one, which is worse than having none.

## 6. What is worth taking

Three things survive, all narrow, none affecting the plan.

**An independent read of live account state.** After go-live the engine reconciles the account through its own Nautilus client. The CLI reaches the same account by a completely separate code path in a different language — `kraken balance`, `positions`, `trades-history`, `ledgers`, `open-orders`, all read-only. Two producers measuring the same thing independently are the check on each other, and a single client cannot report that it is misreading. This is a genuine reconciliation cross-check, and it is the most valuable thing in the CLI for this project. It needs no paper trading at all.

**The mode-tagged audit stream.** Release 0.4.1 makes the MCP server tag every call with the trading mode, re-resolved per call, and log allowlisted financial arguments while keeping credentials out. That is a good pattern for our own agent-facing surfaces.

**The pre-registration pattern, as corroboration only.** The lab hash-seals a hypothesis and its success criteria before any run, re-scores from disk against the session's own recorded track so a session folds to the same numbers forever, and treats a post-freeze edit as damage. This project already has a stronger version — the trial registry, `spec_hash` pins, the holdout ledger with its spent budget, CPCV and deflated Sharpe. The lab is worth knowing about as independent convergence on our discipline, not as something to adopt.

What is **not** worth taking is the paper engine as an evidence source, in any rung, for any gate.

## 7. Post-go-live: the risk it adds exceeds the risk it removes

The question was what use this has once the engine is armed and research runs continuously beside it. The honest answer is that the paper engine removes no risk we currently carry — every gap it could rehearse is one it models more optimistically than reality — while introducing a second order-placement path onto a host that holds the live trade key.

That points at a finding about **this repository's own configuration**, which stands on its own merits regardless of the rest of this report. The MCP server here is registered as:

```
kraken mcp -s all
```

The CLI's default service set is read-only: `market,account,paper,workspace,feedback`. `-s all` additionally exposes **trade, funding, futures, earn, subaccount and auth** — order placement, withdrawals and transfers — and `kraken workspace list` confirms the addressed account is `default`, mode `live`. Guarded mode still applies, so dangerous tools require `acknowledged: true`, but that is an argument the *calling model* supplies rather than a human confirmation; the human gate is the harness permission prompt, not the CLI. `--allow-dangerous` is not set, which is correct and should stay that way.

For a research session that needs market data and read-only account state, the default service set is sufficient and the live-trade surface is unnecessary. Narrowing the registration is a one-line change to the MCP config. This becomes materially more pressing once the engine is armed, since the account being addressed will then hold real positions.

## 8. Recommendation

**Do not change the game plan.** Stage 6a shadow mode and the three 6b rungs remain the evidence path, for the reason they were chosen: Kraken offers no venue-side simulation of spot-margin, and the CLI does not supply one. The four gaps that matter — shorts, the maker/taker cost split, the venue minimums that bind this book, and queue-realistic fills — are exactly the four the simulator lacks, and the plan's rungs exist to measure precisely those.

Bounded adoptions, none of which touch the gates:

1. **Narrow the MCP registration** to the default read-only service set for research sessions. Independent of everything else in this report.
2. **Consider the CLI as a second reader for post-go-live reconciliation** — an independent path to balances, positions and ledgers that does not share code with the engine's client. Worth a design pass when the live book exists; worth nothing before then.
3. **Leave the lab, workspaces and futures paper alone.** They solve problems this project solved better, or model an instrument it does not trade.

## 9. What would change this answer

This verdict is a function of measurable properties of a shipped binary, so it has explicit triggers rather than an expiry date. It should be re-read if **any** of these become true:

- `kraken paper` gains margin or short support — checkable as a `--leverage` or `--reduce-only` flag on `kraken paper sell --help`, or by the disappearance of the `available_balance(&base) < volume` refusal in `crates/kraken-paper/src/lib.rs`.
- The paper fill model becomes depth-aware — checkable by whether `volume` enters the `fill_price` expression in the same file, or empirically by whether a 0.0001 BTC and a 1.0 BTC market order still return an identical fill price.
- `ordermin` / `costmin` enforcement appears in the paper path — checkable by whether a one-satoshi `paper buy` is still accepted.
- Kraken ships a venue-side spot sandbox, which would moot this entire report and is the only development that would genuinely reopen §12's substitution decision.

The first three are all one command each against a newer binary. None of them is presently true at `0.4.1`.
