# 91. The Kraken CLI — its paper trading measured against the shadow + tiny-live decision, and where the CLI earns its place in R&D

**Questions put (2026-09-05).** Two, and this report answers both. **(1) How and when should the CLI enter our R&D**, given the owner's ruling that `kraken-cli` stays **workstation-only and is never deployed into the production landscape**, the engine node least of all? **(2) Does its paper trading help that R&D**, especially the next alpha search? Question 2 is the one with a founding decision behind it: the master plan's Phase-6 design rests on *"Kraken has no spot testnet — shadow mode plus tiny-live replaces it"* (§12, Stage 6a), and Kraken has since shipped an official CLI whose announcement advertises a paper-trading suite. If that suite were as capable as advertised, the substitution — and the design hanging off it — would be worth reopening.

**Verdict on (2): the substitution decision stands, and nothing in Phase 6 changes.** The CLI's spot paper engine cannot represent the deployable's positions at all — it is a long-only cash simulator with no margin and no shorts — and its cost model is cheaper than the best execution the real venue allows. It is not a testnet, does not claim to be one, and Kraken's own promotion gate refuses to accept paper evidence without a live pass. **Verdict on (1): the CLI earns a place in R&D, but nowhere near the paper engine.** Its value is as a **second, independent producer of account facts** — a different implementation reaching the same venue, which is the one thing our own client cannot be. That buys an automated fee-tier read today and a reconciliation cross-check at go-live, both workstation-side and read-only, both compatible with the never-deployed ruling because the calls are remote anyway. §6 states where it earns its place, §8 the non-goals.

## 1. The measured basis

Every claim below was produced by reading the shipped source or running the shipped binary, on 2026-09-05. No finding rests on the announcement post or on secondary reporting; §2 reads the post only to settle what it actually claimed.

- **Binary:** `kraken 0.4.1`, installed at `~/.cargo/bin/kraken`. The same binary backs the `kraken` MCP server registered in the owner's user-scope Claude Code config, which §7 takes up.
- **Source:** `github.com/krakenfx/kraken-cli`, MIT, © Payward, Inc., cloned at `v0.4.1` and read directly. The paper engine is `crates/kraken-paper/`; futures paper is `src/futures_paper.rs`; the promotion gate is `crates/kraken-workspace/src/promote.rs`.
- **Empirical probes:** an isolated throwaway paper workspace (`kraken workspace create zcprobe --capital 100000 --mode paper`), removed after the probes. The real account was never addressed; `kraken workspace list` showed only the `default` live workspace before and after.
- **Venue reference:** `kraken pairs -o json` for `BTC/USD` minimums, and this repo's own `docs/reference/kraken-fee-schedule.md` for the account-confirmed fee ladder.

A deep-research fan-out was launched for this question and **failed**: 75 of its 97 agents died on an API session limit and not one claim reached verification. Its raw claim list is not used here. That failure is recorded so nobody mistakes this report's evidence for having come from it.

## 2. What the announcement actually claimed

The post's whole technical statement of the paper suite is one sentence: the suite *"runs a local state engine that tracks simulated balances, executes limit/market orders against the live public ticker, and calculates unrealized P&L offline."* (`blog.kraken.com/news/industry-news/announcing-the-kraken-cli`, read 2026-09-05.)

Read carefully, that claim is **accurate and modest**, and the source confirms it line for line. It describes a local simulator priced off the public ticker. It does not claim depth, queueing, partial fills, margin, or venue-side matching, and it never uses the word testnet. The post also predates the research features — workspaces, sessions, the lab and replay arrived in `0.4.0` (2026-07-27) and go unmentioned in the announcement. So the premise "if it is as capable as the blog post stated" resolves against reopening the decision: what the post states is a good deal narrower than what a testnet substitute would need to be.

## 3. The disqualifying findings

### 3.1 There are no shorts, and therefore no deployable

`crates/kraken-paper/src/lib.rs` gates a sell on inventory held:

```rust
OrderSide::Sell => {
    let available = self.available_balance(&base);
    if available < volume {
        return Err(PaperError::Rejected(format!(
            "Insufficient {base} balance. Available: {available:.8}, Required: {volume:.8}"
        )));
    }
```

Confirmed empirically, with a control beside it so the refusal is not mistaken for an always-refusing stub:

| Probe | Result |
| -- | -- |
| `paper sell BTCUSD 0.01` holding zero BTC | rejected — `Insufficient BTC balance. Available: 0.00000000, Required: 0.01000000` |
| `paper buy BTCUSD 0.01` (control) | filled at 79664.1, cost 796.641, fee 2.0712666 |

`kraken paper buy` and `kraken paper sell` carry no order-semantics flags beyond `--type market|limit` and `--price`. The real order path (`kraken order buy`) carries `--leverage`, `--reduce-only`, `--oflags`, `--timeinforce`, `--trigger`, `--close-ordertype`, `--stptype` and `--validate`; the paper path carries none of them.

The deployable is a long/short spot-margin book whose short side the master plan costs explicitly. What the plan ratifies is a **core-tier** short permission — §10's risk model allows ≤10% NAV short, core tier only — alongside §4's conclusion that hedging is cheapest via short BTC; the short-BTC-only *thesis* is a conclusion the ~44–88%/yr alt-short carry reinforces, not a ratified rule. The distinction does not soften this finding, because paper refuses **every** short, core tier included. A simulator that does so cannot run the book, cannot shadow it, and cannot produce one number the go/no-go reads. This finding alone ends the substitution question for Stage 6b.

### 3.2 The cost model is cheaper than the venue's best case

Paper charges one flat rate on every fill, market and limit alike — `DEFAULT_FEE_RATE = 0.0026`, with no maker/taker distinction anywhere in the engine. Against this repo's account-confirmed ladder (Tier 1, 30-day volume $0.00, confirmed on the logged-in Kraken Pro fee tab):

| Cost, one round trip | Rate |
| -- | -- |
| CLI paper default (0.26% × 2) | 0.52% |
| Real, all-maker (0.40% × 2) | 0.80% |
| Real, all-taker (0.80% × 2) | 1.60% |

Those venue rates were confirmed live against the account, not merely read from the repo: `kraken volume --pair BTCUSD -o json` returns taker `0.8000` and maker `0.4000` under the key `XXBTZUSD`, with `domain_spot_volume_30d` 46.71198 and the next tier at `0.6000`/`0.3000` from 2500 — measured 2026-09-05 and reproduced independently by a second session. The repo's ladder and the venue agree, which is what makes the comparison below safe to lean on.

Paper's default sits **below the best round trip the venue allows**, by 28 bps against all-maker and 108 bps against all-taker. The ruled execution style is maker-first with a taker fallback, so the realized blend lands between those two — and paper is under the whole range, in every achievable style.

The rate is configurable via `--fee-rate`, so the level is fixable. The *shape* is not: a single scalar cannot express a maker/taker split, and that split is exactly what Phase 6 sends rung 1 to measure. The margin costs are not modelled at all, because margin does not exist here: the real book pays an opening fee of 0.01–0.04% plus the same rate **every 4 hours** a position is open, the standard spot fee on both the open and the close, and 3% at index on forced liquidation. A short held one week accrues 42 rollovers.

For scale: Stage 6b's superseded weekly band was 10 bps, and it was replaced for being 5–12× below the floor the venue minimums impose. The paper engine's default cost error on a single round trip is 2.8× that band at the all-maker end and 10.8× at the all-taker end.

### 3.3 Fills ignore size, and ignore the venue's minimums

The market fill is `fill_price = ask * (1 + slippage_rate)` for a buy and `bid * (1 - slippage_rate)` for a sell. Order volume never enters the price. Slippage is a constant fraction, defaulting to zero, and quotes come from a single REST ticker snapshot — top of book only, no depth. Measured:

| Order | Fill price |
| -- | -- |
| 0.0001 BTC (≈ $8) | 79664.1 |
| 1.0 BTC (≈ $80,000) | 79664.1 |

A $8 order and an $80,000 order clear at the same price. Nor are venue constraints enforced: `BTC/USD` carries `ordermin` 0.00005 and `costmin` $0.50, and paper filled an order of 0.00000001 BTC — one satoshi, a five-thousandth of the minimum, costing $0.0008.

That last gap is precisely inverted from the problem Stage 6b was rebuilt around. The 6b rungs exist because **0 of 801 intended orders cleared `ordermin` at €500 quarter-size** — the binding constraint on this book is the venue's minimums, and this simulator is blind to them. It would have reported a clean fill on all 801 and told us nothing. This project already models what the simulator ignores, in `cli/engine/instruments.py`: the `ordermin` check runs on the *floored* quantity, with `lot_step` and `tick_size` quantization and a committed `COSTMIN`, guarded by `tests/test_costmin_drift.py`.

### 3.4 Limit fills are optimistic

A resting order fills when `ask <= price` (buy) or `bid >= price` (sell), for its **full volume, at its limit price**, charged the same flat rate. There is no queue position, no partial fill, and no maker rate. A real limit order at the touch frequently does not fill when the market trades there, because size ahead of it in the queue does. Here it always fills.

## 4. Kraken's own position agrees with ours

The strongest corroboration is the vendor's, in `crates/kraken-workspace/src/promote.rs`. Its gate requires a frozen experiment, at least two passing sessions, and — decisively — at least one pass whose source is the **live** market:

```
"no experiment pairs 2 passes with a live pass — replay alone never promotes"
```

The shipped skill states the reasoning plainly: *"replay screens and live confirms; two replay passes must never promote on their own."* The vendor's own gap list names flat fees, taker rates charged on maker fills, flat slippage, and no partial fills or latency.

And the gate cannot pass at all today. One criterion is hardcoded unsatisfiable, with an unconditional blocker beside it:

```rust
criterion: "live credentials scoped to this workspace",
satisfied: false,
...
blockers: vec!["live execution needs scoped credentials; until then promotion is
                evaluated but never performed"]
```

`workspace create --mode` says the same in its help text: *"named live workspaces are not yet available."* The changelog calls the project *"still alpha software."*

So Kraken ships a paper suite that refuses to promote on paper evidence, cannot perform a promotion at all, and describes itself as alpha. The design decision this report was asked to re-examine — that simulation screens and live capital confirms — is the same one the vendor encoded in its own gate.

## 5. Futures paper: the only shorting path, and why it is not ours

`kraken futures paper` is a materially better engine than spot paper: it has `sell` as a genuine short, positions, leverage to 200×, maintenance margin at 2%, liquidation, funding accrual on an 8-hour interval, IOC partial fills, and post-only, stop, take-profit, trailing-stop and FOK order types.

It is nonetheless the wrong instrument, and not by a technicality:

- **Different carry.** Futures funding accrues every 8 hours at a market-determined rate; spot-margin rollover is charged every 4 hours at Kraken's published per-currency rate. Neither substitutes for the other in a cost model whose honesty the plan calls load-bearing.
- **Different tax.** German treatment splits these — §20 *Termingeschäft* at 26.375% versus §23 on delivery — and §11's go/no-go economics must hold under the worse scenario. The T2 tax-probe set is specified as margin long plus margin short across rollovers, which futures cannot supply.
- **Different fee schedule, and different instruments** from the EUR spot-margin pairs the book actually trades.
- **Lower precision:** the futures engine computes in `f64` where the spot engine uses `Decimal`.

Substituting futures paper for spot-margin research would replace a missing simulation with a *misleading* one, which is worse than having none.

## 6. Where the CLI earns its place — the answer to question 1

Everything below is **workstation-side and read-only**, which is what makes it compatible with the never-deployed ruling: these are calls to a remote API, so co-location with the engine would buy nothing even if it were permitted. The through-line is that the CLI is a **second producer** — a separate implementation reaching the same venue — and a lone producer structurally cannot report that it is under-reporting.

**The fee tier, read from the account, is the strongest case and it retires an attended step.** `kraken volume --pair <PAIR> -o json` returns the account's live taker and maker rate, its 30-day volume and the next tier's threshold. `docs/reference/kraken-fee-schedule.md` had told its readers that its numbers come from the logged-in Kraken Pro fee tab and so *nothing automated can refresh them*, which made the re-read the attended half of the monthly `zcrypto-refdata-sweep`. That is false for the half that matters: the sweep asks the owner for the tier and the 30-day volume, and both are in this one payload. The endpoint still cannot rebuild the full 17-tier ladder or speak to AoP qualification, so the attended half narrows rather than disappearing. It is also the better source than the register's public `AssetPairs` fee columns, which served the pre-2026-07-09 ladder for weeks after it was superseded. One caution for whoever automates it: the response keys its blocks by the venue's own altname, so `BTCUSD` returns under `XXBTZUSD`, and among the EUR spellings `XXBTZEUR`, `BTC/EUR` and `XBTEUR` all resolve while `XBT/EUR` answers `EQuery:Unknown asset pair` — read the key the payload returns, never the one you asked for.

**An independent read of live account state, at go-live.** The engine reconciles the account through its own Nautilus client. The CLI reaches the same account by a separate code path in a different language — `kraken balance`, `positions`, `trades-history`, `ledgers`, `open-orders`, all read-only. Disagreement between the two is the finding. This runs from the workstation against the API, never from the engine node, and needs no paper trading at all.

**Microstructure cross-checks, at the next alpha search.** `orderbook-l3` is an authenticated per-order book — strictly richer than L2, and the only thing in the toolbox that speaks to queue realism, which §3.4 names as a gap in every simulator available to us. With `spreads` and `trades` it spot-checks `docs/reference/captured-spread-calibration.md`. A cross-check only: 24/7 capture is production, and the ruling excludes it.

**The mode-tagged audit stream.** Release 0.4.1 makes the MCP server tag every call with the trading mode, re-resolved per call, and log allowlisted financial arguments while keeping credentials out. That is a good pattern for our own agent-facing surfaces.

**The pre-registration pattern, as corroboration only.** The lab hash-seals a hypothesis and its success criteria before any run, re-scores from disk against the session's own recorded track so a session folds to the same numbers forever, and treats a post-freeze edit as damage. This project already has a stronger version — the trial registry, `spec_hash` pins, the holdout ledger with its spent budget, CPCV and deflated Sharpe. The lab is worth knowing about as independent convergence on our discipline, not as something to adopt.

What is **not** worth taking is the paper engine as an evidence source, in any rung, for any gate.

## 7. Post-go-live: the risk it adds exceeds the risk it removes

The question was what use this has once the engine is armed and research runs continuously beside it. The paper engine removes no risk we currently carry — every gap it could rehearse is one it models more optimistically than reality — while adding a second order-placement path on a host holding the live trade key. That points at how the CLI is reached, which is a separate decision from what it simulates.

### 7.1 The exposed surface

**This is not the repository's configuration.** The `kraken` MCP server is registered at the **top level** of `~/.claude.json` as `args: ["mcp", "-s", "all"]` — user-scope Claude Code config, live in every project on the machine. This repo's project entry carries `mcpServers: {}` and the tree holds no `.mcp.json`, so the reach is wider than a repo setting and the remedy is not committable here.

The CLI's default service set is read-only (`market,account,paper,workspace,feedback`); `-s all` adds the **trade, funding, futures, earn, subaccount and auth** groups, against an account `kraken workspace list` confirms is `default`, mode `live`. Guarded mode requires `acknowledged: true` on the 41 tools of 174 flagged dangerous, but that argument is supplied by the *calling model*; the human gate is the harness permission prompt. `--allow-dangerous` is unset and should stay so.

**This states exposed surface, not proven reach.** Whether those tools could execute depends on the grants of the credential in `~/.config/kraken/config.toml`, which this report did not read. `docs/reference/kraken-fee-schedule.md` records a **read-only** key created and verified for this account; if that is the configured one, the trade and funding tools fail at the venue and the finding is defence in depth. Settling it means exercising a trade-scoped endpoint against a live account, which this report declined to do.

### 7.2 Remove the server rather than narrow it

The MCP adds no capability, by the vendor's own design statement in `src/mcp/server.rs`: *"Tool calls are rewritten to argv and re-enter the CLI's own clap parse + dispatch path, so tool and CLI behaviour cannot drift."* There is no second implementation to gain anything from.

It is in fact a strictly **smaller** surface. `src/mcp/registry.rs`'s `CLAP_ONLY` constant names the commands deliberately absent from the tool catalog — `record`, `replay`, `streamd start`, `session start`, `playground`, `ws ping`, `mcp` — the recording, replay and session primitives plus the streaming daemon, reachable from the CLI and unreachable through the MCP.

The shell wins on every axis that matters. `-o json` yields the same structured output, and produced every measurement here. Invocations pass the harness permission system, which a human configures and which allowlists read-only commands by prefix. An unregistered tool costs no context; a registered one carries its name into every session.

Removal gives up the mode-tagged audit stream added in 0.4.1, though the harness already records shell invocations, and the server's single-writer lock over concurrent tool calls, which guards the account journal and matters only for paper and session writes this project does not perform.

## 8. Recommendation

**Do not change the game plan.** Stage 6a shadow mode and the three 6b rungs remain the evidence path, for the reason they were chosen: Kraken offers no venue-side simulation of spot-margin, and the CLI does not supply one. The four gaps that matter — shorts, the maker/taker cost split, the venue minimums that bind this book, and queue-realistic fills — are exactly the four the simulator lacks, and the plan's rungs exist to measure precisely those.

Bounded adoptions, none of which touch the gates:

1. **Remove the `kraken` MCP server and call the CLI through the shell** (\[[T0170]\]), for §7's reasons: it adds no capability, exposes strictly less than the CLI, gates its dangerous tools on a flag the model sets on itself, and carries every tool name into every session's context. `-o json` gives the same structured output. The registration is the owner's user-scope `~/.claude.json`, so **the edit is the owner's and is not committable here**; it is the one action this report leaves pending, tracked in \[[T0170]\]. No code or configuration in this repository depends on it: `git grep mcp__kraken__` returns only this report and the changelog entry that tells agents not to use the tool, which is an instruction rather than a dependency, and the tree holds no `.mcp.json`. So removal costs no in-tree change.
2. **The refdata sweep reads the fee tier itself.** `zcrypto-refdata-sweep` step 7 runs authenticated `kraken volume`; the attended half narrows to the full ladder's shape and AoP qualification, and `kraken-fee-schedule.md` no longer claims nothing automated can refresh those numbers. Landed with this report.
3. **The boundary lands where deploys are read.** `fleet-deploys.md`'s invariants now say `kraken-cli` is workstation-only and never installed or invoked on a fleet host, so no role, compose file, image or unit may install it. A ruling recorded only in a report is invisible at execution time; this one is not. Landed with this report.
4. **The reconciliation second reader** — an independent path to balances, positions and ledgers that shares no code with the engine's client. Worth a design pass when the live book exists; worth nothing before then, which is why it is registered rather than scheduled.
5. **Leave the lab, workspaces and futures paper alone.** They solve problems this project solved better, or model an instrument it does not trade.

**The non-goals, stated so a later session does not rediscover them as ideas.** Never a data source of record — canonical datasets carry hash-pinned provenance the CLI bypasses, so a CLI fetch is a cross-check and never the record. Never on the capture path, the engine node or the live trade path. Never paper trading as evidence in any rung or gate. Never a substitute for the trial registry, its `spec_hash` pins or the holdout ledger. And never an unattended path that can place an order: the read-only prefixes belong in the harness allowlist, while `kraken order`, `kraken withdraw`, `kraken wallet-transfer` and `kraken subaccount` stay behind the per-call prompt.

## 9. What would change this answer

This verdict is a function of measurable properties of a shipped binary, so it has explicit triggers rather than an expiry date. It should be re-read if **any** of these become true:

- `kraken paper` gains margin or short support — checkable as a `--leverage` or `--reduce-only` flag on `kraken paper sell --help`, or by the disappearance of the `available_balance(&base) < volume` refusal in `crates/kraken-paper/src/lib.rs`.
- The paper fill model becomes depth-aware — checkable by whether `volume` enters the `fill_price` expression in the same file, or empirically by whether a 0.0001 BTC and a 1.0 BTC market order still return an identical fill price.
- `ordermin` / `costmin` enforcement appears in the paper path — checkable by whether a one-satoshi `paper buy` is still accepted.
- Kraken ships a venue-side spot sandbox, which would moot this entire report and is the only development that would genuinely reopen §12's substitution decision.

The first three are all one command each against a newer binary. None of them is presently true at `0.4.1`.

These triggers, the pending removal in §8.1 and the deferred design pass in §8.2 are registered in \[[T0170]\] and carried in the memo queue. This report states them; it does not track them — a deferral whose only home is prose is not tracked at all.
