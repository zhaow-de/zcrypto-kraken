# Stage 6a — Shadow: close-out and exit-bar report

**Date:** 2026-07-30 · **Stage:** Phase 6, Stage 6a (Shadow) · **Verdict: PASS — Stage 6a is closed.**

Phases 0–5 each closed with a committed report; Stage 6a had none, and the fact that its criterion was met survived only as a subordinate clause inside a changelog entry about a metrics rollout. This is that report.

## The exit bar, derived

§12 states an `Exit bar:` for every phase 0–5 and **none for Phase 6**, so Stage 6a had no plan-level definition of "closed". Rather than amend the master plan — it has never been amended at a phase close; all six of its commits are research ratifications — the bar is **derived here from §12's own Stage-6a scope**, quoted verbatim:

> **Stage 6a — Shadow (2–3 weeks):** engine runs live data, computes targets, *logs intended orders only*; concordance check sim-vs-intended (signal parity backtest↔live is a hard gate). Kraken has no spot testnet — shadow mode plus tiny-live replaces it.

Four clauses, each a testable condition:

| # | Clause | Exit condition |
| -- | -- | -- |
| 1 | *engine runs live data* | the engine is deployed and cycling on live market data on its 4-hourly schedule |
| 2 | *computes targets* | each cycle produces journaled targets |
| 3 | *logs intended orders only* | **zero real orders** — intended orders written to the journal and nothing placed |
| 4 | *concordance check sim-vs-intended … **a hard gate*** | signal parity backtest↔live holds, with **zero** mismatches |
| — | *(2–3 weeks)* | sustained for the shadow duration, operationalized by spec `00039` as **≥14 consecutive clean complete UTC days** |

Clause 4 is the load-bearing one — §12 calls it a hard gate, and it is the only clause whose failure invalidates the stage rather than merely delaying it. Clause 5 is where spec `00039`'s 14-day bar comes from: it is not an independent criterion but the operationalization of "2–3 weeks" plus "hard gate", and it is **the operative bar for this stage**. Recorded explicitly so a later reader does not have to re-derive it, and so `00039`'s bar is not mistaken for a go-*live* criterion applied out of place.

## Verdict against each clause

**Measured 2026-07-30 from the live gate export, never extrapolated.**

| Clause | Evidence | Result |
| -- | -- | -- |
| 1 · live data | engine deployed on `zcrypto` (the only 24/7 host, per the §12 kickoff), cycling 4-hourly at 00/04/08/12/16/20 UTC | ✅ |
| 2 · computes targets | per-cycle `cycle-HH.json` written last, after validation, with `orders.jsonl` and `snapshots/` beside it | ✅ |
| 3 · intended orders only | **A strategy-layer guarantee — see the correction below.** The deployed node registers `KrakenLiveExecClientFactory` and builds a live authenticated `KrakenExecClientConfig` (MARGIN, ZEUR) whenever `exec_enabled` is true, and the deployed `zcrypto.toml` sets it **true** — so the execution transport was live and connected throughout 6a. What makes the stage shadow is that **nothing ever commands it**: no order-origination call site exists anywhere in `cli/`; `ShadowStrategy` only drives the cycle, and `cycle.py` computes intended orders as `delta = target − previous target`, notional against `shadow_nav_eur`, appended to `orders.jsonl` under a header disclosing where the previous targets came from. Spec `00039` D5 by design: "order path, positions, reconciliation genuine Nautilus… in shadow mode logs intended orders instead of submitting" | ✅ |
| 4 · concordance hard gate | `zcrypto_gate_status = 1`, `zcrypto_gate_mismatch_total = 0` | ✅ |
| 5 · duration | `zcrypto_gate_streak_days = 20` against a ≥14 bar — the bar was first *crossed* at streak 14 on ~2026-07-24 20:30 UTC (a day becomes evaluable at its 20:30 cutoff) and first *measured* at 15/1/0 on 2026-07-26; it has run clean since | ✅ |

Supporting freshness: `zcrypto_gate_journal_pull_lag_seconds = 2783.9` (46 min) against a 21,600 s (6 h) alert threshold, so the gate is being computed from a current journal rather than a stalled one — the failure mode a green gate would otherwise hide.

**Clause 3 deserves care, and the first draft of this report got it wrong — the correction is left visible on purpose.** That draft claimed the capability was "absent from the binary", so that no misconfiguration could place an order. A cold review refuted it: the exec client factory is registered unconditionally, `exec_enabled` is deployed `true`, and the live trade key sits on the host *because* the exec transport authenticates with it — the draft had that causality backwards. The grep it rested on (`AddOrder`/`place_order`/`submit_order` in `cli/`) could not see a path supplied by the `nautilus-trader` dependency and switched on by config, so it proved nothing it claimed to prove.

The honest guarantee is narrower and worth stating plainly: **the shadow property lives in the strategy layer**, and holds exactly as long as no code path originates an order. That is verifiable, and verified — there is no origination call site in `cli/` — but it is a behavioural invariant, not a structural impossibility. Stage 6b, which does submit, will run on the same transport that was live and idle throughout 6a; that continuity is the point of spec `00039`'s design, and it is also why the distinction matters more than it might seem.

## What Stage 6a did NOT deliver, stated plainly

§12 names four Phase-6 artifacts: **runbook, ops drill log, concordance reports, go-live decision record.** As of this close-out:

- **Concordance reports** — this report is the first, and it closes only the Stage-6a clause. The gate's continuous output remains a metric, not a document.
- **Runbook** — the surface exists (`infra/runbooks/README.md`, **six** alert/limitation sections at close-out); the go-live day-2 runbook does not. Tracked in \[[T0049]\].
- **Ops drill log** — not started. The drills (kill-switch, WS-loss, restart→reduce-only, full VPS reboot) execute only in attended maintenance windows and are pre-registered go/no-go criteria. Tracked in \[[T0049]\].
- **Go-live decision record** — not made. It is a human decision by §12's autonomy contract (D3(vi)).

**None of these is Stage 6a's to finish** — all four belong to Stage 6b and the go/no-go — but a close-out that omitted them would let a reader infer the phase produced its full artifact set. It did not, and the distinction between "the shadow stage met its hard gate" and "Phase 6 is complete" is exactly what this section preserves.

## Method note

Every figure above was measured at full precision from the live export at close-out time, not carried forward from the 2026-07-26 call — the streak had advanced 15 → 20 in the interval, which is precisely why a close-out re-measures rather than quotes. Clause 3's evidence was corrected after a cold review, and the runbook count with it: the first draft asserted a structural impossibility on a grep that could not see the path it was searching for, and quoted a section count carried forward from a topic file instead of read from the tree — in a report whose whole thesis is that a close-out measures rather than quotes. Both are fixed above and neither correction is hidden, because a close-out that concealed its own overclaim would be the exact failure this document exists to prevent.
