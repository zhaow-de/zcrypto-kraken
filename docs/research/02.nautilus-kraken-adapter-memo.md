# NautilusTrader Kraken Adapter — Phase 0 Data-Path Smoke-Test Memo

**Iteration:** iter-003 · **Phase:** 0 (Preparation) · **Scope:** the autonomous, no-trade-key half of the Phase 0
adapter verification gated by master-plan §7 ("Phase 0 verification" entry criterion for adopting NautilusTrader as
the Phase 6 execution/paper-trading engine). This memo covers **public market-data streaming only** — connect with no
API key, subscribe, and observe real ticks. Order entry, spot-margin, and short semantics require a trade key and are
explicitly out of scope here (see Parked, below).

`nautilus_trader` was installed **only** in a throwaway venv for this smoke test; it is **not** added to this
project's `pyproject.toml`/`uv.lock` (that happens at Phase 6, if this and the account-gated half both pass).

## Kraken adapter — module & API surface

Package: `nautilus_trader.adapters.kraken` (installed at
`.../site-packages/nautilus_trader/adapters/kraken/`, 8 files, ~3.9k LOC: `config.py`, `constants.py`, `data.py`
(1131 lines), `execution.py` (1889 lines), `factories.py`, `providers.py`, `types.py`, `__init__.py`).

**Re-exported top-level symbols** (`nautilus_trader.adapters.kraken.__init__`):
`KRAKEN`, `KRAKEN_VENUE`, `KRAKEN_CLIENT_ID`, `KrakenDataClient`, `KrakenDataClientConfig`,
`KrakenExecutionClient`, `KrakenExecClientConfig`, `KrakenLiveDataClientFactory`, `KrakenLiveExecClientFactory`,
`KrakenInstrumentProvider`, `KrakenInstrument` (a union type: `CurrencyPair | CryptoPerpetual | TokenizedAsset`,
from `nautilus_trader.core.nautilus_pyo3`), `KRAKEN_INSTRUMENT_TYPES`, `KrakenEnvironment`, `KrakenProductType`.

(Note: the official docs page at nautilustrader.io names the data-client factory `KrakenDataClientFactory`; the
actual installed 1.230.0 package exports it as **`KrakenLiveDataClientFactory`** — the docs text and the shipped
code disagree on this one name. Verified against the installed source and the upstream example script, below.)

**Config classes** (`nautilus_trader.adapters.kraken.config`):

- `KrakenDataClientConfig(LiveDataClientConfig, frozen=True)` — fields include `api_key`/`api_secret` (both
  `str | None = None`, sourced from `KRAKEN_SPOT_API_KEY`/`KRAKEN_SPOT_API_SECRET` env vars if omitted),
  `environment` (`KrakenEnvironment`, default `LIVE`), `product_types` (tuple of `KrakenProductType`, default
  `(SPOT,)`), `base_url_ws_spot`/`base_url_ws_futures`/`base_url_ws_l3_spot`/`base_url_http_*` overrides,
  `update_instruments_interval_mins` (default 60 — Kraken has no instruments-update channel, so this is a polling
  task), `ws_heartbeat_secs` (default 30), retry/rate-limit knobs, and `validate_l3_checksum` (default `True`,
  CRC32-verifies L3 book deltas).
- `KrakenExecClientConfig(LiveExecClientConfig, frozen=True)` — adds `spot_account_type` (`CASH` default,
  set to `MARGIN` to enable leverage), `default_leverage`, per-order `params={"leverage": N}` override,
  `use_spot_position_reports`, `margin_balance_asset`. Not exercised in this iteration (needs a trade key).

**Supported data types** (confirmed by reading `KrakenDataClient`'s `_subscribe_*` methods in `data.py`):
`SubscribeInstruments`/`SubscribeInstrument` (no native channel — served from a periodic REST poll, not a WS
push), `SubscribeInstrumentStatus`, `SubscribeOrderBookDeltas` (L2 `depth ∈ {0,10,25,100,500,1000}`, or L3 via a
separate `wss://ws-l3.kraken.com/v2` client that **does** take `api_key`/`api_secret` even though the main spot
feed does not), `SubscribeQuoteTicks`, `SubscribeTradeTicks`, `SubscribeMarkPrices`/`SubscribeIndexPrices`
(Futures only), `SubscribeBars`, `SubscribeFundingRates` (Futures only). Historical `RequestBars`,
`RequestTradeTicks`, `RequestOrderBookSnapshot`, `RequestInstrument(s)` are also wired.

**Instrument types**: `CurrencyPair` (Spot), `CryptoPerpetual` (Futures `PI_`/`PF_`), and `TokenizedAsset`
(per `KRAKEN_INSTRUMENT_TYPES`). A single client instance is configured for one `product_type` (`SPOT` or
`FUTURES`) at a time; both can be requested via `product_types=(SPOT, FUTURES)` on the config, which builds
separate HTTP/WS clients internally.

**Public (unauthenticated) data connection — confirmed from source, not just docs.** In
`KrakenDataClient.__init__` (`data.py`), the main Spot WS client is instantiated as
`nautilus_pyo3.KrakenSpotWebSocketClient(environment=..., base_url=..., heartbeat_secs=..., proxy_url=..., base_url_http=...)` — **no `api_key`/`api_secret` are passed**. Only the separate L3 order-book WS client passes
`api_key=config.api_key, api_secret=config.api_secret`. So quotes, trades, bars, and L2 order-book data genuinely
work with `api_key=None`/`api_secret=None`; only L3 (full order-by-order book) needs a key. This matches the
upstream reference example `examples/live/kraken/kraken_data_tester.py` (fetched from
`github.com/nautechsystems/nautilus_trader`, `develop` branch), which configures `KrakenDataClientConfig` with no
credentials at all for a Spot data test.

## Smoke test

**What was run.** A trimmed copy of the upstream `kraken_data_tester.py` reference example: a `TradingNode` with
one `KrakenDataClientConfig(environment=LIVE, product_types=(SPOT,), instrument_provider=InstrumentProviderConfig (load_all=True))` (no `api_key`/`api_secret`), running the built-in `nautilus_trader.test_kit.strategies.tester_data .DataTester` actor subscribed to `instrument`, `quotes`, `trades`, and 1-minute `bars` for **`BTC/USD.KRAKEN`**.
Executed as `timeout --signal=INT --kill-after=15 45 python3 kraken_smoke.py` — a **hard 45s run bounded by an
external SIGINT, with a 15s SIGKILL backstop** — so the process could not hang regardless of adapter behavior.

**Result: full success.** Sequence observed in the log:

1. Connected the Spot instrument provider over public REST, loaded **1829 Spot instruments** (1669 after Futures
   filtering) in ~370ms.
2. Connected to `wss://ws.kraken.com/v2` (public, no key) in ~1.5s.
3. Subscribed to instrument/quotes/trades/bars for `BTC/USD.KRAKEN`; Kraken's ack log lines confirm each
   subscription (`Subscribed BTC/USD.KRAKEN quotes`, etc.).
4. Over the ~44.5s live window, received **152 `QuoteTick`s**, **12 `TradeTick`s**, and **12 in-progress-minute
   `Bar` updates** — all real, moving BTC/USD prices (e.g.
   `QuoteTick(BTC/USD.KRAKEN,63124.9,63125.0,8.15…,98.88…,<ns-ts>)`,
   `TradeTick(BTC/USD.KRAKEN,63125.0,1.48370500,BUYER,103399949,<ns-ts>)`).
5. On receiving `SIGINT` at the 45s mark, the node logged `Received SIGINT, shutting down`, cleanly unsubscribed
   all four channels, disconnected the websocket (`Disconnected from wss://ws.kraken.com/v2`), and disposed —
   finishing in ~6s, well inside the 15s kill-after grace period. Exit path never needed the SIGKILL backstop.
6. **No errors or reconnects** during the run. The only `WARN`-level lines were expected/benign: no exec-clients
   configured (data-only test), reconciliation deactivated (data-only test), and the SIGINT notice itself.

**A real rough edge found along the way.** The first attempt used
`InstrumentProviderConfig(load_ids=["BTC/USD.KRAKEN"])` (targeting a single symbol, to avoid loading the full
1800+-pair universe) instead of `load_all=True`. That raised, at `node.build()`:

```
File ".../nautilus_trader/adapters/kraken/factories.py", line 288, in create
  provider = get_cached_kraken_instrument_provider(...)
File ".../nautilus_trader/common/config.py", line 476, in __hash__
  return hash((self.load_all, self.load_ids, filters))
TypeError: unhashable type: 'list'
```

`get_cached_kraken_instrument_provider` is `@lru_cache`-wrapped and hashes the `InstrumentProviderConfig` it's
called with; `load_ids` is a `list[str]`, which isn't hashable, so **any `InstrumentProviderConfig(load_ids=[...])`
passed to the Kraken factory throws** — this looks like a real, reproducible bug in 1.230.0's factory caching, not
a usage mistake (the upstream reference example sidesteps it by only ever using `load_all=True`). Switching to
`load_all=True` (loading the full instrument universe, ~1829 pairs, ~370ms) worked cleanly and is what the smoke
test above used. Filed as a finding, not independently reported upstream in this iteration (time-boxed).

Also noted for the record: the standard usage pattern is **synchronous** `node.run()` (which manages its own event
loop and installs its own `SIGINT` handler) — not `asyncio.run(node.run_async())` from an already-running loop.
An initial attempt to drive `run_async()` from inside `asyncio.run(main())` failed with
`ValueError: The future belongs to a different loop than the one specified as the loop argument`, because
`node.build()` schedules tasks against the node's own internally-managed loop before that loop is running. This is
consistent with the upstream example (`node.run()` called bare, stopped via `Ctrl+C`) — not a bug, just a usage
constraint worth remembering for Phase 6.

## Verdict

**The public data path is viable for Phase 6.** With zero API keys, the adapter connected to Kraken's real Spot
WS endpoint, loaded the live instrument universe, and streamed genuine quotes/trades/in-progress bars for a liquid
pair (BTC/USD) cleanly, with a graceful shutdown on signal and no reconnect/error noise in a ~45s window. This
directly de-risks the data half of the Phase 6 adoption criterion in master-plan §7. Two caveats to carry
forward, neither blocking: (1) `InstrumentProviderConfig(load_ids=[...])` is currently broken against this
adapter's factory (use `load_all=True`, or file/patch upstream before Phase 6); (2) this was a short (~45s),
single-pair, Spot-only run — it does not exercise L3 book auth, Futures, reconnect/backoff behavior under a real
network drop, or sustained multi-day stability, all of which matter for a 24/7 VPS deployment and remain open for
a longer Phase 6 soak test.

## Parked (needs a trade key — Phase 6 / T0000)

Per master-plan §7, the adapter's **execution** side — spot-margin order semantics (`leverage` param,
`spot_account_type=MARGIN`), shorts, reduce-only, post-only, FOK/trailing/iceberg order types, and
reconciliation against live positions — is **not** exercised in this iteration; it requires a live (or at least
authenticated) Kraken API key, which is explicitly out of scope for this autonomous smoke test. This is the same
gate already tracked in `docs/open-topics/T0000-phase0-account-actions.md` (verification tier, spot-margin
enablement, read-only + trade-scoped key creation) — the human account actions there are the prerequisite for
running the execution half of this Phase 0 verification. From reading `execution.py` (not exercised live): Spot
FOK is rejected for non-`LIMIT` order types (`UNSUPPORTED_TIME_IN_FORCE`), `reduce_only` requires
`spot_account_type=Margin`, and per-order leverage is passed via `SubmitOrder.params={"leverage": N}` — worth
re-confirming hands-on once the trade key exists, rather than trusting this read-only code inspection alone.
