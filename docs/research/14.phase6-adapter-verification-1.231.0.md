## What changed in the adapter between 1.230.0 and 1.231.0<a name="what-changed-in-the-adapter-between-12300-and-12310"></a>

Established by reading the installed package, not the changelog. The Kraken adapter's Python layer is **byte-identical except `config.py`**, which gained one optional field, `transport_backend: TransportBackend | None = None`, on both the data and exec configs — purely additive, nothing renamed or removed. The pyo3 Kraken symbol set is unchanged. `KrakenSpotHttpClient.submit_order` still has **no `validate` parameter** at either layer, so spec 00039's substitution of zero-fill real orders for a validate-only sweep stands at 1.231.0 exactly as it did at 1.230.0. Per-order leverage is still `SubmitOrder.params = {"leverage": N}`, and the post-only rejection path is present and unchanged.

## Harness<a name="harness"></a>

**The harness is now committed code**, which is the substantive change from the 1.230.0 run: `infra/scripts/kraken-order-semantics-probe.py`, run per `infra/runbooks/order-semantics-verification.md`. Spec 00039 used a scratchpad driver "per the trial-driver precedent", which suited a one-off entry criterion; the obligation is now recurring and mechanically enforced, and probes are only comparable across versions if they are the *same* probes.

Same production-shape `TradingNode` as before — `KrakenDataClientConfig` + `KrakenExecClientConfig(spot_account_type=AccountType.MARGIN, margin_balance_asset="ZEUR")`, `LiveExecEngineConfig(reconciliation=True)`, instrument provider `load_all`. Credentials vault-decrypted into the run's environment only. The account was already funded from the 1.230.0 run (€99.84).

The harness carries its own rails — dry-run default, `--apply` gating every submission, a second gate on the money probe, a per-order notional ceiling that refuses rather than clamps, cancels always by order (never `cancel_all_orders`, because the live engine shares this account), and probe-shaped client order ids that cannot collide with the engine's. Three independent review rounds preceded the run; the findings are recorded in the commit that added the harness, and the two that mattered most were a per-order ceiling that could have refused probe 5's *closing* leg and stranded a real position, and a post-only check that would have passed on any rejection.

## Observations<a name="observations"></a>

1. **Post-only semantics are unchanged at 1.231.0.** A crossing post-only is accepted and then **venue-canceled**, surfaced as `OrderCanceled` with no `OrderRejected` — identical to 1.230.0's Observation 2. The distinguishing evidence is the event stream: 4a/4c/4d each show an `OrderPendingCancel` (our cancel), while 4b goes `OrderAccepted` → `OrderCanceled` at the same millisecond with none. The engine's rule — treat `OrderCanceled` on a post-only as the "would cross" signal — remains correct and needs no change.
2. **The taker fee is still exactly 0.80 %/side**: €0.08000 on €9.99993. Unchanged from the 1.230.0 data point, so nothing in the cost calibration moves on this run.
3. **Instrument count fell 1,675 → 1,609.** A venue-side listing change, not an adapter one; all 10 universe pairs still resolve 1:1.
4. **First-tick latency read 0.04 s against 2.0 s at 1.230.0.** Not comparable as an adapter measurement — the committed harness subscribes at `on_start` and measures from subscribe, where the 2026-07-10 driver measured from strategy start. Recorded so the next run does not read it as a regression or an improvement.
5. **The engine's external-event filter was exercised against real venue events for the first time.** The engine reconciles this same account and was disarmed throughout. Across the run `zcrypto_exec_external_events_total{disposition="unmatched"}` moved **0 → 12** while `matched` stayed **0**, and `zcrypto_exec_position{symbol="BTC/EUR"}` stayed **0** — the engine saw the probe's orders, classified them as unmatched (no ledgered row), counted and dropped them, and did not mistake the probe's fills for its own position. This is the first live exercise of the disposition filter that resolved T0142; before this run it had only ever met synthetic events. **Only the `unmatched` branch was exercised** — `matched` stayed 0 by construction, since the engine holds no ledgered row for a probe order — so the matched path remains live-unproven.

**A cross-branch dependency this measurement carries, stated rather than left to be discovered.** `zcrypto_exec_external_events_total` enters the code at `e8d95d2a` and is **absent** from `732598ff`, the engine revision `docs/reference/fleet-pins.md` records on this branch. The counter exists only because the engine was converged on 2026-08-23 10:21 UTC to `03d4cf1b8df7` (revision `f54431a6`, which the running engine reports as its own `code_version`), and the pins row recording that converge sits on the unmerged `docs/fleet-pins-canary-03d4cf1b` branch. Until that branch lands, the repo's committed state says the engine runs a revision with no such counter, and this observation cannot be reconciled from the tree alone.

## Version re-check rule<a name="version-re-check-rule"></a>

This verification binds to **nautilus-trader 1.231.0 exactly**. The rule itself is unchanged in substance but has moved from prose into two mechanical guards, both reading `cli/engine/order-semantics-verified.json`: the engine Ansible role refuses a converge rendering `exec_armed=true` on a version absent from that file, and `cli.engine.execgate` refuses the gate at runtime when the *running* interpreter's `nautilus_trader` is absent from it. Adding a version to that file is the act that records the re-run happened, and it must never be added without a `docs/research/` verification doc recording its PASS.

The procedure for the next bump is `infra/runbooks/order-semantics-verification.md`; the harness it drives is committed, so the next run is the same six probes rather than a reconstruction of them.
