  3. **A percentile (e.g. p90) rather than the mean** — more conservative for a filter. Rejected, but **the original ground was false and is corrected here (2026-07-22, adversarial review of the merged branch)**: it read "the cap does not bind at any percentile the data supports", which was asserted rather than measured. Measured over the calibration window (1,123,511 DOT/EUR seconds; mean 6.5488, reproducing the committed table exactly at its own 3-dp precision — 5.545406 → 5.545 @ €1k, 12.412050 → 12.412 @ €10k): p50 6.33, p90 8.35, p95 9.25, **p99 10.87**, max 85.86 bps/side — **2.54 % of seconds sit above the 10 bps/side cap**, so a p99 criterion *would* bind on DOT. The rejection stands on the honest ground instead: the mean is the statistic the cost model actually charges ("one derivation, two consumers"), and a per-second tail excursion is not a tradeability verdict for a pair held across 4h bars — screening on a percentile would import a different statistic than the one the round-trip cost is computed from, and would need its own calibration to be defensible.

[iter-115] What cap value, given it will not bind on the current universe? (Decision: 1)
  1. **10 bps/side, anchored to the fee stack and left non-binding.** A round trip crossing twice at the cap costs 25 % of the tier-1 round-trip maker fee (2 × 0.40 % = 80 bps), at which point spread has stopped being a rounding error on the fee stack. (Corrected 2026-07-22: the entry originally said "becomes the dominant cost" — wrong by ~4×. At the cap spread is 20 % of the 100 bps round trip; dominance would need ~40 bps/side. The 25 % is a chosen convention, not a derivation.) At €1,400 every current member passes — DOT worst at 6.55 bps/side (16.4 % of the RT fee), keeping ~35 % headroom; that 6.55 is a log-notional interpolation between the calibration's €1k and €10k anchors, not a measurement at €1,400. Taken: **the criterion excludes nothing today, and that is the honest outcome.** It is a guard for future refreshes ([[T0025]]), not a filter that changes the current twelve names.
  2. **Tune the cap so it bites on the current universe** (i.e. just under DOT) — would make the criterion visibly "do something", at the cost of fitting the rule to the very data it is meant to judge. Rejected; a threshold chosen to exclude today's worst member is a post-hoc rank, not a criterion.
  3. **Express the cap as a live fraction of the current fee tier** rather than an absolute constant — self-adjusting as volume tiers improve. Rejected for a degenerate edge: at the top tiers maker → 0 %, so "25 % of the maker fee" collapses to a cap of zero and rejects everything. The 25 % is kept as the *derivation* of the constant, not a runtime formula.

[iter-115] How should a symbol with no L2 capture be treated? (Decision: 2 — and the gap is registered rather than absorbed)
  Context measured this iteration: the capture daemon subscribes to **EUR-quoted pairs only**, so `ETH/BTC` and `SOL/BTC` — two of the twelve *selected* symbols — have no spread data at all.
  1. **Reject unmeasured symbols** — fail-closed, superficially safe. Rejected: it drops two real universe members on a data gap, and absence of evidence is not evidence of a wide spread.
  2. **Record `spread_bps: null` and do not reject.** Taken. The null is the point: it makes the two unscreened symbols visible on the artifact every reader consults, instead of letting a filter that covers 10/12 read as universe-wide. Registered as [[T0092]], because whether to capture those legs is a capture-config decision (a live, unbackfillable pipeline) rather than an analysis one.
  3. **Silently exempt them** (omit the field when unknown) — smallest diff, and exactly the "green because we stopped looking" shape this project keeps finding in its own artifacts. Rejected.

[iter-136] What supplies the volume source for the two BTC-quoted legs (`ETH/BTC`, `SOL/BTC`), given reach is structurally EUR-only and no re-run of it can produce them? (Decision: 1)
  1. **Extend the reach round itself to be quote-aware, so it mints all twelve legs.** Recommended and taken (the owner's ruling). Feasibility was checked, not assumed: `XETHXXBT`/`SOLXBT` are live pair keys, and `ohlc-full` already carries both series to 2026-03-31, so REST's window overlaps the seam and both come back continuous. Keeps the universe at twelve names and opens no strategy question.
  2. **Drop the two legs for a ten-name universe** (10 ≥ `MIN_NAMES` 8, so `escalate` would stay `False`). Rejected: it removes the two relative-value legs from the tradeable universe, which is a strategy decision and not one a data-plumbing iteration should take unilaterally.
  3. **Tape-derived bars** ([[T0065]]'s live-trades→bars materializer). Rejected as premature: the `/BTC` tape was 20 days deep against a 30-row median (blocked until ~2026-08-21) and `cli/tick/materialize.py::derive_bars` has no production caller, so it would delay the cluster by ten-plus days plus new implementation for the most durable long-term source.

[iter-136] `cli/ohlc/fetch.py::PAIR_KEYS` cannot express two quotes per base — what shape should the re-key take, given the live engine (`cli/engine/store.py`) imports and re-exports the same map? (Decision: 1)
  1. **Re-key `PAIR_KEYS` by full symbol; the engine derives a filtered EUR-only view from it** (`{base: key for symbol, key in PAIR_KEYS.items() if symbol.endswith("/EUR")}`), pinned by a test so a future BTC-quoted leg cannot leak into the engine silently. Taken. One source of truth, and the live engine's ten-EUR-leg basket is provably unchanged — re-keying unqualified would have widened it to twelve, produced store paths like `root/ETH/BTC/EUR/1440.parquet`, and broken the test pinning the BTC legs as excluded.
  2. **A separate literal map in `store.py`.** Fully decoupled and simplest to reason about in isolation, but duplicates ten pair keys that will drift the first time a venue key changes underneath the primary map.
  3. **Keep the EUR map and add a second BTC-only map.** Smaller diff than re-keying, but leaves two maps to keep in sync and makes the symbol no longer the sole identity, which it already is everywhere else in the codebase.

[iter-136] The canonical universe artifact is a fixed filename (`universe/point-in-time-universe.json`) pushed over an additive-only, never-`--delete` transport, so a refresh can never update the hub copy under that name — how should publication work? (Decision: 1)
  1. **Publish each refresh as its own immutable `universe-<stamp>/` set, resolved newest-wins.** Taken. No new transport concept — `rebuild_sets` already mints exactly that sibling (previously discarded by a hand copy) and `push_hot` already takes `extra_sets`; the stamp is `%Y%m%d`, so lexicographic order is chronological with no date parsing. The legacy `universe/` set stays as the resolver's fallback until the first stamped publish, so nothing breaks in between.
  2. **Delete the hub copy so a same-named push lands.** One line, keeps one filename, but converts a structural guarantee (the additive transport can never clobber an edit) into per-operator discipline — rejected on principle, not cost.
  3. **Stamp the filename inside the single `universe/` set instead of minting a new directory.** Transport-viable (`--ignore-existing` skips only files that already exist), but fights the directory grain the rebuild already mints — it would need the file lifted out of its sibling into a shared set, adding a move the directory form does not need.
  4. **A guarded `promote` command that still writes one fixed path.** Rejected as the option that looks like a fix but isn't: it makes the smaller problem (an unverified local copy) safe while leaving the larger one (hub divergence, the actual defect) untouched.
