[iter-100] CORRECTIONS forced by measurement (Decision: n/a — recording two spec claims the venue
  disproved, because both caused real defects):
  - D5's "nanoseconds vs seconds trap" was FICTION. `since` accepts both a seconds epoch and the raw
    ns `last` cursor (Kraken's documented usage). The conversion the spec MANDATED (last // 1e9) was
    itself the defect: it rewinds to the start of that second and, when 1000 rows share one second,
    yields an identical `since` -> an infinite loop against the live venue, precisely during the
    volatility bursts this feature heals. -> D5a: pass the cursor raw + a trade_id-progress guard.
  - D6's "a REST row must be indistinguishable from a WS row" is IMPOSSIBLE. Kraken's REST float runs
    systematically ~+0.7..+1.1us above the WS ISO microsecond (float64 ULP here is only 0.238us, so
    it is a venue offset, not noise). No rounding mode closes it: truncation recovers WS 2/4,
    rounding 0/4. -> D6a: ts is the one field REST cannot reproduce; safe because dedupe keys on
    trade_id ALONE with primary priority, so only RECOVERED rows (no WS counterpart) carry REST's ts.
  Pattern worth keeping: every serious defect this iteration came from asserting a fact instead of
  measuring it, and every one was caught by measuring.

[iter-101] The ops mirror is two hops from source (T0058): `source_lag` rose monotonically (4072 -> 6465 -> 7928 s) after the OPS-5 move, and the final review falsified the "no wrong verdicts" claim (the cutover gate keyed on the NAS->ops rsync, which succeeds against a frozen NAS mirror). Which topology fixes it? (Decision: 2)
  1. **Faster pulls** — tighten the pull cadences so each hop is shorter. Treats the symptom: both hops remain, the gate stays keyed two hops from the truth, and every tightening adds rsync load against a growing archive to the Atom this iteration exists to unload.
  2. **NFS mount** — the NAS exports custody read-only; ops reads the canonical trees through the mount and pulls nothing. Removes the ops hop entirely, keeps custody ingestion independent of ops, retires a key/channel, and subsumes option 1 since cadence becomes free (reads cost no transfer). Recommended, and the owner ratified it with four consensus points: (1) the RO NFSv3 export (`ro,nfsvers=3,nolock,soft,timeo=100,retrans=3,noatime,nosuid,nodev` — `ro` makes `soft` categorically safe); (2) ops's 3-tree rsync retires, the write-back direction unchanged (overlay + panel return via the NAS-initiated rrsync pulls); (3) the reconcile gate consumes the NAS-written `.pull-status` through the mount, fail-closed (capture_ok=1, secondary_ok=1, younger than 4 h) — restoring actual-pull-outcome gate semantics one NAS cycle delayed; (4) the writer cadence doubles (`*:12,42`).
  3. **Reroute VPS -> ops -> NAS** — give ops the first hop and let the NAS pull custody from ops. One hop for the reconciler, but it puts the compute tier inside the custody path and moves the two-hop problem to gate-export's journal — custody ingestion would depend on ops being up.
