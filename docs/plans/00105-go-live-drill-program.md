# 00105 — the go-live drill program: implementation plan

Spec: `docs/specs/00105-go-live-drill-program-design.md`. Branch `feat/00105-go-live-drill-program`, cut from `develop` after PR #352 ([[T0157]] / spec `00104`) merged — `infra/runbooks/observability.md`, `engine.md` and the PROCEDURE kind all exist there now, so no task here creates them.

## Goal

Every go-live drill scenario has an induction instrument, a derived bound and a recording shape before anyone needs one at 03:00; the telemetry tier is **executed**, not just written; and the two gaps no rehearsal can close — the dark-with-exposure alert and the Grafana-dark procedure — are built.

## Global constraints

- **A drill that induces a fault runs in the main loop, never in a subagent or workflow** — the permission gate blocks ssh/sudo there and the step dies where nobody sees the prompt (`agent-ops.md`).
- **Never induce a fault on live capture outside an attended window, and never inside a published Kraken maintenance window** — read `https://status.kraken.com/api/v2/scheduled-maintenances.json` at planning time and again immediately before each induction (`fleet-deploys.md`). The **primary's capture daemon and its Alloy are not touched by any task here.**
- **The owner's 2026-08-29 authorization ([[T0158]]) IS this iteration's attended window, and it covers exactly one class**: every Alloy action, and any container / unit / timer start–stop the loop reverts itself. A **converge** is outside it and stays a human step, as does anything that reboots or powers off a host. An induction the class does not cover **stops the chain where it stands** — revert what is already induced, record why, and hand back; never proceed past it, and never widen a named instrument into a heavier one.
- **Every induction is reverted and verified BY VALUE before the next one starts.** A drill that leaves the fleet degraded is an incident, not a drill.
- **The seven parts of a drill section are spec D1's, in this order**: *What this proves* · *Preconditions* (window, host, tier gate) · *Induce* (exact commands or instrument) · *Must fire* (which alert or dead-man, on which channel, within what bound) · *Operator action* · *Record* · *Retire when*. `infra/runbooks/README.md`'s PROCEDURE row enumerates only the four-part base and defers to D1 for a drill's shape — writing a drill section with those four is the error this constraint exists to prevent, and nothing in the suite checks section shape.
- **Bounds are derived, never guessed**: a Grafana rule's `for` plus its group's evaluation interval, **plus Prometheus staleness (~5 min) for any rule whose condition cannot go true until the series goes stale** — the `count(up{…}) or on() vector(0)` silence shape every `zcrypto-alloy-dark-*` rule carries, where `for` + interval alone understates the real notice by a third and the rule's own comment in `alerts.yaml` states the ~15 min it is (spec D1). The group's interval is in neither `alerts.yaml` nor `grafana-push.sh`, which sets none: read it from Grafana's provisioning rule-group endpoint (`/api/v1/provisioning/folder/<folderUid>/rule-groups/<ruleGroup>`, whose payload carries `interval`), never assumed. A healthchecks check's timeout plus grace, quoted from the check itself. The management API takes a **check name**; `capture-redundant`, `capture`, `ops`, `nas`, `engine` are node **tags** and resolve to nothing there — `observability.md`'s dead-man map is the tag→daemon table, and a lookup that returns nothing is never repaired by reaching for the adjacent check.
- **A cross-file runbook anchor is cited only after the task that creates it.** The tasks run out of numeric order, and every runbook task's Verify runs `test_every_runbook_cross_reference_resolves` — only the index test is ever deselected — so a section citing an anchor a later task lands goes red, and the cheapest wrong repair there is deleting the pointer from the page an operator opens at 03:00. Two sections are written before their target exists and so name it in **words**: drill C′ in `drills-telemetry.md` (Task 2) for `observability.md#grafana-cloud-dark`, and `engine.md`'s `zcrypto-engine-dark-with-exposure` section (Task 5) for `drills-order-path.md#drill-b`. **The task that creates the anchor adds the citation** — Task 6 and Task 3 respectively.
- **A drill result lives in `docs/reference/drill-log.md` and in its runbook section.** A result that lives only in a report or a PR body is not recorded (`open-topics.md`).
- **The entry's shape is spec D2's, copied here for the same reason the seven parts are**: `## <YYYY-MM-DD> — <scenario id> — <pass | fail | partial | blocked>`, then one paragraph of labelled clauses — *host* · *induction* · *time-to-alert* (with the three timestamps wherever a Slack path is involved: rule `activeAt`, message, device) · *channels* · *operator action* · *follow-ups* (a `T<NNNN>` or an explicit drop). **The status vocabulary is closed at those four and `blocked` is one of them, not prose**: an induction that never landed — O's precondition refusing it, no line in Loki for Q's `logs` path — is `blocked` with its reason, since `fail` would assert a guard did not fire when nothing exercised it and `partial` a run that half-happened. Widening the guard's regex to admit a fifth word is the wrong repair: the vocabulary is spec D2's decision and the guard only reads the shape D2 fixed, so a fifth word buys an entry nothing and costs every later reader a status they cannot classify. `tests/test_drill_log.py` is its guard and **every task that writes an entry runs that guard as it lands** — the commit gate runs no pytest, so an entry is otherwise unchecked until the mutation probe, which refuses to start at all on a failing baseline.
- Every commit reviewed by a subagent other than its author; **Fable floor for anything touching the capture path or the live trade path** (`spec-plan-locations.md`).

### Task 5 — `zcrypto-engine-dark-with-exposure`

Add the critical rule to `infra/grafana/alerts.yaml`, in the `zcrypto-gate` group with the engine's other rules. **The expression is pinned here rather than left to the implementer**, because "non-zero at last sight AND the scrape absent" is self-defeating written the obvious way: the gauge publishes from the very target the second half requires to be gone, so once staleness expires `zcrypto_exec_position != 0 unless up{job="engine_app",host="zcrypto"}` matches nothing and the rule never fires — and Task 11's first-sample read, taken while the engine scrapes normally, is green over exactly that. Four nodes, the same A/B/math/threshold chain `zcrypto-ops-verify-replay-backlog-stuck` uses:

- **A** (instant): `max(abs(last_over_time(zcrypto_exec_position{host="zcrypto"}[24h]))) or on() vector(0)`, with `relativeTimeRange: {from: 86400, to: 0}` — the largest exposure **at last sight**, across symbols, an explicit 0 when there is none. `last_over_time` returns each series' **last** sample in the window, never its maximum, which is what D5's "non-zero at last sight" asks for; `max_over_time` is the wrong reach and would keep the rule firing on a position closed hours before the engine went dark. `abs`, because a short is exposure too; `host="zcrypto"`, because the `engine_app` job is scraped on both capture hosts and reads 0 on `zcrypto-red` by design, so the host label is load-bearing on both halves. **The range and the `[24h]` selector are pinned together and must stay equal**: the model rule below couples them on its own ranged node (`{from: 93600, to: 0}` beside `delta(...[26h])`), and the rules that carry this coupling say why in their tests — shortening one silently truncates what the other reads. Copying the model rule's *instant* node's `{from: 600, to: 0}` here would leave `last_over_time` ten minutes of history and the rule inert on a scrape that stopped longer ago than that.
- **B** (instant): `min(up{job="engine_app",host="zcrypto"}) or on() vector(0)` — the scrape's VALUE, with the `zcrypto-alloy-dark-*` fallback but **not** their `count()`. `engine_app` is a **static** scrape target (`infra/ansible/roles/capture/files/config.alloy`), so nothing removes it when the container stops: the series stays present reading 0, `count()` would read 1, and `$B < 1` could never go true on the one event this rule exists for — the same reading `zcrypto-engine-cycle-stale`'s own `noDataState` comment already records, and the reason `up{job="engine_app",host="zcrypto-red"}` has read 0 for every sample of its life on a host where no engine runs. `min` is 0 on a dead exporter and, through the fallback, 0 again when the primary's Alloy takes the series away, so both darkness routes trip it; the fallback is also what lets `noDataState: Alerting` stand, keeping a healthy fleet at an explicit 1 so NoData here can only mean the datasource itself is gone. `execErrState: Alerting` — `test_no_other_rule_quietly_joins_the_execerrstate_exemption` admits no third `OK`. **Its `relativeTimeRange` is pinned too, at `{from: 600, to: 0}`** — what the `zcrypto-alloy-dark-*` rules carry on this same instant read; never the expression nodes' `{from: 0, to: 0}`, and never a copy of A's 24 h, which an instant query cannot use.
- **C** (math): `$A > 0 && $B < 1`; **D** (threshold on C): `gt 0`, since the math node emits only 0 or 1.
- `for: 10m`, `severity: critical`, `notification_settings.receiver: metrics` — pinned, not left to the default, because Task 3's D section must quote the `for` before this rule is pushed. `up` falls to 0 on the **first** failed scrape (60 s scrape interval), so `for` is the only thing between a single missed scrape or an Alloy restart and a critical page: 10m is ten scrape attempts and the posture `zcrypto-alloy-dark-ops` already takes on this same signal, and it is far below the 24 h lookback the discrimination test's horizon clause protects. `metrics` is what every metrics-sourced rule pins (`infra/scripts/grafana-push.sh`).

Its annotations point at the panel that charts A's series: `__dashboardUid__: "zcrypto-engine"` / `__panelId__: "64"` — `Position by symbol (base units)`. **The 24 h lookback is a decision, not a default, and it is also the page's horizon**: the alert self-resolves when the last position reading ages out of it — while the engine may still be dark and the position still open — so it is sized to outlast a full daily ops pass, and the runbook section says in those words that a resolve here is not an all-clear. Runbook section in `engine.md`, response is B. **The section's bound quotes the rule's own `for` and its group's evaluation interval** (spec Verification), read the way Global constraints says — the interval from Grafana's rule-group endpoint. **It is two bounds, because the two darkness routes reach `$B < 1` differently**: the engine container dying is a VALUE read, so one scrape interval (60 s) plus `for` plus the group's interval, no staleness term; the primary's Alloy going dark takes the series away, so that route adds the ~5 min Global constraints prescribes for a condition that cannot go true until a series goes stale. The page is read on a phone with real exposure open, and without both the responder cannot tell five minutes dark from an hour before deciding to flatten. **The response is named in words here — `drills-order-path.md#drill-b` does not exist until Task 3, which runs after this one** (Global constraints), and this task's Verify runs `test_every_runbook_cross_reference_resolves` un-deselected: a citation written now goes red, and the cheapest wrong repair is dropping the route from a critical page. Task 3 adds the citation.

**The discrimination test is written first and seen red**, in `tests/test_infra_alert_rules.py` and modelled on `test_a_healthy_drain_stays_quiet_and_a_stuck_one_pages`: read the lookback out of the expression and `for` out of the rule — never restate either, so the test fails when the rule changes — and replay `(position, scrape)` histories through them. The true positive: exposure open, then the scrape stops ⇒ fires, and is still firing one evaluation before the horizon. Both false positives: the scrape stops with the position flat ⇒ quiet throughout — this is the whole discriminator, since `zcrypto-engine-cycle-stale` already pages on any engine darkness and what this rule adds is *and there is money exposed*; and the engine scraping with exposure open ⇒ quiet. Then the two controls the verdict rests on, each replaying the true positive through a defective form and asserting it does **not** fire, so the simulation is shown to move on each defect instead of passing everything (`agent-ops.md`): the **unlookbacked** form — node A with its `[24h]` stripped, `max(abs(zcrypto_exec_position{host="zcrypto"})) or on() vector(0)` read instant, which holds the condition only until the gauge goes stale and so never survives to `for: 10m`; **not** the `unless` form this task's opening names, which subtracts a right-hand side that is present-at-0 and therefore fires on no history at all, healthy or dark, so a control built on it passes without the simulation having moved — and the **presence-counting** form (`count(up{…}) or on() vector(0)`). The second control is what makes the replay honest about `up`, and the two assertions are only jointly satisfiable under the truth: model the dark scrape as `up = 0` **present** — the static target's real behaviour — and the rule fires while the `count()` form reads 1 and stays quiet, both green; model it as an absent series and the `count()` form falls through its fallback to 0 and fires too, so the control goes red and names the modelling error rather than letting a replay written from this page's own prose certify whichever aggregation it happens to describe.

Two durable claims go false when this rule lands, and re-tensing them is part of the task, not a follow-up: the `alerts.yaml` comment above `zcrypto-engine-cycle-stale` that says "Deliberately no such rule exists today … Revisit only if arming stops being episodic" becomes the record of why the **unscoped** rule is still refused and what this one pins instead; and `NOT_A_FAULT_SIGNAL`'s `zcrypto_exec_position` entry in `tests/test_infra_alert_rules.py`, whose comment reasons the execution gauges are attended-window instruments nothing pages on, must now say that the bare value stays no fault while non-zero **with the engine's scrape gone** pages. Neither breaks a test, which is exactly why nothing else would catch them.
