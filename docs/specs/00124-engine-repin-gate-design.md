# The engine's own re-pin gate: the candidate image's offline preflight on the engine host replaces the capture bake as the engine converge's gate

## Problem

The engine role refuses a re-pin until the secondary runs the candidate digest as capture (spec 00083 D5, `infra/ansible/roles/engine/tasks/main.yml:150-202`): there is no engine secondary, so the capture bake was made the engine's gate.
The bake proves what the two images share — the base layers, the dependencies, the entrypoint, the memory envelope, the log shipping — and nothing of the engine's own payload: the rollout skill already says so (`.claude/skills/zcrypto-rollout-image/SKILL.md:38`, "an engine payload's own proof is its next disarmed boundary cycles, never the bake").
It also couples every engine change to a capture re-pin of the secondary, inside rung 2's box where no capture converge is wanted, and it reads a live host that may be unreachable for a reason unrelated to the engine.
The owner's ruling of 2026-10-05 (`.local/deadman/spec-decisions.md`, carried in the memo): the engine role's canary parity is replaced by an engine preflight on the candidate digest, run on the engine host before the re-pin — an offline self-test from that image — with CI green on the revision the image was built from, the converge inside the inter-cycle gap, and the disarmed proving cycle after; the capture bake stays the capture role's alone.

## Decisions

### D1 — The engine role reads no capture bake

Everything at `roles/engine/tasks/main.yml:150-202` goes: the comment that cites 00083 D5 and the four tasks under it — the running-engine digest probe, the secondary's capture-digest probe, the parity assert and its override echo; the first one's read, the running container's `.Config.Image`, returns beside the preflight's block as its engagement probe, under its own name and register (D3).
Two comments that describe the parity go with it: the role's :278-279, which contrasts the cache proxy with the engine image's canary parity, says instead that the proxy's upstream image carries no `zcrypto` command and so takes neither the preflight nor a bake; `infra/ansible/scripts/run.sh:9`, "the capture and engine roles probe the other capture host by delegate_to", names the capture role alone.
`canary_override` becomes the capture role's alone, with its grammar, its echo and its count entry `canary-bypasses-on-the-primary` unchanged — the capture re-pin on the primary is still the set that count reads.
The ten tests under "engine canary parity (spec 00083 D5)" in `tests/test_infra_converge_guards.py:784-897` go with the tasks; D10 names what replaces them.
Spec 00083 is not edited: D5 stays as the record of what was built, and this spec is the record of its replacement.

### D2 — The image carries its own preflight: `zcrypto engine preflight`

A new subcommand, `zcrypto engine preflight --state-dir <dir>`, offline and read-only: it writes nothing under the state dir or anywhere else and opens no socket, and on the engine host it runs under `--network none` (D3), so a check that reached for the network would fail and refuse rather than reach a venue.
It makes no claim about its imports — the exec gate's readers it reuses sit in a module that imports the venue status reader at its top (`cli/engine/execgate.py:9`) — so the network boundary is the container's, not the import graph's.
Its checks, each a field of one JSON line on stdout:
- `config`: the engine configuration is `zcrypto.toml` in the working directory — `/app/zcrypto.toml` in the container, `/app` being the image's WORKDIR — loaded by `cli.config.load_config()`, the loader `engine run`'s `_load_engine_config()` wraps (`cli/engine/command.py:95-103`); it is called directly because that wrapper logs its refusal to stdout and raises an `Exit` that carries no text. The value is `ok`, or why it refused: no `zcrypto.toml` in the working directory (`engine run`'s `ZCRYPTO_REQUIRE_CONFIG` check at :811-815 made unconditional, since `load_config` answers an absent file with the built-in defaults, `cli/config.py:244-248`); the `ConfigError` text; or a `store_dir` or `journal_dir` that does not lie under `--state-dir`, the one directory the container mounts, once both are normalised with `os.path.normpath`, so a `..` segment cannot climb out of it, and compared by path component (`Path.is_relative_to`), so a sibling sharing its prefix, `<state-dir>-old`, is not under it.
- `verified`: the library version the image runs is a member of the image's own `cli/engine/order-semantics-verified.json` — read through the exec gate's own readers, `_verified_nautilus_versions()` and `_installed_nautilus_version()` in `cli/engine/execgate.py`, so the preflight and the gate can never disagree — and an image whose order semantics were never verified is refused before it ever runs.
- `stores_missing`: the BASKET×GRID store files `engine run` requires before it connects (`cli/engine/command.py:822-834`), walked as it walks them — `_store_path(store_dir, symbol, interval)` under the loaded configuration's `store_dir`, which the role renders as `{{ engine_state_dir }}/store` (`roles/engine/templates/zcrypto.toml.j2:8`) — and listed when absent; the preflight reads the directory listing and nothing else.
- `journal`: the newest record under the loaded configuration's `journal_dir`, rendered as `{{ engine_state_dir }}/journal` (`zcrypto.toml.j2:9`) — the last of `_journal_artifacts(journal_dir, "*", "cycle-*.json")`, the walk `engine replay` makes (`cli/engine/command.py:121-132`, called at :1023) — loaded with `cli.engine.journal.from_json` and checked with `validate_record`, as the cycle's back-search reads its previous record (`_previous_success`, `cli/engine/cycle.py:407`): `ok`, `none` when no record exists, or the reader's error text; it is a load, never a replay, so a candidate whose decisions legitimately differ from the recorded ones still passes.
- `version` and `nautilus`: the image's own `zcrypto` version string and the library version, for the record.
- `ok`: true when `config` is `ok`, `verified` is true, `stores_missing` is empty and `journal` is `ok` or `none`; when `config` is not `ok`, `stores_missing` and `journal` are null, their roots being the configuration's.
Exit 0 when `ok` is true, 1 when any check failed. An image built before this spec has no such command and answers Click's usage exit, 2, with `No such command 'preflight'` on stderr; 2 is every usage error — an unknown option, a missing argument, an absent `engine` group — so D3's assert names the missing preflight only on that stderr.
The subcommand lives in `cli/engine/preflight.py`, wired in `cli/engine/command.py`; its help text carries no internal term.

### D3 — The role runs the preflight on the engine host, against a candidate render, before anything else renders

Engagement: the running engine container does not run the candidate. The probe is the read the removed parity probe made (`main.yml:155-161`), `docker inspect --format '{{.Config.Image}}' zcrypto-engine`, written in the role's escaped form (`main.yml:156`), `check_mode: false`, `failed_when: false`, `changed_when: false`; the block runs unless the probe answered rc 0 with `{{ engine_image }}@{{ engine_image_digest }}` in its stdout — the reference the compose template pins (`roles/engine/templates/compose.yaml.j2:10`) and the container carries as its `.Config.Image` — so it fails closed: a probe that failed (no container), answered nothing, named another image, carried no `rc` or was skipped engages. The compose file is never read for engagement: the rollout skill stages the compose pin on the host before the converge (`.claude/skills/zcrypto-rollout-image/SKILL.md:21`), and a compose file can pin one image while the container runs another (:103), so a pin that already names the candidate says nothing of what runs.
A converge onto the digest the engine already runs takes no preflight. A stopped unit has no container — its `ExecStop` is `docker compose down` (`roles/engine/files/zcrypto-engine.service`), which removes it — so a converge onto a stopped engine engages whatever its digest. The store repair (`infra/runbooks/engine.md`; the role's comment at `main.yml:451-462`) stops the unit, moves the store aside and converges again with the digest it ran: its real pass delivers the store before the gate, but its preview, whose copy writes nothing, finds the store aside and refuses on `stores_missing`, so a store repair takes the bypass with its reason, which the three texts that name that converge's operands carry — the role's store comment, the store assert's `fail_msg` (`main.yml:487-504`) and the runbook's repair (D7). A compose pin edited by hand and started by `docker compose up` outside a converge — the rollout skill's rollback edits it back to the previous digest — is the operator's own re-pin, outside this gate. A first deploy, with no container, engages, and its preview, run before the account, the state dir and the store exist, cannot pass: a first deploy takes the bypass with its reason.
Position: the probe and the block sit after the store delivery and its assert and after the compose project directory (`roles/engine/tasks/main.yml:463-514`), and before the cache proxy's render (:519), the role's first: `engine_uid` and `engine_gid` have no default and are first set at :423-432, the candidate path's directory is created at :508-514, and an absent store is delivered before it is checked.
The role first renders the engine configuration template to a candidate path beside the live one, `/opt/zcrypto-engine/zcrypto.toml.candidate`, `owner: root` and `mode: "0644"` like the live render (`main.yml:607-614`; the `--user` container reads it), with `check_mode: false` and no handler: the candidate is tested against the configuration it will run with, not the previous converge's render, so a template error is refused here and not at the restart.
The run, on the engine host: `docker run --rm --network none --user {{ engine_uid }}:{{ engine_gid }} --memory 512m -v {{ engine_state_dir }}:{{ engine_state_dir }}:ro -v /opt/zcrypto-engine/zcrypto.toml.candidate:/app/zcrypto.toml:ro --entrypoint zcrypto {{ engine_image }}@{{ engine_image_digest }} engine preflight --state-dir {{ engine_state_dir }}` — exactly these arguments and no other: no `--env-file` or `-e`, no published port, no further mount, the state dir read-only, the network none: nothing of the live engine (its arm file, its restart hold, its journal, its key, its cache session, its metrics port) is reachable from the preflight container.
The task is `check_mode: false`, `failed_when: false`, `changed_when: false`, registered; what the gate quotes and books is the run's last stdout line — the JSON line, on a run that printed it — null when stdout is empty, `stdout_lines | default([]) | last | default(none)`, since a bare `last` raises on an empty list: a run that never reached the preflight (Click's rc 2, Docker's 125) or crashed before the console entry ran leaves stdout empty, and a fault raised inside the subcommand is logged to stdout by the console entry (`cli/__main__.py`'s `run()`) and exits 1, its last stdout line the exception's. The candidate render is removed in the block's `always`, `check_mode: false` as the cache proxy's candidate removals are (`main.yml:544-548`, `:587-592`), whether the asserts passed or failed. The block carries no `rescue` and no `ignore_errors`, and neither assert carries an `ignore_errors`, a `failed_when` or a `when` of its own: each turns a refusal into a pass — a rescue catches the failed assert and the play goes on to render the refused digest; the cache proxy's removal at :544-548 is safe in its `rescue` (:543) only because that rescue ends in a `fail` (:557).
The assert, "engine preflight — refuse an engine re-pin the candidate image has not passed on this host": `rc == 0` (a register without an `rc` refuses), or `engine_preflight_override` under spec 00082 D1's grammar (longer than 8 characters, not `true`/`false`/`1`/`yes`); its `fail_msg` quotes the last stdout line and the stderr on rc 1, which a run that crashed also answers — from inside the subcommand the exception's line and an empty stderr, from before the console entry an empty stdout and the traceback on stderr; on rc 2 with `No such command 'preflight'` on stderr it says the image carries no preflight (an image built before this gate existed); on any other rc — a usage error, Docker's own 125, an out-of-memory kill's 137 — it says the preflight could not be run and quotes the rc and stderr; every arm gives the bypass as JSON — `-e '{"engine_preflight_override": "<why this cannot wait>"}'`.
The echo task, "engine preflight override — print the reason where it bypassed a refusal", a `debug` whose `msg` names the reason and what it bypassed — `engine preflight override accepted: {{ engine_preflight_override }} — preflight rc <the run's rc>: <its last stdout line, as the gate quotes it>; revision <the label, trimmed>, first-parent merge: <D4's assert's first disjunct verbatim>` — since one override bypasses both asserts and a reason approved for one refusal must not pass the other unseen, fires when the override passes the grammar and either assert's first disjunct is false — this one's or D4's — each negated clause that assert's first disjunct verbatim, so a provenance-only bypass prints its reason and an override that bypassed nothing prints none. Its name states no outcome, since the default callback prints a task's name whether the task fires or skips: the acceptance is its `ok` line's `msg`. No key hides what D7's Phase 3 reads: neither assert's arguments carry `success_msg`, which replaces `All assertions passed`, or `quiet`, which keeps the result off the default verbosity; the echo's carry no `verbosity`, which above 0 skips it there; and no `no_log` sits on the block, either assert or the echo, since it censors the result.
`engine_preflight_override` joins `converge.sh`'s `OVERRIDES` list (:50), so the braced-JSON form is the only one the wrapper admits.

### D4 — The image's revision is a merge on `develop` or `main`

The pulled image's `org.opencontainers.image.revision` label is read on the engine host — `docker image inspect --format '{{index .Config.Labels "org.opencontainers.image.revision"}}' {{ engine_image }}@{{ engine_image_digest }}`, one field, never `.Config` — written in the role's YAML in the escaped form its other inspects use (`main.yml:156`), `'{{ "{{" }}index .Config.Labels "org.opencontainers.image.revision"{{ "}}" }}'`, because Ansible templates a task's string and the literal braces do not render.
The controller lists the commits on the first-parent lines of its own `origin/develop` and `origin/main` — `git rev-list --first-parent origin/develop origin/main` run from `playbook_dir`, `delegate_to: localhost`, `become: false` (the engine play is `become: true`, `site.yml:65`, and a delegated task inherits it, as every other `delegate_to: localhost` task under `infra/ansible/` already sets), `run_once`, `check_mode: false` (under `--check` the command module does not run and answers rc 0), no fetch.
The assert, "engine provenance — refuse an image whose revision is not a merge on develop or main", admits the label, trimmed, only as an exact member of that list; its `fail_msg` quotes the trimmed label and, when the list is empty, the list read's rc and stderr, says a stale controller refuses a fresh image and names `git fetch origin` before a re-run, and gives the bypass as JSON, as D3's arms do. The label is never handed to git, so a ref name such as `origin/develop` is no member; a commit of a merged pull request's branch is an ancestor of `develop` but on no first-parent line, so a branch-built image (`capture-image.yml`'s `workflow_dispatch` builds any ref) stays a bypass after its branch merges — narrower than Ruling 2's ancestor wording, which every such commit passes. The three revisions `docs/reference/fleet-pins.md` records today, `7ab4fc1a`, `77df6273` and `a1a39280`, are each on `develop`'s first-parent line.
A stale `origin/develop` refuses a fresh image until the operator pulls, which `merge-pr` has them do at every merge.
What it proves: by the branch rule, a commit on that line is a pull request merged through a green `Full test suite` (`.github/settings.yml:66-77`; `test-suite.yml` runs on pull requests alone and the image workflow runs no tests). It does not prove the suite ran on the image's own tree: `develop`'s required check is `strict: false` (`.github/settings.yml:73`) and `merge-pr` merges a `BEHIND` pull request (`.claude/skills/merge-pr/SKILL.md:44`), so the suite ran on the pull request merged with the `develop` of its last run, and the merge commit — the label, `${{ github.sha }}` (`capture-image.yml:95-96`) — carries that tree only when `develop` had not moved since. The owner closed that gap on 2026-10-08 ("(b) as recommended"): `infra/scripts/merge-gate.py` gains an arm that refuses a pull request whose head lacks its base's tip when the paths its diff changes touch a path whose push builds the image. Behind is read from the clone — `git merge-base --is-ancestor origin/<base> <head>` exiting 1, run right after the fetch the gate's range walk already makes — never from GitHub's `mergeStateStatus`, which under `strict: false` reports a behind pull request `CLEAN` (an open one behind `develop` read `CLEAN` on 2026-10-08), so an arm keyed on `BEHIND` never fires. The changed paths are read from the clone too, after the same fetch — `git diff -z --name-only --no-renames origin/<base>...<head>`, which lists a rename's old path beside its new one, and every path as it is once split on NUL, a name whose bytes are not UTF-8 failing the read's decoding and answering no list, as a failed read does: without `-z` git prints a path holding a byte outside ASCII, a `"`, a `\` or a control character C-quoted inside double quotes, which matches no glob, and `core.quotePath=false` unquotes only the first of those four — never from GitHub's file list, whose `filename` is a rename's new path alone, so a file moved out of an image path would show the arm nothing. A read that answers neither 0 nor 1, or a behind head whose changed paths git did not list, is the arm's refusal, never a pass. The paths whose push builds the image are `capture-image.yml`'s `on.push.paths`, and a test holds the gate's list equal to them. The refusal carries the remedy: merge `develop` into the branch, which the gate admits past the read line, so the pull request's last green run is on the tree that merges.
Every door onto a first-parent line, and what holds it: `merge-pr`, whose gate the arm is and whose Step 3 runs the gate again immediately before `gh pr merge`, so `develop` moving during Step 2b's reads is caught — the seconds between that run and the merge stay open, `strict: true`, the setting that would refuse a behind head at the merge itself, being off on purpose; the `dependabot` skill's squash (§2d), which bypasses the gate and so takes the same `--is-ancestor` read immediately before it, a behind reading sending the pull request back to its rebase (§2a) once and a second on the same pull request stopping for the user, the seconds between the read and the squash open as `merge-pr`'s are, and the read unscoped where the arm is scoped — a behind pull request off the image paths costs a rebase and a CI run it did not need, which keeps the image paths in the one list the gate's test holds rather than a second in the skill; the release skill's three merges — its pre-release sync and its back-merge into `develop`, its release pull request into `main` — dropped, since each lays over a `develop` tree only the release commit's version files (its step 9), so a behind one differs from a tree a suite ran by those files alone, of which the engine reads only the version string, to journal it (`cli/engine/cycle.py:85-91`); a bare `gh pr merge` from an agent session's main loop — a dispatched agent's is refused by `.claude/hooks/bash-guard.sh` — which `.claude/settings.json`'s `Bash(gh pr merge:*)` allow rule runs without a prompt, held by CLAUDE.md's rule that a merge goes through `merge-pr` alone; and a merge by hand outside these skills, dropped as the operator's own act, as a hand-edited compose pin is outside D3's gate.
With the arm and its two closures, a commit on `develop`'s first-parent line that changed a path whose push builds the image ran the suite on its own merged tree, but for the openings just named, and D4's membership check is then the proof of "CI green" the ruling asks for. The arm and both closures are tasks of this plan; `.claude/skills/merge-pr/SKILL.md`'s gate item 3, which calls `BEHIND` fine, names the exception.
The assert shares D3's override: a hotfix image built off a branch is a bypass with its reason on the record, never a silent pass.
An empty label (an image built outside the workflow) is no member and is refused the same way.

### D5 — The row records the preflight, and two counts read it

The engine role adds a `preflight` object to the window record `site.yml` writes before the role runs (`zcrypto_window_record`, :165-190, the flat `{at, floor, arm, override}`): one task after the block — on the real pass only (`not ansible_check_mode`, as `site.yml`'s copy) and only when the record path is set, `delegate_to: localhost`, `become: false`, `run_once` — reads the file back and writes it with `preflight` merged in: `{"engaged": <bool>, "digest": "<sha256:…>", "rc": <int or null>, "revision": "<label or null>", "first_parent": <bool or null>, "line": <the last stdout line or null>}`. `engaged` is whether the run happened, and the four after `digest` are null when it did not; `first_parent` is D4's assert's first disjunct verbatim. The task runs on every real pass that gets past the gate, engaged or not; a converge the gate refuses stops at its assert and books no `preflight`.
`converge.sh` pops `preflight` out of the loaded record before it books the rest as `window` (:281-302), so `window` keeps the four keys the deploy-log audit's `carries_the_record` requires (`infra/scripts/deploy-log-audit.py:115-128`) and the row carries `preflight` beside it; a record holding nothing else books no `window`.
`infra/scripts/count-list.sh` gains two entries over one set, D6's: rows since the last refine round closed, from the log's first row that carries a `preflight` — the rows before it were gated by the capture bake — whose `limit` is `zcrypto`, as `c_canary_bypasses` scopes its rows (a run limited to another host matches no `engine_host` member, so its engine play converges nothing), whose `tags` reach `engine` and whose `extra_vars` carry `engine_image_digest`:
- `engine-repins-without-a-preflight`: of those, the rows whose `rc` is 0, whose `extra_vars.engine_preflight_override` is null, and whose `preflight` is absent, or engaged with an `rc` other than 0 or a `first_parent` other than true: a converge that went through with nothing gating it and nothing bypassing it. The role books `preflight` on every pass that gets past the gate, so a successful row without one was written outside the role's path, and an engaged non-zero `rc` or non-true `first_parent` beside a row `rc` of 0 is an assert that did not refuse — the preflight's or the provenance's, the rule's two refusals (D6); a refused converge (`rc` ≠ 0) and one onto the digest the engine already ran (`engaged` false) are not counted.

Both are `jq` over the log, read and windowed as `c_canary_bypasses` (:334-338) reads its own, slurped to find the first `preflight` row, and select the set through one preamble the two share — the canary entry's own selector reads `limit` and neither the tag nor the digest; `tests/test_count_list.py` moves each conjunct of both with a fixture row, and both join its `WINDOWED` table.
