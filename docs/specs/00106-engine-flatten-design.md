# 00106 — `zcrypto engine flatten`: the red button

Resolves the build half of [[T0159]]. One command, one host wrapper, one runbook section, one widened guard, one verification row — on one branch and one PR, at the Fable review floor (live trade path).

**What it is.** With the engine's kill file written first so nothing can re-open, stop the engine, then against the venue's REST surface: cancel every resting order account-wide, close every margin position with a reduce-only **market** order, sell every non-EUR spot balance at **market** — and report, per leg, what the venue answered. **The default invocation is a dry run** — it prints the plan and stops; only `--execute` touches the venue, and then behind a typed word; every action journaled; exit codes that distinguish *flat* from *partial* from *could not reach the venue*.

**The ruling it implements (owner, 2026-08-29)**: whole account, market orders, kill file first. And what that overrides: spec `00090` D6 rejected MARKET *as the probe machine's fallback* — "unbounded price on the live path when a bounded marketable limit does the same job". That rejection stands for the probe machine. For this command it is overridden, and the reason is the opposite regime: in a crash the price is not the variable, time is, and a bounded IOC in a fast market leaves residue — and the residue is the exposure.

## Decisions

### D1 — One host command, engine stopped first, one-off container

The operator runs **one thing**: `sudo zcrypto-flatten` on the engine host — a dry run by default, `sudo zcrypto-flatten --execute` to press the button — a wrapper the engine role deploys to `/usr/local/sbin/zcrypto-flatten` (rendered from `infra/ansible/roles/engine/templates/zcrypto-flatten.sh.j2`, reaching the host on the next attended converge). With `--execute` it does, in order:

1. Writes the kill file — `/var/lib/zcrypto-engine/exec/kill`, one line `<ISO-8601 UTC> flatten`, the engine's own shape (`executor.py:1731`) — **before anything else**. `exec/` is not guaranteed to exist: the engine role creates only the state dir, `store/` and `journal/`, and `exec/` is otherwise created lazily by the engine's own `_write_kill_file` — so on a host that has never tripped a kill the directory is absent and the redirection would fail under `set -eu` before anything was latched or stopped. The wrapper therefore `mkdir -p`s `exec/`, `chown`s it to the engine account and `chmod`s it 0750 (the role's own posture, which root's umask would otherwise widen to 0755) before writing. If the engine is running it refuses the next submit and revokes any resting order within a tick; if it is not, the file waits for the next start's adopt pass, which cancels everything at level `none`. The file is a FINDING afterwards, never swept (`engine.md`'s standing rule).
2. `systemctl stop zcrypto-engine` and waits for the unit to be inactive. Spec `00100` measured the drain at ≤ 20 s.
3. `docker run --rm -it --network host --user "<engine_uid>:<engine_gid>" --env-file /opt/zcrypto-engine/engine.env -v /var/lib/zcrypto-engine:/var/lib/zcrypto-engine -v /opt/zcrypto-engine/zcrypto.toml:/app/zcrypto.toml:ro --entrypoint zcrypto <the image the compose file pins> engine flatten --state-dir /var/lib/zcrypto-engine --execute` — the same digest the engine runs, so the verified nautilus version is the one that presses the button. **`--entrypoint zcrypto` is load-bearing**: the image's ENTRYPOINT is capture's `sh -c` script (`infra/docker/Dockerfile:60`), and without the override the words `engine flatten` are appended to that script — the container starts **capture**, not flatten, on a host whose engine was just stopped with positions open. `compose.yaml.j2` bypasses the same trap with its exec-form `entrypoint:` (its own comments at lines 8–9 and 15–27). `--user` matches compose so the journal is not root-owned inside the engine's exec dir; `--state-dir` is explicit so the button does not depend on a config mount when the environment is what broke; `-it` because the confirm reads the terminal. A test renders the wrapper template and asserts all three tokens are present; D8.2's live dry-run goes **through the wrapper**, never a hand-typed `docker run`.

**Without `--execute` — the default — steps 1 and 2 do not happen**: the wrapper runs the container with no flag, the command reads the account with the engine **running** (reads only; the nonce cost of a few reads is accepted for a dry run, and the wrapper says so), prints the plan, and exits 0. The stake is the reason the polarity is this way round: the invocation an operator gets by accident, by muscle memory, or by a half-remembered runbook must be the one that changes nothing. There is no `--dry-run` flag — a flag that means "do nothing" is one that gets forgotten. The dry run's reads beside a running engine are a **named override of `00090` line 36's one-key-one-client rule, for reads only**: the cost is a nonce race that can fall on either side — an engine cancel or submit can be rejected and stranded `ambiguous` (`executor.py`'s `_ACK_WAIT`) — accepted because the engine's next adopt pass reconciles it, and because `--execute` stops the engine before any write. The host wrapper is the phone-reachable halt the master plan §10 names, to the extent ssh from a phone is phone-reachable: one command, one word typed.

Rejected: a control file the running engine acts on (`exec/flatten`) — it does nothing when the engine is stopped or wedged, which is when the button is needed. Rejected: a `LiveNode` of its own — startup reconciliation and a data feed are unneeded for a sweep, and the node is the thing that fights over nonces.

### D2 — Transport: the adapter's HTTP client, and nothing hand-rolled

`cli/engine/flatten.py` builds one `KrakenSpotHttpClient(api_key, api_secret)` from `KRAKEN_SPOT_API_KEY` / `KRAKEN_SPOT_API_SECRET` (the env the container already carries; the probe harness's precedent) and uses only: `request_instruments`, `request_order_status_reports(open_only=True)`, `request_position_status_reports(account_type=MARGIN)`, `request_account_state(account_type=CASH)`, `request_book_snapshot(depth=1)`, `cancel_all_orders`, `submit_order` — five reads, two writes. Every return is parsed by a small adapter layer with **named fields it requires**; a response missing one on any **pre-write** read aborts — before `cancel_all_orders()`, the first write — with exit 3 and the raw shape recorded: journaled with `--execute`; the default dry run writes no artifact at all, so there the abort message, which names the field that could not be read, is the whole record; on a post-write read it is exit 2 (D6 row 3) — a shape the venue changed is a finding, never something to guess through. **One exception**: the book-price read (D3's fifth read) degrades the one leg instead of aborting the sweep — its failure never reaches exit 3. And this rule is about an absent or unreadable **named field**, never about an unrecognised **value** in a field that is present: a value this command cannot act on names its own row and lets every other leg run (D3's `position_side`). The key is a local and a constructor argument: never logged, never in the artifact (`api_key_masked` is what the journal records).

### D3 — Enumeration: what "everything" is

- **Resting orders**: `request_order_status_reports(open_only=True)` — journaled before and after the cancel; the cancel itself is `cancel_all_orders()`, one call, account-wide.
- **Margin positions**: `request_position_status_reports(account_type=MARGIN, use_spot_position_reports=False, quote_currency="ZEUR")` → per row the required named fields are `instrument_id`, `position_side` (LONG / SHORT / FLAT) and the **unsigned** `quantity` — `PositionStatusReport` carries no signed quantity and no leverage (`model/__init__.pyi`); a LONG or SHORT row is a leg, FLAT is not; a row missing either field aborts with exit 3 before the first write. A row whose `position_side` is **present but none of the three** — the installed build's `PositionSide` carries a fourth member, `NO_POSITION_SIDE`, and which members the Kraken adapter emits is unmeasured until D8.2 runs — is **not** an abort: no close side can be derived for it, so it is journaled a residual under `unrecognised_position_side`, every other leg is still cancelled, closed and sold, and the row reads exit 2 (the same rule D4's `pair_not_listed` carries, for the same reason). The account id on every call is the engine's, `KRAKEN-001` (`cli/engine/node.py:54`).
- **Spot balances**: `request_account_state(account_type=CASH)` → free balance per asset; every asset that is not EUR (`EUR`/`ZEUR` — the register's alias rule, `_classify_spot_close`'s `BTC/XBT/XXBT` precedent) with a balance above zero is a leg.
- **Constraints**: **one** `request_instruments()` call with no pairs argument — the full listing, taken at the snapshot, from which every leg's pair is looked up and pairlessness is read (a per-pair request would error on an unknown pair and abort the whole sweep over an unrelated holding; that the no-arg call returns the full listing is Kraken's `AssetPairs` default, confirmed by D8.2's live dry-run) — the required named fields per pair are `ordermin` (`min_quantity`), `lot_step` and `tick_size`; **`costmin` is not read from the venue** — the repo's measurement is that the adapter never maps it (`cli/engine/venuestate.py:20-24`, spec `00089` D5a; measured on 1.230.0 and again on 2.0.0rc4), so it comes from the committed `cli/engine/instruments.py::COSTMIN` for basket symbols, and a non-basket asset has no `costmin` gate: its sell is sent, a venue minimum rejection is journaled as that leg's error, verbatim in the venue's own words and under no minted label — which Kraken message means "below the minimum" is unmeasured, and a label guessed from the text would be a claim the raw answer already makes better — and the **final snapshot judges a non-basket balance against `ordermin` alone** — so such a balance at or above `ordermin` reads as a residual and the run exits 2, the journal naming the leg; the operator resolves it by hand. The exit code never reads a leg's answer (D5). Sizing reuses `size_order` (floor to `lot_step`, then the floors), the same arithmetic the engine trusts. The reference price for sizing and for the taker-rate estimate is a **fifth read**, `request_book_snapshot(instrument_id, depth=1)` — best bid for a sell, best ask for a short's buy — with its own required fields. A leg whose book read fails — the request errors, the required side is empty, or its top level answers a price at or below zero, which is not a price and from which every notional would read as nothing — is priced `None` rather than aborting the sweep (D2's one exception): the price is never the order price, since every order this module sends is MARKET (D1), so the leg is sized on `ordermin`/`lot_step` alone and sent, its `costmin` floor not applicable, and the cancel and every other leg's close proceed regardless.

### D4 — Order semantics per leg

- **Margin close**: side derived from `position_side` **only** — LONG → SELL, SHORT → BUY, never from a sign; quantity = the report's `quantity` floored to `lot_step` and **never above it**; `order_type=MARKET`, `time_in_force=IOC`, `reduce_only=True`, `account_type=MARGIN`, `leverage=2` always — the report carries no leverage field, and 2 is the ratified rung-1 leverage and the only value ever verified live; what the venue does with a mismatched leverage on a reduce-only closer is unknown and is drill B's to observe. The client-side side-and-cap invariant is the bound this repo has proven; the venue's `reduce_only` is the second. A rejection is journaled and the sweep continues. A margin row whose pair is **absent from the one `request_instruments()` listing** does not abort the button either: no order can be sized or constructed for it, so it is journaled a residual under `pair_not_listed`, every other leg is still cancelled, closed and sold, and the row stands in the final snapshot — exit 2, never 3, the same rule the spot side already carries, because one row among many must never cost the operator the whole sweep. A row carrying an unrecognised `position_side` (D3) takes the same route under its own label. That rule governs **every** per-row and per-leg judgement this command makes before the first write: no single row's data may abort a sweep that has not yet cancelled an order, closed another position or sold a balance.
- **Spot sell**: `order_type=MARKET`, `time_in_force=IOC`, `account_type=CASH`, `reduce_only=False` (spot cannot carry it — `00090` line 76), quantity = the free balance floored to `lot_step`. Against `<ASSET>/EUR` where the venue lists it; an asset with no EUR pair (the basket's BTC-quoted legs) sells against `<ASSET>/BTC` in pass one, and pass two sells the BTC balance against EUR after balances are re-read. An asset with **neither** pair is a journaled residual `no_eur_or_btc_pair` and reads exit 2 (D6 row 2) — never 0; and never 3, because pairlessness is read from the **one** `request_instruments()` listing taken at the snapshot, never from a per-pair request that would error on an unknown pair.
- **Dust is a spot-only class.** A spot leg whose sized quantity is below `ordermin` or whose notional is below `costmin` is **listed, not sent** — the venue would reject it — and does not make the account "not flat". A margin position is **never** dust: the engine's own machine deliberately produces sub-`ordermin` remainders (`executor.py`'s `BelowMinimum` path, spec `00090` D6), and a remainder left open is exposure. Its reduce-only closer is sent regardless of the floors — whether Kraken applies them to a reduce-only closer is unmeasured, so the venue rules — and the rejection of a closer this code had **already sized below the pair's `ordermin`** is journaled `unclosable_below_minimum` **beside the venue's verbatim words** — the label is this code's own pre-send reading, and the words beside it are what separate a genuine minimum refusal, which only Kraken's UI settle-position can clear (`00090` line 13: the adapter cannot emit it), from a transient refusal a re-run clears; the runbook section sends the operator to that `error` before the settle-position action. That label is minted from what this code knew *before* sending and never inferred from the venue's message text — which Kraken message means "below the minimum" is unmeasured — so any other margin rejection is journaled verbatim under no label. A quantity that floors to nothing carries the same label without a venue round trip: there is no order to construct.
- **Client order ids** are minted with a `FLT-` prefix and never collide with the engine's (`executor.py`'s own-order routing would otherwise treat an ack as its own — the reader's caveat).

### D5 — The sequence, re-runnable

with `--execute`: kill file present? (the wrapper wrote it; the command **refuses with exit 1 if it is absent** — the file is load-bearing; without `--execute` this gate is skipped, since the wrapper writes no kill file for a dry run) → venue `online` via `cli/engine/venue.py::read_system_status` — the public unsigned endpoint the exec gate already uses, its own 10 s timeout (not online ⇒ exit 3) → snapshot orders, positions, balances, constraints → print the plan: every leg with side, quantity, pair, the estimate at the taker rate (`docs/reference/kraken-fee-schedule.md`, tier 1 0.80 %), every dust line, every refusal → **without `--execute` the command stops here, exit 0** → with `--execute`, the confirm: `Type FLATTEN to close every position and sell every non-EUR balance at market, anything else aborts:` read from the controlling terminal, never stdin (converge.sh's rule; no terminal ⇒ exit 1; there is deliberately **no `--yes`** — a red button pressed by a script is a different product) → `cancel_all_orders()` (its own failure is journaled and the sweep continues — exit 2 at the end, D6) → re-read open orders **and positions** (a non-empty order list is journaled and the sweep continues; the closes are sized from **this** positions read, never from the pre-confirm snapshot — a fill can land during the human-paced confirm) → margin closes, sequentially, each answer journaled, a rejection never retried → re-read positions → re-read balances → spot pass one over every non-EUR balance → re-read balances → spot pass two over every non-EUR balance (BTC included, not BTC only) → final snapshot — **orders first, then positions, then balances**, so an order that fills between the reads lands in a read that follows → exit code **derived from the final snapshot plus D6's two write-side failures** (the cancel's own; a post-write read's) — never from a leg's answer. A second run finds less to do and does it; nothing in the sequence is one-shot.

### D6 — Exit codes and the journal

| code | meaning |
| --- | --- |
| **0** | the final snapshot shows **no open order**, no margin row that is not FLAT (a LONG, a SHORT and an unrecognised side alike, D3), every non-EUR free balance below **any** of its applicable floors **of a pair it has** (dust listed), and no free balance above zero in an asset with neither a EUR nor a BTC pair — or the default dry run completed |
| **1** | refused with nothing sent: kill file absent, no terminal, confirmation did not match, credentials missing — the kill-file, terminal and credential refusals precede every read, the confirm mismatch follows the plan's reads and precedes every write |
| **2** | the final snapshot shows **any open order** (one that outlived the cancel can fill after the operator was told flat), any margin row that is not FLAT — LONG, SHORT, or a side this command does not recognise, which is exposure it could not close and must never read as flat (a FLAT row is not a leg, D3) — any non-EUR free balance at or above **every one** of its applicable floors, or any free balance above zero in an asset with neither a EUR nor a BTC pair (`no_eur_or_btc_pair`, D4); and the cancel's own failure — `cancel_all_orders()` raising or answering an error — is 2 with the sweep continuing, since the closes do not depend on it — whatever each leg answered; the journal names each leg's answer, `unclosable_below_minimum` included |
| **3** | the venue could not be reached or read **before the first write** — `cancel_all_orders()` is the first write: `SystemStatus` not `online`, a request failed, a required field absent. A read that fails **after** the cancel or any order went out — the final snapshot included — is exit 2 with the journal saying which read failed: never 0, and never 3, because the account may have changed |

The journal is `/var/lib/zcrypto-engine/exec/flatten-<ISO-8601 UTC>.json` — its own artifact, never `exec-<HH>.json` (D-basis: unlocked single writer): the snapshots before and after, every request with its parameters and every venue answer verbatim, the confirm's outcome, the exit code. The engine's next start reconciles its own ledger against the venue per its adopt rules and reads the kill file as the finding it is; the runbook section says what the operator reads then.

### D7 — The guard widened deliberately, the help text clean

`tests/test_engine_executor.py::test_the_venue_mutating_names_have_exactly_one_module` pins that only `executor.py` names `submit_order`/`cancel_order`. `flatten.py` is a second venue-mutating module **by design** — the guard's allowlist gains it, with the reason in the test's docstring: the engine's machine and the red button must never share code paths, because the button must work when the machine is what broke. `--help` and every printed line carry no internal token (`tests/test_cli_help_hygiene.py` enforces it).

### D8 — Verification before the button is trusted

1. **Unit tests** against a fake HTTP client that records every call and answers from a script: the happy sweep; a rejected margin leg (exit 2, sweep continues); a race fill between snapshot and cancel; dust below `ordermin`; a response missing a required field on a pre-write read (exit 3, no write sent — the cancel included); **a required field missing on the post-cancel re-read: the cancel sent, no order sent, exit 2** — the fixture that separates the first-write boundary from the retired first-order one; a resting order that survives the cancel, with no position and no balance, reading exit 2, never 0; the cancel raising, the closes still sent, exit 2; the absent kill file (exit 1, no request); the confirm mismatch (exit 1); the default invocation sending nothing, and with no kill file exiting 0 after the plan; a FLAT row producing no order and, alone in the final snapshot, exit 0; a SHORT row producing a BUY and never a SELL, a LONG row's order quantity never exceeding the report's; a margin row on a pair the listing does not carry — nothing aborted, the cancel and every other leg still sent, the row a `pair_not_listed` residual in the final snapshot, exit 2; a margin row carrying an unrecognised `position_side` — the same three properties, under `unrecognised_position_side`; a leg whose book read raises, and one whose book answers a price of zero — the leg still sized and sent on the quantity floor alone, every other leg's price intact, nothing aborted, and never listed as dust; a sub-`ordermin` margin row sent and, on rejection, journaled `unclosable_below_minimum` beside the venue's verbatim words, exit 2 — and a margin row that cleared `ordermin` gaining no label from its own rejection; a fill between the confirm and the cancel enlarging a position — the close sized from the post-cancel read, the residual in the final snapshot, exit 2; an instrument with `min_notional=None` still sized and sent; a balance in an asset with neither pair left in the final snapshot reading exit 2, never 0; a rendered wrapper carrying `--entrypoint zcrypto`, `--user` and `--state-dir`, and latching on a host whose `exec/` does not exist yet; and a test that the ONLY path to `submit_order` or `cancel_all_orders` passes through `--execute` and a matched confirm. The fake asserts the call **order** of D5.
2. **A live read-only dry-run** on the engine host, **through the wrapper** — attended, the engine running, a spot balance present so the MARGIN position read is seen not to surface a spot holding as a row — proves the five read shapes against the real venue and is recorded as a row in `docs/reference/adapter-verification/<version>.md` (the order-semantics runbook's precedent). Until it exists the command's live use is unverified, and the runbook section says so.
3. **Drill B** (`00105` D4) is the end-to-end proof: rung-1 money, a real position from A2, the button pressed, decision-to-flat measured. Reduce-only MARKET on margin is proven there and nowhere earlier; the runbook carries that caveat until the drill-log entry reads `pass`.
