## Adapter verification protocol (§7 Phase-6 entry criterion — pre-registered)

Scripted probes against the live account (scratchpad drivers, per the trial-driver precedent), attended. The committed deliverable is a **verification memo** — `docs/research/14.phase6-adapter-verification.md` (appended to the mdformat allowlist as a research report) — recording, per probe, expected vs observed. **Pass = probes 1–6 behave per documented Kraken semantics through the Nautilus adapter.** Failure handling per decision 1: an order-semantics/reconciliation failure (probes 2, 4–6) triggers the pre-approved fallback; any other failure is documented and escalated. A probe that turns out unexecutable *as designed* is a protocol artifact — redesigned and re-run, never counted as an adapter failure. Probes, in order:

1. **Auth + account read**: balances via the adapter's execution client; expect the account's actual balances.
2. **Reconciliation read**: open orders + open positions on node start; expect empty-or-actual state, no spurious entries.
3. **WS market data**: subscribe trades/quotes for the 10-asset EUR universe; expect ticks on the liquid pairs within seconds, clean unsubscribe/shutdown.
4. **Zero-fill order semantics through the adapter (×4, each canceled immediately after acknowledgment)**: (a) spot post-only limit buy ≥ 25 % below market → expect accepted + resting → cancel confirmed; (b) spot post-only limit buy priced to cross the ask → expect Kraken's post-only rejection surfaced as an adapter order-rejected event, no fill; (c) margin long: leveraged limit buy ≥ 25 % below market → expect accepted + resting (leverage accepted by the venue) → cancel; (d) margin short: leveraged limit sell ≥ 25 % above market → expect accepted + resting → cancel. No probe in this set can fill at its placement distance within its seconds-long lifetime; an unexpected fill is bounded by the ~€10 order size and is itself a reportable finding.
5. **The one real fill**: ~€10 BTC market buy → fill event → position/balance reconciliation → market close → flat again.
6. **Post-cancel reconciliation**: after probes 4–5, open orders and positions read back empty; balances reflect only probe 5's round-trip.

## Go-live criteria (pre-registered 2026-07-10)

- **Stage 6a concordance gate (hard)**: ≥ **14 consecutive days** with zero missed daily cycles and the node's target weights matching a replay to **|Δweight| ≤ 1e-6 per asset**. Pinned semantics: *daily close* = the 00:00 UTC bar boundary; the cycle must complete by **00:30 UTC** (retries allowed within the window; later = a missed cycle); the node **journals its input data snapshot** alongside targets, and the concordance check **replays the journaled inputs through `build_combined_system` on the workstation** — input identity is a mechanism, not an assumption, so any weight drift is a defect. A missed cycle or mismatch resets the 14-day clock and is investigated before restart.
- **Stage 6b tracking band** (tiny-live sleeve €500–1,000, quarter size): weekly **|live − sim| sleeve return ≤ 10 bps of sleeve NAV**; per-trade realized cost ≤ **2×** the modeled 0.6 %/side; **zero unreconciled order/position states** — all three held for **≥ 3 consecutive weeks**. The weekly tracking-error report covers §12's full contents — fills, fees, rollover accrual, slippage vs the cost model — and feeds **cost-model recalibration from real fills** (6b executor scope).
- **Model consistency (§12's fourth criterion)**: realized 6b performance must sit **within the validation CI** of the deployed system's simulation — not "profitable", *consistent with the model*; a >20 %-style divergence means the backtest is wrong and the project **returns to Phase 5**.
- **Ops drills, each passed at least once before go/no-go**: kill-switch (flatten + halt within one cycle), WS-loss recovery, restart→reduce-only, full VPS reboot recovery.
- **Ramp (each step a D3(vi) human decision, never an automatic calendar promotion)**: go/no-go admits 25 %; each subsequent step (→ 50 % → 100 %) requires **no gate breaches and the DD ladder untouched or correctly handled** over the ~2 weeks since the prior step; **before exceeding 25 %, the §11 tax-pipeline verification must be closed — T2 pass or T3 fallback deployed**. The governor enters live at its **true carried state (×0.5)**.
