# 00098 — adopted orders' fills become observable, without widening the kill trip

Resolves [[T0142]]. After a restart, a fill on a preserved resting reducer currently reaches no handler in this process: nautilus 1.230.0 reconciles a venue-resting order under `StrategyId("EXTERNAL")` unless its instrument is claimed, and order events publish on `events.order.<strategy_id>` — a topic this strategy does not subscribe to. The row never appends, no counter moves, and the forensic record the reconciliation trip is measured against silently diverges from venue truth. The topic's original dilemma — claim the instruments and gain observability but route the operator's sanctioned hand settle into the unknown-order kill trip — is a false binary, and this spec dissolves it.

## The measured basis

Verified against the installed library, 2026-08-22. **The coordinates below were READ off a wheel that shipped Python source; the pinned wheel does not — the execution engine, the cache and the order state machine are compiled, and `nautilus_trader/execution/` holds an `__init__.py` and a stub file and nothing else.** So none of these line references can be reopened, and each claim below is kept only because it is carried by something that can be run: the topic and the subscription by `tests/test_engine_node.py`, the apply-before-dispatch ordering by `tests/test_engine_executor.py`, which drives a real order through a real engine and reads the Cache from inside the handler.

- The order-events topic is `f"events.order.{strategy_id}"`, cached per strategy id.
- The fill path publishes on that topic **unconditionally**: no special case drops the publish for `EXTERNAL`. A fill on a reconciled external order therefore does publish on `events.order.EXTERNAL`; before this spec it merely had no subscriber.
- `EXTERNAL_STRATEGY_ID = StrategyId("EXTERNAL")`, with `is_external()` as the predicate.
- `self.msgbus` is a public attribute on every registered `Actor`; a `Strategy` may subscribe to any topic.
- **The publish's TIMING relative to the subscriber's birth — the fact the first draft of this spec did not ask about, found by the whole-branch review.** The kernel awaits execution reconciliation and only then starts the trader, which is what runs `Strategy.on_start` and therefore installs this subscription — and on a FAILED reconciliation it returns without starting the trader at all, so the adopt pass can only ever run against a successfully reconciled cache. That is what makes the cache "venue truth" rather than a hopeful reading. Reconciliation's own generators (the inferred fill, the generated fill, and every terminal generator) route through the same handler, which applies the event to the order and to the Cache and publishes it **in one synchronous body with no `await`** — and both it and this engine's `on_timer` run on the single event loop, which is what makes a snapshot between an apply and its publish impossible (apply-then-publish ordering alone would not). That ordering is the one claim here that survives the loss of readable source, because it is MEASURED rather than read: `test_the_cache_already_carries_the_fill_when_the_strategy_handler_sees_it` reads the Cache from inside a real handler and finds the fill, the settled order status and the moved position already there. So a fill that happened while this process was down IS published on `events.order.EXTERNAL`, before any subscriber exists, and the message bus has no replay for late subscribers (probed against the installed build: a handler subscribing after a publish receives nothing). `open_check_interval_secs` and `position_check_interval_secs` both default `None`, so nothing re-infers later. The quantity is not lost, though: apply-then-publish means it is resident in the reconciled order's own `filled_qty` by the time this process's first tick runs. That is what D7 reads. Two further library guards bound what can reach that quantity at all: a re-delivered `trade_id` is rejected before any processing, and a fill past the order's own quantity is rejected — and never published — with `allow_overfills` defaulting `False`.
- Client-order-id continuity across restart-reconciliation is **supported but not yet production-observed** (no order has ever been submitted; the probe window has not run). The adapter submits our full id, and reconciliation prefers `report.client_order_id`, falls back to venue-order-id lookup, and otherwise mints a UUID4 id. The venue's echo of `cl_ord_id` across sessions is the one unproven link — and its failure direction is inert: a UUID-minted id matches no ledger row, so the adopt pass cancels the order and its events land unmatched — scope intact, feature dark, nothing mis-recorded. Nothing is therefore owed on it and no topic is opened; the first armed-window restart is where it would be observed, not a check anyone must remember to take.

## Decisions

### D1 — subscribe to `events.order.EXTERNAL`; never claim

`ProbeExecutor` subscribes (at registration/start, via `self.msgbus`) to the external order-events topic and routes those events to a **dedicated handler** (public `on_external_order_event` wrapping private `_on_external_event`, mirroring `on_order_event`'s shape). `external_order_claims` stays unset. The two properties the topic said could not both be had:

- **Observability**: a matched adopted order's events reach this process the moment they happen.
- **Scope**: the unknown-order trip is untouched — it still runs only on the strategy's own topic, and an unmatched external event (the operator's hand settle) is ignored by the new handler, reaching no trip, no row, no cancel. `node.py`'s scoping precondition survives verbatim and gains a sentence describing the second, filtered path.

### D2 — the handler's matched path reuses the row/counter machinery, and trips on matched overfills only

Matching is against `self._attached` — the ledger-vouched rows the adopt pass re-attached. For a **matched** event:

- `OrderFilled` → overfill check first, exactly as `_trip_on_fill` does for own orders: a fill taking `filled_qty` past the ledgered ordered quantity (beyond `_OVERFILL_TOLERANCE`) records the fill (`_record_trip_fill` semantics — the fill happened; no-fill-without-a-record has no divergence exemption) and **trips the kill switch**. A ledgered adopted row is this engine's own pre-restart order; divergence on it is the same class the existing per-order trip guards, and tripping on matched rows only is what keeps the scope property intact. A clean fill appends to the row (`update_submitted_row`), credits `row["filled_qty"]`, and publishes counters via `_publish_fill`; when it completes the ledgered quantity (within `_OVERFILL_TOLERANCE` — the external path has no active intent to borrow a lot step from), the row is additionally marked `"filled"` and `_inc_order("filled")` counts the completion — nautilus publishes no separate terminal event after a resting order's final fill, so without this the row reads open forever. The entry stays in `_attached` (the no-pop ruling above), guarded so the completion write fires once: a further fill on the completed row goes to `_trip_on_fill`, whose overfill arm latches — the same divergence semantics an own order has. One scoping fact, so the arm is not read as broader than it is: nautilus rejects a venue-CONSISTENT overfill before it publishes (`is_duplicate_fill_c` drops replays and `_check_overfill`, with `allow_overfills` defaulting `False`, refuses a fill past the order's own quantity and logs rather than publishing), so what actually reaches this arm is the ledger-vs-venue divergence — a row whose ledgered quantity is SMALLER than the order the venue is filling, which is exactly the case a previous process's order and an operator's web-UI amendment produce. A venue-consistent overfill surfaces as a nautilus error log, not as a kill; that is the library's containment, and this spec does not duplicate it.
- Terminal events → row state update via the existing payload idiom. **The entry does NOT leave `_attached` — neither path ever pops** (amended after Task 2's review): the first ruling had the external handler pop on terminal events, which re-created the exact race D4 cites as the reason the own path retains rows — Kraken's `ownTrades` and `openOrders` are separate WS channels with no cross-stream ordering guarantee, so a fill racing a terminal ack would have arrived unmatched, counted but never journaled, falsifying the no-fill-without-a-record invariant on the one path built to restore it. Retained rows make the two paths symmetric: a late fill within the ledgered quantity journals as a detached append; one beyond it trips the overfill arm, on either path. The mapping is ruled here, from `validate_exec_record`'s existing names, and it is keyed on the ORDER's own status rather than on the event's class name (amended after the whole-branch v2-native sweep): `_ADOPTED_TERMINAL_STATES`, the one map both this path and D7's startup pass write through, proven total over the library's declared closed set. An order event is applied to the order and to the Cache BEFORE it is dispatched — measured against a real engine, and that measurement is what the fixture derives rather than asserts — so the status is the settled answer to what the event did. Keying on status buys a totality proof a class name cannot express, and it is the more truthful answer wherever the two disagree: they disagree exactly when the state machine REFUSED the event and it was published anyway, and a stale `OrderExpired` landing after a cancel this engine asked for and got would otherwise write `venue_canceled` permanently over a row that was `canceled`. `canceled` still makes **no we-requested claim** — the dominant real source is a cancel this very process sent from the adopt pass or a trip, whose ack now arrives matched. Every OPEN status falls through untouched, so `OrderCancelRejected` needs no special case: the order is still resting, and the row keeps pointing at it. A side effect worth its own assertion: the adopt pass's cancel acks now **close** their rows, which previously stayed open forever and re-read as possibly-live on every future scan. **The state write is not unconditional: a row already reading `"filled"` is never demoted** (amended after the whole-branch review) — completion is inferred from the LEDGERED quantity, so the venue's order can outlive it and be canceled afterwards, the commonest shape being the adopt pass's own cancel of a non-reducer opener that fills its ledgered quantity in the race; and nautilus publishes REPLAYED terminal acks too (an event the order's own state machine refuses is published anyway — the duplicate-fill and overfill guards cover fills only). Either way the demotion is permanent, because a terminal row never re-attaches, and it contradicts an `_inc_order("filled")` already counted: exactly the counter-vs-record disagreement `_publish_fill`'s docstring forbids. The event still appends — it is evidence. The write that does land is **mirrored into `self._attached`'s row** for the same reason D7's repair mirrors its own: the completion guard and the sweep both read that state, and a stale one makes them reason from a row the ledger has left behind.
- Other events (`OrderAccepted` re-acks etc.) → row event append only.

### D3 — unmatched external events are counted and logged, never acted on

`zcrypto_exec_external_events_total{disposition="matched"|"unmatched"}` (counter), plus one info-level log line naming event type, instrument, and client order id. This is deliberately the **only** instrumentation of externally-originated activity: it makes a hand settle's existence visible in forensics with zero behavioural coupling — and it INSTRUMENTS the question T0142's second next-step wanted a probe-window measurement for (whether external acts are visible to this process at all) rather than answering it: whether Kraken's settle-position act emits an order event on the adapter's streams has never been measured, and the measured basis above covers reconciled ORDERS' publishes only. The counter is what takes the reading at the first settle, which is why the probe window's verify step queries the family — a rise means the settle reached this process and was correctly ignored, a flat counter means it did not, and either is the answer that sub-item wanted. Metric lifecycle obligations travel with it, and one has a converge consequence: the capture role's `config.alloy` keep-regex **enumerates families with no wildcard**, so `zcrypto_exec_external_events_total` must join it — which makes this change touch `roles/capture/files/config.alloy`, and per `capture-deploys.md` the engine converge that ships this image must run `--tags capture,engine` with both currently-running digests, never `--tags engine` alone, or the family publishes unadmitted and silently. Also: the Alloy pin test's hand-pinned name list, a dashboard target on `engine-dashboard.json` (the charted-family guard enforces this), HELP text with no internal tokens, and eager registration at 0 for both label values so `increase()` is never blind to a first event (the counter is registered at startup, not born on the event — the venue-not-online lesson inverted deliberately: here presence-at-zero is correct because the family must exist before any external event does).

### D4 — lifecycle and wiring

Subscription established once, where the strategy's own handlers are wired (`node.py` / executor start), against the topic string derived from `StrategyId("EXTERNAL")` through the same format the engine uses. The handler is defensive in the `on_order_event` idiom: wrapped, logging on internal failure, never raising into the event loop. **Neither path removes rows from `_attached`** (amended after Task 2's review — the earlier external-pop ruling re-created the race this very paragraph names) — a late fill after a cancel ack must land as a detached append, and popping at the ack would send that fill to `_trip_on_fill`'s no-attachment branch and latch the kill on a routine late fill (the existing `test_a_late_fill_on_a_superseded_order_shrinks_the_next_resubmission` pins exactly this). No new venue calls anywhere.

### D7 — the adopt pass reconciles each row against venue truth, because the subscription cannot reach backwards

D1's subscription closes exactly one window: fills arriving **after** the adopt pass has attached the row. Three others stay open, and the measured basis above is why:

- **The down-window** — the venue fills while the process is down. Reconciliation replays the fill on `events.order.EXTERNAL` before `on_start` subscribes; nobody hears it.
- **The pre-adopt window** — a fill arriving between `on_start`'s subscribe and the first adopt tick finds `_attached` empty, is counted `unmatched`, and is dropped. It **is** bounded by `_TICK_SECONDS`: the subscription is installed after both the startup cycle and the timer, not before — so the synchronous startup cycle lengthens the down-window above, never this one.
- **The closed-while-down order** — one that fully filled, was canceled, or expired while the process was down is reconciled into the cache as CLOSED, so it never appears in `orders_open`, is never attached at all, and its ledger row stays open with a stale quantity forever.

None of these is created by this spec; all three predate it (the adopt pass's body is untouched by this branch). But D1–D4 make claims — "a matched fill appends to its row … exactly as an own order's fill does", the completion write that stops a row reading open forever — that are only true of the first window, so the record would overclaim unless the rest close too. They also newly matter: the external-path overfill trip now reasons from `row["filled_qty"]`, and an undercounted base makes it **under**-fire (it can never false-fire).

**The ruling: before it classifies anything, the adopt pass reconciles every ledgered row it can match to a cache order against that order's own `filled_qty`.** The reconciled order carries venue truth for every fill applied before this process could hear it, which is precisely the union of the three windows.

- **Matching widens from resting to ALL orders the cache holds for the venue.** `orders_open` is the classification population — which orders may keep resting — and it stays exactly that. Reconciliation needs the wider read, because the closed-while-down order is by definition absent from the open one. Consequently the pass no longer returns early when nothing is resting: a startup with zero resting orders can still owe row repairs. The wide list is indexed by client order id and the **rows** are iterated, never the orders: the cache holds no previous session's state (no cache database is configured) but the venue's mass-status read is `open_only=False` with no lookback bound, so that list can be the account's entire closed-order history.
- **The comparison takes exactly one of four arms, on a dead-band of `_OVERFILL_TOLERANCE`.** The ledgered figure is a SUM of per-fill Python floats and the venue's is one exactly-rounded `float(Quantity)`, so a clean multi-fill restart differs by ulps and **must be silent** — a repair arm without the dead-band would journal a phantom repair and a WARNING on every clean restart:
  - `|delta| <= _OVERFILL_TOLERANCE` — no repair, no event, no log.
  - `delta > _OVERFILL_TOLERANCE`, total within `_ordered_qty(row) + _OVERFILL_TOLERANCE` — journal the repair, mirror it, and complete the row if it reaches the ledgered quantity.
  - `delta > _OVERFILL_TOLERANCE`, total past the ledgered quantity — journal the repair FIRST, then trip: the fill happened, and no-fill-without-a-record has no divergence exemption.
  - `delta < -_OVERFILL_TOLERANCE` — trip, with a reason naming both figures and the direction. The ledger claiming more filled than the venue reports is divergence in the dangerous direction — it makes the engine believe it reduced more than it did — and it is the same class the per-order trip already guards. Clamping it to zero would swallow the signal.
- **A repair is journaled as a repair, not as a fill**: `update_submitted_row(..., add_filled_qty=delta, event=<a reconciliation payload naming the delta and the venue-truth total>)`. It is deliberately **not** published to the fill/fee counters — there is no per-fill detail and no fee behind it, and a fills increment with no fee would make the two counters disagree in a way the ledger row cannot explain. The row is the authority; the repair is visible there and in a WARNING log line, the primary debugging surface. One knock-on is named rather than discovered later: `_publish_fill` is also what admits an instrument to `self._traded`, the domain of `_realized_eur()`, so a leg whose only fill happened while this process was down does not enter the realized-PnL gauge until it fills live again. The position gauge is unaffected — it is seeded from the newest `venue-<HH>.json`.
- **A repair that completes the ledgered quantity writes `state="filled"` and counts `_inc_order("filled")`**, by the same arithmetic and the same once-only guard the D2 completion uses — otherwise the repair would restore the quantity and still leave the row reading open, which is the defect it exists to fix.
- **The terminal-state write for a CLOSED order is INDEPENDENT of all four arms** — an order canceled while down with zero fills is the commonest closed-while-down shape, and it has no delta at all. It is written from the total `OrderStatus → execledger._ROW_STATES` map `_ADOPTED_TERMINAL_STATES`: `FILLED → "filled"`, `CANCELED → "canceled"`, `EXPIRED → "venue_canceled"`, `VOIDED → "venue_canceled"`, `REJECTED → "rejected"`, `DENIED → "rejected"`. There is exactly ONE such map and D2's live path writes through it too — a status key reaches what no event could, the commonest closed-while-down shape being a cancel with zero fills that publishes no event this process is alive to hear and leaves no quantity delta to notice it by. Any status outside the map leaves the state untouched rather than minting one: `_store` refuses a state outside `_ROW_STATES`, and a raise here would cost the classification pass. `canceled` makes no we-requested claim on this path either — nothing at startup can tell a venue cancel from one the previous process sent.
- **The repair writes `self._attached[client_order_id]` itself, and mirrors `state` as well as quantity.** Attaching in the sweep rather than mutating a dict the classification loop happens to reuse is what puts a CLOSED order's row in the map too, so a late duplicate or racing event for it lands matched rather than counted as a hand settle; and mirroring the completion's `state` keeps `_on_external_event`'s once-only guard reading the true state rather than a stale one.
- **A ledger failure may never cost the classification pass.** The sweep is wrapped PER ROW — `_record_trip_fill`'s precedent — logging CRITICAL with the client order id and continuing to the next row, and wrapped again as a whole, falling through to the classification loop. A trip on one row does not stop the sweep: the remaining rows still get their repairs. This matters because the sweep introduces raising calls the pass never had, and `_adopted` is set before it: an escape would leave a previous process's resting opener working at the venue, uncanceled and unattached, for the life of this process.
- **Idempotence is structural, not asserted**: the pass runs once per process (`_adopted`), reads each order's `filled_qty` exactly once, and journals a difference — a second restart sees a delta of zero. Double-counting against the subscription is impossible because the apply and the publish share one synchronous body on one event loop: any quantity resident in `filled_qty` at snapshot time was published at or before that snapshot, so it was either never delivered or dropped unmatched; any publish after the snapshot carries quantity the snapshot did not contain.

What this does **not** cover, stated rather than implied: a row whose order the cache holds no record of at all (never reconciled — the venue no longer reports it) is left exactly as it is. There is no venue-truth source for it at this point in startup, and inventing one would be worse than an open row a human can read.

### D5 — resolution is at merge; the deploy rides the standing converge cadence

The engine is live but **disarmed** (`exec_armed` renders `false`): submission happens only inside attended windows, where a restart is an abort, so the defect this spec fixes cannot fire in production before the fix deploys. T0142 resolves when the routing is decided (this spec), implemented, proven at the library boundary, and merged with both doc surfaces moved — the image change reaches the engine at its next canary-gated converge per `capture-deploys.md`, and the engine's payload proof is, as always, its next disarmed boundary cycles. No special converge is owed, and holding the topic open for an unschedulable live scenario (restart + resting reducer + fill) would repeat the `ripe_when` trap T0145 closed.

## Verification

- **The library boundary is proven with the real message bus, not a mock of our own assumption**: a test constructs a `MessageBus`, publishes a genuine `OrderFilled` on the topic the *installed engine's own format* produces for `StrategyId("EXTERNAL")`, and asserts the handler received it. This doubles as the tripwire for the pending nautilus bump (PR #270): if a future version renames the topic or stops publishing external events, this test — not production — is where it surfaces.
- Constructed-event tests (the repo already constructs real nautilus fills — `venuestate.py`'s precedent): matched fill → row append + counters; matched overfill → kill trip latched, fill still recorded; unmatched fill → counter increments, log line, **no** row, no trip, no cancel; terminal event → row terminal + detached.
- **D7 meeting D1 is pinned as one sequence, because that is where a mis-mirror costs money**: the sweep repairs a partial, then an external fill for the remainder arrives — the row reads the full ledgered quantity, state `filled`, `_inc_order("filled")` exactly once, no trip. Double-mirrored, that fill overshoots and false-kills; unmirrored, the completion never fires. Its mirror is pinned too: after a repair completes a row, a later dust fill trips.
- **D7's four dispositions are each pinned against a constructed adopt pass**: a positive delta journals and mirrors; one that completes writes `filled` and counts it once; one that overshoots trips; a negative delta trips. The closed-while-down case is pinned end to end — a row whose order the cache holds only as CLOSED is repaired AND given its terminal state, from a startup where `orders_open` is empty, which is the case the pre-D7 early return could not reach.
- The existing suite pins the own-topic path unchanged; the trip's own tests must pass untouched.
- Both counter label values present at startup (eager registration test), HELP swept by the operator-facing-text test, Alloy pin + dashboard target guards green.
