## Decisions

### D1 — every scenario is a PROCEDURE section with the same seven parts

*What this proves* · *Preconditions* (window, host, tier gate) · *Induce* (exact commands or instrument) · *Must fire* (which alert or dead-man, on which channel, within what bound) · *Operator action* · *Record* · *Retire when*. The seven parts are this decision's own: `00104` D7 set the four-part base for every kind, and `infra/runbooks/README.md`'s PROCEDURE row defers here for a drill's shape rather than restating it — so this line defines them, and the plan's Global constraints carries a verbatim copy for the task implementers who work from the plan alone: this line is the authority, that one the copy. The bound is **derived, never guessed**: a Grafana rule's `for` plus its group's evaluation interval, **plus Prometheus staleness (~5 min) wherever the condition cannot go true until the series goes stale** — the `count(up{…}) or on() vector(0)` silence shape every `zcrypto-alloy-dark-*` rule carries, where `for` + interval alone understates the real notice by a third and the rule's own comment in `infra/grafana/alerts.yaml` states the ~15 min it actually is; a healthchecks check's timeout plus grace. The `Retire when` is checkable as the runbook README demands; for a drill it is usually "the code path it exercises no longer exists" — and for Q, deliberately, never.

Two files, split by tier so neither crosses the README's ~12-section bar: `drills-telemetry.md` carries C, C′, I, J′, K, O, P+R, Q and one section stating when the **proven** tier — F, H, J, L, M, N, T — is re-verified: only when the code path it proved changes, with the incident or drill that proved it cited. **N is due now by that rule**: its proof was the 2026-07-15/16 incident and [[T0048]]'s fix changed the Alloy path it fires through afterwards, so N re-runs in this iteration's windows. Two items from the original T0049 matrix are dropped with their reason written in that section: the reboot-window overlap check (both capture hosts have been attended-reboot since [[T0027]]'s flip, so no automatic windows can overlap), and drills for [[T0039]]'s phantom-splice guard and [[T0043]]'s lost-trades detector (code guards with tests, not fleet failure scenarios). `drills-order-path.md` carries A1, A2, B, D, E, F2, G. Both join `infra/runbooks/README.md`'s index under their own headings.

**Inducing a fault on live capture happens only inside an attended window, never inside a published Kraken maintenance window**, and the primary's capture daemon and Alloy are not touched by any telemetry-tier drill in this iteration (`fleet-deploys.md`; spec `00104` D7 homes the gate).

### D2 — the drill log is Markdown, one run per entry, lightly tested

`docs/reference/drill-log.md`: `## <YYYY-MM-DD> — <scenario id> — <pass | fail | partial | blocked>`, then one paragraph with labelled clauses — *host* · *induction* · *time-to-alert* (with the three timestamps where a Slack path is involved: rule `activeAt`, message, device) · *channels* · *operator action* · *follow-ups* (a `T<NNNN>` or an explicit drop). `tests/test_drill_log.py` asserts only the heading shape and that dates do not decrease. **`blocked` is a status, not prose**: it is the outcome when the induction never landed — a precondition refused it (J′'s or O's not-green check) or the instrument did not take (no line in Loki for Q's `logs` path) — and the reason is then a required clause. It exists because the alternatives are both false records: `fail` asserts a guard did not fire when nothing exercised it, and `partial` asserts a run that half-happened. The master plan's artifact list names this file at closeout.

### D5 — the alert and the procedure no drill can supply

- `zcrypto-engine-dark-with-exposure` (critical): `zcrypto_exec_position` non-zero at last sight and the engine's scrape not answering — the plan pins the expression against `up{job="engine_app",host="zcrypto"}` — the job is scraped on both capture hosts and reads 0 on `zcrypto-red` by design — and the gauge's staleness. **The scrape half is read by VALUE, never by presence**: `engine_app` is a static scrape target, so the `up` series stays present at 0 while the engine container is gone, and the `count(up{…})` shape the `zcrypto-alloy-dark-*` rules carry — where presence *is* the signal — would read 1 and hold the rule inert through exactly the event it exists for. An aggregation that reads the value (`min`) with the same `or on() vector(0)` fallback trips on both darkness routes: the exporter dead at `up = 0`, and the primary's Alloy taking the series away. **"At last sight" is an explicit bounded lookback, never an instant read**: the gauge publishes from the very scrape target the other half requires to be gone, so an unlookbacked `zcrypto_exec_position != 0 unless up{…}` returns nothing the moment staleness expires and the rule can never fire — a state indistinguishable, at a first sample taken while the engine scrapes normally, from a rule that works. The lookback is therefore also the page's horizon: the alert self-resolves when the last position reading ages out, while the engine may still be dark and the position still open, so it is sized to outlast a full daily ops pass and the section states in those words that a resolve here is not an all-clear. The plan pins the whole expression, that lookback and `noDataState`. Runbook section in `engine.md`; the response is B. Pushed after its inputs exist, first sample verified by value — and what makes them exist is the shape, not the fleet's current state: `up{job="engine_app"}` is a static scrape target, while `zcrypto_exec_position` is a per-symbol labelled gauge that publishes no series at all until a position is seeded from the journal, and an engine that has never held one journals nothing to seed from — so the position half's `or on() vector(0)` is load-bearing for the no-data question and not only for the arithmetic.
- `observability.md#grafana-cloud-dark` (PROCEDURE): for the duration rely on the dead-man domain and the daily pass's direct healthchecks read (`00104` D4), `docker logs` on hosts, `exec-status` on the engine host; on return, the list of rules blind to a condition already present at first sample, re-verified by value; the permanent-loss statement per plane — drill C's **measured** half (what a restarted shipper replays, and its `max_age` ceiling) beside the Cloud-dark half **derived** from `config.alloy` (remote_write's WAL against `loki.write`'s absence of one), each labelled which it is, because a stopped shipper and a dark destination lose opposite planes; the page bound from C′.

## Verification

- Every telemetry drill has a drill-log entry with measured times and a runbook section or amendment; no result lives only in a report. **Q is the one exception and by design**: its three paths ride K, I and its own `logs` induction, so its readings land in those three entries and its cross-path summary is its runbook section rather than an entry of its own.
- `tests/test_drill_log.py` bites on a malformed heading (mutation probe).
- The alert's first sample is read by value; the guard's `for` and interval are quoted in the section's bound.
- `zcrypto-engine-dark-with-exposure` is proven to **discriminate**, because the first-sample read cannot: a replay test over the `(position, scrape)` pair asserts it fires on exposure-plus-dark-scrape, stays quiet on a dark scrape with a flat position and on a live scrape with exposure open, and still fires one evaluation before the lookback horizon — with two controls that replay the true positive through a defective form and see it stay quiet, so the simulation is shown to move on each defect rather than passing everything: the unlookbacked form, and the presence-counting form, which also forces the replay to model a dark scrape as `up = 0` **present** rather than as an absent series.
- The order-path sections are dry-read against the probe procedure by a cold reviewer: every command resolves, every expected ledger value names its field.
