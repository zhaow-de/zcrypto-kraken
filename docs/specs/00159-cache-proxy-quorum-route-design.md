## Intent and the measured defect

The engine reaches the cache set through one HAProxy 3.4.5 container on its own host, `zcrypto-cache-proxy` (`infra/ansible/roles/engine/templates/haproxy.cfg.j2`). Today a session's life is tied to the reachability of ONE Sentinel, possibly the remote one, although the session's own path (the engine host to the in-region primary) and the Sentinels' 2-of-3 quorum are intact. This spec unties the two: a session is cut only when the Sentinels the proxy can read contradict the node it sits on, and a new session goes only where two Sentinels point.

What marco measured on 2026-11-11 between 11:33Z and 11:45Z from the observability node, carried here as read and not re-read:

- Since 2026-11-08 the proxy logged 36 server-DOWN lines; 24 are `node2/via-node3`, every one `Layer4 timeout, info: " at step 1 of tcp-check (connect)", check duration: 1000ms` or `1001ms`, each back UP 2 s later with a 28 ms check; 22 of the 24 since 05:48Z of 2026-11-11, 9 in hour 07Z; `haproxy_server_check_failures_total` reads 83 on `node2/via-node3` and 0 or 1 on every other route.
- valkey3 the host was healthy over the same 6 h: load ≤ 0.34, 537 MB available, CPU steal about 0, no interface drops, every WireGuard handshake age ≤ 121 s on every pair; Linode's public incident feed lists nothing since 2026-11-08. The Sentinels on valkey2 and valkey3 marked each other `+sdown` at 08:46:51Z and 09:01:04Z, cleared within 2 s under `down-after-milliseconds` 5000, and valkey1's Sentinel logged nothing. The trigger is short packet-loss bursts, 2 to 7 s, on the inter-region path to valkey3, per pair.
- The cost: the proxy's connection log shows sessions cut (`DC` termination) three times since 2026-11-08 — 2026-11-09 07:35:30Z, BOTH engine sessions on `node1/via-node3`, cut by a `Layer4 timeout` on that one check while the backend kept 2 of 3 servers, the primary and the quorum intact; 2026-11-09 17:23:44Z, one on `node1/via-node2`, `Layer7 timeout`, around a failover from node1 to node2; 2026-11-10 21:33:26Z, at the engine host's own reboot. After a cut the library reconnects only on its next write, which it drops, so the first cache write of the next boundary is lost and `zcrypto-engine-cache-write-failed` pages, as it did at 2026-11-09 16:02:40Z and 2026-11-11 00:02:40Z after valkey3's 17:25Z reboot slot. The day's 22 flaps cut nothing only because no session sat on `via-node3`; sessions are spread over the three server lines at connect, so any engine restart can put one there.

The defect has two parts, both read in the 3.4.5 source (*The constructs, read in 3.4.5*):

- **The check's connect budget is 1 s.** A check connects within min(`timeout connect`, `inter`), so today's `inter 1s` under `timeout connect 2s` gives 1 s, equal to the kernel's first SYN retransmit: one lost SYN fails a check, two failures in a row (`fall 2`) mark the line DOWN.
- **The cut is per server line.** `on-marked-down shutdown-sessions` acts on the one server that fell; a backend has no quorum form of it. Each backend's three lines are the same Valkey address checked through three Sentinels, so the line that falls takes the sessions placed on it. The same shape leaves a hole: a session on a partitioned primary's own Sentinel line is never cut by the proxy, since that Sentinel still names it.
- Beside them, a wording fault: 00120 D1 and `infra/runbooks/cache.md` say the default balance is roundrobin; 3.4's default is `random` (manual: "set to "random" when no other algorithm, mode nor option have been set").

## Goals, non-goals, anti-goals

Goals:

- One Sentinel's reachability — a loss burst, a reboot, a Sentinel restart, a converge on its node — never cuts an engine session, whichever node is down beside it.
- A real failover still cuts the old primary's sessions promptly, and a partitioned old primary loses every session the proxy carries to it, wherever it was placed.
- A new session goes only to a node two Sentinels name, as today.
- The route survives any one node or Sentinel down, the daily reboot slots at 09:25, 13:25 and 17:25 among them.
- The configuration is proven on the pinned HAProxy 3.4.5 binary on this workstation before rollout, its result recorded.
- The page that says the proxy routes nothing, and the panel it links to, read the new routing rule exactly.

Non-goals:

- The loss bursts themselves: why the inter-region path to valkey3 drops packets is the coordinator's attended work on the owner's word (D8) — a two-layer probe run on valkey3, its reading going to the owner — and not by raising it with Linode; this spec names no file for it. This change makes the proxy tolerant of the bursts; it removes none of them.
- The library's lazy reconnect, which drops the first write after any cut; the engine's retry budget (00120 D5); Sentinel's own timers; the cache nodes' configuration.
- A flags-aware Sentinel expect, set aside for good in 00120 D1.
- Running the harness in CI.

Anti-goals, what the change must not do:

- Route a new session on fewer than two Sentinel votes.
- Cut a session because one Sentinel cannot be reached.
- Raise `timeout connect`, which is also the proxied connects' timeout.
- Change the Sentinel exchange the check runs — `AUTH`, `PING`, `SENTINEL master` with the anchored expect and no `QUIT` — which 00120 measured.
- Add a moving part outside the proxy container, or touch the engine image, the cache nodes or the Sentinels.
- Print the Sentinel `requirepass`: the rendered file carries it, and the harness renders a dummy.

## Decisions

**D1. Each node gets votes and a route: a votes backend of three check-only servers, one per Sentinel, which no session rides, and a route backend of one server, `valkey`, which carries the engine's sessions and is health-checked against a loopback `frontend quorum`; `on-marked-down shutdown-sessions` sits on the route server alone.** The owner's ruling, 2026-11-11, on three asks marco put — (1) which option: the redesign under this serial with the skeptic's refinement, tolerance only, or an interim budget change followed by the redesign, marco recommending the redesign with the refinement and no interim; (2) whether the configuration may be verified against a real HAProxy 3.4.5 on this workstation before rollout; (3) whether the loss bursts themselves are pursued — verbatim: "1 as recommended, yes to 2, pursue the loss bursts investigation but raising it with Linode does not seem like an option as none of the other services got impacted while in the end it is just a service listening on a TCP port like any other services we created at and deployed to the fleet." Why this shape: the only server that carries sessions changes state on what the quorum frontend answers, and the quorum frontend reads the votes as a count, so a session's life follows the Sentinels' agreement and no single Sentinel's reachability. No session rides a vote: a session enters by `frontend cache`, whose routing lines are its three `use_backend` lines, each naming a route backend, which `test_a_new_session_routes_only_on_two_votes_and_an_up_route` pins exactly; `frontend quorum` answers every request itself, its lines pinned by `test_the_quorum_frontend_answers_503_only_on_a_contradiction`, and `frontend metrics` serves the exporter; and *The template* carries no `default_backend`, nor a server-state file or a runtime socket that could set a server's state — `awk '/^## The template$/{p=1;next} /^## /{p=0} p' docs/specs/00159-cache-proxy-quorum-route-design.md | grep -c -E 'default_backend|server-state|stats socket'` printed `0`. Set aside: the judge's design 1 as written, which cut on quorum LOSS (`/nodeN` 200 only while two votes pass) and so, in every window with an in-region node down — the daily replica reboot, a Sentinel restart, a converge there — tied both sessions to the remote Sentinel alone, a 4 s burst cutting both while the session's path and the quorum stood (the skeptic's Important); design 2, one-line tolerance (`timeout connect 8s`, `inter 8s`, the per-line cut kept), which removes the burst cuts only, keeps a one-in-three cut on every reboot and Sentinel restart, keeps the partition hole, and gives proxied connects an 8 s connect timeout; design 3, in-region placement under `balance first`, which moves the cut onto the in-region replica's reboot and makes it certain; the interim budget change, which costs two gap-bound engine restarts for the same end. Constructs that cannot carry the design: `track` follows one server and refuses `init-state`; one `tcp-check` across the three Sentinels stops at its first failed step, an all-of-three check; switching rules alone never cut a session, since a stream's backend is chosen once (`process_switching_rules`).

**D2. The contradiction form: `/nodeN` answers 503 while another node holds two votes or nodeN holds none, 200 otherwise; the cache frontend routes a new session to nodeN only while nodeN holds two votes and its route server is up.** The form is the owner's ruling (D1's "as recommended", the skeptic's refinement); the rule text, its order and the 404 fallback are the author's. Why these two conditions and no other: they are the two facts that make a route wrong — a quorum naming another primary (a failover, a partition healed or not), or no Sentinel the proxy can read naming this node (the engine host cut off from the set). The quorum frontend reads nothing but the three `nbsrv(votes-nodeN)` counts — its thirteen rules, which `test_the_quorum_frontend_answers_503_only_on_a_contradiction` pins in order — and for a node's path its two 503 conditions and its 200 line partition every value those counts can take: another node at two or more, this node at zero, or this node at one or more with no other node at two or more. One vote, or two lost to reachability, is no evidence the route is wrong, and cutting on it is the defect. No route can open early: the cache frontend's `ge 2` holds it until two votes pass. No session can be cut while the votes rise: node2/valkey falls only on v1 ≥ 2, v3 ≥ 2 or v2 = 0, and while the three Sentinels name node2, v1 and v3 stay 0 and v2 only rises. With one Sentinel unreachable at the start the route opens at the second vote all the same; with two unreachable, node2/valkey rises at the first vote but no route opens, the engine's start exhausts its retry budget and the unit restarts it ten seconds on, as today with one line passing.

## The harness

- **What runs the binary.** The pinned image's own `haproxy` and shared libraries, unpacked from the image's `linux/amd64` layers, run through the image's own dynamic loader with an explicit library path into the unpacked tree, inside an unprivileged user and network namespace (`unshare -rn`, loopback up): no Docker, no root, no listener outside the namespace, no packet leaving it. Before it binds a port or writes an `nft` rule it reads the namespace's interfaces and refuses unless `lo` is the only one (the plan's `test_the_run_refuses_a_namespace_with_any_interface_but_lo` holding the predicate; *Operating model* for what a fresh namespace lists here), so a run that failed to enter a fresh namespace touches nothing on this fleet host. It calls `nft` as `/usr/sbin/nft`, which is off this user's `PATH` here (`command -v nft` prints nothing). `haproxy -vv`'s first line must name 3.4.5.
- **How it gets the binary.** `uv run python infra/scripts/cache-proxy-harness.py fetch --digest sha256:<the cache-proxy pin> --into <dir>`: the index by that digest from Docker Hub, anonymously, its sha256 checked against the pin, the `linux/amd64` manifest, each blob checked against its sha256, the layers applied in order with their whiteouts into a new empty directory, no member, hard link or whiteout reaching outside it — the six escape forms of the plan's `test_the_fetch_writes_no_member_outside_its_tree` holding it, a form they lack being a new id there. The fetch is a network read, so the coordinating session runs it once, into the branch worktree's `.tmp/00159/haproxy-76928c0d6b39/`, before the harness task; the implementer and every later run work offline against that tree, and nothing Python is run from inside it.
- **The configuration it runs.** The role's own template rendered with the role's Jinja settings, the three nodes at `127.0.0.11` to `127.0.0.13` (each the length of a mesh address, so the anchored expect's length marker reads 10 as on the fleet) and a dummy `requirepass`, then four named line changes and no others: the `global` section's `chroot`, `user` and `group` lines dropped, three lines, since the namespace maps one user and has no `/var/lib/haproxy`; and `bind 0.0.0.0:6379` made `bind 127.0.0.1:6379`, one line, since a wildcard listener on 6379 would collide with the scripted Valkeys on the same port. Every other line is the role's render, and every case, `parse` among them, runs this render: the shipped one, with its `global` lines and the real `requirepass`, is first parsed by the converge's preview (*What it cannot show*). No case needs a fifth change: each fault is injected by the scripted peers and the namespace's `nft` rules, never by the render.
- **Scripted Sentinels and Valkeys.** Three Sentinels, one per address on 26379, each answering `AUTH` with `+OK`, `PING` with `+PONG` and `SENTINEL master zcache` with the RESP2 array 00120's measured basis records, its `ip` field the node the script names; each can be switched to name another node, to refuse (its listener closed), to go silent (its packets dropped by an `nft` rule in the namespace), to hold its `SENTINEL master` reply past `timeout check` on the connections it accepts inside a window the harness names, or to have every connection made to it lose its first SYN and no other (an `nft` rule dropping a SYN whose source port its set has not seen, adding the port, so the retransmit passes). Every `nft` rule a case writes sits in the case's own table, deleted at the case's end (*Operating model*, *The harness's processes*), so `no-early-route`'s still-silent Sentinel and `no-vote-cuts`' three are not silent in the case after. Each Sentinel records when each connection to it opens, gets its master reply and is closed by the client. Three Valkeys, one per address on 6379, accepting sessions and answering `PING` with `+PONG`, so a session's survival is read as a reply and its cut as an end of stream.
- **The bounds.** Every timed case passes on the source's worst case plus a margin of 1.0 s, and prints its measured figure beside its bound. The worst cases are the timer counts of *The scenarios, walked*, from the source rows of *The constructs*: a vote failing on a silent Sentinel rises at most 3.0 s after the silence ends — a check started up to 2 s before the end can still time out at its 2 s budget as its second retransmit lands, then `downinter` 1 s and `fastinter` 1 s; a vote waiting out a reply naming another node rises at most 4.0 s after its Sentinel switches — a 2 s `timeout check`, `downinter` 1 s, `fastinter` 1 s; a vote at full health falls at most 7.0 s after its Sentinel goes silent or switches — `inter` 2 s, a 2 s budget or `timeout check`, `fastinter` 1 s, 2 s again; a route falls at most 0.5 s after its path turns to 503 and rises at most 0.25 s after it turns to 200. ```

## Failure modes

- **The quorum frontend fails.** A misrender or a wedged worker takes every route down within 0.5 s, or about 4.3 s on a stall, cutting every session; the page reads 0 and fires after two minutes, the runbook's step 2 naming it. The tests pin the frontend's text and the harness runs it; a stall the 32m cap causes is read at the rollout by `docker stats` and afterwards by the route's failures counter.
- **A stray loopback failure.** One is absorbed by `fall 2`; two in a row cut both sessions and cost a write. `haproxy_server_check_failures_total` on the route server stays 0 outside cuts, or this is happening.
- **The failover's overlap.** For 0.25 to 0.5 s after the new primary's second vote the old primary's route is contradicted but not yet down, its rule still matching: a new session opened then goes to the old primary and is cut at the fall (D4's `inter 250ms`, `fall 2`). Then the old primary's stale votes contradict the new primary's route until they fall, so new sessions have no route until 5 to about 7.3 s after the switch, about 1 to 6 s longer than today where the new primary's rule comes first; a write in those seconds is dropped (Q1).
- **A session kept on a primary the proxy reads at one vote.** The engine host cut off with the primary, or both replicas gone: both sessions stay, and the node accepts their writes until its once-a-second cron finds no replica ACK within `min-replicas-max-lag`'s 10 whole seconds, 9 to 12 s on — this bullet's Valkey timings, the demotion's close and the full resync all readings of Valkey 9.1.2's source, not run — then refuses them, paged by write-failed, the page firing after two minutes. With both replicas gone no Sentinel majority promotes another node, and on recovery the kept sessions write again with no reconnect write lost. With the engine host cut off together with the primary, if the partition outlasts the Sentinels' 5 s `down-after-milliseconds` and the two beyond it promote another node, every write the primary accepted since the partition, up to 9 to 12 s of both sessions', is acknowledged and then lost at the heal, the primary taking the new one's data whole as its replica; the heal's demotion closes the kept sessions, so the next write fails and pages. Today the same loss is 3 to 4 s on two placements in three, cut by their per-line checks, and 9 to 12 s on the third. D2's ruled trade (Q1).
- **A split no quorum resolves.** Each node named by one Sentinel: no route is contradicted, open sessions stay where they are, nothing new routes, the page fires; a session left on a replica is refused its writes by the node.
- **Vote failures by class.** A burst under about 4 s fails at most one check of a vote; `L7TOUT` counts data loss after a handshake as well as a mismatched reply, so the failures counter reads wider than lost SYNs alone, and the board's code panel tells the classes apart.
- **Warnings unseen.** The role's `haproxy -c` passes warnings silently, being run without `-dW`; the harness reads them at the pinned version, and only there.
- **Series.** Twelve servers and six backends in place of nine and three: about a third more `haproxy_server_*` series on the observability node's Prometheus.
