# 00090 — the rung-1 order path: the probe executor, the maker-first state machine, and the engine's first real submission

Fourth spec executed in the 6b build — third of [[T0018]]'s five-spec risk-first sequence — after `00088` (the execution safety envelope, live on the engine since 2026-08-12), `00089` (venue truth, deployed 2026-08-16), and `00094` (the /BTC twelve-leg widening, deployed 2026-08-16, run ahead of this spec by the owner's [[T0137]] sequencing ruling). This is the first spec with monetary blast radius: **real money, ~€10–30 per leg**, and everything in it is refusal-by-default — every path from an error, an ambiguity, or an absent input ends in "no order", and nothing here widens any `00088` floor (the restart hold still clears only by a human act; later specs may narrow that, never widen it).

## Context — what exists, what rung 1 is, and what the installed adapter can actually emit

Measured on the working tree and the installed `nautilus-trader 1.230.0` (`.venv`), not carried from prior specs:

- The deployed engine is an authenticated trading client behind a proven-but-unconsumed gate: `cli/engine/execgate.py::ExecutionGate.evaluate` computes `none | reduce_only | full` with plural `reasons`, `cli/engine/execledger.py` journals a per-cycle `exec-<HH>.json` with a `submitted: []` key reserved since schema 1 — and `grep -rn 'submit_order' cli/ tests/` still returns **0**. The gate refuses correctly and restrains nothing; making it and the ledger **unavoidable** is this spec's first requirement, inherited by name from [[T0018]].
- **Rung 1 IS the §11 T2 tax probe** (master plan §12, amended 2026-08-02): ≥1 margin long + ≥1 margin short, each held across ≥2 rollover events (rollover recurs every 4 h a position is open — `docs/reference/kraken-fee-schedule.md`), one position closed, one settled; it proves the order path, fills, fees, rollover ledger rows, reconciliation and the tax pipeline in one pass, and supplies the first measured maker/taker blend to [[T0090]]'s cost re-pricing. The execution style is already ruled — maker-first with a taker fallback (owner, 2026-08-03) — rung 1 measures the realized blend, it does not re-decide the style.
- **The model book cannot be rung 1's driver**: 0 of 801 journaled intended orders clear Kraken's `ordermin` at tiny-live size (measured 2026-07-30, [[T0119]]), and the probe's trades (two directions, leverage, held across rollovers, one settled) are nothing the model would ever emit. The probe is operator-authored by construction.
- **The installed adapter's submit path, verified in source** (`nautilus_trader/adapters/kraken/execution.py`, pyo3 stubs): `Strategy.submit_order(order, params={"leverage": N})` flows `SubmitOrder.params` → `_parse_leverage` (int, 0–65535, else the order is DENIED) → `KrakenSpotHttpClient.submit_order(..., reduce_only=, post_only=, leverage=, account_type=)`. `reduce_only` is denied under `spot_account_type=CASH` and permitted under the MARGIN type the node already runs; LIMIT supports post-only and IOC (FOK is limit-only); fills arrive on the private executions WS as `FillReport` carrying `commission` and `liquidity_side` — the exact two fields the fee ingestion and the blend measurement need; positions reconcile via the quote-agnostic `OpenPositions` branch. `default_leverage` stays **unset** per the [[T0120]] ruling — `None` means cash, and rung 1 passes leverage per order, exactly as that ruling prescribes.
- **The adapter cannot emit Kraken's settle-position** — `grep -rn 'settle' adapters/kraken/ core/nautilus_pyo3.pyi` finds no settle order type, no settle endpoint, nothing (the hits are unrelated `settlement_currency` fields and a Bybit `settle_coin`). Kraken settles a margin position in kind via its own `settle-position` order type, which charges **no trade fee** (fee schedule: fees on open and close, "none on settling in kind"). So the "settled" leg of the T2 set is **not emittable by this engine** and must be a manual venue action — a human gate below, not a code path.
- **Kraken feasibility fixes which leg settles**: settling in kind repays the extended currency from the wallet. The wallet holds EUR (~€100, funded at iter-079) and no crypto, a margin **long** extends fiat EUR (fee schedule: the quote leg is extended), so the long can be settled from wallet EUR — the purchased crypto then lands as a spot holding. A short extends the base crypto, which the wallet does not hold, so the short cannot be settled and must be the closed leg.
- One structural fact the state machine leans on: the 4-hourly cycle runs synchronously **on** the node's event loop (`ShadowStrategy._on_cycle_alert` → `run_cycle`, blocking), so executor timers, order events, and cycle journal writes are serialized on one thread — no file race between the sink's exec-record write and the executor's, and a probe that straddles a boundary simply waits out the cycle.
- The iter-079 adapter verification proved post-only rest+cancel (spot and margin, leverage 2, both sides), the crossing post-only's accept-then-venue-cancel surface, and one real ~€10 spot round trip. **`reduce_only` has never been exercised live** — the close leg is its first use, and the checklist treats it accordingly.

## Decisions

### D1 — Rung 1 submits operator-authored probe plans through the one real order path; the model book stays shadow

The deliverable is the order path itself — gate consultation, venue-truth precondition, sizing, the maker-first state machine, submission, fill/fee ingestion, reconciliation — exercised by **probe plans** the owner authors, sized ~€10–30 per leg. The cycle's intended orders keep journaling to `orders.jsonl` exactly as today; no cycle delta reaches the venue in this spec.

Rejected: wiring cycle-driven submission behind the gate now. It builds rung 2/3's loop inside the money-proving spec, its deltas cannot clear `ordermin` anyway (measured above), and [[T0018]]'s table assigns the full loop to `00092`. Rejected: a probe path that bypasses the future order path ("just submit two orders by hand through a script"). The whole point of rung 1 is that the machinery later rungs run on is what gets proven — a throwaway script proves nothing the deployable inherits.

### D2 — [[T0119]]'s `target − held` is OUTSIDE 00090 — ruled, with grounds

The delta formula is `00092`'s, not this spec's: [[T0018]]'s execution-order table names "`00092` — rung-3 accumulation — [[T0119]]'s `target − held`, skip-or-carry, the full loop" verbatim; the topic file itself says the formula is rung 3's mechanism and that consuming the held read is the fill-ingestion build item while "this topic owns the formula and its tests". And structurally, no delta is computed anywhere in this spec — probe intents carry explicit side/notional/leverage, so there is no call site for any delta formula to be right or wrong at. What `00090` delivers to T0119 is its prerequisite: fills flow into the Cache-backed position view and the journaled venue/exec records, so `00092`'s `target − held` will read a `held` that this spec has proven against real fills.

### D3 — The probe plan is a TTL-bounded control file, consumed by the executor inside the live node

`<engine_state_dir>/exec/probe-plan.json`: a JSON plan carrying `plan_id`, `created_at`, and a list of intents `{symbol, side, notional_eur, leverage, action: open|close, mode: execute|rest-cancel}` (the D7 disposal intent carries an explicit base `qty` in place of `notional_eur`, and `leverage` absent means spot). The node's executor (a new `cli/engine/executor.py`, driven by a 5 s Nautilus timer that does one cheap `lstat` when no plan is present) picks it up, journals the plan verbatim into the exec ledger, **deletes the file**, and runs the intents sequentially through the state machine. The operator authors the plan after `zcrypto engine probe-plan --check` (offline validator: shape, caps, sizing against the newest venue record's constraints — advisory only; the node re-validates live).

Three stacked defenses make a stale or resurrected plan inert, because the plan file lives inside the state dir that is also the backup/rsync unit ([[T0018]]'s second probe-checklist consequence): the plan **expires 60 minutes after its own `created_at`** (an expired plan is refused and journaled as refused); a `plan_id` already present in the exec ledger of the current or previous UTC day is **never re-executed** (restart- and restore-safe idempotency; per-intent, a ledgered submitted row is never resubmitted); and acceptance deletes the file, so only a filesystem restore can bring one back — into the TTL and dedup walls.

Rejected: a second process or CLI submitting through its own client — one trade key, and iter-079 measured adapter nonces outpacing sidecars; two concurrent authenticated clients on one key is a nonce fight and a double-vision reconciliation. Rejected: restarting the engine into a "probe mode" — every restart latches the reduce-only hold, so the mode flip fights the envelope it should ride, and it turns each probe into an engine restart on the capture primary. Rejected: making the 4 h cycle the consumer — an attended probe cannot wait up to 4 h between steps.

### D4 — The gate becomes unavoidable: one submission chokepoint, a fresh verdict immediately before every venue call

All venue-mutating calls (`submit_order`, `modify`, `cancel` issued as part of submission handling) live in exactly ONE module, `cli/engine/executor.py`, and its submit function's first act is `gate.evaluate(now)` — an open intent requires `full`, a close intent requires at least `reduce_only` plus the D10 classification. There is no constructible path to a submission without a fresh verdict: the function takes the gate, not a verdict, so a caller cannot pass a stale or forged permission in. This deliberately supersedes the candidate shape [[T0018]] inherited by name — a submitting client constructible only from a fresh verdict — because a verdict object, however fresh at construction, is a value a caller can hold while the world changes; take-the-gate-evaluate-inside gives the same freshness guarantee with no holdable token to go stale. Two guards pin it structurally: a repo-wide test walks `cli/` and fails if any module other than `executor.py` references `submit_order`/`order_factory`, and a mutation probe deletes the evaluate call and watches a kill-file test observe an order reaching the stub client.

This also discharges [[T0018]]'s gate-evaluation-cadence revisit, as a ruling: **every executor evaluation publishes to the `_ExecGauges`** (submission-time evaluations included), so during a probe window the published gate state is seconds fresh; between cycles the `00088` cadence stands unchanged — the heartbeat gauge and its staleness rule already make that staleness visible, and `00088` already weighed and rejected a dedicated timer inside the live engine for observability alone; nothing in this spec changes that calculus.

### D5 — The ledger becomes unavoidable: write-ahead, merge-never-clobber, and a schema the reader validates

The exec ledger's write moves into the submission path as a **precondition**: before any venue call, the intent's row (intent, sized order, client_order_id, `state: submitting`) is written into the current boundary's `exec-<HH>.json`; a failing write **refuses the submission** — at the submission site the `00088`-era swallow inverts, because a fill with no forensic row is exactly the state this spec exists to make impossible. Outcome events (accepted, venue-canceled, rejected, canceled, fills with qty/px/fee/fee currency/liquidity/trade_id) append to the row as they arrive. `write_exec_record` gains merge semantics — the sink's per-cycle verdict write can never drop existing `submitted` rows — and the exec schema bumps to 2 with `validate_exec_record` refusing a record whose key shape disagrees with its declared version, `{1, 2}` loadable (the journal's `_LOADABLE_SCHEMA_VERSIONS` pattern).

The one-shot `zcrypto engine cycle` gap [[T0018]] registered is ruled **closed by construction, not by patching the sink**: submissions exist only inside the node's executor, a one-shot cycle has no node, no client, and no executor, so the no-exec-record-from-a-manual-cycle gap remains intent-side only and stays as `00088` designed it. The monitoring gap ("nothing monitors exec-record presence") is discharged by ordering plus proof, scoped honestly: the sink writes the ledger **before** updating any gauge, so **between probe windows** a persistently failing `write_exec_record` starves `zcrypto_exec_last_evaluation_timestamp_seconds` and the existing `00088` staleness rule pages — proven by constructing the raising writer and reading the frozen gauge (Verification). Inside a window the heartbeat stays fresh regardless (D4's executor evaluations and the startup evaluation update the gauge with no ledger write), and there the cover is the write-ahead refusal itself: a failing ledger refuses each submission loudly at the attended operator, which is a stronger signal than a page.

### D6 — The maker-first state machine: join the touch post-only, bounded reprices, a time-box, then a price-bounded IOC cross

Per intent, after the gate, the venue-truth precondition (D8) and sizing: subscribe the instrument's quotes (first quote within 30 s, else refuse the intent — deliberately claimed as the rung-1 per-instrument cover `00088` deferred "until an order needs it": a dead or halted instrument's stream refuses the intent before any order exists, and a venue rejection on a non-tradeable instrument halts the intent with no retry; full `InstrumentStatus` consultation belongs to `00092`'s continuous loop, deferral owned below); submit a **GTC post-only LIMIT at the touch** (buy at best bid, sell at best ask — joining, never improving into the spread, so the price is bounded by the book by construction), with `params={"leverage": N}` on margin intents. A crossing post-only has **two surfaces in the installed adapter** and the machine treats both identically as "the touch moved": the accept-then-venue-cancel Kraken streams (iter-079, verified through this adapter) and the synchronous `OrderRejected(due_post_only=True)` the adapter's submit-exception mapping produces (`POST_ONLY_REJECTED:` in the error text, present in this pinned version) — either one counts **one reprice**: re-read the quote and resubmit. The counter counts **reprices** — resubmissions after the initial order — at most **5**, so the sixth reprice refuses and the initial submission is never counted. **Every resubmission — reprice or IOC attempt — is sized as the intent's quantity minus the cumulative filled quantity across ALL of the intent's orders** (Kraken streams partial fills incrementally, and an IOC can itself partially fill before cancelling its remainder), and a remainder below the instrument's `ordermin`/`lot_step` halts the intent as a terminal partial rather than emitting an unfillable order. If the resting order is unfilled — or partially filled, the remainder falling back — when the intent's **15-minute time-box** lapses: cancel it, then fall back to a **marketable LIMIT IOC priced at the opposite touch** — taker by intent, but price-bounded where a MARKET order is not; at most 3 IOC attempts (each re-reads the quote and re-sizes to the remainder), then the intent halts as `unfilled` for the operator. Partial fills are legitimate terminal states: the ledger records filled quantity, and a close intent always sizes from the Cache's live position, never from the plan.

**An ambiguous submit outcome halts, never retries.** The installed adapter maps ANY exception in `_submit_order` — network timeout, disconnect, cancelled request — to `generate_order_rejected`, indistinguishable by event type from a true venue rejection, and the Rust HTTP client's retry knobs (`max_retries`, unset in our node config, so the Rust default governs) have opaque idempotency on AddOrder. So the machine trusts a rejection only when its reason positively identifies a venue verdict — a Kraken error code (`EOrder:`/`EGeneral:`/`EAccount:` prefix) or the `POST_ONLY_REJECTED:` marker; any other rejection reason is treated as **ambiguous — the order may be live at the venue**: the intent halts as `ambiguous` with no resubmission and no IOC fallback, and no further order on that intent is permitted until an open-orders/own-trades re-read (the attended operator, or the next startup reconciliation) establishes what actually reached the venue. The double-submit this refuses — a timeout surfaced as a rejection, then a second marketable order while the first fills — is direct money loss, and D11's trips are all post-harm; refusal-by-default is the only pre-harm wall.

While any order rests, the executor re-evaluates the gate on every 5 s tick: the kill file appearing, disarming, the hold latching, the venue leaving `online`, **or the quote stream going silent — no quote update within 30 s while an order rests —** cancels the resting order and refuses everything further — the exact mid-flight revoke `00088` built the per-submission gate for, and the quote-silence leg is §10's stale-WS watchdog at intent scale: a resting post-only priced at a touch nobody is updating is priced at nothing (the account-wide cancel-all-and-freeze watchdog belongs to `00092`'s continuous loop, deferral owned below). This is also where the [[T0105]] ruling is discharged, stronger than its "check at cycle entry" floor: the gate's venue leg (the `00088` D4 `SystemStatus` read, 30 s bound) is consulted before **every** submission and on every tick while an order rests, so a `maintenance`/`cancel_only` transition defers or cancels instead of firing into a venue that will reject. `mode: rest-cancel` runs the same path but prices its post-only order **5 % away from the touch on the passive side** (never joining — a join can fill in the instant after acknowledgment, and the drill's whole claim is zero fills) and cancels on acknowledgment — a zero-fill, zero-fee live drill of the whole machine (resting untouched orders are free, per the fee schedule; the iter-079 zero-fill sweep's shape, now through the real executor), used by the checklist before any funded intent.

Rejected: MARKET as the fallback — unbounded price on the live path when a bounded marketable limit does the same job. Rejected: maker-only with no fallback — already rejected at the [[T0090]] ruling (an unfilled probe leg would strand the tax probe, and rung 1's deliverable is the realized blend, which needs the cross to be reachable). Rejected: pricing inside the spread — better queue position priced against adverse selection, and at probe size the queue at the touch fills on noise; simplicity wins at €10–30.

### D7 — The probe trade set: BTC/EUR long (settled by hand, residual disposed by the engine), ETH/EUR short (closed by the engine)

The T2 set is two margin intents at leverage 2 (the iter-079-verified value, comfortably inside both pairs' committed 2–10× bands — `kraken-snapshot-register.md`): a **BTC/EUR margin long** and an **ETH/EUR margin short**, €10–30 notional each, opened in one signed-off plan, held across ≥2 rollover events (≥ ~9 h wall clock buys two 4 h rollovers with margin), then: the **short is closed by the engine** — a second signed-off plan with a close intent, submitted reduce-only with leverage through D6's machine (its first live `reduce_only`; a venue rejection halts the intent and surfaces to the attended operator — no automatic retry without the flag); the **long is settled by the owner in the Kraken UI** (human gate — the adapter cannot emit settle-position, measured in Context), repaying the borrowed EUR from wallet balance, which converts the position into a spot BTC holding of ~€10–30 — and **the engine then disposes that holding**: a third signed-off plan carrying a spot sell with an explicit base `qty` read from the owner's ledger export (never sized from the Cache — whether a UI-placed settle's balance propagates live into `balances_free` is exactly the unproven link below, and the plan-carried quantity removes the dependency), run through the D6 machine like every other intent, so the probe ends **flat**. Three grounds: the sale forces Blockpit to compute gain/loss off the carried basis, completing the settled-in-kind lifecycle the T2 verdict inspects instead of leaving the basis treatment latent; a residual lot would otherwise be unwound by `00092`'s loop at an uncontrolled moment inside live-trading FIFO (BTC/EUR is a traded leg), destroying the probe's self-contained tax evidence; and the disposal is the machine's only **spot-class** order before `00092` — cash-by-default, hence spot — goes live on exactly that class (iter-079's spot round trip ran through the raw adapter, not this machine). Rejected: keeping the holding as a standing lot — unverified basis, uncontrolled future disposal. Rejected: disposing by hand in the UI — identical tax outcome, but the machine forfeits its only spot proof and reconciliation absorbs a second external fill. An over-quantity sell is venue-rejected with a Kraken error code and halts attended; a remainder below `ordermin` is accepted as terminal dust. The engine observes the settle as venue truth — but the **verified** observation path is startup reconciliation (`OpenPositions` plus the connect-time account read), not any standing feed: the installed client subscribes the executions channel only and fetches account state once at connect, so whether a UI-placed settle's external events propagate live into Cache positions AND `balances_free` is unproven on the installed source. The checklist therefore reads the terminal venue truth — position gone, BTC balance back to ~zero (dust-bounded) — from the venue record written after the disarm converge's restart (owed the same day anyway, D13), where the verified path produces it; the settle's intermediate holding is evidenced by the ledger export and by the disposal's own fill (an own-order fill streams live on the executions channel — the proven path), and an earlier next-boundary record is corroboration, never the gate.

The probe is scheduled **within the first two 6b weeks** — the master plan's D3(iii) standing commitment (§12 Decision Register, not this spec's D3), restated here because the >25 % ramp step is blocked until G5 closes (T2 pass or the T3 fallback deployed), so a late probe silently caps the whole ramp. Pair choice grounds: the two most liquid legs minimize spread cost and fill latency at probe size; EUR quotes keep every notional, fee, and Blockpit row in the account currency with no FX term; and BTC-long/ETH-short exercises both extended-currency fee regimes (fiat extended on the long, base extended on the short). Rejected: short BTC instead of short ETH (the cheaper carry side and §4's preferred short) — carry is negligible over ~9 h at €30, and an opposing leveraged order on a pair with an open margin position closes that position before opening anything (Kraken's own margin semantics, and the node's OMS is NETTING), so a BTC/EUR short beside the BTC/EUR long would close the long instead of standing as a second position — destroying the "two distinct positions, two rollover streams" evidence the T2 inspection needs. Rollover ledger rows are verified during the attended window from the owner's Kraken ledger export (the read-only key already carries the Ledgers grant — `kraken-fee-schedule.md`); automated ledger-export ingestion is deliberately NOT built here — it is `00091`'s (the tracking-error report is its consumer). Blockpit: after all three terminal acts — the close, the settle, and the disposal — the owner re-syncs the depot and records the **T2 verdict** in the decisions log (bucket assignment, rollover fees attached, FIFO lots intact, no phantom balances, and the disposal's gain/loss computed off the settle-carried basis — §11's checklist plus the lifecycle completion the disposal buys); [[T0005]]'s T1 check rides the same window. If T2 fails, §11's T3 fallback (the deterministic ledger→Blockpit-CSV pre-transform) becomes a build item and is registered as its own topic at that event — a conditional deferral with its trigger named, not silent scope.

### D8 — Sizing at the call site: `size_order` + the [[T0138]] denomination guard, discharged here

Every intent is sized through the one proven function — `cli/engine/instruments.py::size_order` on the Cache-fresh `ordermin`/`lot_step`/`tick_size` and the committed `COSTMIN` — and **the comparison site gains the guard T0138 holds** — T0138 resolves at this spec's closeout, its ripe trigger being exactly the consumer this decision creates: immediately where a notional meets `constraints.costmin`, the executor asserts `constraints.costmin_quote` equals the denomination of that notional and fails the intent loudly on mismatch. Probe notionals are EUR and EUR-leg floors are EUR, so the live path is the matched case; the mismatched case (a `/BTC` leg's `2e-05` BTC floor against a EUR notional — the fail-open defect T0138 names) is constructed in tests and seen to trip, and any future `/BTC`-leg notional goes through `fx_eur_notional` (landed pure and uncalled by `00094` D5 precisely for this consumer) rather than a second conversion written beside real money. The venue-truth precondition is `00089` D7's deliberately-deferred consequence, now implemented: each intent begins with a fresh `venue_state_from_cache` read (constraints, positions, balances); a raise or an absent account refuses the intent — **no venue truth → no orders**. Two plan-level caps ride the same site: total plan notional ≤ `exec_max_plan_notional_eur` (new `EngineConfig` key, default **100.0**, rendered explicitly by the role so a converge diff shows it — the blast-radius bound), and §10's margin floor wired at rung scale — `sum(notional_i / leverage_i) × 2.5 ≤ free ZEUR balance`, refusing a plan the 250 % floor could not survive. Rejected: a `__post_init__` validator on `InstrumentConstraints` — T0138's own findings rule it out (it couples an evidence dataclass to a committed constant, breaks the concordance tests' deliberately-wrong states, and guards the wrong proposition; the defect is a wrong comparison, so the guard lives at the comparison). Rejected: a `(value, quote)` pair threaded into `size_order` — `00094` D4 drew the seam at the caller on purpose, and moving it now would churn a proven pure function one spec after it was pinned.

### D9 — [[T0140]] ruled: the venue record (and the exec record with it) gets a schema-aware validator — option (a)

This spec makes the venue record's payload **structurally read**: the executor seeds `zcrypto_exec_position` gauges at startup from the newest `venue-<HH>.json`'s `state.positions`, and the probe checklist's reconciliation evidence (held-before vs held-after, the settle observation) is read from the same payload — so T0140's own closing line applies and provenance-only labelling, option (b), stops being available. Ruling: build `validate_venue_record` mirroring `cli/engine/journal.py::validate_record` — schema-aware in both directions, refusing a record whose key shape disagrees with its declared `schema_version`, `{1, 2}` loadable in symmetry with the exec ledger's loader — for the venue record v1 loadability covers only workstation-side journals, because no v1 `venue-<HH>.json` ever existed on the engine host (`00089` first deployed 2026-08-16 with the schema already bumped to 2 by `00094`; `fleet-pins.md` records it) — called by every reader this spec adds and by `_seed_venue_state`. The two self-referential tests are replaced with refusal tests (a stored schema-2 record with base keys is refused, not normalized; a v1 record validates in its own shape). The exec ledger gets the identical treatment in D5 for the identical reason: `00091` reads its fills structurally, and an unvalidated stamp on a forensic record beside real money is the same trap one artifact over. T0140 resolves at this spec's closeout.

### D10 — `reduce_only` is enforced by classification, and a restart cancels resting openers

The gate returns a level; the executor judges the order, now that held exists (`00088` D3 drew this seam on purpose): at `reduce_only`, an intent passes only if it is a genuine reducer. For a margin intent: `action: close`, side opposing the sign of the Cache's live position, quantity ≤ |held|, and the `reduce_only` flag set on the order itself so the venue enforces it too. For the D7 spot disposal: a sell whose plan-carried `qty` is ≤ the newest venue record's spot balance for that asset — strictly shrinking, never flipping — with NO venue-side flag, because Kraken's `reduce_only` is a margin-order concept a spot order cannot carry, so the executor-side quantity bound is the whole guard. Everything else refuses. At startup, while the restart hold is present, reconciliation-adopted resting orders are classified **against the exec ledger, never against the adopted report's flags** — whether Kraken's OpenOrders echo survives adoption with a truthful `is_reduce_only` is unverifiable in the installed source (the population happens in the opaque Rust layer), so the ledger's own write-ahead row is the only trusted witness. An adopted order matching a non-terminal `submitted` row whose ledgered order was reduce-only is **left resting, and the executor re-attaches to that row and resumes outcome-event appending for it** — a post-restart fill on it lands in its ledger row, not beside it, so the no-fill-without-a-forensic-row invariant (D5) survives the restart. Every other resting order — an opener, a matched row not ledgered reduce-only, or any order with no ledger row at all — **is canceled**: a resting opener is a pending widening that would fill while the engine is held, which is the exact state the hold exists to forbid, and an order the executor cannot re-attach to a ledger row would fill with no appender — the exact state D5 exists to make impossible. A canceled close leg is re-dropped as a new signed-off plan: cancel-and-reissue over trusting an unverifiable flag. This is a narrowing on top of `00088`, not a change to it: the hold, its human-only clear, and the gate's semantics are untouched.

Rejected: leaving resting openers and alerting — an alert races the fill, and the fill is the harm. Rejected: cancel-all at every startup regardless of ledger state — it would cancel a legitimately resting, ledger-attached reduce-only order that is actively shrinking exposure. Rejected: classifying by the adopted report's `is_reduce_only` — it makes the preserve/cancel call on a flag whose venue-side round trip nothing installed can prove; a constructed-Cache test would pass while the live adoption defaults the flag.

### D11 — The first automatic kill-switch trip lands where its condition now exists: reconciliation divergence

[[T0018]] deferred automatic trips out of `00088` because their conditions were unobservable; fills and reconciliation exist now, so the first trip ships: the executor **creates the kill file** (latching, human-cleared, exactly `00088`'s semantics) when post-terminal reconciliation diverges — the Cache's position after an intent's terminal state contradicts the ledger's expectation beyond size precision, or a fill for an order claimed by the engine's own strategy id carries a client_order_id the ledger does not know, or a fill's cumulative quantity exceeds its order's submitted quantity, or an intent's cumulative filled quantity across ALL of its orders exceeds the intent's quantity — the cross-order overfill D6's remainder sizing exists to prevent, tripped here as its backstop. The unknown-order trip is **strategy-scoped deliberately**: the executor observes its own strategy's order events, and account-external fills route through reconciliation as venue truth, never through this trip — the G4 settle is a sanctioned external fill, and an account-wide listener would latch the kill file on the probe's own final act. Tripped means: resting orders canceled, every further intent refused, the gauge `zcrypto_exec_kill_tripped` and its existing alert rule announce it. Drawdown and tracking-error trips stay with `00092`/`00091` where their inputs are built — deferral named, owners named.

### D12 — Metrics, panels, and the venue-gauge gap: the execution families land first-class, and the Engine board gains its execution and venue rows
