## Operating model

- **Machines and processes.** Each fleet host runs one Alloy — native under systemd on the observability node (`zcrypto-mon`) and the dead-man node (`zcrypto-hc`), the `grafana-alloy` container on the capture hosts, ops, the three cache nodes and the NAS — reading its host's journal (and on ops its containers) into one `loki.process "parse"` pipeline, whose stages per container set `level` through a labels stage from the level a line carries. Every host ships to the node's Loki on `zcrypto-mon`; the node's Grafana evaluates the node rules over it, and the logs board and Explore read it. A source a host's config names no stage for ships with no `level`.
- **What a level decides.** The node rules select on the label: `level=~"ERROR|CRITICAL"` pages (`zcrypto-ops-error-logs`, `zcrypto-mon-grafana-error-logs`, the capture and engine error rules), and `level=~".+"` is `zcrypto-ops-unit-parse-dead`'s proof that the ops regex stage parses. The level is set once, at ingestion, by the host's Alloy; nothing downstream rewrites it.
- **Shared state.** The one state the hosts share is Loki's stream index on the node: a stream is its label set (`host`, `container`, `level`, and the source's own labels), so a line that gains a `level` moves from its unlevelled stream to a levelled one, and a source gains at most one stream per level its stages set. No log, lock or file here has a second writer: each Alloy config is written by its role alone, `grafana.ini` by the `mon` role, `haproxy.cfg` by the `engine` role, and a rule or panel by the push skill. A pipeline is alive while its host's Alloy runs; a config change takes effect at that Alloy's restart by its role's converge, and lines shipped before it keep the labels they had.

## D1 — a level for every line, set in Alloy, keyed on the text the source already prints

Every source in the measured set gets its level from a stage in its host's Alloy config, matched on the line shape the source already prints. No source's text changes: tests pin it (`tests/test_mon_selfcheck.py:68`, `tests/test_hc_selfcheck.py:53`), a rule reads it (`zcrypto-hc-service-down` matches `|= "web=ok"`), and runbooks grep it (`infra/runbooks/hc.md:383`, `infra/ansible/roles/ops/templates/tape-bars.sh.j2:49`). Each stage is a trailing `stage.match` on `{container="<name>", level=""}` with a line filter, setting the level by `stage.static_labels`, after the host's parsing stages, so it never overwrites a level a parser set. A source that prints its level in a form the fleet already parses — the dead-man node's own Alloy, logfmt with a `level` key — takes the fleet's parse block for that form instead. A line a source prints on failure takes the level of what it reports: a self-check's `=FAIL`, `-> not pinging` or `ping failed` is WARNING (its dead-man check pages the failure, the line explains it); a prune unit's refusal, which never matches its success shape, is ERROR.

## D2 — journald's priority is never the level

The journal's priority does not carry the level for any of these sources: a systemd unit logs stdout and stderr alike at `SyslogLevel=`, info by default, and no unit here sets it; HAProxy reaches the journal only as `docker compose up`'s stdout; Docker's journald driver writes a container's stderr at err, so a priority fallback would raise every harmless stderr notice of Valkey or uWSGI to ERROR, and the ops error rule would page it. No config reads `__journal_priority` today, and none starts to.

## D3 — the ops parse canary keeps its meaning

`Ops · unit log parse dead` (`zcrypto-ops-unit-parse-dead`) reads any levelled `zcrypto-*` line on ops in 26 hours as proof the regex stage parses. D1's fallback levels would satisfy it with the regex stage broken. Its selector takes, besides `level=~".+"`, the shape the regex stage ships: the stage ends in `stage.output { source = "rest" }` (`infra/ansible/roles/ops/files/config.alloy`), so a parsed line leaves Alloy as `<logger> [<file>:<line>] - <message>`, or `[<script>]` for a script's own `log()` line, its timestamp and level cut, and the canary's line filter is `|~ "^\\S+ \\[\\S+\\] - "`. Only that stage's lines count, no fallback's line has that shape, and a mutation of the stage still trips it. Its one dashboard copy, the logs board's `ops units, leveled lines` target (`infra/grafana/zcrypto-logs-dashboard.json`, refId F), follows; the board's other ops targets stay as they are: panel 103's D, `Ops · log pipeline dead`'s, and its E read other containers, `alloy`'s own lines as they are and `liquidations`; its G counts `zcrypto-archive-pull`'s lines at any level, fewer by D4's echo drop; and panel 102's D is `zcrypto-ops-error-logs`'s copy, which shows a tape-bars day's ERROR as that rule pages it.

## D4 — a duplicate is dropped, not levelled

Three sources print a line twice, once levelled and once not, and the unlevelled copy is dropped in Alloy: HAProxy's log target repeats each server state event (`Server … is UP|DOWN`, `Proxy … stopped`, `backend … has no server available!`) that its stderr already prints as `[WARNING]` or `[ALERT]`; `zcrypto-verify-replay` and `zcrypto-archive-pull` `cat` a captured file whose `typer.echo` lines repeat their `logger.info` lines (`cli/archive/command.py:1301-1305,1330-1331`, `:1362-1370` against `cli/trades/backfill.py:300-305`). HAProxy's connection log lines, which have no other copy, are INFO.

## D5 — a cancelled query, an unserved probe and a test notification are not errors

The node's Alloy re-levels to INFO, at ingestion, four line shapes that report no fault: a Grafana or Loki line whose error is a cancelled context (`context canceled`, bare or wrapped as `Get "<url>": context canceled`, the browser leaving a panel); Grafana's `Request Completed` for `path=/apis/quotas.grafana.app/` with `status=501`, the 13.3.0 dashboards page asking an API the OSS build does not serve; Grafana's `Missing notification reason` with an empty `receiver=`, a contact-point test; a bundled plugin's `plugin process exited` with `error="signal: terminated"`, Grafana stopping. Re-levelling at ingestion fixes the logs view and the rule together, where a rule exclusion would leave the ERROR in every view; `zcrypto-mon-grafana-error-logs` and its panel 911 then need no new exclusion, and its existing `error="context canceled"` exclusion stays as written. Loki's `error notifying scheduler about finished query … err=EOF`, which comes with the cancellations, keeps its level: an EOF from the scheduler is also what a scheduler failure looks like.

No Grafana 13.3.0 runs off the node, so its start on the two lines is not verified ahead: the premise is carried by a check immediately after the node's converge — `grafana-server` active and the node's rules evaluating — and by its rollback, the `grafana.ini` commit reverted on a branch and the `mon` role re-converged from it at once, the node's paging down for that interval alone; the revert's pull request merges into `develop` before any further converge of the node, and until it does no `--tags mon` or un-tagged converge of the node runs from `develop`, each of which renders the refused ini again. Grafana's source at `v13.3.0` reads both lines as this needs, the definitions and not a run: a filter is keyed on a logger's exact name (`pkg/infra/log/log.go:106,155`) and the watcher's logger is `log.New("search-manifest-watcher")` (`pkg/storage/unified/client.go:350`, `pkg/storage/unified/resource/manifest_watcher.go:101`), so no other logger's level moves; the notice is logged only while the setting reads true (`pkg/setting/setting.go:2100-2102`). Each setting's effect is read by value after that check, and a setting 13.3.0 does not honour costs only its noise — the rollout goes on and the setting is reworked on a branch of its own.

## D8 — what stays at its level

A real event keeps its level, and no stage touches it: the cache failovers and HAProxy's `no server available` at each node restart; Valkey's and Sentinel's failover lines; the venue's socket closes as nautilus and capture log them; a stale browser session; a CSRF refusal; a Loki series-limit refusal; a silence edit the node refused; the old store's residual-position lines, the true report of the store before it was cleared. Each is the true report of something that happened, and each comes with a restart, a reboot or the venue.

## D9 — UNK stays at zero

A node rule, `Fleet · log lines with no level` (uid `zcrypto-mon-unlevelled-log-lines`, warning, the `logs` receiver, `for: 0s`, `noDataState: OK`), pages when any host ships a line with no level in 15 minutes — `topk(5, sum by (host, container) (count_over_time({host=~".+", level=""} [15m])))` — one instance per source, so a new script or a changed line shape is classified when it first ships rather than discovered in a view. Its runbook section in `infra/runbooks/mon.md` says to read the line, find its stage per D1, and add the source's stage.

## D10 — the engine's dust warning is the owner's

The engine warns at each start that the venue holds a balance the Cache reads as 0 — 1e-08-scale SOL and ETH after the store clear. The statement is true, and the dust sits below the pair's order minimum, so nothing trades it away. Silencing it means engine code, a dust threshold read from the instrument, and so an image and an engine converge: it is offered to the owner as a choice and, unanswered, stays as it is. This branch carries no engine code.

## D11 — the rollout is the owner's, host by host

Every change but D7 is an Alloy config, `grafana.ini` or a rule, each reaching its host by that host's converge with `--tags alloy` or the `mon` role's own tag, read by the owner: the node first, then hc, ops, the NAS, the three cache nodes, and the capture pair's Alloy last, the secondary first, outside any Kraken window. After the merge, the secondary's `--tags alloy` converge precedes any converge of `zcrypto-red`, and the primary's any of `zcrypto`, that runs the capture role — the nautilus bump's among them — since that role refuses one without `capture_alloy_digest` while the deployed config differs from the repo (`assert the deployed alloy config matches the repo`), and one with it would land the config outside these converges' reads; so the pair's config reaches it by these two converges alone. D9's rule reaches the node by the push skill. Verification is by value on the node after each host: `sum by (host, container) (count_over_time({host="<host>", level=""} [1h]))` reads no series once an hour of the host's sources has passed, and the levels the stages set are read back on a sample line of each source that prints within a day; a source that prints only at a restart or on a failure is proven by the real-Alloy reading of its stage before the merge, and D9 pages a line of it that ships with no level.
