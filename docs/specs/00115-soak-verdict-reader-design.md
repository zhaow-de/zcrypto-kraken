# The daily pass reads soak-check's gating verdicts, from the journal alone

## Problem

`zcrypto engine soak-check` files a verdict per metric in `gating_verdicts` and nothing reads them on a schedule ([[T0210]]), which also leaves [[T0184]]'s and [[T0201]]'s triggers unevaluated every pass.

Two decisions are open, and the owner asked for each option costed by codebase change before ruling: where the run is sited, and what shape the reader takes. The owner's stated lean is the option with the least codebase change, tentatively a run sited off the engine host and a reader that reads a verdict. This spec costs every option against that lean and proposes one; the Decisions below are the proposal, and the Alternatives under each are what the owner rules between.

The second half is the daily pass's classifier. `infra/scripts/ops_daily.py` builds one read shape for six `zcrypto engine` subcommands from `_ZCRYPTO_READ_SUBS`, and one shape cannot be right for six option sets: it admits options no sub has, omits most of each sub's real ones, types `--nav` as an integer where the CLI takes a float, and declares `--json` valueless, which is wrong for `soak-check`, where it takes the path it writes. It fails in the safe direction — default-deny — so the cost is a word asked for on reads that should be autonomous. The owner ruled it rides this iteration.

## Decisions

**D1 — The run is sited inside the daily pass, on the workstation, and takes no timer.** `ops-daily.py report` gains one check, appended to the verdict list the way `read_unattended_upgrades` and `read_agentboard_cgroup` are: a keyword-only `runner` seam, no default, injected in tests. The daily pass is already the scheduled reader of every other fleet verdict, so the schedule T0210 asks for exists; what is missing is the row. The run needs the journal, the canonical dataset and the trial registry. Two of the three read the same from any checkout — the journal is the read-only NAS mount and `docs/reference/trial-registry.jsonl` is tracked — but `data/ohlc-full` is gitignored and therefore per-checkout, while the pass is run from whichever checkout sits at `develop`'s tip, routinely a worktree. So the canonical dataset is handed to the run as an absolute path naming the workstation's main checkout rather than left to resolve against the running one; left relative, the row reads `unreadable:` and the whole pass exits 2 every day it is run from a worktree, for a reason that is a property of the operator's shell and not of the book. It reaches no host and no venue.

**D2 — The store input is derived from the journal, and no store is pulled.** `soak-check` reads the engine's price store at one site: `realized_series` in `cli/engine/soak.py` reads `ts` and `close` of each leg's `240.parquet`. Every successful cycle journals that same read — `_journal_snapshots` in `cli/engine/cycle.py` writes the whole union-aligned series for all twelve pairs on both grids as `{ts, close}` parquet, hash-recorded, at the path the record's own `snapshots[].path` names. The check copies the newest success record's twelve `240` snapshots into a store-shaped temporary directory (`<BASE>/<QUOTE>/240.parquet`) and passes it as `--store-dir`. A union-aligned snapshot carries `None` at a stamp a leg lacks, and the soak's scoring loop already treats a `None` close as an absent one, so the derived store yields the series the engine's own `read_store_series` returned at that cycle — the closes the engine ACTED on. What is NOT established is equality with the engine host's store as it stands at read time: that store has no replica, so a later hand-edit or a tail replace of a historical bar would leave the two instruments scoring different closes with nothing to say so. The one reading that would settle it is an attended read of the live `240` legs on `zcrypto` compared against the newest record's snapshots; it is the owner's to run, the branch does not wait on it, and it is carried as a next step of [[T0201]], the topic whose own trigger reads that store's last bar. No `cli/` file changes, so no image is rolled and the NAS gate cache's fingerprint does not move.

**D3 — The reader is a verdict row: one `Check`, three states.** `PASS`, `FAIL` (the pass exits 1) and `unreadable:` (the pass exits 2), which are the three states every other row of that list already has. The row's value always carries the evidence a person needs to disagree with the verdict: the panel line, the panel's indeterminate line whenever a metric's two null constructions gave opposite verdicts, the count of metrics the panel decided whenever the reachability floor is the arm that failed the row — a metric no band could judge is dropped from the panel's counts, so neither panel line names that cause — the scored-bar count and the stamp of the last scored cycle, which is what tells one day's row from the day before's, `window_bound`, the three self-test flags with `skipped` told apart from `ok` — the instrument voids on a check that RAN and FAILED and never on a skipped one, so a skipped check cannot move the verdict word and the row's evidence is the only place it reaches a reader — each outside metric by name with whether one or both null constructions called it, the realized no-book bar count and the `hhi` verdict. The last two are [[T0184]]'s operands, printed on every pass that reaches a verdict. A `FAIL` naming `void_reasons` prints the payload's copy of them, which `soak-check` leaves unscrubbed: its vocabulary lock rewrites its own rendered report, and the daily pass imports no `cli` module to borrow that scrubber, so the lock's scope is that report and not this row, and a reason carrying an exception's words reaches the row as it was raised. The report's journal paragraph carries the row's value whole on every day, a `PASS` included, so the ops journal is the row's history: nothing else keeps the report, and its paragraph otherwise names only the checks that failed.

**D4 — The reduction, in this order, and its threshold is PROVISIONAL.** First the run itself: a missing journal mount, a record with no readable snapshots, a non-zero exit with no fresh payload, a timeout or an unparsable payload is `unreadable:`. A `void_reasons` entry saying the canonical is absent is `unreadable:` too — the run had no reference dataset to judge against, a source it could not read and not a finding about the book; with D1's absolute `--canonical-dir` that means the workstation's own `data/ohlc-full` is missing, which is a data question and not the book's. That arm is the absence probe alone: a canonical the null cannot be BUILT over — present but incomplete, or unreadable for any other reason — carries `soak-check`'s other spelling, `null unavailable: …`, which the row reads with the rest of the reasons as a `FAIL`. Second, any other non-empty `void_reasons` is `FAIL` naming the reasons, and this is tested BEFORE any verdict is read, because the JSON payload carries populated `gating_verdicts` and `panel` beside a non-empty `void_reasons`. Third, the panel decides, and it decides on two of its counts rather than one: `panel.n_outside >= 3` is `FAIL` naming the outside metrics, and so is a panel that left fewer than three metrics decided — `panel.n_metrics - panel.n_indeterminate < 3`, the same constant read as a reachability floor, since a run with fewer decided metrics than the threshold can never reach it and its `PASS` would read as better than chance on the day the instrument disagreed with itself or judged nothing at all. Fourth, the window: a panel is a verdict on today's book only when the scored window is current, so a window whose last scored cycle ended more than twelve hours before the pass, or one whose `window_bound` is not `journal`, is `FAIL` whatever the panel says. `soak-check` scores the LONGEST contiguous run of cycles, so one failed boundary leaves it scoring the run before the gap, with empty `void_reasons` and healthy counts, until the newer run outgrows it; twelve hours is PROVISIONAL too, a current window ending under ten hours before the pass that reads it. Otherwise `PASS`. The row never keys off the word `inconsistent` on one metric: at a 90% band one exceedance in seven is the count chance expects, and the instrument's own disclosures say the seven are fewer than seven independent looks. Three is where a binomial over seven looks at 10% puts under 3% — an upper bound the correlation loosens — and it is a named constant with that reasoning beside it. No re-derivation is scheduled and none is registered: the evidence that would move the number is the row's own history, which D3 has the daily journal keep, so a change is an ordinary change to the constant, argued from the entries under `docs/reference/ops-journal/`.

**D5 — The classifier's generated shape becomes a per-sub table.** Each of the six subs names its own real options and whether each takes a value; `--store-dir`, `--canonical-dir` and `--state-dir` are path-valued directory reads, `--nav` takes a float, and `--date` and `--pair` go, since no sub in this table has them — `replay`, which is not a read this table admits, is the one `zcrypto engine` sub that carries `--date`, and `--pair` is on no sub at all. Two options name a FILE whose reader echoes content when it refuses it — `read_ledger_export` prints the header line of whatever `--ledger-export` hands it, and `_load_registry_record` prints a `--registry` line that is JSON but not an object — so both stay out of their shapes for the reason `cat` and `grep` are held to read-safe roots: a read can surface a secret. The one option that WRITES a path — `soak-check --json <path>` — stays out too, so that form remains `prepared`: the module has no write-safe-location concept, its read-safe roots include `/var/lib/zcrypto-engine/exec/` where the arm and kill files work by presence, and inventing one is not needed by D1, whose run never passes through the classifier. A test introspects the Typer app's real options against the table, so the two cannot drift apart again. It is a guard change: a fixture per sub, a prepared pin for the write form and for each content-echoing file option, and `infra/scripts/mutate-probe.sh`.

**D6 — [[T0210]] resolves in the PR that lands D1–D4, and its deferred sub-item is dropped with its reason recorded.** The topic's last next step — re-read `governor_engagement` once the null has power — is discharged by the row itself, which names every outside metric and its construction count each day; the Resolution says so. No new topic is registered: what this design leaves open has a home already — D2's settling read is a next step of [[T0201]], and D4 drops a scheduled re-derivation of its threshold with the reason. The row is a report section `.claude/skills/zcrypto-daily-ops/SKILL.md` does not walk, so an operator meeting its first `FAIL` would have no prescribed reading; that reading rides this PR as its own `claude(skills)` commit, a fold-in the owner directed on 2026-09-19 after it had been written on a one-commit branch of its own.

**D7 — Each dependent trigger gains an arm the daily pass can decide, and section 5b is left as it is.** [[T0184]]'s operands are printed by every row that reaches a verdict, but `zcrypto-daily-ops` section 5b names an evaluation statement unevaluated, so the printing alone gives that trigger no reader; and [[T0201]]'s trigger reads the ENGINE's store last bar, which a journal-derived store puts on a 4h boundary by construction, so this design cannot evaluate it at all. What 5b decides is the owner's to change and is not changed here. Each topic's `ripe_when` instead gains a second arm of a shape 5b already decides, the next change to the code the topic is about — `cli/engine/soak.py` for [[T0184]], the two store doors in `cli/engine/store.py` for [[T0201]] — and no file of this PR is either. The row's own reading instructions — what an operator does with a `FAIL`, that `void:` names the instrument, and that `unreadable:` names a source only when its value names one — the journal mount, a record or store read under it, or the canonical dataset — and this reader or the instrument otherwise, none of the three a host action — the owner folded into this PR as one `claude(skills)` commit, and that paragraph is the only `.claude/` change here.

## The measured basis

- **The journal-derived store yields a full verdict.** Driven on the workstation against the NAS journal mount: exit 0, all three self-tests `ok`, `window_bound : journal`, and a panel reading of the same shape as the real-store run [[T0210]] records. Payload equality against a real-store run at the same bar is NOT measured; the plan proves the input instead, with a fixture — a store, the snapshot a cycle writes from it through the engine's own union-align and journal functions, and every leg's closes compared one by one. Series equality is score equality because D2's single store read is the only consumer, so the fixture proves the derived input and never scores it twice.
- **The payload's fields D4 leans on are pinned by the plan** in `tests/test_engine_soak_command.py`, and the panel block field for field in `tests/test_engine_soak.py`, since a reader now depends on them.
- **The classifier's shape, driven through `ops-daily.py classify` against each sub's `--help`.** `prepared`: `exec-status --state-dir <path>`, its only option; `tracking-report --gate-from`, `--simulated-fills` and `--ledger-export <path>`; `accum-replay --nav 10000.5`; `soak-check --store-dir <path>`, `--json <path>`, and the form carrying `--canonical-dir`, `--registry`, `--band`, `--floor`, `--null` and `--fee-per-side`. `autonomous`: every sub bare, the boolean `--json` of `decompose`, `tracking-report` and `accum-replay`, a valueless `soak-check --json` the CLI itself refuses, and `report --date 2026-09-19 --pair XBTEUR`, two options `report` does not have. Of the refused forms three stay refused under D5: `soak-check --json <path>`, which writes, and `--ledger-export` and `--registry`, whose readers echo content.

## Out of scope

- Paging between daily passes. D3 accepts that a verdict is read once a day; the metric and the healthchecks.io rows above are what buying more would cost, and arming is the moment to revisit it.
- `zcrypto-daily-ops` section 5b deciding an evaluation statement from a report row (D7): the owner's to change.
- A write-safe location in the classifier (D5).
- Replicating the engine store. It stays unreplicated (`docs/reference/fleet.md`); D2 removes this reader's need for a replica, not the fact.
