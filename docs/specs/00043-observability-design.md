# Grafana Cloud observability for the VPS stack (design)

**Iteration:** authored during iter-084's boundary wait (attended); **execution deferred** — parked as open topic T0020, to be executed in a later attended window. **Goal:** the two production containers (capture + engine) on the D2 VPS ship logs and three levels of metrics (OS, container, application incl. trades/portfolio) to the **already-provisioned Grafana Cloud instance** via a single **Grafana Alloy** agent, presented on **one dashboard** (metrics + logs) with **email alerts** on ERROR logs and alerting metrics. *(Revised after the three-agent adversarial pass: per-rule no-data semantics, the Alloy security posture, capture-counter honesty, exporter failure isolation, restart-safe alert math, mount/path corrections, mechanical deploy embargo.)*

Relationship to the existing healthchecks.io dead-man switches: **complementary, not a replacement** — the external dead-man checks stay authoritative for "is it alive at all" (they live outside the host); Grafana Cloud adds diagnosis depth (what happened, trends, resource pressure) and alert coverage the dead-man semantics cannot express (ERROR-rate, disk watermark, saturation).

## Architecture — one agent, one guarded socket, three signal paths

Two new compose services on the VPS, deployed by a new ansible role `obs` (`site.yml` after `engine`, all tasks `tags: [obs]`), rendering `/opt/zcrypto-obs/{compose.yaml,config.alloy}` plus a `zcrypto-obs.service` systemd unit mirroring the capture/engine pull/up/down pattern; both images digest-pinned:

- **`docker-socket-proxy`** (GET-only guard): exposes only the read endpoints (`CONTAINERS=1`, everything mutating disabled) on **`127.0.0.1:2375`**. Alloy talks Docker exclusively through it — a misbehaving or compromised Alloy can *read* container metadata but can never stop/kill/exec anything (the capture container is untouchable through this path).
- **Grafana Alloy**, running **non-root** with `network_mode: host` (loopback scraping + no per-project network wiring). Host mounts, all read-only, at *alternate* paths with the component path arguments set (mounting over the container's own `/proc`//`/sys` is impossible): `/proc→/host/proc`, `/sys→/host/sys`, `/→/host/root` (with `procfs_path`/`sysfs_path`/`rootfs_path` pointed at them), plus `/var/lib/docker:ro` for cadvisor, and one **read-write persistence mount `/opt/zcrypto-obs/data:/var/lib/alloy`** for Alloy's `--storage.path` — log positions and the remote_write WAL must survive container replacement, otherwise every redeploy re-ships each container's retained log backlog into the ingest quota. (No `/dev/disk` mount: disk **IOPS is out of scope** — free space is enough, and it comes from the filesystem collector.)

**§8 posture (named, not skipped).** The trade key stays unreadable: Alloy is non-root, so `0600 root:root` files (`engine.env`) are unreadable through the rootfs mount; the socket proxy removes the container control plane. **Named residual:** `env_file` values appear in `docker inspect` output, and the proxy's read scope includes inspect — a *compromised* Alloy image could read them. Accepted against: Grafana-signed digest-pinned image, GET-only scope, loopback-only proxy (no new reader beyond existing local root/deploy users). This is a conscious §8 waiver recorded here, not an oversight.

1. **Logs** (both containers, no capture-code changes): `discovery.docker` + `loki.source.docker` (via the proxy) → `loki.process`: **strip ANSI first** (nautilus colors on by default), then extract `level` with **two patterns** (zcrypto's `%(levelname)s` shape *and* nautilus's `[ERROR]` shape), attach `container`, **mask `hc-ping.com/<uuid>` capability URLs** (defense-in-depth; see hygiene) → `loki.write` → Grafana Cloud Loki (basic auth: Loki username + token from the vault). **The legacy host logrotate policy on the container console logs is removed in the same rollout** (`/etc/logrotate.d/zcrypto-capture-docker`, installed by the base role: daily `copytruncate` + 90-day archive into `/var/log/zcrypto-capture`): durable retention moves to Loki, local disk stays bounded by the compose `json-file` caps that already exist on every service, and `copytruncate` truncating json-file logs behind dockerd's back risks clipped/lost lines under an API log-follower. The base role's install task is dropped and the obs role deletes the policy file from the host (`state: absent`); the already-rotated archive under `/var/log/zcrypto-capture` is left in place (historical data — cleaning it, if ever, is an attended call).
2. **Host + container metrics**: `prometheus.exporter.unix` with an **explicit `set_collectors` list — `cpu`, `loadavg`, `meminfo`, `filesystem`, `netdev`** (free space via `filesystem`; **no `diskstats`** — disk IOPS deliberately not collected; path args as above) and `prometheus.exporter.cadvisor` (`docker_host` = the proxy; `docker_only: true`; **network metrics group disabled**) → `prometheus.scrape` → `prometheus.remote_write` → Grafana Cloud Prometheus (basic auth from the vault). **Series minimization is a design principle, not an afterthought**: every scrape job carries keep-only `write_relabel_configs`, seeded from the Grafana Cloud **Docker integration's ~16-metric allowlist** (the integration's `job`/`instance` label conventions are adopted too, keeping panels compatible with Grafana's prebuilt Docker dashboards); Alloy's own `go_*`/`process_*` self-metrics are dropped. Target: well under 1 k active series. Container coverage is CPU/mem/fs — **cadvisor has no restart-count series for plain Docker**; restart visibility comes from `resets(container_cpu_usage_seconds_total[1h])` / `container_last_seen` gaps, and outages from the container-absent alert.
3. **Application metrics — uniform `/metrics` HTTP endpoints on both containers**: a shared exporter helper (new `cli/obs/metrics.py`, `prometheus_client`, TDD), **opt-in via `ZCRYPTO_METRICS_PORT`** (unset → no exporter; the VPS compose files set it, so the workstation soak stays exporter-free), designed for **late registration of collectors over live objects** (the capture objects are constructed inside `_run()`). Ports published **on `127.0.0.1` only** (capture `:9101`, engine `:9102`) — loopback never leaves the host, nftables untouched. Failure isolation is pinned:
   - Exporter startup failure in either daemon **logs ERROR and continues without metrics** — data continuity outranks telemetry; "fail loudly" applies to alert semantics, never to killing a production daemon for telemetry's sake.
   - **capture** (starts inside `_run()` after object construction, in `zcrypto capture` — the single top-level command): per-pair `GapMonitor` gap seconds (exported as the monotonic counter `zcrypto_capture_gap_seconds_total{pair,reason}` — `increase()` is restart-safe) + per-book `desynced` flags are true read-only taps; WS reconnect count, resubscribe count, and segment writes/bytes **require tiny additive state-only counters** at the existing reconnect/resubscribe/finalize sites (no state exists to tap today). Constraint reworded honestly: **no behavioral capture changes; counters are additive state only** — the image rebuild + restart was already budgeted. Scrape-time reads take snapshot copies (`dict(...)`) so a scrape can never raise into the asyncio loop.
   - **engine** (starts in `engine run` only, never one-shot subcommands): gauges updated **after** the record/sidecar is written, wrapped try/except-log exactly like `_ping_healthcheck` — a raising metrics update can never affect the `CycleResult` or the journal artifact (tested). Exported: per-asset target weight, order count + notional EUR, cycle success (0/1), **`zcrypto_engine_cycle_completed_at_seconds` (completion time, not the boundary — preserving the ~30-min completion-latency allowance in the staleness math)**, cycle duration. **At `engine run` startup the completed-at gauge is seeded from the newest journal artifact** (same day-dir glob as `startup_action`), falling back to process start — so a routine restart never leaves the series absent to false-fire the staleness alert. (Gate *streak* is deliberately not exported: it is the gate-ops report's derived quantity.)

Riding the same commits (two-line hygiene fixes): the dead-man **ping-URL warnings in `cycle.py` and `gap_monitor.py` redact the URL** (capability-bearing; they would otherwise ship to a third party), nautilus `LoggingConfig(log_colors=False)` (clean parseable lines), and capture's transient subscribe/unsubscribe rejection logs demote ERROR→WARNING (self-healing reconnect noise; the gap metric is the real signal — otherwise they page).

## Dashboard — one, committed as code, pushed by API

`infra/grafana/zcrypto-dashboard.json`: a host row (CPU/RAM/disk-free/network), a containers row (capture + engine CPU/mem/fs + restart-resets), an engine row (target weights, orders, cycle age/duration/status), a capture row (gap ratio per pair, desynced pairs, WS reconnects, segment throughput), and a Loki logs panel (both containers, level filter). **Provisioning is scripted, not clicked**: a small helper (`infra/scripts/grafana-push.sh`, ~20 lines) POSTs the dashboard JSON (`/api/dashboards/db`) and the alert rules (provisioning API) to the instance using a **service-account token from the vault** — the committed JSON/YAML is authoritative, edits round-trip through re-export + commit + re-push, and the attended step reduces to one script run.

## Alerts — Grafana Cloud alerting → email

Contact point: the account email. **No-data handling is per-rule, not blanket** (empty LogQL results are NoData — a blanket "no-data ⇒ alert" leaves the ERROR rule permanently firing in the *healthy* state; dead-VPS detection is owned by the metric rules + the dead-man switches):

| Rule | Condition (initial threshold) | No-data |
|---|---|---|
| ERROR logs | `sum(count_over_time({container=~"capture\|engine"} \| level=~"ERROR\|CRITICAL\|FATAL" [15m])) or on() vector(0)` > 0 (app containers only — Alloy's own lines never feed it) | OK (query yields 0 when clean) |
| Disk watermark | root fs used > 80% (also the journal-retention topic's ripe trigger and T0003's disk-watch item) | Alerting |
| Memory pressure | available RAM < 10% sustained 15 min | Alerting |
| CPU saturation | CPU > 90% sustained 30 min | Alerting |
| Engine cycle stale | `time() - zcrypto_engine_cycle_completed_at_seconds > 16500` (4 h 35 min from *completion*, mirroring the dead-man threshold; startup seeding keeps restarts from false-firing) | Alerting |
| Container absent | `count(container_last_seen{name=~"capture\|engine"}) < 2` for 10 min (never `absent()` — it inverts) | Alerting |
| Capture gap ratio | `increase(zcrypto_capture_gap_seconds_total[24h]) / 86400 > 0.001` per pair — **watches checksum-resync gaps only**: WS-disconnect windows, restarts, and host downtime do not enter this counter (adding them is a capture-logic change, excluded); those classes are covered by container-absent + the dead-man switch. Green here must never be read as "exit bar holding" on its own. | OK |

Thresholds are initial values; tuning rides the execution topic's shakedown, with the alert-rule export committed beside the dashboard JSON. Each rule is test-fired once during the shakedown **without breaking production** (rule-test facilities / a harmless `logger.error` probe).

## Secrets & config hygiene

The Grafana Cloud stack credentials (Prometheus remote_write URL + username + token, Loki push URL + username + token, **plus a service-account token for the dashboard/alert push script**) enter `group_vars/capture_host/vault.yml` via the established scripted vault append — fetching them from the provisioned instance's UI is a **human sub-item** of the execution topic. `config.alloy` embeds them, so it renders **`0600` (owned by Alloy's non-root uid) with `no_log: true` + `diff: false`** (the engine.env precedent); `compose.yaml` stays secret-free and diffable. The obs role asserts only its own hard precondition (docker present). The app-port probes belong to the attended shakedown checklist, **not** role asserts — Alloy legitimately deploys before the exporters exist (see Deployment sequencing), so a role-level port assert would fail exactly when the role is correct.

## Resource budget (2 vCPU / 4 GB host, capture protected)

Alloy: `cpus: "0.5"`, `memory: 512m`, `cpu_shares: 256`, **`GOMEMLIMIT` ≈ 460 MiB set explicitly** (Alloy under default Go GC behavior is known to overshoot small caps; the embedded cadvisor's 1-second housekeeping is the CPU hog, hence `docker_only` + trimmed metric groups and the 0.5 cap). Socket proxy: `cpus: "0.1"`, `memory: 64m`. Priority under contention stays capture-first (1024) → engine (512) → telemetry (256). Ceiling arithmetic: 2 g + 1 g + 512 m + 64 m leaves ≈ 450 m for the OS — acceptable because caps are ceilings, not reservations (actual RSS: capture < 1 g, engine ~200–300 m, Alloy ~200–300 m steady-state). The WAL/positions persistence mount prevents the known restart spiral (WAL replay + full log re-read on every replacement). Grafana Cloud free-tier fit: ~2–3 k active series (10 k limit); log volume bounded by the compose log caps, with `loki.process` drop rules as the relief valve.

## Deployment sequencing (the two redeploy risks, pinned mechanically)

The app-exporter compose deltas are **gated behind role variables `capture_metrics_enabled` / `engine_metrics_enabled`, both defaulting `false`** — an unrelated `site.yml` converge before the windows below therefore cannot restart either container into its metrics configuration by accident. The embargo is mechanical, not memorial; the flags flip in the attended execution window and double as the rollback knob.

- **capture** (exporter = capture image rebuild + container restart = a small, *unbackfillable* L2 gap): flip `capture_metrics_enabled` **only after the ≥7-day clean-run clock completes (≈ 2026-07-15)**, ideally inside the same attended window as T0003's workstation/NAS remainder. Never spend gap budget early.
- **engine**: flip away from a 4h-boundary+30-min window (same rule as the store delivery) so no Stage-6a gate cycle is put at risk.
- **Alloy + proxy**: no dependency on either container — may deploy first and begin shipping logs + host/container metrics immediately (`up` for the two app scrape jobs stays 0 until the exporters exist; the app-level and container-absent alert rules are created in the same attended pass as the exporters, so the interim is alert-silent by construction).

## Testing

- `cli/obs/metrics.py` + both wirings: unit tests (TDD) — helper starts/serves/updates and supports late collector registration; `ZCRYPTO_METRICS_PORT` unset → no server; exporter startup failure → ERROR logged, daemon continues; capture taps read snapshot copies (fixture objects mutated mid-scrape stay safe); engine update called on success AND sidecar paths, a *raising* update leaves the journal artifact intact (regression test); startup seeding reads the newest journal artifact.
- Alloy config: render-smoke via the role (jinja stub vars) + `alloy validate` against the rendered config (offline syntax check, no live creds).
- Live shakedown (execution topic, attended): logs from both containers visible in Loki with correct `level` labels on *both* line formats; all three metric levels queryable; each alert rule test-fired once; the dashboard rows populate; Alloy RSS/CPU observed against the budget.

## Out of scope

The workstation (soak retires at the 6a exit; journalctl suffices). Replacing healthchecks.io — noting that **Grafana Cloud IRM (OnCall) heartbeats do offer dead-man semantics**: the deliberate choice is to keep the external service as an **independent failure domain** (if the Alloy→Grafana pipeline breaks, an in-Grafana heartbeat can die with it); consolidation is registered as an explicit option in T0020, not silently dropped. Behavioral capture changes (additive counters + the two log-hygiene lines are the entire capture delta). WS-disconnect gap accounting in `GapMonitor` (documented limitation of the gap-ratio rule). Traces/profiling. Log-retention tuning beyond free-tier defaults.
