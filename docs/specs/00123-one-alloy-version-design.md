# One Alloy version across the fleet: a shared `alloy` tag, the apt Alloys held at the fleet's version, and one wave

## Problem

Every host in the inventory's `observed` group runs Grafana Alloy. Seven run the digest-pinned `grafana/alloy` container: the capture pair `zcrypto` and `zcrypto-red`, `zcrypto-ops`, the NAS and the three cache nodes, all at v1.19.2 (`b8ec653c4423`). Two run the apt package from `apt.grafana.com`: the bridgehead `zaccess`, last recorded at `1.20.0-1`, and the observability node `zcrypto-mon`, last recorded at `1.20.1-1`, both read 2026-10-03. Spec 00122 builds a third apt host, the dead-man node `zcrypto-hc`. Three versions ran at that last record, because the apt hosts take whatever a hand `apt upgrade` or their first install brought and the container hosts move only when the bump skill runs. The readings of 2026-10-05 and 2026-10-06 find the same three running: v1.19.2 on every container host the observability node reads, `1.20.0-1` on the bridgehead with `1.20.1-1` its candidate, and `1.20.1-1` on the node (the measured basis).

The owner's rulings of 2026-10-05 are taken as given: every host on the fleet runs the same Alloy version, always; every role's Alloy tasks share one tag, `alloy`, so `--tags alloy` is the one Alloy converge on any host; on the apt hosts `alloy` is excluded from every upgrade, not only unattended upgrades — the package is held — and `--tags alloy` installs the same version as the rest of the fleet; a bump goes to the newest Alloy version only if that same version is available both in the image registry and in the apt repository. The reversal of the apt hosts' present stance is decided, with the owner's reason (D3). A bump keeps the bump skill's canary order and its per-host verification as the only gate between hosts, with no timed bake, and the invariant's one admitted exception is the duration of one wave (D1).

This spec settles where the version lives, how each host class reaches it, how the apt hosts are held at it, how a bump is gated on upstream, what the record and the count read, and the first wave that brings the fleet to one version. The owner ruled its seven open questions on 2026-10-06, each as recommended (`## Open questions`). It delivers T0219.

## Decisions

**D1. The invariant, and the one state in which hosts differ.** DECIDED by the owner (2026-10-05). Every host of the `observed` group runs the Alloy version the fleet file of D2 names. The one admitted exception is a wave in progress: it opens when the change that moves the fleet file merges and closes when the last `observed` host's `alloy` row in `docs/reference/fleet-pins.md` reads that version. Between hosts the next host follows as soon as the previous host's verification, the bump skill's Step 3 (D12), reads green, with no timed bake: the skill already says no canary bake is owed for an Alloy digest and no timed bake beyond that verification, and the owner agrees that baking an Alloy image for a fixed time buys nothing. Each host's own step is bounded by the alert windows the skill names: each host's `Fleet · Alloy dark` rule fires after `for: 10m` plus about five minutes of staleness, and on ops `zcrypto-hcio-watchdog` after about ten, so a host's dark window stays under about eight minutes. A host the wave cannot reach is the skill's held host: its own `fleet-pins.md` row carries the version it still runs and the reason, its hold is committed as D16 says, the count of D8 reads it as off, the wave is not closed while it stands, and it goes to the owner. One wave at a time: a change that moves the fleet file again does not merge while a wave is open. In the first wave the NAS's and the capture pair's verification also carries plan 00121's per-host proof for the observability node's leg, whose shipper-loss read is taken an hour after the recreate; that read, not a bake, is what puts the primary at least an hour behind the secondary there. In a later bump, Step 3 alone is the gate.

**D2. One source of truth for the version: `infra/ansible/group_vars/observed/alloy.yml`.** RECOMMENDED. The fleet's version is three values, written together by a bump from one reading of the gate of D9: `alloy_version`, the upstream version (`1.20.1` in shape); `alloy_image_digest`, the multi-arch index digest of `grafana/alloy:v<alloy_version>`; and `alloy_deb_version`, the package version string apt.grafana.com's index carries for it (`1.20.1-1` in shape), read from the index and never derived. `observed` is the group of every Alloy host, so every role sees the three. Each consumer reads the file or is checked against it:

- The apt roles install exactly `alloy_deb_version` (D3, D5), and refuse an extra-var `alloy_deb_version` that differs from the host's committed value, read on the controller — a held host's hold file's (D16), else this file's — unless the run carries the override of D16.
- The capture, ops and cache roles keep their per-converge operand `<role>_alloy_digest`, because it does two jobs no file can: a converge without it skips the Alloy block, which keeps an application re-pin from touching Alloy (the bump skill calls that skip load-bearing), and the deploy-log row carries it, which is the evidence `infra/scripts/pins-converged.py` reads. Each role's Alloy part refuses an operand that is not `alloy_image_digest` — on a held host the value its hold file sets, which outranks this file (D16) — unless the run carries `-e '{"alloy_override": "<reason>"}'`, JSON with a reason as `canary_override` is, which `converge.sh`'s `OVERRIDES` admits.
- `nas_alloy_image` stays the bare literal `grafana/alloy@sha256:<64 hex>` in `infra/ansible/host_vars/nas/vars.yml`: `converge.sh` records `committed_pins` from the limit's host vars by a regex that matches only such a bare literal, and `tests/test_fleet_contracts.py` reads it there. A test holds it equal to `grafana/alloy@<alloy_image_digest>` — while the NAS is held, its hold file's (D16).
- `infra/scripts/alloy-version.py` (D8, D9) reads the file.

Rejected: a role default for each `<role>_alloy_digest` taken from the file, which would make every capture, ops or cache converge land Alloy; the `alloy` tag as the Alloy block's gate with the digest read from the file, which rewrites the gate in five roles, the drift assert's remedy (T0110) and every published form, and leaves the deploy-log row without the digest the pins reader needs; `nas_alloy_image` templated from the file, which the committed-pins regex would silently drop, leaving the NAS's Alloy pin unrecorded; the deb version derived as `<version>-1`, which a repackaged `-2` would make a version the index does not carry.

**D3. The apt hosts hold Alloy at the fleet's version — the reversal of "followed from apt, never held".** DECIDED by the owner (2026-10-05); the mechanism, the hold and the pin together, DECIDED by the owner's ruling of 2026-10-06 (Open question 6, as recommended).

- *The stance reversed.* The access role installs `alloy` at `state: present` with no version and actively clears a `dpkg` hold (`dpkg_selections: {name: alloy, selection: install}`), its comment headed "Alloy and Caddy are apt packages from THIRD-PARTY repos, so this role FOLLOWS what apt installs", and records no version in `fleet-pins.md`; commit `2b54bd236` (2026-08-20) set it. The mon role took the stance over — "Packages followed from apt, never forced or held", its header says, and spec 00121 D2 gives "the access role's reasoning" — and `tests/test_infra_mon_role.py::test_no_package_is_forced_held_or_pinned_to_a_version` holds it.
- *What it guarded against.* Three risks, each from that commit. (a) A held package that silently ages: `apt-mark hold` makes `apt upgrade` skip it silently, and nothing in that output says which entries are held, so the burden of remembering lands on whoever reads a long upgradable list. (b) A forced version that drops the host from the play: with ansible's default `allow_downgrade: false`, a role asking for `alloy=1.18.0-1` over the `1.18.1-1` the owner had installed by hand was a refused downgrade; the task, third in the role, failed, the bridgehead dropped from the play, and every task below it became unreachable — the pinned-leaves and Caddyfile tasks among them, which are the client-certificate revocation path. (c) A version written into `fleet-pins.md` with no producer and no consumer, which drifts into a confidently wrong number.
- *The owner's reason for the reversal, as given.* The stance was taken because Alloy was not a separately deployable object in the old setup; now it is. New Alloy versions become known through the container images — today a new release is noticed only when the bump skill runs, so nothing gets worse; one version removes the effort of troubleshooting behaviour that differs between nodes on different Alloy versions; and the monthly patch pass keeps the version recent.
- *What covers each risk now.* (a) The version is the tree's decision, no longer the host's, so the host's apt output is no longer where a new Alloy is learned of: the gate of D9 reads upstream at every bump's Step 0 and in the observability node's monthly patch pass, `infra/runbooks/mon.md#mon-patch-pass`, which the daily pass reminds and which carries a newer version present in both sources into the bump skill; and the count of D8 and the rule of D10 show a host that has fallen behind the fleet. The pin below makes the held version the candidate too, so `apt list --upgradable` stops naming Alloy at all — quieter at the host than a hold alone — and that is accepted for the same reason. (b) The install names exactly `alloy_deb_version` with `allow_downgrade: true` and `allow_change_held_packages: true`, so a host on another version is moved, never refused; what failure remains — a version absent from the index, a config the binary refuses — cannot reach the revocation path, because the access role's Alloy part runs after the pinned-leaves and Caddyfile tasks and after a handler flush that applies `reload caddy` (D5), and a test holds that order. (c) The apt rows of `fleet-pins.md` have a producer, the role that installs the version and the wave's host read that re-trues the row, and consumers, the count of D8 and the bump skill's Step 0 baseline.
- *The mechanism: a hold, an exact-version pin, and the install of that version.* `dpkg_selections: {name: alloy, selection: hold}`, after the install, since the module hard-fails on a package dpkg has never seen; a preferences file `/etc/apt/preferences.d/alloy` reading `Package: alloy`, `Pin: version <alloy_deb_version>`, `Pin-Priority: 1001`, a priority above 1000, the level at which apt installs the pinned version even over a newer installed one; and `alloy=<alloy_deb_version>` installed with the two options above. Both, because each covers what the other leaves: the hold is the owner's word and the floor dpkg itself enforces, standing when the pin file is deleted or names a version the index does not carry, in which case apt's ordinary candidate returns; the pin makes the held version the candidate, so an interactive `apt-get install --only-upgrade alloy` — the patch pass's own shape, which asks to change a held package and moves it on a "Y" — finds nothing to do. Rejected: the hold alone, for that prompt; the pin alone, which is not "held" and leaves no floor when the pin matches nothing; a version force without `allow_downgrade`, the failure of 2026-08-20.

**D4. "Any upgrade", path by path, on an apt host.** RECOMMENDED. Each path that could move `alloy`, and what stops it:

- Unattended upgrades: the base role's origin pattern admits the Debian-security origin alone, so apt.grafana.com was never in it; the hold stops it as well.
- `apt upgrade`, `apt-get upgrade`, `apt full-upgrade`, `apt-get dist-upgrade` and a Debian release upgrade: the hold keeps the package back, and the pin makes the installed version the candidate.
- `apt-get install --only-upgrade alloy` and `apt install alloy` with no version: the pin, since the candidate is the installed version.
- `apt install alloy=<other>` and `dpkg -i`: an interactive `apt install` lists the held package as changed and moves it on a "Y", refusing it only under `-y` without `--allow-change-held-packages`, and an explicit `dpkg -i` ignores the hold and resets the selection to `install`, so only a deliberate act moves it; the role's next converge holds the package again and returns it under `allow_downgrade`, and until then the rule of D10 shows it once the moved version runs — at once on the node, whose package restarts Alloy, and on the bridgehead at its next restart — the count of D8 reading the record, which a hand install does not change.
- The role's own converges — `--tags alloy`, `--tags access`, `--tags mon`, the node's un-tagged converge in its patch pass, a rebuild's first converge — install the fleet's version, a held host's its hold file's (D16), which is the design.
- The observability node's monthly patch pass drops `alloy` from the package list of its `--only-upgrade` line, keeps reading the installed version, and compares it with the fleet file's.

Proof: after each apt host's first converge in the wave, the plan reads on the host, as the deploy user and read-only, `apt-get -s upgrade`, `apt-get -s full-upgrade` and `apt-get -s install --only-upgrade alloy` each naming no change to `alloy`, `apt-mark showhold` listing it, and `apt-cache policy alloy` showing the pinned version at 1001. The behaviour of each path above is apt's and dpkg's documented behaviour, not run here (*Not confirmed here*).

**D5. `--tags alloy` on the apt hosts: what it runs, in what order, and what it never touches.** RECOMMENDED.

- *Shared task files* for the three apt roles — access, mon and the dead-man node's `hc` —: the install, steps (1) to (4) below, and the post-condition, step (7), two task files of one shared role, since each role's own step (5) falls between them and one file cannot hold both ends. They are brought in with `import_role` and `tasks_from`, which is static as `import_tasks` is, so the `alloy` tag on the import reaches every task inside them, and no importing role names a path into another role's directory; an `include_role` or `include_tasks` would carry the tag on the include statement alone and select nothing inside. Their path is the plan's: a role of their own, whichever of this package and spec 00122's shared role `node_common` merges first, since the access role imports them as well and `node_common` is task files that spec 00122 has the mon and `hc` roles include with variables.
- *The order.* (1) The Grafana apt repository (deb822). (2) The preferences pin file. (3) `alloy=<alloy_deb_version>` with `update_cache`, `allow_downgrade` and `allow_change_held_packages`, skipped in a preview whose (1) or (2) would change: the apt module checks the requested version against the pin file on disk and against package lists a preview does not refresh, so a version move's preview would fail there, and `converge.sh` refuses the whole converge on a failed preview, the access role's revocation path with it. (4) The hold. (5) Per role, outside the shared file: the env file where the role renders one (access, `hc`), and the config, each config copied with `validate: alloy validate %s`, so the installed binary checks the new file before it replaces the live one, as the mon role's copy and the access role's Caddyfile task already do; the access role's copy gains the validate. (6) Enabled and started. (7) A handler flush carrying the `alloy` tag, then a post-condition: the running process runs the installed binary — its `/proc/<MainPID>/exe` resolves to a file still on disk, where a process that predates the install reads its executable as ` (deleted)`, dpkg having moved the new binary into place over the old one — and the service is restarted when it does not, or when no process runs; the read is the shape of the access role's relay drift gate, `systemctl show -p MainPID` and then the process's own `/proc` entry. Not the unit's `ExecMainStartTimestamp` against the binary's modification time: dpkg sets an installed file's modification time from the package archive, so it is the build's and not the install's, and a process started between the two would pass that test while it runs the replaced binary (the measured basis). A state read rather than a notify, because a `restart alloy` notify stranded by a later failure is never sent again: the next converge finds the package and the files unchanged and reports success while the old binary runs, the class the access role's relay drift gate already documents for its relay.
- *Why the role restarts and not the package.* The deb's postinst restarts Alloy on an upgrade under `RESTART_ON_UPGRADE=true` in `/etc/default/alloy` (spec 00121's measured basis, from the 1.20.1 deb). The access role renders that file itself without the key, and the bridgehead's `/etc/default/alloy` carries no `RESTART_ON_UPGRADE` line, so a version change there does not restart Alloy by itself; the node keeps the package's own file, which carries `RESTART_ON_UPGRADE=true`, so its package restarts Alloy on an upgrade (the measured basis, the owner's read of the bridgehead and the orchestrator's of the node). The two apt hosts differ in exactly that, and the post-condition covers both: on the bridgehead it finds the process older than the installed binary and restarts it, on the node it finds the package's restart already done and restarts nothing.
- *What it never touches.* On `zaccess`: Caddy (its package, CA, pinned leaves, Caddyfile and `reload caddy`), WireGuard (`restart wg-quick@zaccess0`), the SSH relay and its drift gate, the probe. On `zcrypto-mon`: Caddy, Grafana, Loki and Prometheus (their packages, configs and handlers, `stop grafana around a store restart` among them), the token tasks, the self-check and the reboot check. On the dead-man node: the `hc` container, Caddy, the backup timer and the self-check.
- *The access role's order.* Its Alloy part moves after the pinned-leaves and Caddyfile tasks and after a handler flush, so no Alloy failure takes the revocation path with it or strands `reload caddy`; under `--tags alloy` none of those tasks runs at all.
- *The mon role's closure.* Its preview facts `mon_repos_previewed` and `mon_units_previewed` are built from the registers of both repository tasks and of all three install tasks, Caddy's among them, and its `restart alloy` handler is gated on the second; tagging the Alloy tasks alone would leave that handler reading a name no tagged task defines. The Alloy part takes a preview fact of its own, from the Grafana repository's register, the pin file's and its own install's, and `alloy` leaves the `[grafana, loki, alloy]` install task for one of its own.
- *Guards*, each with its `infra/scripts/mutate-probe.sh` verdict: the capture role's three — selection (the tagged tasks by name, their notifies), closure (every name a tagged task or a notified handler reads is produced by an earlier tagged task) and exclusion (the lists above) — per role; the access role's order; and the post-condition.

**D6. `--tags alloy` on the container hosts and the NAS brings the container to the digest.** DECIDED by the owner's ruling of 2026-10-06, as recommended: the container roles recreate Alloy under the tag and assert the running image (Open question 5), and the NAS's narrow run writes its own image line (Open question 7).

- *Today.* The capture, ops and cache roles render the Alloy compose file, config and secrets file and reload a running Alloy, and never start, recreate or pull it — "the first start is an attended step, not a converge side effect", in the capture role's words — so a new digest or a new env file reaches the container only through the bump skill's host-side `sudo docker compose up -d`, and the version a converge claims is false until that hand step.
- *The decision for the capture, ops and cache roles.* Each container role's Alloy part now ends with `docker compose up -d` in its own Alloy project, with `--force-recreate` when the secrets file changed in this run, since Compose's recreate on an env file's change is version-dependent and plan 00121's R2 and R5 each carry a stop for it; then it reads `docker inspect grafana-alloy --format '{{.Config.Image}}'`, that one field, and asserts it names the run's digest, so a recreate the read refutes fails the run. The `up` pulls the image when it is absent. On a converge whose digest and secrets file are unchanged, it recreates nothing. This reverses the roles' attended-first-start stance for Alloy alone: the stance mirrors the capture daemon and the liquidations poller, whose restarts lose data nothing backfills, while Alloy is its own compose project on every container host, beside neither of them, and its WAL and log positions survive a recreate in `alloy-data` (the bump skill); the attended act is the `--tags alloy` converge itself. The wave's first host, ops, is this decision's first run and the wave's stop point (D12).
- *Their forms today, and what joins the tag.* The ops and cache forms this replaces are wider than Alloy: the bump skill's ops leg is an un-tagged run of the ops play — `base`, `chrony`, `docker`, `ops` and `access_ops` — with only the image-gated blocks skipped, and its cache leg is `--tags cache` with `cache_alloy_digest` alone, which still runs the cache role's ungated tasks, the sysctl and the reboot-check and clock-offset timers among them. What joins the tag: on ops, the stale-config removal (line 720), the drift check (730) and the Alloy block (772); on the cache nodes, the drift check (333) and the Alloy block (368), its digest-shape refusal and its Alloy pins-recording refusal with it; on both, the fail-fast and whatever the closure test proves a tagged task reads, such as an account lookup hoisted above the block.
- *The NAS.* The NAS's Alloy-only form is built (`005ffa179`, on this branch): `--tags alloy` lands the config and the secrets file, and under `-e nas_apply_compose=true` reads that the stack `.env` names `ALLOY_IMAGE=<nas_alloy_image>`, refuses the recreate when it does not, and runs `compose up -d --no-deps --force-recreate alloy` — never `archive-pull`, so no gate-export replay. As built it cannot land a new Alloy pin: the tag never renders the `.env`, which carries the puller's image pin, its pull sources and the gate's dead-man URL beside `ALLOY_IMAGE`, so a bump there is two runs, a render-only `--tags nas` that lands every NAS file unapplied and then the narrow applied run. The decision: the narrow run writes the `.env`'s one `ALLOY_IMAGE=` line itself — a line edit under `no_log` and `diff: false`, the line byte-identical to what `templates/env.j2` renders from the same `nas_alloy_image`, so the whole converge's render and the narrow run's edit never disagree at one tree and the next whole render of an unchanged tree reads `changed=false` — and then recreates Alloy alone, so one applied `--tags alloy` run does the NAS's bump as it does every other host's. On the real pass the `.env` check before the recreate then reads the line the run just wrote, and the post-recreate image read of the other container hosts follows it, through `sudo /usr/local/bin/docker`; in the preview `converge.sh` runs first with the same operands, the line edit reports its pending write and writes nothing, so the check stands down while that write is pending, and the image read and its assert stand down in every preview, as the other container hosts' do. The hash-scope assert stays with the template's render, outside the tag: it guards a puller value the narrow run never writes. The pins evidence stands as built (D17), and is stronger: the committed `nas_alloy_image` an applied `alloy` row records is now the pin that run itself wrote and recreated from. Alloy's memory cap and mounts, in `infra/nas/compose.yaml`, stay the whole apply's.
- *What each role's Alloy part never touches.* Capture as built, nothing of the capture daemon, its compose render, its unit or `capture_image_digest`; ops, nothing of the liquidations project or `liquidations_decision`, the timers, the NAS automount, the rrsync keys, the watchdog and keep-alive or the docker drop-in, and no task reading `ops_image_digest`; cache, nothing of Valkey or Sentinel, their compose file, unit or configs, the sysctl, `cache_image_digest` or `cache_config_reset`; the NAS, nothing of `archive-pull`, the rrsync key or `hot/`.
- *Rejected.* Keeping the host-side step and having the count read the running digest, since the count reads the tree, and a converge that succeeds while the host runs the old thing is the class T0109 and T0110 closed for the config; a restart handler, since a restart keeps the image. For the NAS: keeping the two runs, whose render-only first run lands the puller's pending changes on disk as a side effect of an Alloy bump and makes the NAS the one host whose bump is not one action; Alloy as a compose project of its own on the NAS, as on the other container hosts, which would also bring its memory cap and mounts under the tag but costs a migration of the running container inside the first wave and a rework of the form just built, for a gain no ruling asks for — rejected and not pursued; an interpolation file of Alloy's own passed by `--env-file`, which every compose command on the NAS, the runbooks' hand lines among them, would then have to carry.

**D7. Every role carries the tag, and the wrapper refuses an `alloy` run that would select nothing.** RECOMMENDED. At this branch's `c734bd635`, `converge.sh` accepts `alloy` for every host while the capture and nas roles alone carry the tag, so a run on ops, a cache node, the bridgehead or the node runs its play's `always` charter note and nothing else, and exits 0 — what the carriers test there implies. The consequence is not only a no-op: the deploy-log row of such a run carries the digest it was handed, and `pins-converged.py` counts a row's extra var as evidence on any successful run, so the record would say a pin converged that nothing landed. This package lands every role's join in its one pull request — capture, NAS, ops, cache, access and mon — so `develop` does not hold that state at the merge, and two checks keep it from returning, both reading the tree through one shared walk, the capture role's tag test's walk of `site.yml` and the roles' task files joined to `infra/scripts/pins-converged.py`'s read of the inventory: `converge.sh` refuses `--tags alloy` on a limit none of whose plays reaches an `alloy`-tagged task, before the preview, so no such row is ever written; and a static test holds that every host of `observed` has a play that reaches it and runs an `alloy`-tagged task — read per host, since the engine play reaches `zcrypto` and carries no Alloy task while the capture play reaching the same host carries the capture role's — so the refusal never meets a host of the fleet as it stands. The carriers' list that `test_only_the_roles_that_joined_the_tag_carry_it_and_no_play_does` holds at `c734bd635`, the capture and nas roles, becomes exactly the six roles, and widens to `hc` in the change that makes the dead-man node's role join (D14). Each container role carries the capture role's fail-fast — an `alloy` run without the role's digest refuses — so no tagged run there exits 0 having landed nothing; the apt roles and the NAS take their version from committed files and have nothing to forget. The capture role's play-selection test generalises to every play: under `--tags alloy` a play runs its `always` tasks and its role's Alloy part and nothing else, and the base, hardening, firewall, fail2ban, chrony, docker, `cache_link` and `access_ops` roles carry no `alloy` task. Rejected: a hand-kept list of host classes in `converge.sh`, a second copy of the inventory; the static test alone, which holds `develop` but leaves the record open to a run from any other tree; a play-level `always` assert, which would run on every converge of every play for what only an `alloy` run needs.
