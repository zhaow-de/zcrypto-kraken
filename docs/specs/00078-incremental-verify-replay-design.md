# 00078 — incremental `verify-replay`: checkpoint raw facts, recompute the chain

**Goal:** `verify-replay` keeps certifying the **whole** archive every night while replaying only what changed — so its runtime is `(new hours) + (fixed budget)` forever, independent of archive size, and its journal output is flat. This dissolves both of [[T0114]]'s dated cliffs (journald `RateLimitBurst` ~2026-08-14; runtime reaching the 24 h cadence ~2026-09-11) and closes the topic.

## Why this shape and not the others

- **Windowing is refuted, permanently.** Spec `00076` D7 shipped it and it was reverted the same evening: a window cuts the chain-anchoring predecessor set (1,870/2,218 hours `anchored=False` on real data). Anchor-aware windowing was measured and rejected too — snapshot anchors are ~17 days stale and get rarer the healthier capture is, so the lookback grows without bound. **D13 below closes T0114's "re-evaluate windowing" sub-item with a decision: never build it.**
- **T0114's own suggestion over-specifies.** It says to persist "the reconstructed `OrderBook` state". There is no such state: `replay_segment` constructs a **fresh `OrderBook` per hour**, and the only cross-hour computation is `_chain_anchor`, a pure fold whose per-pair carry is `(prev_hour, prev_ok)`. The checkpoint is verdict metadata only.
- **A cold Fable review of the first draft found a certain silent-false-pass** (D1's rationale) plus four leaks in the invalidation argument (D3, D5, D6) — all folded in below. The design's danger is exactly that it makes the integrity instrument stop executing most of what it reports; every guard here exists to make wrong-reuse loud.

## Current state, measured

- 6,000 canonical hours as of 2026-08-01, growing +288/day (12 pairs × 24 h). Full sweep measured twice end-to-end: 4.80–4.82 s/hour ⇒ 8 h 00 m tonight, 24 h at ~17,900 hours (~2026-09-11).
- The CLI prints one line per hour; journald drops past `RateLimitBurst=10000`/30 s/unit at ~2026-08-14, losing the **tail of the `(pair, hour)`-sorted stream** — whole pairs plus both summary lines.
- Every canonical final has a `.sha256` manifest sidecar written **before** publish (`mint.py`; capture `segment_writer.py`) — so a crash leaves sidecar-without-final, never final-without-sidecar. The NAS pull re-hashes **its own replica** hourly; that covers the primary tree (`/nas` *is* that replica's source) but **not** the ops-local overlay (`rsync -a` never re-reads an unchanged file).
- The runner reads the primary from `/nas` (`ro,soft` NFS — can EIO or resolve empty; spec `00077` D2 records an unmounted bind reading as "no canonical hours") and the overlay from `/data` (**mounted `:ro`** today).
- `canonical_segments` is reconciled-first: an hour's path (and hence bytes) flips primary→overlay when the reconciler mints it.

## Decisions

**D1 — The checkpoint caches RAW per-hour facts only; the chain verdict is recomputed every run and never persisted.** `_chain_anchor` computes `anchored = raw OR (contiguous AND prev_ok)` — a fold that can only widen. Caching its *output* makes anchoring irrevocable: hour H, chained through a good H−1 and cached `anchored=True`, stays green forever even after the reconciler rewrites H−1 into a failure — `True OR … = True`, for H and every downstream hour, while `delta(failed_hours)` reads 0. So the checkpoint stores `opens_with_snapshot` (the raw fact) plus the other pure-function-of-bytes fields (`ts_ordered`, `checksum_present`, `replay_ok`, `error`, `rows`, `messages`), and every run refolds the full `(pair, hour)` sequence — cached and fresh alike. The fold is metadata-only: microseconds at any archive size. With raw facts cached, the refolded result is **provably equivalent** to a full replay's fold, and the equivalence is pinned by test (Verification).

**D2 — Identity is the sha256 of the bytes actually replayed, at a hand-bumped `VERIFIER_VERSION`.** Not the sidecar's claim: both writers publish sidecar-*then*-final, so a crash mid-mint leaves new-sidecar + old-final, and trusting the sidecar would let an old-bytes verdict certify the new bytes once the mint completes. The replay already reads the whole file, so hashing the bytes read is nearly free, and it also closes the overlay-bit-rot hole the NAS instrument cannot see. A bytes-vs-sidecar mismatch is reported as that hour **failing** (it violates the archive's manifested invariant) — and failures are never cache-trusted (D3), so it re-checks nightly until resolved. A missing/empty/unparseable sidecar is the same: replayed every run, reported failing, never cached as good.

**D3 — The stale predicate, and failures are never trusted from cache.**

```
stale(pair, hour) =  hour not in checkpoint
                  OR checkpoint.byte_hash != current bytes' hash   (via sidecar short-circuit, D2 note)
                  OR checkpoint.verifier_version != VERIFIER_VERSION
                  OR cached verdict is a failure (any check false, or error != None)
```

The last clause exists because `replay_segment` isolates **any** exception into `error` — including a transient EIO from the `ro,soft` NFS mount. Cache-trusting a failure would turn a one-off hiccup into a permanently-failing hour that pages once and never self-heals; today it heals the next night, and that must survive. Failures are few by construction, so re-replaying them is cheap. *(Implementation note: for unchanged hours the cheap staleness probe is the sidecar read; the byte-hash is recomputed — and compared against the sidecar — only on the hours actually replayed. An unchanged sidecar over changed bytes is bit rot or tampering, which the D6 audit owns.)* Two new read paths sit outside `replay_segment`'s never-raises contract — the sidecar staleness probe and the pre-replay `read_bytes()` hash — and both **isolate `OSError` into that hour's failure** (`error=…`, never cached as good, run continues): a transient EIO from the `ro,soft` mount must stay one failing hour that heals tomorrow, exactly as it does today, not a whole-run crash. Precisely: a *cached failure* is `error != None` or any of `ts_ordered`/`checksum_present`/`replay_ok` false; `opens_with_snapshot=False` is a raw fact, not a failure — including it would re-replay ~96% of the archive nightly.

**D4 — Mandatory new hours, then an oldest-first drain under a 120-minute wall-clock budget.** Hours never seen before are replayed unconditionally — otherwise the sweep falls permanently behind ingest and `hours_total` stops matching the archive. Older stale hours (version bumps, rewrites, `--reverify-all`) drain oldest-first until the budget is spent; the remainder is `pending` and announced (D11, D12). Steady state ≈ 288 new × 4.8 s ≈ 23 min; worst night ≈ 23 min + 120 min + audit ≈ 2.5 h, comfortably clear of the 02:25 reboot from the 03:41 start. Budget spends drain ≈ 1,500 hours/night.

**D5 — `VERIFIER_VERSION` is bumped by hand, only for deliberate semantic changes; the environment is recorded but does NOT auto-invalidate.** The first draft put `polars.__version__` in the invalidation key. That is unsustainable at exactly the horizon this spec exists for: dependabot bumps polars ~monthly (#218, 1.43.0→1.43.1, merged 2026-07-28), a full drain takes ~74 nights at year-one size, so the instrument would sit permanently mid-drain, mixed-version, `pending` never reaching zero. Instead: each checkpoint row **records** `polars_version` and `depth` for forensics; a systematic reader regression is caught by the D6 audit (which replays under *current* code nightly) at constant cost, which is strictly better detection than a year-long drain. `depth` is verdict-neutral today (traced: throws come from message shape, the CRC return is ignored) but T0045's planned byte-exact replay makes it verdict-affecting — recording it now is one column instead of a silent wrong-cache later. A deliberate full re-verification is `--reverify-all` (marks every row stale; drains under D4).

**D6 — The sampled audit is the guard that can actually fail.** Every run re-replays **K=25 uniformly random cache-trusted REUSED hours** (~2 min) — never pending ones: a pending row is known-stale by construction (its cached hash or version already failed the predicate), so auditing it mismatches with certainty and would fail every night of a legitimate large drain — ~74 consecutive false CRITICALs at year-one size, precisely the D5 pathology this spec exists to prevent. The lie the audit exists to catch can live only in rows *trusted as current this run*, recomputes the full raw-fact tuple under current code, and compares it — byte hash included — against the checkpoint. Any mismatch **fails the run loudly**: named in output, summary withheld, so `run_ok=0` and the `00077` run-broken rule pages. Without this, `replayed=288 reused=5712` is simultaneously the healthy signature and the signature of wrong reuse — a census cannot distinguish them. The audit converts "cache wrong in any way" (environment drift, bit rot in the overlay, checkpoint corruption, a stale-predicate bug) from an indefinite lie into a detected event. **Its own proof is mandatory**: a test plants a doctored checkpoint record and shows the audit trips on it (Verification).

**D7 — Eviction guards; an empty or shrunken enumeration never destroys state.** Hours absent from the current enumeration are evicted from the checkpoint (the report always describes what is canonical *now*) — but: (i) an **empty** enumeration never writes the checkpoint (the CLI's existing `no canonical book hours found` rc-0 path already yields `run_ok=0`, which pages); (ii) if eviction would remove **more than 10%** of checkpoint rows in one run, the run **fails**: summary withheld (`run_ok=0` pages), checkpoint unwritten. The case this catches is `/nas` resolving empty while the overlay is present — a nonempty enumeration that would otherwise evict the entire primary on a green-looking night and force an unplanned multi-night rebuild. The operator path past a *legitimate* mass shrink (a deliberate archive restructure) is: delete the checkpoint dir and accept the announced rebuild — one runbook line (D12's entry carries it).

**D8 — A checkpoint-write failure is fatal, and the checkpoint flushes mid-run.** If the state dir is unwritable (missing `:rw` mount, perms, disk), the run fails with the summary withheld — `run_ok=0` pages. Silently warning would degrade the instrument permanently while reporting green. The checkpoint is additionally flushed at least every **250 replayed hours** (~20 min of work at risk), so a rebuild or long drain killed mid-run (02:25 reboot, OOM) resumes instead of restarting — load-bearing once a full replay no longer fits one night.

**D9 — Storage: one parquet snapshot, atomically replaced, ops-local, not replicated.** Path `/var/lib/zcrypto-ops/verify-replay-state/checkpoint.parquet`, written to a temp name and `os.replace`d (the mint pattern), carrying a `schema_version` column — an unreadable or wrong-schema file is a **loud** full-rebuild fallback — announced by `reused=0, replayed≈hours_total` (every hour is *new*, hence mandatory and unbudgeted; `pending` stays 0 because pending counts only *budget-deferred* hours), never a silent skip. Named consequence: past ~17,000 hours (~2026-09-08) a rebuild no longer fits one night — the 250-hour flush makes it a multi-night resume, and each 02:25-reboot-killed night pages run-broken and misses the dead-man until it completes. Loud by design; budget the nights or schedule the rebuild deliberately. Rows: `pair, hour, byte_hash, verifier_version, opens_with_snapshot, ts_ordered, checksum_present, replay_ok, error, rows, messages, polars_version, depth, verified_at`. Scale check, so nobody re-litigates it: ~6,000 rows today, ~1 M rows at +288/day for a decade ≈ tens of MB parquet and ~40–80 MB held columnar — no partitioning, ever, on current growth. The runner gains a narrow `-v …/verify-replay-state:/state:rw` mount; `/data` **stays `:ro`** — the read-only instrument still cannot touch the overlay it verifies. Not replicated: the NAS pulls are exact-subtree rrsync pins (`capture-reconciled`, `l2-panel`, `liquidations`, `hot-out`), so a new sibling is outside every pin — the [[T0057]] lesson honored by construction, not by hope.

**D10 — Checkpointing is opt-in via `--state-dir`, and refused alongside `--pair`/`--since`.** Only the runner passes `--state-dir`. An ad-hoc scoped run engaging the checkpoint would evict every other pair (D7 would catch the big case, but the refusal is correct at any size); scoped runs stay what they are today — ad-hoc tools whose `anchored` is meaningless in the narrowed view.

**D11 — Output: census + failures + summary; the summary line is byte-compatible with `00077`.**

```
verify-replay census replayed=288 reused=5712 audited=25 pending=0 evicted=0 duration_s=1381
verify-replay complete hours=6000 ok=6000 failed=0
replayed 6000 hour(s): 6000 ok, 0 failed
```

*Shipped drift, recorded rather than rewritten: the census ships **seven** fields, not the six above — `mismatches=` sits between `audited=` and `pending=` — and **five** new series, not the four listed below: `ops_verify_replay_audit_mismatches` joins them. D6's audit needed a count of its own, and it is deliberately the one series **not** gated on `run_ok`: an audit mismatch is the only run where it is nonzero and is exactly the run whose summary is withheld, so gating it would publish the previous night's stale value over the sole condition it exists to trace.*

Plus one line per **currently-failing** hour, archive-wide (cached or fresh) — the runbook sends the operator to the journal for failing-hour identities, so a persistently-failing old hour must keep appearing. Normal night ≈ 4 lines: journald flat forever. The per-hour `ok` lines are gone. The `verify-replay complete hours=… ok=… failed=…` logfmt line and counts stay **exactly** as `00077` shipped them: `failed_hours` remains archive-wide, so the `delta()` new-breakage semantics and the existing template parse are untouched. The runner additionally publishes `ops_verify_replay_replayed_hours`, `ops_verify_replay_reused_hours`, `ops_verify_replay_pending_hours`, `ops_verify_replay_duration_seconds` — the duration metric closing T0114's third sub-item (the runway becomes a trended quantity, not a hand-derived one).

**D12 — One new alert: re-verification backlog stuck.** `Ops · verify-replay backlog stuck`, warning: fires when `ops_verify_replay_pending_hours > 0` **and** `delta(ops_verify_replay_pending_hours[26h]) >= 0`, with **`for: 27h`**.

The 26 h window spans exactly the last two runs — wide enough that night two's sample is always inside it (24 h plus slack for a late start), narrow enough that a third night's history never is, so the sign of `delta` means "did the last run make progress" and nothing else. A 49 h window is wrong for exactly that reason: it drags a third and fourth night into the same difference.

**`for` is arithmetic, not taste.** `pending` is a persistent textfile gauge — the runner prints it every run, so it is scraped continuously and holds its value between the daily runs. The condition goes true at the bump night's publish `T1` and **cannot** go false until the window's left edge passes `T1`: before then the window still contains a pre-bump sample, so `delta` stays positive even after night two's decrease has landed. A healthy drain therefore holds the condition true for exactly `max(24 h, window)` = 26 h, independent of how much progress night two made, and **`for` must strictly exceed that**. Simulated over four nightly-gauge histories (steady / healthy / stuck / growing): `for: 25h` fires on the healthy drain at the same instant it fires on a stuck one — the false page this rule exists to avoid — and `for: 26h` trips on the 26 h true run; `for: 27h` leaves the healthy drain quiet and pages the stuck one an hour later. Widening the window obliges widening `for` by the same amount.

With that `for`, the rule is shape-based rather than dated — a healthy drain of any length keeps decreasing nightly and never fires; a stuck one (budget mis-set to 0, drain code broken, state dir lost nightly) fires on day two. One caveat carried into the runbook: a persistently *broken* run carries `pending` forward unchanged, which is "not shrinking" by this arithmetic, so a run-broken condition also trips this rule a day later — the runbook entry's first step is therefore to check `run_ok`. `00077` D8's "no standing known-bad-hours alert" precedent does not apply: pending stuck means the **instrument** is degraded, not that data is bad. `noDataState: OK`, `execErrState: Alerting`, runbook entry alongside the two `00077` rules.

**D13 — Windowed verify: decided, not deferred — never build it.** T0114 sub-item 2 asked, once checkpointing exists, whether a genuinely windowed verify is worth having. Answer: no. The runtime motive is gone (incremental runs are cheap), and windowing's structural defect — a window cuts the chain-anchoring predecessor set — is unchanged and unfixable. `--since`/`--pair` remain ad-hoc tools with their documented sharp edge. This closes the sub-item with a decision; nothing is parked.

## Non-goals

- Persisting `OrderBook` state (refuted above — no such state exists).
- Any change to what a verdict *means*: `replay_segment`'s checks, `_chain_anchor`'s rule, and the CRC-ignored contract (T0045) are untouched.
- Windowing in any form (D13).
- Checkpoint partitioning or a database (D9's scale check).

## Verification

Every guard below is proven by constructing its defect — reading the assertion is not verification (the `00077` branch shipped eight guards that could not fail; two were minted by fixes for others).

- **Equivalence**: on a synthetic multi-pair tree, a full replay and an incremental run (warm checkpoint, no changes) produce identical `ReplayResult` lists — field-for-field, chain verdicts included.
- **The D1 sequence**: build H−1 good + H unanchored-but-chained; checkpoint; rewrite H−1 to fail; the incremental run must flip H to unanchored/failing. This is the review's exact breaking sequence, pinned forever.
- **Recorded environment never invalidates (D5)**: doctor `polars_version`/`depth` in a cached row → the hour is still reused. Without this constructed proof, accidentally adding them to the stale predicate passes every other test and ships the permanent-mid-drain pathology D5 exists to prevent.
- **The audit never samples pending (D6/F1)**: warm checkpoint, force a drain spillover, assert a clean night reports zero mismatches.
- **Empty enumeration in incremental mode (D7/F3)**: an empty tree with `--state-dir` takes the existing `no canonical book hours found` early return — **no census, no summary** — so the runner's `run_ok=0` path pages; printing `hours=0` would read an unmounted NAS as healthy.
- **Transient read errors stay one hour's failure (D3/F5)**: one unreadable final (or sidecar) → the run completes, that hour fails, the census is emitted.
- **The audit bites (D6)**: plant a doctored checkpoint record (flip one cached fact, and separately corrupt the cached byte-hash); the audit run must fail naming that hour. Also prove the sampler actually samples: K > cached-count degrades to all-cached, never crashes.
- **Eviction guards (D7)**: empty enumeration → checkpoint file untouched (byte-identical before/after); a tree missing >10% of checkpointed hours → run fails, summary withheld, checkpoint unwritten.
- **Cached failures re-replay (D3)**: an hour cached with `error != None` is replayed even with matching hash+version; after the underlying file is healed, the run reports it healthy with no manual intervention.
- **Write-failure fatality (D8)**: a read-only state dir → run fails, summary withheld; the template test proves `run_ok=0` on that path.
- **Mid-run flush (D8)**: kill the process after >250 replayed hours; the next run's census shows the flushed progress (replayed < first run's total).
- **Refusals (D10)**: `--state-dir` + `--pair` (and `+ --since`) exit with a clear error; `--reverify-all` without `--state-dir` likewise.
- **Census/summary parse (template tests)**: every field the runner's `sed` extracts is proven against the CLI's real emitted line — **all** parsed fields, per the `00077` finding where covering one field silently dropped the other's coverage.
- **Alert shape (D12)**: the rule's query, window, and `noDataState`/`execErrState` pinned by the alerts test, with the internal-vocabulary check applying to its summary.
- **Deploy verification by outcome**: first post-converge run shows the census with `reused ≈ 0` then next night `reused ≈ hours_total − 288`; `pending` drains to 0; `failed_hours` unchanged; the `00077` rules stay `health=ok`.

## Deploy (attended tail — the branch documents it, the owner runs it)

`cli/` changes ⇒ image rebuild + ops re-pin; the runner template gains the `:rw` state mount and new metric emission; one alert rule is **added** (nothing retired — no prune this time). Order per `capture-deploys.md`: record the pin → converge `--limit zcrypto-ops` (no `ops_alloy_digest` — `config.alloy` untouched; liquidations roll-or-defer decided explicitly, prefer rolling) → push rules → verify by value at the first tick. First converge also creates the state dir via the role.

## Rollback

Re-converge to the prior digest **from a tree whose runner template predates this branch** (or revert the template commit first): the new template passes `--state-dir /state`, which the old image's CLI rejects — rolling back only the digest yields no summary, `run_ok=0`, and a dark dead-man nightly. With the matching template the old runner replays fully — correct at today's size, unrunnable-in-one-night after ~2026-09-11, which is this spec's whole point. The checkpoint dir is inert under the old image and safely deletable.
