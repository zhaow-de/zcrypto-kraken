# Self-hosting the dead-man service: the fleet's checks on the owner's healthchecks.io replacement, in one cutover

## Problem

Every dead-man check the fleet relies on lives on healthchecks.io: eleven checks pinged from five hosts through eleven vaulted ping URLs under seventeen variable names, read by the daily pass through the v3 management API with a read-only key, scraped by the ops Alloy for `hc_check_up` and `hc_checks_down_total`, and notifying Slack through healthchecks.io's own integration. The owner has read healthchecks.io's source, judged its quality, security and resilience insufficient, and built a hard fork — a dead-man ping service with near-complete v3 API compatibility, Prometheus metrics under the same names, and higher security standards (the healthchecks session's facts of 2026-10-04, `State first` and items 1 to 10). This spec moves the fleet onto it in the shape of spec 00121's self-hosting of the observability stack, but without a dual-shipping stage: one cutover, every ping URL re-minted, which is also the rotation T0085 has carried as its last step. The spec delivers T0218.

The owner's three rulings of 2026-10-04 (the peer facts file's last section) are taken as given: the service runs on its own Linode in a region apart from the fleet's, already provisioned and running at `zcrypto-hc.zhaow.me` and waiting for bootstrap as the observability node was; Grafana watches it the way Grafana Cloud and healthchecks.io watch each other today, the mutual watchdog keeping its shape with the clone in healthchecks.io's place and no healthchecks.io check kept; and the cutover comes as soon as possible. Timing is stated against rung 2's box, Mon 2026-10-05 to Sun 2026-11-01, which may slip one week under its own rule: nothing from this work converges the engine on `zcrypto` inside it, so the engine's check alone stays on healthchecks.io until the box closes.

Two words of the owner's of 2026-10-04 govern the design's shape: "learn/reuse as much as possible from T0217/00121; no need to re-invent the wheels", and "get the code-level abstraction and reuse, not only the skin-deep conceptual level". Every decision below names its 00121 counterpart and what it reuses; D15 names the code the `mon` and `hc` roles would otherwise hold twice, extracted into one place both use before the `hc` work consumes it.

## Decisions

**D1. The service runs on its own node, `zcrypto-hc`, a Linode in a region apart from the fleet's, in the observability node's shape.** DECIDED by the owner (the peer facts file's answer 6/3). The reasoning: the dead-man and the thing it watches on one node would collapse the mutual watchdog, since a node that holds both Grafana and the service pages nothing when it dies. The node is already provisioned and running at `zcrypto-hc.zhaow.me`, waiting for `bootstrap.yml` as `zcrypto-mon` was: Debian 13, Backups on, and a Cloud Firewall of TCP 10022, TCP 443 and ICMP after bootstrap, TCP 22 during it alone, exactly spec 00121 D2's shape. Its plan, region and host key are read at the rollout's first steps and recorded there (`[[ROLLOUT: …]]` slots in the plan's R1 and R3), never assumed. A new inventory group `hc_host`, a child of `observed`, and a play of `base`, `hardening`, `firewall`, `fail2ban`, `chrony`, `docker`, the new shared `edge` role and the new `hc` role, the last three under the tag `hc`; the `docker` role is the one departure from the node's play, since the service is one container (D3). The node joins every hand-kept host list `zcrypto-mon` joined in spec 00121's phase 1, by the same test contracts, and reboots by hand at a slot the base role's collision assert admits. Reuses 00121 D2 whole; differs in the container runtime.

**D2. One public hostname on tcp/443, Caddy terminating TLS and proxying to the container on loopback.** DECIDED: `zcrypto-hc.zhaow.me`, live now, an A and an AAAA record as the node's; Caddy from the cloudsmith apt repository the bridgehead and the node already declare, followed from apt, never pinned; TLS on 443 over both families with the HTTP challenge disabled and nothing on 80; `reverse_proxy 127.0.0.1:8000`, uWSGI's http-socket inside the container, bound to loopback by the compose file (facts item 9). No ingest path and no basic-auth user: the service authenticates its own API with its keys (item 3), a ping URL is its own capability, and the UI's login is the service's own, with registration closed. Two routes of the node's Caddyfile are parameters here rather than copies: the `404` set for paths served without a login is empty, since the clone serves `/metrics` nowhere unauthenticated (its Prometheus endpoint takes the read-only key, item 4), and the cookieless-`HEAD` matcher for Slack's link pre-resolution is rendered only once a read says the clone's check pages need it, the plan's acceptance read of one Slack message's link (Open question 8). Reuses 00121 D4's edge whole through the shared `edge` role of D15; differs in the routes.

**D3. A new role `hc`, one container pinned by digest with a `fleet-pins.md` row, its state in one named volume, its secrets vaulted per host and refused by shape before any `no_log` task.** The role, `infra/ansible/roles/hc/`, is the `mon` role's skeleton with the shared pieces of D15 included rather than copied: its first task is the shared secrets preflight over `hc_secret_key` (50 or more characters of the generator's alphabet), `hc_admin_password` (48 hex), `hc_email_host_user` and `hc_email_host_password` (the SES SMTP pair's shapes, read from the credential AWS issues at the plan's P-step), `hc_ping_key` and `hc_readonly_api_key` (the clone's shapes, D4 and D7); then the compose directory `/opt/zcrypto-hc`, the env file `hc.env` (`0600 root:root`, rendered with `no_log` and `diff: false`: `SECRET_KEY`, `SITE_ROOT=https://zcrypto-hc.zhaow.me`, `ALLOWED_HOSTS`, `REGISTRATION_OPEN=False`, `DEBUG=False`, the SES SMTP values and the sender, `DB_NAME=/data/hc.sqlite`, and the proxy-header setting the clone reads for `https` behind Caddy — the exact names are read from the clone's `docker/` directory and `hc/settings.py` at the task's first step, since the peer facts name the paths and not the variables), the compose file `compose.yaml` with `image: ghcr.io/zhaow-de/healthchecks@{{ hc_image_digest }}`, the named volume `hc-data` at `/data`, `ports: ["127.0.0.1:8000:8000"]`, `restart: unless-stopped`, journald logging and the image's own `HEALTHCHECK` of `GET /api/v3/status/` (item 9), and a systemd unit `zcrypto-hc.service` in the cache role's shape (`docker compose up` under `Restart=always`, `ExecStartPre=-… pull`), so the service boots with Docker. The digest is a converge-time extra var, `-e hc_image_digest=sha256:<64 hex>`, refused when malformed or not pulled and refused when the running digest is absent from `fleet-pins.md` unless `pins_override` names a reason — the cache role's three guards, copied as the ops and cache roles copy them from each other today, since the digest block is the one piece of the container roles D15 does not extract (its reasoning says why). The release to deploy is the first cut after the clone's `django-setup` branch merges (facts, `State first`), named by digest at pin time: `[[ROLLOUT: the clone's release and its image digest, read from ghcr.io after the django-setup merge]]`. The superuser is created by the role (D11), the nightly backup timer is the shared one (D10), the self-check timer the shared pattern with the clone's probes (D8), and the reboot-check timer the shared one. Reuses 00121 D2, D5 and D7's shapes and the cache role's digest guards; differs in being one container, not four packages.

**D4. The pingers move to slug URLs under one project ping key, the slugs fixed in the tree and the key the one vaulted value.** RECOMMENDED. Every ping URL becomes `https://zcrypto-hc.zhaow.me/ping/<project-ping-key>/<slug>` (item 2 and item 10's slug form), the slug equal to the check's name — the eleven names of `tests/fixtures/healthchecks_descriptions.json` plus `zcrypto-hc` (D8), each already slug-shaped — so every host's URL is rendered from one vaulted value, `hc_ping_key` in `group_vars/observed/vault.yml`, through one plain group var, `hc_ping_base: "https://zcrypto-hc.zhaow.me/ping/{{ hc_ping_key }}"` in `group_vars/observed/vars.yml`, and the per-host variables the templates read today keep their names and take their values from it: `capture_healthcheck_url: "{{ hc_ping_base }}/zcrypto-capture"` in `group_vars/capture_host/vars.yml`, `zcrypto-red`'s override `…/zcrypto-capture-red` in its `host_vars`, `engine_healthcheck_url` in `group_vars/engine_host/vars.yml`, `nas_gate_healthcheck_url` in `host_vars/nas/vars.yml`, the six ops values in `host_vars/zcrypto-ops/vars.yml`, `selfcheck_healthcheck_url` in `host_vars/zcrypto-mon/vars.yml` and the clone's own in `host_vars/zcrypto-hc/vars.yml`. No template changes: `roles/capture/templates/compose.yaml.j2` (`HEALTHCHECK_URL`), `roles/engine/templates/engine.env.j2` (`HEALTHCHECK_URL`), `roles/ops/templates/compose.yaml.j2` (`LIQUIDATIONS_HEALTHCHECK_URL`), the five ops timer scripts, `roles/nas/templates/env.j2` (`GATE_HEALTHCHECK_URL`) and `roles/mon/templates/zcrypto-mon-selfcheck.env.j2` read the same variable names, so what changes per host is the rendered value, and each host takes it by its own converge (D5). The eleven vaulted URLs under seventeen names become one key plus twelve non-secret slugs; T0085's rotation of "the 11 ping URLs by delete-and-recreate" becomes a new ping key minted in the clone's UI, one vault edit and the converges of D5, with no check deleted and no history lost; and the shape every secrets preflight holds a ping URL to becomes the clone's, `https://zcrypto-hc\.zhaow\.me/ping/[A-Za-z0-9_-]{16,}/[a-z0-9-]+\Z`, its key part narrowed to the measured shape once the key is minted (the measured basis's last item). What every pinger sends is unchanged and compatible: a plain `GET` on the URL, `GET <url>/fail` from the engine's cycle, the gate export and the ops watchdog, no `/start`, no `/log`, no body and no `POST` (the measured basis), all of which the clone records on the slug form too (item 2). The alternative, per-check UUID URLs as today — eleven vaulted values, each minted by the clone, each a `read -rs` P-step — keeps T0085's delete-and-recreate rotation, T0085's two-copies trap for every rotated check, and eleven P-steps where one does; it was set aside for that, and because a lost database (D10) would then owe eleven re-mints where the slug form owes one. The cost of the slug form is that whoever holds the project key can feed or fail every check at once, where a UUID leaks one: accepted, since the eleven URLs already sit in the same five container environments and vault files, so the blast radius of a leak was the fleet's already. `cli/logging/redact.py`'s `ping_failure` drops the URL's path and keeps the host, so a failed ping logs `zcrypto-hc.zhaow.me` and never the key: a test case over the new shape holds it. Reuses nothing of 00121 directly, since no ping URL changed there; the vars-over-templates shape is the ops role's `ops_*_healthcheck_url` wiring, kept.

**D5. The cutover is one attended sitting for every host that can move, with the engine's check the one overlap the box leaves.** Each host takes its new ping value by its own converge, and a container that holds the URL in its environment takes it by a recreate. In the sitting, in this order: `zcrypto-ops` (`--tags ops` with the running Alloy and ops digests; the five timers read their rendered scripts at the next tick; the liquidations poller is recreated by `docker compose up -d`, a gap of seconds in a stream nothing backfills, taken as T0085's rotation would take it; the Alloy container recreated for D7's scrape), `zcrypto-mon` (`--tags mon`; the next self-check run pings the clone), the NAS (`-e nas_apply_compose=true`, which recreates `archive-pull` and replays the gate export, sized by `fleet-pins.md`'s standing constraint), then the capture pair: `zcrypto-red` and, an hour later, `zcrypto` as `--skip-tags engine -e converge_primary=true -e capture_image_digest=<running>`, each a capture-unit restart whose gap the other host's stream splices (`.claude/rules/fleet-deploys.md`; `fleet-pins.md`'s hour between the two), the Kraken maintenance feed read whole immediately before each of the three venue-facing converges. The engine's `HEALTHCHECK_URL` is in `engine.env`, read at an engine start, and an engine-tagged converge inside the box re-renders `exec_armed = false` and restarts the engine (`infra/runbooks/engine-procedures.md#engine-rung-2-box`): so the engine's check alone stays on healthchecks.io until the box closes, `[[ROLLOUT: the box's closing date, 2026-11-01 or a week later]]`, and moves in an after-box sitting by `--tags engine` inside the inter-cycle gap. This is the one overlap "as soon as possible" cannot remove, and the spec says so plainly: for those weeks the engine's check is read on healthchecks.io, its `hc_check_up` row reaches Grafana Cloud through nothing (the ops scrape moves to the clone in the sitting), and `zcrypto-engine-shadow`'s page comes through healthchecks.io's own Slack integration alone; `zcrypto-engine-cycle-stale` on both Grafana stacks keeps watching the cycle by value throughout, so the overlap costs the double-page, not the detection. The capture pair's move in the first sitting is the recommendation and Open question 1: the alternative, the pair after the box with the engine, leaves three checks on healthchecks.io for four weeks and keeps the whole account alive for them; the pair's move is two attended capture restarts the rule licenses and the rollout-image skill's primary form takes, inside the box, since the box forbids an engine restart and not a capture one. healthchecks.io is retired after the after-box sitting's first clean day (D14). Reuses 00121 D15 and D22's per-host order and the attended forms; differs in there being no dual period.

**D6. The checks are provisioned on the clone by a script from healthchecks.io's own listing, idempotently, and the fixture is re-fetched from the clone.** A new `infra/scripts/hc-provision.py`: `plan` reads healthchecks.io's `/api/v3/checks/` with `healthchecks_readonly_api_key` (name, slug, tags, desc, grace and, on a simple check, timeout, which the read-only listing carries — item 3 — so no table of timeouts is kept in the tree) and prints the twelve definitions it would write, the eleven plus `zcrypto-hc` from a definition in the script (D8); `apply` writes each to the clone through `POST /api/v3/checks/` with `unique: ["name"]` and the clone's read-write key, so a second run updates and never duplicates (item 10), with `channels` set to the id of the Slack integration the owner attached in the UI (item 3: channels are settable with the read-write key; the integration itself has no API and is the P-step of Open question 2), and reads the result back; `fixture` re-fetches the clone's listing with the clone's read-only key and writes `tests/fixtures/healthchecks_descriptions.json`, `name`, `tags` and `desc` alone, sorted by name, so the fixture's keys stay inside the trio the read-only key returns and the daily pass's description check keeps reading it; `retire` (D14) deletes healthchecks.io's checks by uuid through its read-write key after reading the clone's listing holding all twelve, and refuses otherwise. The keys reach the script through `grafana_auth.vault_var(name, vault_file)`, the clone's read-write key as `hc_readwrite_api_key` in `group_vars/all/vault.yml`, the workstation-only custody that holds `healthchecks_api_key` today's equivalent, and its read-only key as `hc_readonly_api_key` in `group_vars/observed/vault.yml` (D7). The token cache under `~/.config/zcrypto/` of 00121 D6 is not used: it holds a machine-minted, re-mintable token, and the clone's keys are UI-minted under sudo mode (item 3), so a rebuild of the workstation would need the owner's hands either way, and the read-only key must reach ops in any case. Every check's description keeps its `Runbook:` citation, and the daily pass's `check_descriptions` holds each one against the runbooks as it does today. Reuses `grafana_auth.vault_var`, the fixture contract `tests/test_ops_daily.py` holds and the P-step shape of 00121's phase 2 P1; differs in writing checks by script rather than by hand.

**D7. The read-only key is held once, RECOMMENDED: `hc_readonly_api_key` in `group_vars/observed/vault.yml`, rendered onto ops by the ops role alone and read by the workstation by file path through `vault_var`'s `vault_file` parameter, which closes T0085's trap of two copies that must match; `healthchecks_readonly_api_key` and `hc_prometheus_metrics_path` leave the vault at retirement, and `infra/scripts/count-list.sh hc-readonly-key-in-a-role` is re-pointed to the new name and its one legitimate render, `roles/ops/templates/alloy-secrets.env.j2`, so a second role naming it is the finding. Reuses the scrape, the rule, the panels and the timer; differs in the address, the token form and the key's custody.

**D8. Grafana watches the clone through the ops scrape, the clone watches Grafana through the ops timer, and the clone's own self-check pings a check of its own.** DECIDED by the owner (answer 7/4): the mutual watchdog keeps its shape with the clone in healthchecks.io's place — Grafana Cloud's `zcrypto-hcio-watchdog` over the ops Alloy's scrape of the clone's metrics pages when the clone is dark (`999`, the scrape returning nothing) or a check is down, and the clone's `zcrypto-grafana-watchdog` check, pinged by ops' timer, pages through the clone's Slack integration when Grafana is dark; no healthchecks.io check is kept, and the account is retired after the cutover (D14). What the scrape proves and does not: a scrape that answers proves the web process up and the database readable, since the metrics view reads every check; it does not prove the database writable, the notifier alive or a ping stored. RECOMMENDED, the clone's own check for that: a self-check on `zcrypto-hc` in the node's self-check shape (the shared pattern of D15), every five minutes, three probes — `GET http://127.0.0.1:8000/api/v3/status/` answering 200, the image's own health; the notifier's process present in `docker top zcrypto-hc`, a read that prints no environment, the clone running `sendalerts` beside uWSGI as upstream's image does (a premise the plan's first `hc` task reads from the clone's `docker/uwsgi.ini`, and whose absence drops this probe for the status read alone); and the ping itself, `GET <hc_ping_base>/zcrypto-hc` answering 200 `OK`, which the clone sends only after the ping row is written, so the ping is the write probe — pinging only when the first two pass, and printing `selfcheck: … -> pinged` or `-> not pinging` as the node's does. Grafana reads it as `hc_check_up{name="zcrypto-hc"}` through the scrape: a clone whose web answers but whose database refuses writes, or whose notifier died, shows that check down within its `timeout 600 + grace 600`, and `zcrypto-hcio-watchdog` pages it, where the scrape alone would read green. When the whole clone is dark the check cannot page and the `999` route does; the two routes are the drills of D13. Reuses 00121 D16's self-check and the T0083 watchdog's two halves; differs in the probes.

**D9. Retention and limits are the clone's defaults, as given.** From item 8: pings per check `ping_log_limit` 100, set in the admin and left at its default (Open question 9); flips kept at least 93 days; notifications as old as the oldest kept ping; test notifications 30 days, sessions to expiry, the admin log 365 days; pruned daily at 03:17 UTC inside the container. No API rate limit, logins rate-limited per address and email, no maximum number of checks, ping bodies to 10,000 bytes with `[django-setup]`'s uWSGI cap over 2,621,440 — none of which a fleet pinger approaches, since none sends a body. Nothing here is a fleet setting; a change is the owner's in the admin.

**D10. Backup is a nightly `VACUUM INTO` on the node under Linode Backups, restore is proven on a scratch container first, and a lost database costs one ping-key rotation.** From item 9. A shared timer of D15, `zcrypto-sqlite-backup`, runs nightly at 02:47 UTC on the node: `VACUUM INTO` through `docker compose exec -T web python3 -c …` into `/data/backups/hc-<date>.sqlite` inside the volume, owned by the container's uid 100 so no file is created under root beside the live database's `-wal` and `-shm`, then `docker compose cp` of that file to `/var/backups/zcrypto-hc/`, kept 14 days in both places; the timer's unit writes `zcrypto_sqlite_backup_last_success_timestamp_seconds` into the textfile directory, read by `zcrypto-hc-backup-stale` (D12). Linode Backups, file-based and able to catch a running store mid-write (00121 D3), then carry a consistent copy on every snapshot, since the `VACUUM INTO` file is a closed, consistent database. Restore, `hc.md`'s `hc-restore`: the backup is first started on a scratch container on the node, `127.0.0.1:8001`, with a copy of the file and the same `SECRET_KEY`, and the twelve checks are counted through its `/api/v3/checks/` with the read-only key, which proves the file, the key's HMAC under the secret key and the listing in one read; then the live container is stopped, `hc.sqlite-wal`, `-shm` and `-journal` deleted, the file copied in as uid 100 and the container started (item 9's steps). What persists across a rebuild and what does not: `SECRET_KEY` is vaulted, so API keys stay valid on a restored database; the project ping key lives in the database alone (items 3 and 10: keys are minted in the UI, with no API to set one), so a database lost beyond the last backup owes a new ping key, one vault edit and the converges of D5 — the one rotation round D4 made cheap — and a re-run of `hc-provision.py apply`, which re-creates the twelve checks with new uuids and the same names, the metrics' `name` label surviving and `unique_key` not (T0085's note). An off-host copy was set aside, Open question 3: a pull channel to the NAS is a keypair, a user, an entrypoint block and a NAS apply, what 00121 D3 set aside for the node, for a database the tree re-creates in one script and one rotation. Reuses 00121 D3's Backups-plus-rebuild reasoning and the ops timers' textfile shape; the backup timer is new, designed once for the clone now and Grafana's SQLite later.

**D11. Reuses 00121 D7's bootstrap discipline; differs in the mechanism, since the clone mints no token for a role.
