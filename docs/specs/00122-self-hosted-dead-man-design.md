# Self-hosting the dead-man service: the fleet's checks on the owner's healthchecks.io replacement, in one cutover

## Problem

Every dead-man check the fleet relies on lives on healthchecks.io: eleven checks pinged from five hosts through eleven vaulted ping URLs under seventeen variable names, read by the daily pass through the v3 management API with a read-only key, scraped by the ops Alloy for `hc_check_up` and `hc_checks_down_total`, and notifying Slack through healthchecks.io's own integration. The owner has read healthchecks.io's source, judged its quality, security and resilience insufficient, and built a hard fork — a dead-man ping service with near-complete v3 API compatibility, Prometheus metrics under the same names, and higher security standards (the healthchecks session's facts of 2026-10-04, `State first` and items 1 to 10). This spec moves the fleet onto it in the shape of spec 00121's self-hosting of the observability stack, but without a dual-shipping stage: one cutover, every ping URL re-minted, which is also the rotation T0085 has carried as its last step. The spec delivers T0218.

The owner's three rulings of 2026-10-04 (the peer facts file's last section) are taken as given: the service runs on its own Linode in a region apart from the fleet's, already provisioned and running at `zcrypto-hc.zhaow.me` and waiting for bootstrap as the observability node was; Grafana watches it the way Grafana Cloud and healthchecks.io watch each other today, the mutual watchdog keeping its shape with the clone in healthchecks.io's place and no healthchecks.io check kept; and the cutover comes as soon as possible. Timing is stated against rung 2's box, Mon 2026-10-05 to Sun 2026-11-01, which may slip one week under its own rule: nothing from this work converges the engine on `zcrypto` inside it, so the engine's check alone stays on healthchecks.io until the box closes.

Two words of the owner's of 2026-10-04 govern the design's shape: "learn/reuse as much as possible from T0217/00121; no need to re-invent the wheels", and "get the code-level abstraction and reuse, not only the skin-deep conceptual level". Every decision below names its 00121 counterpart and what it reuses; D15 names the code the `mon` and `hc` roles would otherwise hold twice, extracted into one place both use before the `hc` work consumes it.

## Decisions

**D1. The service runs on its own node, `zcrypto-hc`, a Linode in a region apart from the fleet's, in the observability node's shape.** DECIDED by the owner (the peer facts file's answer 6/3). The reasoning: the dead-man and the thing it watches on one node would collapse the mutual watchdog, since a node that holds both Grafana and the service pages nothing when it dies. The node is already provisioned and running at `zcrypto-hc.zhaow.me`, waiting for `bootstrap.yml` as `zcrypto-mon` was: Debian 13, Backups on, and a Cloud Firewall of TCP 10022, TCP 443 and ICMP after bootstrap, TCP 22 during it alone, exactly spec 00121 D2's shape. Its plan, image, region, Backups state and host key are read at the rollout's first steps and recorded there (`[[ROLLOUT: …]]` slots in the plan's R1 and R3), never assumed. A new inventory group `hc_host`, a child of `observed`, and a play of `base`, `hardening`, `firewall`, `fail2ban`, `chrony`, `docker` and the new `hc` role, each under its own tag as every play holds its roles, the `hc` role reaching the shared `edge` role through an include whose tasks take the `hc` tag, since a role the play also listed would run twice, the first time on its defaults; the `docker` role is the one departure from the node's play, since the service is one container (D3). The node joins every hand-kept host list `zcrypto-mon` joined in spec 00121's phase 1, by the same test contracts, and reboots by hand at a slot the base role's collision assert admits, `hc_host` joining that assert's host list as `mon_host` did. Reuses 00121 D2 whole; differs in the container runtime.

**D2. One public hostname on tcp/443, Caddy terminating TLS and proxying to the container on loopback.** DECIDED: `zcrypto-hc.zhaow.me`, live now, an A and an AAAA record as the node's; Caddy from the cloudsmith apt repository the bridgehead and the node already declare, followed from apt, never pinned; TLS on 443 over both families with the HTTP challenge disabled and nothing on 80; `reverse_proxy 127.0.0.1:8000`, uWSGI's http-socket inside the container, bound to loopback by the compose file (facts item 9). No ingest path and no basic-auth user: the service authenticates its own API with its keys (item 3), a ping URL is its own capability, and the UI's login is the service's own, with registration closed. Two routes of the node's Caddyfile are parameters here rather than copies: the `404` set for paths served without a login is empty, since the clone serves `/metrics` nowhere unauthenticated (its Prometheus endpoint takes the read-only key, item 4), and the cookieless-`HEAD` matcher for Slack's link pre-resolution is rendered only once a read says the clone's check pages need it, the plan's acceptance read of one Slack message's link (Open question 8). Reuses 00121 D4's edge whole through the shared `edge` role of D15; differs in the routes.

the ping key is held through every ping URL's shape (D4) and the read-only key by its P-step's shape, since the role renders neither; then the compose directory `/opt/zcrypto-hc`, the env file `hc.env` (`0600 root:root`, rendered with `no_log` and `diff: false`: `SECRET_KEY`, `SITE_ROOT=https://zcrypto-hc.zhaow.me`, `ALLOWED_HOSTS`, `DEBUG=False`, the SES SMTP values and the sender `z-no-reply@zhaow.pro` (Open question 4), `LOG_FORMAT=json` (D8, D12), `DB_NAME=/data/hc.sqlite`, and the proxy-header setting the clone reads for `https` behind Caddy — the exact names are read from the clone's `docker/` directory and `hc/settings.py` at the task's first step, since the peer facts name the paths and not the variables), the compose file `compose.yaml` with `image: ghcr.io/zhaow-de/healthchecks:{{ hc_image_tag }}`, the named volume `hc-data` at `/data`, `ports: ["127.0.0.1:8000:8000"]`, `restart: unless-stopped`, `pull_policy: never`, journald logging and the image's own `HEALTHCHECK` of `GET /api/v3/status/` (item 9), and a systemd unit `zcrypto-hc.service` in the cache role's shape (`docker compose up` under `Restart=always`) without its `ExecStartPre=-… pull`, so the service boots with Docker and runs the image a converge pulled: over a version tag a pull at every unit start would run whatever image the tag then names, past every guard that reads the tag, and Compose's default `pull_policy`, `missing`, would pull it on a start that finds the image pruned. The pin is a version tag, the owner's ruling (Open question 5): a converge-time extra var, `-e hc_image_tag=v<major>.<minor>.<patch>`, refused when malformed or not pulled and refused when the running tag is absent from `fleet-pins.md` unless `pins_override` names a reason — the cache role's three guards, re-worded from a digest to a tag and copied as the ops and cache roles copy them from each other today, since the pinned-image block is the one piece of the container roles D15 does not extract (its reasoning says why). The release the role was built on is `v6.1.0`, DECIDED by the owner (2026-10-05); the release the node is bootstrapped on and the cutover run on is `v6.2.0`, DECIDED by the owner (2026-10-07); both are of the major version cut after the clone's `django-setup` branch merged (Open question 5, D17), and each logs every failed notification dispatch at `ERROR` and names a check in its flip summary by its name, never its UUID (D8), the `hc` row of `fleet-pins.md` naming `v6.2.0` from the node's first converge (D5). The superuser is created by the role (D11), the nightly backup timer is the shared one (D10), the self-check timer the shared pattern with the clone's probes (D8), and the reboot-check timer the shared one. Reuses 00121 D2, D5 and D7's shapes and the cache role's pin guards; differs in being one container, not four packages.

**D4. The pingers move to slug URLs under one project ping key, the slugs fixed in the tree and the key the one vaulted value.** RECOMMENDED. Reuses nothing of 00121 directly, since no ping URL changed there; the vars-over-templates shape is the ops role's `ops_*_healthcheck_url` wiring, kept.
