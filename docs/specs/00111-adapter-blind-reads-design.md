# 00111 — the adapter's blind reads: flatten's cache, and a funding gate that fails open

`zcrypto engine flatten` reports `0 resting order(s)` against an account with two open orders, and the engine's funding gate reads a free balance that overstates available cash by whatever the venue has reserved. Both trace to the same nautilus Kraken adapter, and one of them sits on the arming path rather than the red button.

## The measured basis

Every figure in this section was measured on the live account on 2026-09-03, not inferred; the section after it is the offline instrument, and says so in its own words. The fixture is two resting SOL/EUR buy limits placed by hand on 2026-09-01 — `OZRI5U-U7WGD-OYCOMW` (spot) and `OVNLAJ-6PXBH-T4GDXF` (2:1 margin), 0.06 @ 45.95, unfillable ~46 % below market.

**Their existence has three witnesses that do not share a code path**: Kraken's web UI, the owner's `kraken open-orders` CLI, and a nautilus client with its instrument cache populated. That matters because an earlier reading of this same defect was retracted on a control that could not distinguish blind from healthy.

**The fixture is re-confirmed before the branch spends anything, not only at the attended step.** Every decision below inherits this table, and the two limits could have filled or been cancelled since — `kraken open-orders -o json` and `kraken extended-balance -o json` are read-only, need no adapter and no allowlist change, and settle it. A reading that disagrees is a finding that stops the branch, not a number to update in passing.

| read | result | truth |
|---|---|---|
| `request_order_status_reports` (cold cache) | **0 rows**, every parameter shape, both `AccountId`s | 2 open |
| `request_order_status_reports` (cache populated) | **2 rows**, both `ACCEPTED` | 2 open |
| `request_fill_reports` (cache populated) | **6 rows** | **no committed anchor carries this quantity.** `adapter-verification/2.0.0rc4.dev20260825.md` holds 6 unique *order* txids, four of them recorded `filled_qty=0.0`, and no trade or fill id at all — so the matching count is a coincidence, not a witness (D4) |
| `request_account_state` → `locked` | **0.00000000** | Kraken `BalanceEx` `hold_trade` = **2.757** |

**Which account a row was read on is load-bearing for D2 and for nothing else here.** The repo's only caller of `request_account_state` is flatten's `read_balances`, which sends `account_type=AccountType.CASH` — so the `locked` row above is a reading of the cash branch. The engine's exec client is built `spot_account_type=AccountType.MARGIN` (`node.py`'s `_exec_client_config`), and *that* is the account D2's refusal consumes. D2 states the gap and what closes it.

**Two independent mechanisms, read from upstream source at `develop` HEAD `bb721205`:**

1. `crates/adapters/kraken/src/http/spot/client.rs`, in `request_order_status_reports`: each open order is looked up by raw symbol against `instruments_cache`, and **the `if let Some(...)` has no `else`** — an unknown symbol drops the order silently, with no warning and a successful empty return. The cache's only writer reachable from Python is `cache_instrument` — `hasattr(KrakenSpotHttpClient, 'cache_instruments')` is **False** on the installed binding, so there is no batch form to reach for; **`request_instruments()` does not populate it**. `cli/engine/command.py` builds a bare `KrakenSpotHttpClient` and never caches, so the cache is empty for flatten's entire run.
2. The same file's cash branch builds `AccountBalance::from_total_and_locked(amount, Decimal::ZERO, currency)` — a **hardcoded zero** for `locked`, so the platform derives `free = total`. The adapter calls `/0/private/Balance` (amounts only) and never `/0/private/BalanceEx`, which is what carries `hold_trade`.

**Why mechanism 2 reaches the arming gate.** `venuestate.py`'s `venue_state_from_cache` builds balances from `account.balances_free()`; `command.py`'s `probe_plan` and `executor.py`'s `_pickup` take `free_zeur` from that; `probeplan.py`'s `plan_refusals` refuses a plan when `margin_required > free_zeur`. An overstated `free_zeur` makes that refusal **less** likely to fire. **The margin floor fails open**, and it does so by exactly the amount already committed to resting orders — largest precisely when the guard matters most. Nothing in `cli/engine/` subtracts commitments: no reference to `locked`, `hold_trade`, `reserved` or equivalent exists.

*(Symbols, not line numbers, throughout: a coordinate is correct only in the tree that produced it, and this project has already lost time to a citation that was right in two trees at two different lines.)*

**A hypothesis disconfirmed, recorded so it is not re-tried.** Flatten reads orders (`read_snapshot`) before it loads the listing (`read_listing`), which looks like the bug. It is not: A/B tested on the live account, cold cache **0 rows**, `request_instruments()` called first **still 0 rows**. Reordering flatten's calls fixes nothing, because that call does not populate the cache. Only `cache_instrument` does.

## The second instrument: the whole read pipeline runs OFFLINE

Measured 2026-09-03 against the pinned wheel, with `cli.__file__` asserted to come from this worktree before any reading was trusted. The client's credential check is a **string-presence gate** and `base_url` redirects its transport to a loopback HTTP server, so `request_instruments()` rebuilds the listing from whatever `AssetPairs` body that server returns, and `request_order_status_reports` / `request_position_status_reports` then parse a canned `OpenOrders` / `OpenPositions` body against the instrument cache exactly as they would against the venue. Listing → cache → report runs end to end with **no venue, no credential and no host** — which is what lets this fix be discriminated on the legs the live fixture cannot reach, and lets CI run that discrimination. `tests/test_engine_data_socket.py` is the committed precedent for the shape.

**Two properties of the cache, measured there, and D1 rests on both.** It is keyed on the **instrument id** and scanned by `raw_symbol` — so a twin sharing the real instrument's id REPLACES it rather than joining it, and the key spelling then misses the cache altogether (100/100 stable, in either caching order). And nothing validates the two against each other: `raw_symbol="TOTALLY-GARBAGE-NOT-A-PAIR"` cached against `id=BTC/EUR.KRAKEN` is accepted, returns `None`, raises nothing.

**The three arms**, driven through this module's own `read_listing` / `read_snapshot` / `build_plan` / `judge_final` over six real `AssetPairs` listing rows — the five basket legs whose altname differs from their pair key, plus `SOLEUR` as the coinciding-spelling control — with one resting order per leg, each spelled the way Kraken's `descr.pair` spells it. **The last column is a residual-row count, not an order count**: `judge_final` collapses every resting order into ONE `{"kind": "order", "count": N, "reason": "resting_order"}` row, so the list it returns is length 0/1/1 across the three arms and the orders read are in the column before it.

| arm | cache | orders read | `judge_final` |
|---|---|---|---|
| A | cold — today's deployed flatten | **0 of 6** | no residual: *the account reads flat* |
| B | every listing row cached — D1 as first written | **1 of 6** (`SOL/EUR` alone) | one residual row, `count: 1` |
| C | listing rows **plus altname twins** | **6 of 6** | one residual row, `count: 6` |

Arm B is the finding: caching the listing alone is inert for **BTC/EUR, ETH/EUR, XRP/EUR, LTC/EUR and ETH/BTC**, and the live `SOLEUR` A/B moves 0→2 under B and under C alike — so the branch's own live proof cannot tell the two apart. That is why the arms above, not the live count, are what D1 is decided on.

**The position read is the same cache and a different failure**, measured on the same harness through `read_positions` and `margin_legs`:

| cache | the venue's `pair` | what flatten does |
|---|---|---|
| cold | key (`XXBTZEUR`) | **raises** — `FlattenUnreachable`, exit 3 |
| listing only | key | one `BTC/EUR` SELL leg — correct |
| listing only | altname (`XBTEUR`) | **raises** — exit 3 |
| listing + twins | altname | an `XBTEUR` row, **no leg**, `pair_not_listed`, exit 2 |
| listing + twins, alias applied | altname | one `BTC/EUR` SELL leg — correct |
| listing + twins, alias applied | key | one `BTC/EUR` SELL leg — unchanged |

Two things follow. The first row is **a live defect independent of this fix**: the deployed cold-cache flatten aborts at exit 3 whenever any margin position is open, whichever spelling the venue sends, so the red button is already unusable on a leveraged account — and D1's caching is what resolves it. The fourth row is what the twin costs if nothing else changes, and D1's alias is what pays it.

## Decisions

### D1 — Flatten populates the instrument cache before it reads anything, under BOTH of the venue's spellings

The fix is flatten's, not a reordering: after fetching the listing, feed it to the client's cache, then read. **Feeding the listing alone is not enough**, and the arms above are why — the cache is scanned by the listing row's `raw_symbol`, which is Kraken's `AssetPairs` **key** (`XXBTZEUR`), while an open order is looked up by its own `descr.pair`, which is the **altname** (`XBTEUR`). For every pair whose two spellings differ, the lookup misses and the row is dropped silently on a fully populated cache.

**So every such row is cached twice: once as itself, and once as a twin.** For each listing row whose altname differs from its `raw_symbol`, flatten additionally caches a `CurrencyPair` built from that row with `raw_symbol` set to the altname and a **distinct `instrument_id`** (`<altname>.KRAKEN`). The distinct id is mandatory rather than stylistic, and it is the cheap-looking edit a later reader will reach for: the cache is keyed on the id, so a same-id twin *replaces* the real entry and the key spelling then misses entirely — measured and disproven, not argued. On the 2026-08-04 listing that is **44 twins over 1429 rows**; no altname there equals another pair's key and no altname is held by two pairs, so the twin set mints no collision as the listing stands. **That listing is not committed** — `docs/reference/kraken-snapshot-register.md` pins its sha256 and says in its own words that the body under `data/snapshots/` is gitignored — so these three counts re-derive from that file or from the plan's own live re-reading of the endpoint, never from the repo alone. A future listing could, and on a `raw_symbol` collision the scan's answer is **non-deterministic** (~50/50, measured) with nothing in the adapter saying so.

**The twin's foreign identity is inert on the order path and NOT on the position path.** Every consumer of an order report in this module reads `len()` — `build_plan`'s `n_open_orders`, `_snapshot_payload`, `sweep`'s `orders_after`, `judge_final`'s residual count — and the cancel is `cancel_all_orders`, account-wide, taking no instrument id; no order report's `instrument_id` is read anywhere in flatten, so a row that comes back as `XBTEUR.KRAKEN` is counted correctly and acted on correctly. A **position** row is different: it carries the twin's id into `_symbol_of`, which yields `XBTEUR`, which the listing — keyed `BTC/EUR` — does not carry, so `margin_legs` builds **no closer** and the row surfaces as `pair_not_listed` at exit 2. That is a red button reporting a leveraged position instead of closing it, which is worse than the state the twin fixes. **So flatten resolves a twin-spelled position back to its real pair before anything reads it**: minting the twins yields `{altname: symbol}`, and the position read maps each row's symbol through that map. Measured, it restores the ordinary `BTC/EUR` SELL leg on the altname spelling and leaves the key spelling byte-for-byte as it is today.

**The altname comes from the public `AssetPairs` endpoint, fetched unauthenticated inside flatten — not from a committed map, and not from a derivation.** It is not on the listing row: the adapter's `CurrencyPair` carries no altname and its `info` is `{}`. It cannot be derived: stripping a leading `X`/`Z` from four-character asset codes reproduces all 44 real altnames but *invents* a difference for **16 of the 1429 rows** whose tickers genuinely begin with X or Z (XAUT, ZETA, ZORA, …), which is 16 spurious twins and, on some later listing, 16 chances at the non-deterministic collision above. And it must not be a twelve-pair basket map, because **flatten is account-wide by ruling** — `T0159`: the whole account, pre-existing spot balances included, "engine-owned-only is not 'everything to EUR'" — the basket **changes** (`DOT/EUR` was retained after the universe deselected it, `T0137`), and a hand-placed order on a pair nobody selected is exactly what an emergency exit meets. A map would leave the verdict blind on every non-basket pair, which is this same defect relocated. This is **not a new failure domain**: `read_listing` already calls the venue, and it calls this same endpoint — `request_instruments()` is `GET /0/public/AssetPairs`.

**A fetch that fails degrades VISIBLY, and a run without twins may not report a flat account in the same words as one with them.** If the fetch fails, flatten caches what it can and continues: refusing outright would kill the button over a second read of an endpoint that answered a moment ago, and cached-listing-only is still strictly better than the deployed blind state. But it continues **saying so** — the failure is journalled, told to the operator, and **counted as a residual**. **In an `--execute` run a missing-twins flat is exit 2 with a named residual, never exit 0** — measured. **A dry run cannot carry that code, and this spec does not give it one**: it returns before `judge_final` and before both residual appends, and its 0 means "the default dry run completed", which is spec `00106`'s rule and not this spec's to change. So on the dry run — the runbook's step 1, the first thing an operator runs — the printed degradation line is the whole signal, which is why the message is `say`-ed as well as logged, and why that step's own paragraph says a 0 there does not mean the read was complete. Visible is the requirement; the exit code is how execute mode meets it and the terminal is how the dry run does. The reason is the containment rule below, arrived at independently and for the same cause: the run computes its own flat/not-flat verdict from reads that are missing rows, and *the account reads flat* over exposure nothing looked at is the failure this spec exists to close. Silent degradation back to 1-of-6 is precisely how this class of defect works — the number moves and nothing says it moved. A twin that fails to construct or cache on its own row is contained per row and joins the same list, exactly as an uncacheable listing row does.

**Not** a workaround for an upstream defect we are hiding — the upstream silent-drop is separately reported (see D7). This is our code failing to meet a contract the adapter documents by having a public `cache_instrument` at all.

**A row that cannot be cached is contained, and the containment reaches the verdict.** Caching runs over the whole ~1600-row listing, so one bad row must not abort a button that has cancelled nothing — but a row nothing cached is a row this run cannot SEE, and the run computes its own flat/not-flat verdict from reads that row is missing from. Silent containment would therefore let flatten print *the account reads flat* over exposure it never looked at, which is the failure this spec exists to close. So: an uncached row is named in the journal, told to the operator, and **counts as a residual**, so the run cannot be called flat. And the case where **no** row could be cached is not containment at all — it is the pre-fix blind state, and it refuses before the first write. These add INPUTS to flatten's existing exit rule; the rule itself, the write sequence and the confirmation gate stay spec `00106`'s and are untouched.

**The new inputs reach the operator's own surfaces, because the rule's DESCRIPTION is now narrower than the rule.** Exit 3's cause is pinned on the venue everywhere an operator meets it (spelled "the venue could not be reached or read", or just "the venue could not be read"), and the whole-listing refusal is not the venue — an operator reading it during an incident goes and checks Kraken's status page while the venue is healthy and our own cache writer is not, with the red button unpressed for the length of that detour. Exit 2's **two** new residual `reason`s are likewise absent from the runbook's exhaustive per-`reason` triage list, whose nearest neighbours all end in "run it again" — which against an unchanged cause reproduces the same residual, when the action owed is to hand-check the pairs this run was blind to: the pairs the record names for an uncached row, and every legacy-coded pair on the account when the altname fetch is what failed. So the exit-3 clause is widened wherever it is written to say the account could not be READ before anything was sent — unreachable, or the reads not preparable — and the triage list gains both new `reason`s. **Widening the cause is not enough on its own**: exit 3's one statement of what to DO reads "nothing was sent; the account is as it was", whose implied wait-and-retry is right for an outage and wrong for a cache writer that will refuse identically on the next run, so that statement gains the action the new cause owes — the account was not read at all, so it is checked by hand on the venue's own pages. The rule is unchanged; what changes is that its description stops being false.

### D2 — The funding gate fails CLOSED when the free balance is known to be untrustworthy

`plan_refusals` gains a refusal: when the account reports `locked == 0` **and** any order is resting, `free_zeur` cannot be trusted and the plan is refused. This converts a fail-open safety gate into a fail-closed one **without replicating Kraken's reservation semantics**, which are non-obvious — measured, the spot order held 2.757 EUR and the 2:1 margin order held nothing.

**The signal is MEASURED on the cash branch and ASSUMED on the margin one, and that gap stays open until the attended verification closes it.** The `locked == 0` above is flatten's `CASH`-typed `request_account_state`. The gate's input is a different account object: `executor._pickup` reads `venue_state_from_cache`, which takes `Cache.account_for_venue` — filled by the exec client `node.py` builds `spot_account_type=AccountType.MARGIN`, the branch D7 records as already deriving a real `locked` through `from_total_and_free`. Nothing in this repo has read `locked` there. Every reading of that account recorded to date prints `.total` alone, and the probe harness's own comment beside that render says whether those figures are wallet balances or TradeBalance-derived equity "is not readable from here", its printed note asking the operator to RECORD which; `adapter-verification/1.230.0.md` answers the same question for an older version with **TradeBalance-derived equity in `margin_balance_asset`**, a different quantity again that says nothing about holds. So the refusal keys on a premise this spec did not measure on the path the refusal runs on.

`docs/plans/00111-adapter-blind-reads.md`'s attended task takes that reading before this ships, in both states the fixture makes available — the minted position open, and closed again with the spot order still resting — and every outcome is decided here rather than on the day. **`locked == 0` on that account and the refusal holds as designed. `locked > 0` and D2 is inert exactly where it was wanted**, since a hold reported for any reason satisfies the conjunct that releases the refusal. That re-keys the refusal: it is a stop before closeout, and the reading is recorded either way. A reading that could not be taken is recorded as not taken — a null is never read as the zero that would confirm the design.

**Keyed on the account, never on one currency.** The guard reads the whole locked map (`{currency_code: held}`), not a single `ZEUR`/`EUR` scalar: it refuses when **no** balance reports a hold while an order rests. A per-currency lookup would have to pick a spelling, and the two live surfaces disagree — the instrument quote currency is `ZEUR`, the account's free-cash key is `EUR` (measured, `{'EUR': 99.84}`) — so a wrong pick reads a permanent 0.0 and jams the gate shut with no way to tell that from a real reading. An **empty** map is treated as no balance reporting a hold, which refuses: a read that learned nothing is exactly the untrustworthy input this refusal exists to catch.

**Where it runs.** The refusal has to hold at the live arming gate — `executor._pickup`, which reads the Cache directly and can therefore see both the locked map and the resting-order count at one instant. `zcrypto engine probe-plan --check` is the other `plan_refusals` caller and it can supply neither: it reads a journalled `venue-<HH>.json`, whose `state` carries no holds and no orders. **It does not evaluate this refusal, and says so in its output** — that command's own contract already declares it "Advisory only -- the engine re-validates every plan live before any order", and widening the venue-journal record format to carry both inputs would bump `VENUE_SCHEMA_VERSION`, put three other readers' `schema_version != 2` filters and `validate_venue_record`'s exact key set in the blast radius, and add a rollback hazard on the live trade path. `VenueState` therefore gains `balances_locked` as a live field that `to_payload()` does **not** journal.

**What declining the schema bump leaves open, named rather than implied.** One of those three readers is not advisory: `executor._newest_venue_balances` returns the journalled `state.balances` and `_classify_close` hands it to `_classify_spot_close`, whose `qty <= balance` bound at `REDUCE_ONLY` is on the live trade path — that function's own docstring calls the bound plus the venue's insufficient-funds rejection "the whole guard". Those balances are `account.balances_free()`, the figure mechanism 2 above shows is overstated by whatever the venue holds. So this spec closes the fail-open at `plan_refusals` and **leaves the identically-caused one at `_classify_spot_close` open**, at the stated price of not bumping the schema. It is registered in `T0160` beside the `hold_trade` report that would remove the overstatement at its source; a decision recorded only here would be untracked.

**Rejected: computing held funds ourselves** from open orders. It requires reimplementing venue-specific reservation rules we have exactly one observation of, and a wrong reimplementation fails open again while looking correct.

**Rejected: the engine reading `BalanceEx` directly.** That is a second signed client on the trade key, which is what spec `00090`'s one-key-one-client rule exists to prevent, and `kraken-cli` is a workstation development tool that is never an engine dependency.

**The cost is real and stated**: arming is blocked whenever an order rests, which at RUNG 1 may be exactly when arming is wanted. That is the deliberate trade — a blocked arming is recoverable, an overcommitted plan is not.

### D3 — D2's guard asserts loudly whenever a balance reports a hold

D2 keys off `locked == 0` as the signal that the number is untrustworthy. If the upstream fix lands, `locked` becomes real and the guard silently stops firing — correct behaviour reached by accident, and invisible.

So: **`locked > 0` on any balance is a loud, logged assertion**, not a silent pass. The upstream release cadence is outside this project's control, so the change must announce itself rather than be noticed later. The guard is not pinned to an adapter version — a version pin rots as silently as the thing it guards.

**It announces on every evaluation, not once — a decision, not an oversight.** A first-time-only announcement needs state that survives ticks and process restarts, which is a mechanism with its own failure modes bought to make a log quieter. So the guard keeps no memory, and its line says what it READ — a balance reports held funds, and the refusal does not fire while that holds — never that the adapter has *changed*, because nothing in the guard observed a change. Whether that line appears once in this branch's life or on every pickup is settled by the same unmeasured reading D2 names: zero on the exec client's `MARGIN`-typed account and this is the rare transition alarm it was designed as; non-zero and it is a per-pickup line on the live trade path, whose reader would be re-deriving the funding gate against an upstream change that never landed. That is the second reason the reading is owed before this ships.

**The announcement is evaluated independently of the refusal, never as its `else` branch.** On a map that is wholly zero or wholly positive the two are complementary and the shape makes no difference; the state that separates them is a map carrying **both** a non-finite hold and a real one — there the refusal fires on the broken reading while a balance is genuinely reporting a hold, and the real hold still has to announce itself.

**Its stated limit, which no code shape removes.** The signal comes from a balance reporting a hold, and the measurement above says a resting 2:1 margin order holds nothing. So **on the cash branch's reading** an account whose only resting order is a margin order produces `locked == 0` even after the upstream fix lands: the refusal keeps firing on a reading that has become truthful, and nothing announces it. What the `MARGIN`-typed account the guard actually consumes does here is a different question and not a milder one — its `locked` is derived `from_total_and_free`, which moves with margin in use rather than with an order's hold — and it is the same unmeasured reading D2 names, whose outcomes D2 decides in advance rather than this paragraph restating one. The fixture's spot leg is what supplies the hold in practice. Recorded rather than engineered around — the alternative is inferring trustworthiness from the absence of a reading, which is the fail-open this whole decision exists to close.

### D4 — The mechanism is proven OFFLINE, by value; the live fixture proves it survives the real venue

The prior version of this defect was retracted on a control that read the same whether the defect was present or not. The offline harness above is the instrument that answers that properly — it discriminates the fix on the legs the live fixture cannot reach, it needs no venue, and CI runs it. The live readings are still taken, and what each one is now FOR is stated rather than assumed:

- Orders, offline: **arms A/B/C, 0 of 6 / 1 of 6 / 6 of 6**, over six listing rows and six resting orders spelled as the venue spells them. That is the whole discriminator for the mechanism, and it is the only reading in this spec that can tell the twin fix from the cached-listing-only one. It is a committed test, so it also guards the fix against a later edit that quietly removes the twins.
- Orders, live: the A/B is **across code versions, not across cache states inside one run** — a post-fix flatten performs exactly one order read, so it has no cold arm of its own, and it prints a count and never a txid. So: the count read through the *deployed* pre-fix flatten (0), the count read through this branch's (2), and both fixture **txids by identity from `kraken-cli`**, the non-adapter witness, taken between the two arms. **What this pair is now for**: not the mechanism, which the arms above settle, but that flatten's twin path survives the real venue — the real listing rather than six replayed rows, the real `AssetPairs` body behind the altname fetch, and the real credential. A count moving against an unchanged witness is still the reading; either arm alone reads the same whether the defect is present or not.
- **The live fixture's spelling class, stated because it stays true and no longer limits the FIX.** The fixture pair is one whose Kraken `AssetPairs` key and altname coincide (`SOLEUR`), so a live count moving 0→2 on it moves identically under arm B and arm C, and cannot separate them. It does not need to: the twin makes the lookup succeed **under either spelling the venue might send** — key spelling hits the real entry, altname hits the twin, and both are measured — so which one Kraken puts in `descr.pair` stops being a question flatten's correctness turns on. What the enumeration is still for is reading the live counts honestly: `docs/reference/kraken-snapshot-register.md` and `cli/ohlc/fetch.py`'s `PAIR_KEYS` — two committed records of the same live `AssetPairs` fetch, and they agree — give a pair key that is NOT the display symbol with the slash removed for **seven** of the basket's twelve legs (BTC/EUR `XXBTZEUR`, ETH/EUR `XETHZEUR`, XRP/EUR `XXRPZEUR`, DOGE/EUR `XDGEUR`, LTC/EUR `XLTCZEUR`, ETH/BTC `XETHXXBT`, SOL/BTC `SOLXBT`), of which **five** part company with their altname as well and are exactly the legs arm B leaves blind; both legs of spec `00090`'s T2 set, the BTC/EUR long and the ETH/EUR short RUNG 1 opens first, are among them. **Where the spelling question does still stand open is the ENGINE, not flatten**: `executor`'s three readers of the nautilus Cache take their orders from a reconciliation read through this same adapter, on a client nothing in this repo caches instruments into, and no twin of flatten's reaches it. That is registered in `T0160` beside the cancel-sweep blind spot it belongs to, not closed here.
- **Fills are NOT verified here, deliberately.** Nothing in `cli/` reads them — `request_fill_reports` and `fill_report` appear in no file under `cli/`, `tests/` or `infra/`, and `read_snapshot` is exactly orders, positions, balances — so no run this change makes could produce a fill row, and the committed record carries no fill identity to compare one against (the measured-basis table says what it does hold). D1's claim about `request_fill_reports` stands as a statement about the adapter; it gets no verification leg because this repo executes no fill read.
- Positions: assert the minted margin leg appears **by symbol and by the closing side that corresponds to what `kraken-cli`'s `positions` read reports** — not against a row count, and not against the adapter's own second opinion. Never side-equality: flatten's plan prints the closer's side (`margin_legs` maps `LONG`→`SELL`, `SHORT`→`BUY`), so a minted long appears there as a `SELL` leg. Asserted as equality the two surfaces disagree by construction and a correct run reads as a failure; asserted as "whatever it says", an inverted side passes. The mapping is what makes the comparison a comparison.
- The guard: assert it refuses while orders rest, and that `locked > 0` trips D3's assertion.
- The gate's own account: `total`, `locked` and `free` read on the exec client's `MARGIN`-typed account — the one `plan_refusals` actually sees, and the one D2's signal is assumed rather than measured on. The outcomes are named in D2, in advance; a reading that could not be taken is recorded as not taken and never as a zero.
- **A degenerate fixture proves nothing.** An empty account passing every check is the failure mode this spec exists to close.

### D5 — `request_position_status_reports` is verified HERE — measured offline across every branch, and corroborated against a real position minted for the purpose

It reads 0 on the live account with the cache warm — but the account holds no position, only an unfilled margin order, so 0 is the correct answer and carries **no information**. A path that returns the right answer for the wrong reason is exactly the degenerate control this spec exists to stop accepting.

**Flatten's entire close half depends on this path.** If positions are blind the way orders were, `--execute` would cancel the orders, see no positions, and report the account flat with a position still open — the self-confirming failure, on the half that moves money.

**The assumption that the order fix covers positions is no longer an assumption — it is measured, and it was wrong in both directions.** The offline harness drives `read_positions` and `margin_legs` through the real client across six branches (the table above): the cache gates this read too, but it **raises** on a miss where the order read drops silently, so a cold cache aborts the button at exit 3 rather than reporting flat — and with twins cached, an altname-spelled position produces `pair_not_listed` and no closer unless flatten maps it back. Both are behaviours no assumption predicted and no live reading in this branch's budget would have found. They are pinned by committed tests, on the real client, for every spelling.

So the fixture still grows a **filled margin leg**, and the attended verification task of `docs/plans/00111-adapter-blind-reads.md` reads both paths before it ships: orders **and positions**. What that live read is for has narrowed to match: not whether the mechanism works, which the harness settles for both spellings, but that it works against the real venue's own payload, listing and credential, on a position the venue actually opened. The minted leg is `SOL/EUR`, so the live reading is on the coinciding-spelling class — which no longer limits the fix, only that reading.

**The test double stays ORDER-only, and the reason has changed.** It was ungated on positions because a cache gate nobody had observed would have manufactured agreement; the gate is now observed, but modelling it in `FakeClient` would force a fixture migration across every positions test in the suite and buy nothing, because the loopback harness exercises that read on the **real client** — a stricter witness than any double. Recorded so the ungated position read is not later "corrected" into the double.

**The verification must run THIS branch's code, and the host wrapper cannot.** `/usr/local/sbin/zcrypto-flatten` runs `{{ engine_image }}@{{ engine_image_digest }}` — the deployed pin, which predates this branch — so a wrapper run exercises flatten without the fix and returns the same empty list the defect returns, indistinguishable from a failed fix. The route is the one the 2026-08-26 pass already used and documented: run from the workstation worktree with the vaulted trade key in the environment, the workstation's public IP temporarily allowlisted on the `zcrypto-engine` key, and the allowlist closed again as a numbered step (spec `00039` decision 3's closure step). The dry run is read-only and shares the key with the running engine, which is the same accepted exposure `zcrypto-flatten`'s own dry-run banner names.

**Cost, stated**: one market-filled margin leg at `ordermin` — roughly EUR 5 of exposure plus ~EUR 0.04 taker fee, and Kraken rollover accruing every 4 h while it is open. The position is closed by the attended task's own `close` step, through the same committed script that minted it; it is not left open.

### D6 — The fixture is minted by a committed script, not by clicking

Click-driven order entry is error-prone and unrepeatable, and this fixture will be re-minted every time the account is flattened. So the mint is a committed script over `kraken-cli`, with:

- **`--validate` as the default and `--execute` opt-in** — the same safety inversion `zcrypto-flatten` uses, and `kraken order buy --validate` ("Validate only, do not submit") makes it a real end-to-end exercise against the live API rather than a simulation.
- **`--cl-ord-id` on every order**, so each fixture leg is identifiable by name rather than by matching txids after the fact. The owner could not tell the spot leg from the 2:1 margin leg in the venue's own list; that is a property of the fixture, not of the venue.
- **`mint` places exactly ONE leg** — the margin leg this decision prices below. The two hand-placed limits are not re-minted here: they already rest, they must survive, and a second executing leg is money nothing authorised. Any other submitted count is a defect, and the script states the number it will submit.
- **A `close` mode carrying the exact netting command**, `--validate` by default like `mint`. Closing the minted leg is the one live-money act with a rollover clock on it, and typing it by hand under that clock is how a netting sell becomes a fresh short. The order is `--reduce-only` so the venue itself refuses to open a position with it.
- **`-o json` throughout**, so verification parses rather than eyeballs.
- **A verify mode reading back through `kraken-cli`** — `positions`, `extended-balance`, `open-orders` — which is the **independent, non-adapter witness**. Every verification in D4 compares the adapter against this, never the adapter against itself.

**`kraken-cli` is a workstation development tool.** It is used for R&D and fixture management before RUNG 3 completes; it is **not available in CI, is never imported by `cli/`, and is never a runtime dependency of the engine.** The script lives beside `infra/scripts/kraken-order-semantics-probe.py` and carries that constraint in its own header.
