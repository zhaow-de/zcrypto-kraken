# The engine on the VPS — deployment, watchdog, gate ops (design)

**Iteration:** iter-084 (attended — the deployment iteration; decisions log `[iter-084]`). **Goal:** the shadow engine runs 24/7 on the D2 VPS as a second compose service beside capture, with the §8-hardening gate honored before the trade key lands, the §10 dead-man's switch live, and the workstation equipped to run the pre-registered gate ops — **the Stage-6a gate clock starts at the VPS node's first journaled cycle** (deploy-now decided `[iter-084]` item 1). *(Revised after the three-agent adversarial pass — secrets handling, the sync channel that turned out not to exist, fail-fast node startup, host resource budget; decisions log `[iter-084]`.)*

## One image, two services

The existing `ghcr.io/zhaow-de/zcrypto-capture` image installs the whole `cli` package — the engine reuses it with a compose-level **entrypoint override** (`["zcrypto", "engine", "run"]`, exec-form, cleanly bypassing capture's shell ENTRYPOINT; `zcrypto` resolves on the image's venv PATH). Workflow change: `.github/workflows/capture-image.yml` path triggers extend to **`cli/**` + `pyproject.toml` + `uv.lock`** (today's image predates `cli/engine`); the image name stays (a comment notes it serves both services). Both services deploy **by digest**; the engine role takes `engine_image_digest`, asserted non-empty.

## Code additions (TDD, before any infra)

1. **The dead-man's switch** (`cli/engine/cycle.py`): after the record/sidecar lands — if `HEALTHCHECK_URL` is set, GET it (success → the URL; sidecar → `<url>/fail`), short timeout, one attempt, exceptions swallowed and logged; injectable opener. **The third completion path is pinned by design**: a *propagating* exception (poisoned store, disk error) produces **no ping — the dead-man's switch alerts by silence** after period+grace; an alert *without* a preceding `/fail` ping therefore reads "the node is up but a cycle raised — `journalctl`, suspect the store", not "the container died". Tests: success ping, /fail ping, unset → no call, opener exception → cycle result unaffected.
2. **Fail-fast `engine run`** (`cli/engine/command.py` / `node.py`): before building the node, `run` **hard-fails** (exit 1, clear message) when the store dir is missing/empty (a node with no store is always misconfigured — the ansible-delivered store must exist) or when `ZCRYPTO_REQUIRE_CONFIG=1` is set (the engine compose sets it) and no `zcrypto.toml` was found — closing the silent-degradation hole where a mistyped bind-mount runs a default-config node (exec off, journal under `/app`) indistinguishable from generic missed cycles. After starting, a **supervision watchdog** exits non-zero if the node's trader is not RUNNING once `timeout_connection + timeout_reconciliation + slack` has elapsed — a failed exec-client connect (bad key, IP/family mismatch, venue outage) becomes a **visible crash loop that `restart: unless-stopped` heals**, never a silent zombie burning gate days. `run` also logs the effective config (`exec_enabled`, both dirs) at startup — the deployment's first-start verification reads that line. Tests: store-missing exit, require-config exit, watchdog exit on a never-running trader (mocked), config log line.
3. **`--journal-dir` overrides** on `replay` and `report` (flag → config, the repo convention) so the workstation verifies the pulled VPS journal; **README `## Usage` documents both flags in the same change** (readme-usage rule).

## The `engine` ansible role (`site.yml` gains it after capture, all tasks tagged `engine`)

1. **The §8-hardening gate — asserts before anything else** (read-only commands with `check_mode: false` so dry-runs still evaluate them): nftables unit **enabled** (`systemctl is-enabled nftables` — it is a `RemainAfterExit` oneshot, so `is-active` alone can be stale) **and the live ruleset non-empty** (`nft list ruleset | grep -q .`), fail2ban active, unattended-upgrades installed + enabled, and the sshd posture spot-checked (`sshd -T` reports `permitrootlogin no`, `passwordauthentication no`, `allowusers deploy`). Any failure aborts **before a single secret is rendered**.
2. **`kraken-engine` account — created by the engine role itself** (deliberately unlike `kraken-capture`, which the base role creates: in-role creation keeps `--tags engine` self-sufficient on first deploy). System user, `nologin`, home = the state dir, `create_home: false`; uid/gid derived via `ansible_facts["getent_passwd"]` (not the deprecated top-level fact), guarded for first-run check mode.
3. Directories: `/var/lib/zcrypto-engine/{store,journal}` owned `kraken-engine:kraken-engine`, `0750`.
4. **Store delivery** (only when absent — converges never clobber a live store): copy the workstation's warm, QA'd `data/engine-store/` (7.7 MB; ansible runs from the workstation). **Run the delivering converge away from a 4h-boundary+30-min window** (the workstation soak rewrites the store inside it — a mid-write copy could deliver a truncated parquet) and read-verify one file after delivery. **VPS store-poisoning runbook (the code's `engine seed` repair is workstation-only — the image has no canonical dataset):** stop the unit → `rm -rf /var/lib/zcrypto-engine/store` → re-run `site.yml --tags engine` (the only-when-absent copy re-delivers) → start.
5. **Secrets via env_file, never in compose**: `/opt/zcrypto-engine/engine.env` rendered **`0600 root:root`** with `no_log: true` and `diff: false` on the task (a `--check --diff` must never print key material), carrying `KRAKEN_SPOT_API_KEY`, `KRAKEN_SPOT_API_SECRET` (vault), `HEALTHCHECK_URL` (vault, the new check), and `ZCRYPTO_REQUIRE_CONFIG=1`. The rendered `compose.yaml` (0644, like capture's) references it via `env_file:` and **stays secret-free and safely diffable**.
6. **Rendered `zcrypto.toml`** (`/opt/zcrypto-engine/zcrypto.toml`, bind-mounted read-only at `/app/zcrypto.toml` — WORKDIR is `/app` and `load_config` reads CWD, verified): `[zcrypto.engine]` with absolute `store_dir`/`journal_dir` → the volume paths, **`exec_enabled = true`**, `shadow_nav_eur`/`settle_delay_secs` stated explicitly.
7. **Rendered compose** (`/opt/zcrypto-engine/compose.yaml`): image@digest, the entrypoint override, `user:` kraken-engine uid/gid, `env_file`, volumes (state dir + the toml), **resource budget sized to the 2-vCPU/4-GB host with capture as the protected service**: engine `cpus: "0.75"`, `memory: 1g`, `cpu_shares: 512` (capture's default 1024 wins contention deterministically; combined memory caps 2g+1g stay under host RAM with OS headroom; the workstation node's measured RSS informs any adjustment — measured before deploy). Capture-style logging caps, `restart: unless-stopped`.
8. **systemd unit** `zcrypto-engine.service` (system; capture's pull/up/down pattern; enabled — boot resume).
9. **The journal pull channel — provisioned here, it does not exist yet** (the vaulted `sync_ed25519` key material was never installed anywhere; sshd `AllowUsers deploy` stands): install the sync **public** key as a second entry in **`deploy`'s** `authorized_keys` with `command="rrsync -ro /var/lib/zcrypto-engine/journal",restrict` (rrsync from the `rsync` package — ensure installed) — that key's sessions can only read the journal subtree regardless of deploy's other powers; add `deploy` to the `kraken-engine` group so the 0750 top dirs are traversable (container-written content lands 0755/0644 under umask 022 — verified once on the host at deploy). **Cross-linked to T0003's open pull sub-item** (same mechanism can later serve the capture pull; scoped paths differ — noted in T0003, not built here).

**Capture safety (the L2-gap rule):** the role touches no capture file, unit, or variable. Deployment order: full-site **`--check --diff` dry-run with BOTH digests supplied** (`-e capture_image_digest=sha256:<current — read from the host's rendered compose> -e engine_image_digest=sha256:<new>`; without them the digest asserts abort the dry-run before surfacing drift) → review → **`site.yml --tags engine`** only. The capture container is never restarted by this deployment.

## Workstation gate ops

1. **Journal pull one-liner** (documented in README's engine section): `rsync -az -e "ssh -i infra/ansible/files/sync_ed25519 -p 10022" deploy@<vps>: data/engine-journal-vps/` — the rrsync forced command pins the remote side to the journal subtree, so the source path is implicit. First pull **verified attended** before the timer is installed.
2. **The daily gate-ops user timer** (`infra/systemd/zcrypto-engine-gateops.{service,timer}`, workstation): a oneshot with `WorkingDirectory=<repo>`, `ExecStart=/bin/sh -c` wrapping pull → `replay --journal-dir data/engine-journal-vps --path verified --date "$(date -u +%%F -d yesterday)"` → `report --journal-dir data/engine-journal-vps`, sequenced so **report still runs when replay exits non-zero** (capture the rc, run report, exit rc); `OnCalendar=06:30 UTC` (all of UTC-yesterday complete); failures surface in the user journal (the human's daily read — no pager for gate-ops itself, stated). This automates the pre-registered **≥ 1 verified-path replay per day**. `date -u` is load-bearing: a local-time "yesterday" computed near midnight CET names the wrong journal day.
3. The workstation soak keeps running in parallel until the 6a exit review (`[iter-084]` item 3); the new ping code no-ops there (`HEALTHCHECK_URL` unset). Known cosmetic: a mid-cycle kill + restart can append a duplicate `orders.jsonl` block for one boundary (records are unaffected; headers carry `cycle_ts` for de-duplication) — accepted and noted so 6b never treats those blocks as at-most-once.

## The attended deployment sequence (closeout, in order)

1. **Healthcheck**: `POST /api/v3/checks/` with the vaulted API key — `name=zcrypto-engine-shadow`, `timeout=14400`, `grace=2100` (30-min gate-passable window + 5-min margin ⇒ worst clean success-to-success gap ≈ 4h29m < 4h35m alert threshold); vault the ping URL as `engine_healthcheck_url`. Note: **a never-pinged check does not alert** — the attended first cycle (step 4) supplies the first ping and arms it.
2. **Image**: `workflow_dispatch` off merged `develop`; digest from the job summary.
3. **Deploy**: the exact dry-run above → review → `./scripts/run.sh site.yml --tags engine -e engine_image_digest=sha256:<…>` → unit active.
4. **First-start verification, then the first cycle watched live**: `journalctl` shows the effective-config line (`exec_enabled=True`, the volume paths), the exec client connects and reconciles (the iter-079 probe-2 semantics — no crash-loop from the watchdog), the key's allowlist matches the VPS's actual egress IP/family; at the next 4h boundary the cycle journals, **the healthcheck receives its arming ping**, and a manual journal pull + `replay --path verified` + `report` on the workstation round-trips it — **the Stage-6a gate clock's first tick**, quoted in the history entry.
5. **Gate-ops timer** installed on the workstation after the attended first pull.
6. Closeout: **T0018 sync** (Done-so-far gains iter-084 with links; Suggested-next-steps trimmed to the 6b executor alone; `ripe_when` refreshed to "the Stage-6a gate is met and the human convenes the 6b executor session"); **a journal-retention deferral registered** (VPS journal grows ~1.4 GB/month at full-history snapshots — prune-after-verified-pull design deferred with a `ripe_when` disk watermark, folded into or beside T0003's disk-watch item — prose is not registration); iterations-history entry; PR into develop; merge on the human's go.
