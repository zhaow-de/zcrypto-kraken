# The store door holds a frame to its whole width and names one recovery per host

## Problem

`_require_joinable_ts` in `cli/engine/store.py` is the door both store readers that join, `seed_store` and `refresh_store`, hold a frame at before the seam, and it reads two dtypes and nothing else: `ts` held to `Datetime("us", "UTC")` and `close` to any numeric dtype. Everything else a parquet round trip preserves passes it ([[T0199]]): a re-typed `open` or `count`, an extra column or another column order dies at `_reconcile`'s concat as a bare polars `SchemaError` or `ShapeError`, past `run_cycle`'s `except OHLCError` and both commands' `except EngineError`, and when the deviated file is the canonical it has already been copied into the store, so every later run fails on the store's own file; a re-typed `close` of real prices is refused at the seam as an overlap mismatch that blames the data and, under `refresh_store`, prescribes `zcrypto engine seed`, which over that file reaches the same concat; a frame with no rows is copied and then refused as a window shortfall; a null stamp is carried into the store by both readers and refused later by `read_store_series` under `run_cycle` with a type-shaped message and no recovery, or dropped silently by a replacing re-seed; a repeated stamp is carried by both readers, inflates the seam's overlap count and collapses silently in `_union_align` and `select_model_inputs`; an interior stamp off the leg's grid enters the model calendar from any EUR leg, which the soak's realized leg refuses since [[T0201]] and the cycle does not; and a close that is NaN, infinite, zero or negative at a stamp outside the REST overlap is carried to `_journal_snapshots`, which refuses it at every boundary under spec 00116 D1, the store poisoned until someone repairs it. The door's two recoveries are written for `ts` alone: the store-file text prescribes an in-place `ts` recast, which a Float32 price has no equivalent of, and the two `close` refusals and both of `read_store_series`' carry no recovery at all; neither routes by host, though `refresh_store` runs at every boundary on the engine host, where `zcrypto engine seed` does not exist.

The owner ruled on 2026-09-20 and 2026-09-21, in chat, on the memo's analysis and this branch's first half: the door's width is the whole `FRAME_SCHEMA`, non-empty, no null or repeated stamp, every stamp on the leg's own epoch-anchored grid, and a present close finite and positive exactly as spec 00116 D1 holds the engine's snapshot write, `None` staying admitted as an absent bar; the check runs at the store door and over the canonical before it is copied; the claim the change carries is that every frame it newly refuses either already fails at the seam or at `_reconcile`'s concat, or is a null, repeated or off-grid stamp or an unusable close no writer in the tree produces; one workstation recovery for every refused store file, the leg moved aside and `zcrypto engine seed` copying the canonical for the absent file and REST filling the gap, the loss named being any bar past the canonical's tail that REST cannot reach, which replaces the in-place recast text; the engine host's repair is the store copied aside on the host, the attended converge with `-e converge_primary=true` re-delivering the workstation's copy, the validation measurements the runbook prescribes taken, and the aside copy purged after the last of them, the `rm -rf` text leaving the engine role's `fail_msg` and delivery comment and spec 00042; the three code carriers that send an operator to the workstation command route by host; and no converge is part of the change. This spec records that ruling as D1 to D8 and settles what it left open: the refusal's text (D4), what the seed prints over a refused canonical (D5), the host repair's aside destination and purge point (D7), the amendable status of spec 00042 (D8), the tests the width changes (D9), the enumeration behind the live-path claim (D10), and the side the seam's absent-close refusal routes by, which the ruling's one recovery reaches through `_reconcile` (D6); D11 records what [[T0201]]'s host read settled in spec 00115. It settles one thing the ruling's one recovery presumes and does not say: a row the venue's own REST answer carries that the door refuses -- a stamp off the grid, an unusable present close -- must not enter the store, or the prescribed re-seed fills it back from the same window and the next refresh refuses the same file forever; so the door runs over the REST frame before the merge as well, and that refusal is the venue's, with no store repair and no edit (D1, D3, D4).

## Decisions

**D1. The door holds a frame to the whole width, in one order; the canonical is held before the copy, and the REST fetch before the merge and, in the seed, before that copy.** `_require_joinable_ts` becomes `_require_store_frame`, the same signature, over a new `_frame_differences(frame, interval)` that returns the first failing arm's differences in the order a later arm presumes the earlier: every `(column, dtype)` of `FRAME_SCHEMA`, imported from `cli/ohlc/dataset.py`, present with that dtype, and no column outside it, each difference listed as `_read_canonical` in `cli/ohlc/reach.py` lists it (`open is Float32, not Float64`, `close is absent`, `extra is not a column of it`); then the column order (`the columns are in another order (...)`); then the keys, no rows (`it has no rows`), a null stamp (`ts is null in N row(s)`), a repeated stamp (`N row(s) repeat a stamp another row carries`); then the grid (D3); then the value (D2). The order is the one a reader can act on: a dtype difference makes the order question moot, an absent row set makes the stamp questions moot, and a stamp question precedes a value question because the value's message names the stamp. `seed_store` runs it over the canonical with `frozen=True` before `write_parquet` copies it, as it does today for the two dtypes, so a refused canonical leaves no store file for the next run to refuse under the store's recovery, and over the store file with `frozen=False` after the copy or the read, and `refresh_store` over the store file, before `_reconcile`; both readers run `_frame_differences` over the REST frame too, through `_require_rest_frame`, after `to_frame` and `drop_in_progress` and before the merge -- in `seed_store` above the `if not store_existed:` block, so a refused fetch leaves no store file either, exactly as a refused canonical does (D4) -- because a row the venue's own answer carries that the door refuses must not become resident -- every re-seed would fill it back from the same window and every refresh would refuse the file again (D3, D4) -- and the schema, order and repeated-stamp arms cannot fire on a frame `to_frame` wrote while a null stamp is dropped by `drop_in_progress` before the call (D10), so what that call catches is the grid arm and the value arm over the venue's own row, an empty fetch being left to `_reconcile`'s shortfall, which names it with its own recovery; `read_store_series`' checks are untouched, a type reader for the soak whose docstring names the door as the owner of the dtype, of the grid and of the value, since a frame the width refuses at the store never reaches a boundary's read, and the soak's own leg holds the 4h grid since [[T0201]], the second reader, over a store no door of the store module read -- the daily row's scratch copy. The check is a schema comparison, three series reads and two filters over one leg's frame, run twice for each of the twenty-four legs at the refresh, over the store frame and over the REST fetch; nothing is read that `_reconcile` does not read already.

**D2. A present close is finite and positive; `None` is an absent bar and passes.** The predicate is spec 00116 D1's, `close is not None` first and then finite and positive, written over the column as a polars filter, `is_not_null() & (is_nan() | is_infinite() | (close <= 0))`, and the message names the first offender the way that spec's message does, `close[<k>] at <stamp> is <repr>, not a finite positive number`, then the count of such closes in the leg, so the two doors agree on every value and an operator reads one sentence at either. A null close at an unshared stamp is what spec 00116 D2 admits at the write and what this branch's seam keeps admitting at a REST-only row: the door admits it too, and a null close at a shared stamp is the seam's refusal, one step later, unchanged.

**D3. Every stamp is on the leg's own epoch-anchored grid.** The grid is `interval` minutes from the Unix epoch, as `aggregate_minutes` in `cli/backfill/aggregate.py` floors it and `_on_grid` in `cli/engine/soak.py` tests it for the 4h leg, so no origin is read off any frame: `ts.dt.epoch("us") % (interval * 60 * 1_000_000) != 0` is the filter, over both grids, 1440 and 240, read in microseconds because that is the frame's own resolution -- `ts` is `Datetime("us", "UTC")`, and `dt.epoch("s")` floors a sub-second offset to a zero remainder, so a seconds arm would admit at this door a stamp `_on_grid`, exact to the microsecond, refuses at the same instant -- and the message names the count and the first offender (`N stamp(s) are off the 240-minute grid, the first <iso>`). This closes [[T0199]]'s live-path case, the interior off-grid stamp `select_model_inputs` admits into the model calendar from any EUR leg: `refresh_store` is `run_cycle`'s step 1, so a store leg carrying one is refused at the boundary's refresh, before `read_store_series`, `_union_align` and the calendar, and the `_validate_grid` in `cli/portfolio/crossfreq_system.py` that checks only that stamps ascend is never handed one from the store. A stamp the venue sends off the grid inside a REST fetch does not reach the file at all: `_require_rest_frame` (D1) refuses the fetch that carries it, in the boundary it arrives in and before the merge, so nothing is written and no re-seed can fill it back. That refusal is the venue's, not the store's, and says so (D4), and the cycle raises there, where it journals a refresh-deadline record today -- a boundary with no sidecar and no dead-man ping, the shape `infra/runbooks/engine.md`'s cycle-stale bullet reads as a store to suspect, so that bullet gains the one reading of it that is not a store to repair and that D7's procedure does not answer: a traceback naming the REST fetch rather than a file. The reading is an unusable close's too, which spec 00116 D1 refuses at the write of the boundary it arrives in and this door refuses a step earlier, in the fetch; what stays out of scope is the hold over the merged frame, below.

**D4. The refusal names the file, the pair, the grid, the first difference and one workstation recovery for every store-file arm, and the REST fetch's refusal names the fetch and no repair; the in-place recast text goes.** The message is `<fn_name>: <path> is not the frame the store readers join for <pair>@<interval> -- <differences joined by "; ">; <recovery>`, the shape `_read_canonical`'s carries, so the two doors read alike and every existing pin on `<reader>` and `<path>` holds. The store-file recovery is one text for every arm, held in the module constant `_STORE_RECOVERY`: on the workstation move this leg aside, outside the store, and run `zcrypto engine seed`, which copies the canonical for the absent file and fills the gap from REST; what is lost is any bar past the canonical's tail that REST no longer reaches, and when the canonical's tail is itself outside the REST window the seed refuses on its own shortfall until the next quarterly ingest is minted; then the host routing of D6. A third recovery, `_REST_REFUSED`, belongs to the REST frame's refusal (D1), which names the fetch rather than a file and prescribes no repair and no edit: nothing from this fetch is written, the store holds what it held before the fetch, the next run fetches again, and a row that returns is the venue's to answer, not the store's -- the shape `_ABSENT_REST_HINT` already carries for a REST-side null (D6). It is what keeps the store-file recovery from writing back what the door refused: the seed's own REST door refuses the venue's row rather than filling it into the leg, so the move-aside and the re-seed leave the file clean, and the refusal the operator then reads names the fetch, which no store repair and no converge answers. On the seed's fresh-copy path that door runs BEFORE the copy: a refused fetch leaves no store file, so the next seed still reads the leg as absent and keeps its fresh-copy abort over a canonical/REST disagreement, where a copy left behind would make `store_existed` true, `allow_replace` with it, and the disagreement a tail replaced under a WARNING the operator does not see. "The next run fetches again" lasts as long as the venue's answer carries the row: `fetch_ohlc` takes the window's 720 bars, about 120 days on the 240 grid and about two years on the 1440, and the cycles stay stopped at that leg for as long as it does, with no bypass minted here -- a door an operator could wave through would write the row it refused into the store, which is what this door exists to prevent -- so the runbook's REST reading states that reach beside the refusal (D7). One text because the store-file arms share one repair: a Float32 price has no in-place recast, an extra column or another order has a trivial one that nothing in this tree re-vouches, a null or repeated stamp is a row edit with the same standing, and a value in the file is a REST-window question the seed answers; the seed over an absent file is the one path that reaches the canonical, and its loss is the one loss, so the message names it and names no edit. The `ts` recast text and its seam clause (`six shared stamps into the canonical and every shared close equal`) leave the tree with the door, and `tests/test_engine_store.py`'s pin on them is re-pinned on the one recovery. No string the door raises names a spec, a decision or a topic: `tests/test_internal_terms_not_operator_visible.py` reads every string literal under `cli/`.

**D5. A refused canonical is the data pipeline's to republish, and the seed says so and copies nothing.** The canonical recovery, `_CANONICAL_RECOVERY`, is the reach door's: nothing was copied to the store; a canonical is the data pipeline's to republish, so rebuild the set (`zcrypto data rebuild ohlc-full --no-push` mints the newer stamped sibling the seed reads once it is whole) rather than recast this file, whose `dataset_hash` a recast changes and nothing in this tree re-vouches. The clause `then promote the verified sibling into the canonical name` goes: since spec 00116 D8 the seed resolves the newest whole stamped sibling through `resolve_canonical_root`, so a rebuilt sibling is read as soon as it is whole and no promotion is a step. What `zcrypto engine seed` prints then is the door's message through the command's `except EngineError`, `seed_store: <canonical path> is not the frame the store readers join for <pair>@<interval> -- <differences>; <the canonical recovery>`, exit 1; the legs before it in `PAIR_KEYS` order, the daily grid first, are seeded and written, the refused leg's store file is absent, and a re-run after the republish seeds it, since the copy is for an absent file alone.
