## The live price store — `cli/engine/store.py`

Canonical layout inside `store_dir`: `<ASSET>/EUR/{1440,240}.parquet`, same schema as the research dataset (`cli.ohlc.dataset` read/write).

1. **Seeder** (`seed_store`): copy the frozen canonical (through 2026-03-31) into the store, then **REST-gap-fill** each pair × grid via `fetch_ohlc` (Kraken returns the trailing 720 bars — the 4h window still reaches 2026-04-01 until ≈ Jul 25). Seam QA, two distinct guards: **(i) non-empty overlap required** — ≥ 6 shared stamps per pair × grid between the canonical/store tail and the REST rows; an empty or thin overlap is a **window shortfall**, failing loudly with its own message naming the T0018 fallback ("REST window no longer reaches the tail — use the quarterly OHLCVT dump"), never falling through to a vacuous mismatch check; **(ii) overlap equality** — closes must match exactly on every shared stamp (the holdout pull's precedent — 621 bars exact); a mismatch aborts with `EngineError`, never silently prefers a side. Gap tolerance is an *interior* property only — it never applies at the seam. Idempotent: re-seeding only appends missing completed bars, re-runs both guards, and **may replace divergent store-tail rows within the REST window** (logged as a correction) — the documented repair for a poisoned tail (see the appender note). The printed seam-QA summary includes per-pair overlap bar counts.
2. **Appender** (`refresh_store`, each cycle): fetch both grids per pair; **drop in-progress candles by rule** — any row whose interval end (`stamp + interval`) lies after `now` is dropped (Kraken's OHLC always includes the currently-forming candle as its last row); verify the overlap with the store tail (equal closes on shared stamps, else `EngineError` — and since a poisoned tail row would re-fail every subsequent cycle, the documented recovery is `zcrypto engine seed`, whose re-seed path replaces divergent tail rows within the REST window); append only new completed bars. Venue gaps stay absent (union-calendar semantics downstream); freshness is *enforced later* by the journal boundary invariant, not papered over here.
3. **Pair-key map**: display symbol → Kraken pair key (e.g. `BTC → XXBTZEUR`), one committed constant in `cli/engine/store.py`, scoped to exactly the ten EUR-quoted assets of `data/ohlc-full`, transcribed from the snapshot register (`docs/research/01.1.kraken-snapshot-register.md`; live derivation exists in `cli/snapshot/assetpairs.py` — no importable committed constant exists today, so this becomes it). The store must produce series continuous with the canonical files it seeds from.

## The cycle core — `cli/engine/cycle.py`

`run_cycle(cycle_ts, *, config, fetch_fn=fetch_ohlc, clock=…) -> CycleResult` — a pure, dependency-injected function (fully testable without network, node, or dataset):

1. **Refresh** the store via the appender with a **settle-verify loop**: the first fetch happens at the boundary + settle delay; if a pair's raw tail still lacks a bar the boundary invariant expects — the 4h bar at `cycle_ts − 4h`, and *at midnight boundaries* the new daily bar too *\[precision added at the Task-2 review: checking only the 4h tail would burn the reserve at 00:00 cycles\]* — (a *successful* fetch of a not-yet-committed candle is not a transport error), that pair re-fetches with backoff, alongside transport-error retries — both bounded by **`clock.now() ≤ cycle_ts + 25 min`** (a 5-min reserve so any success inside the retry window still yields a gate-passable `completed_at ≤ cycle_ts + 30 min`); exhausting the reserve fails fast with a distinct *refresh-deadline* reason.
2. **Snapshot**: read full-history `(ts, close)` per pair × grid from the store; **staleness is checked on each pair's RAW series first** (own last stamp vs the boundary invariant: last 4h stamp == `cycle_ts − 4h`; last daily stamp == (last midnight ≤ `cycle_ts`) − 1d); then the snapshots are **union-aligned per grid** (one shared calendar — the union of the pairs' stamps, `None` closes at absences — exactly the builder's and `replay_cycle`'s required shape; the content hash covers the aligned series, `None → NaN`). A stale pair ⇒ write a **failed-cycle sidecar** (below) and skip the build — per the ratified gate, freshness failure = missed cycle, honestly recorded. `SnapshotEntry.pair` carries the display asset symbol (`"BTC"`), exactly matching `CrossfreqSystemConfig.assets`.
3. **Journal snapshots**: write per-pair×grid snapshot parquet files under the cycle's journal dir; manifest entries with content hashes via **the one shared helper** (`cli.engine.journal.snapshot_content_hash`) — writer and reader never diverge.
4. **Build**: `build_crossfreq_system_fast` (default config) → newest-row `final_targets`.
5. **Intended orders**: `Δtarget = target − previous targets`, where *previous* = the **most recent successfully journaled cycle's** `final_targets` (searching back across failed/missed boundaries, disclosed in the orders line when a gap was crossed; flat 0 only when none exists — the first cycle's shadow book starts flat) × `shadow_nav_eur` ÷ **the pair's 4h snapshot close at `cycle_ts`** (the close of the bar stamped `cycle_ts − 4h` — current at every boundary; the daily close would be up to 20 h stale intra-day) ⇒ per-asset side/quantity/notional appended to a human-readable `orders.jsonl` in the day's journal dir.
6. **Record**: the schema-v1 `CycleRecord` (snapshots manifest, targets, `started_at`/`completed_at`, code version, `builder_path="fast"`) via `to_json`, validated with `validate_record` before write — **success records only**. Layout: `journal_dir/<YYYY-MM-DD>/cycle-<HH>.json` with snapshots at `<YYYY-MM-DD>/snapshots/cycle-<HH>/<PAIR>-<GRID>.parquet`; **`SnapshotEntry.path` is stored relative to `journal_dir`** (the reader's closure resolves it against the configured root — journals must relocate across machines and still replay; a relocation round-trip test pins it).
7. **Failed-cycle sidecar** (an iter-083 addition *alongside* — not a change to — schema v1, so the out-of-scope clause holds): `journal_dir/<YYYY-MM-DD>/failed-cycle-<HH>.json` carrying `{cycle_ts, attempted_at, completed_at, reason: "stale_pair" | "refresh_deadline", offending_pairs}`, written **without** `validate_record` (which by design can never pass for it).
8. **Timezone convention (pinned)**: **aware-UTC everywhere** — `cycle_ts`, `started_at`/`completed_at`, snapshot `ts` (the dataset frames already yield aware-UTC datetimes), the sidecar fields, and the `now` passed to `evaluate_gate`. The cycle layer normalizes/rejects mixed awareness at its boundary (a naive/aware mix makes `validate_record`'s `!=` checks silently always-true — unit-tested). The injected `clock` is a callable returning an aware-UTC datetime (default: `datetime.now(timezone.utc)`).

## The node wrapper — `cli/engine/node.py`

The production-shape Nautilus `TradingNode` (the iter-079-verified adapter configuration): Kraken data client; **exec client behind `exec_enabled` (default `false`)** — the trade key is IP-bound to the VPS, so local runs are keyless; deployment (iter-084) flips it on for reconciliation-from-day-one. A thin strategy owns only **timer arithmetic** (pure UTC — DST is structurally irrelevant): **startup** computes the most recent elapsed boundary *B*; if no journal record (success or sidecar) exists for *B* and `now ≤ B + 25 min` (the refresh reserve), it runs *B*'s cycle immediately — a restart inside a still-passable window never burns a clean cycle; otherwise it only schedules ahead. Each alert **schedules the next boundary first, then** invokes the cycle core (a hung cycle can never stall the alert chain; overrun into the next boundary is structurally impossible — 25 min ≪ 4 h). **No catch-up** applies only to boundaries whose window has lapsed: those are missed cycles — the journal's absence records them; the gate counts them honestly.

## The CLI — `cli/engine/command.py` (the first Typer sub-app; `app.add_typer` in `cli/__main__.py`)

- `zcrypto engine seed` — build/refresh the store from canonical + REST (idempotent; prints the seam-QA summary).
- `zcrypto engine run` — the node, foreground (the soak runs this under a systemd user service).
- `zcrypto engine cycle [--at ISO_TS]` — one cycle manually (defaults to the most recent elapsed boundary). `--at` is **rejected unless exactly on the 4h boundary grid**; an existing record for that boundary is **refused by default** (`--replace` to overwrite — journaled soak evidence is never silently clobbered).
- `zcrypto engine replay [--date YYYY-MM-DD] [--path fast|verified]` — `replay_cycle` + `compare_targets` over journaled **success** cycles (default: all; `--path verified` for the daily spot replay); a record that fails read-side validation or hashing is **classified, not crashed on** (`EngineJournalError` → validation-failed, `HashMismatchError` → mismatch), and sidecars are reported as failed cycles.
- `zcrypto engine report` — builds `CycleOutcome`s by **replay-on-demand** (path=fast — 1.9 s/build makes re-replaying weeks of journal cheap; no persisted replay results in this iteration) with the same error classification, sidecars → `validation_failed`, absent boundaries left absent (the gate scores them missing), then `evaluate_gate` with an **aware-UTC** `now` → streak status, last-failure detail.

Loggers `get_logger("engine.<module>")`; README `## Usage` documents the group + the `[zcrypto.engine]` config table in the same change (repo rule); CLAUDE.md's subcommand parenthetical drops `cli/engine` from its no-command examples in the same change (the sub-app falsifies it).

## Config — `[zcrypto.engine]` in `zcrypto.toml`, parsed by `cli/config.py`'s pattern

`store_dir = "data/engine-store"`, `journal_dir = "data/engine-journal"`, `shadow_nav_eur = 1000` (`[iter-083]` item 2), `exec_enabled = false`, `settle_delay_secs = 90`. ## The soak (closeout, attended)

1. `zcrypto engine seed` — the store lands inside the REST window; seam QA printed.
2. One manual `zcrypto engine cycle` at the next boundary, watched live; its `replay` and `report` run immediately after — the first end-to-end evidence.
3. A systemd **user** service (`infra/systemd/zcrypto-engine-shadow.service`, committed as a template + a README note) starts `zcrypto engine run` on the workstation — with `Restart=on-failure`, `WantedBy=default.target`, and the documented prerequisite **`loginctl enable-linger`** (verified via `loginctl show-user -p Linger`; without it a user service dies on logout and the soak fails silently). **Dev evidence only** — labeled as such in the history entry; also keeps the store warm as the **rsync fallback** for iter-084 if the REST window closes — *registered in T0018's constraint 3 at closeout* (prose is not registration).

**Journal growth (stated, not deferred-by-omission)**: full-history snapshots ≈ 1.6 MB/cycle × 6/day ≈ **0.3 GB/month** — append-only with **no pruning in Phase 6** (the journal is gate evidence; retention is never improvised on the box). Disk headroom is an iter-084 VPS sizing input (T0018); a future retention/dedup scheme is an explicit **drop** for this phase, recorded in the decisions log.
