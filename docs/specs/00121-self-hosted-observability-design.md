# Self-hosted observability: the fleet's metrics, logs and alerting on one node, in four phases

## Problem

The fleet's metrics, logs, five dashboards and 106 alert rules run on Grafana Cloud's free tier. That tier has no ticket support and no remedy, and its faults reach the pager: from 2026-09-28 to 09-30 its rule evaluator timed out against its own Prometheus and paged false errors (179 error transitions across 52 rules on 09-30 alone), `/api/health` answered 404 in bursts, the stack hibernated under a keep-alive built to prevent it, and its 14-day retention has bitten twice. The rules that watch a held position evaluate there. `docs/research/92.self-hosted-observability-assessment.md` weighed the alternatives and recommends one node the project runs itself; the owner trusts its reasoning and approved the design below on 2026-10-01. This spec does not re-argue the assessment: it cites it for the why, records the owner's decisions where they depart from it, and carries the figures the labs of 2026-10-01 measured after it was written.

The work is one spec in four phases, each its own pull request or short run of them, and each with its own plan under this spec's serial, written once the phase before it has been read: (1) the node up, taking a shadow push of every rule to a shadow Slack channel; (2) dual-shipping, every host sending to both stacks; (3) the cutover of paging; (4) the retirement of the Grafana Cloud leg. Timing is stated against rung 2's box, as ruled Mon 2026-10-05 to Sun 2026-11-01, which may slip one week under its own rule: Grafana Cloud stays the pager through the box, and nothing from this work converges the engine host `zcrypto` inside it. The spec delivers T0217.

## Decisions

**D1. Self-host on Grafana OSS, one Prometheus, single-binary Loki, Caddy and Alloy, on one node with no HA.** Grafana stays the evaluator, so the rule file, the Slack template, the dashboards, `infra/scripts/grafana-push.sh` and the rule tests keep their shape and no expression is rewritten; the evaluator's read of its store becomes a loopback call, which removes September's failure class, and hibernation and the 14-day retention go with the tier. Rejected, each for the reason the assessment's sections 1 and 2 give: the unlicensed Enterprise build, PostgreSQL, Mimir, VictoriaMetrics and VictoriaLogs, a hybrid watch node, and Grafana Cloud Pro. The costs are the assessment's section 7 and are accepted: one more host with no HA, hand patching, evaluator and stores sharing one fate, and $29 a month.

**D2. The node is `zcrypto-mon`: a 4 GB Linode, Docker-free, on the bridgehead's shape.** Linode `g6-standard-2` (2 vCPU, 80 GB), Debian 13, in a region apart from the engine host's, reached as `zcrypto-mon.zhaow.me` through an A and an AAAA record, as the fleet's other public hosts are: the owner's word of 2026-10-01, setting aside the assessment's IPv4-only record. The firewall role's table is `inet`, so one opener covers both families, and the Cloud Firewall's rules name both. A new inventory group `mon_host`, a child of `observed`, and a play of `base`, `hardening`, `firewall`, `fail2ban`, `chrony` and a new role `mon` under the tag `mon`, with no `docker` role. Packages and their sources: `grafana`, `loki` and `alloy` from `apt.grafana.com`, the source the access role already declares; `prometheus` from Debian main without recommends; `caddy` from the cloudsmith repository, as on the bridgehead. Each is followed from apt and never forced or held, the access role's reasoning, and none takes a `fleet-pins.md` row; Debian's own `loki` is unrelated software, so the role asserts the candidate's origin before installing. Grafana, Prometheus, Loki and Alloy bind loopback alone. fail2ban is the fleet's standard role with its sshd jail and nothing else: no Grafana jail, agreed by the owner on 2026-10-01, because a ban is by address at the firewall and the owner's dynamic home address cannot be whitelisted, so mistyped logins from home would ban the address the ops node and the NAS ship from; Grafana's own lockout answers guessing. Containers were set aside: every component has a native package and a pinned-container node would owe digests, bakes and a pruner for nothing.

**D3. Unattended upgrades with the automatic reboot off, a reboot by hand, a monthly hand patch pass, and Linode Backups.** The base role's unattended upgrades install the Debian-security origin's patches, and the node never reboots itself: `base_unattended_upgrades_automatic_reboot` is `"false"` in its vars, as on the capture pair and ops, the owner's word of 2026-10-01 in place of the unattended reboot first designed. A pending reboot pages through `zcrypto-mon-reboot-pending` (D16), read from the role's copy of the reboot-check timer, until the owner reboots by hand, in the host's slot, 06:25 UTC, which the base role's collision assert still reads and which passes the fleet's slot rule (off the hour, an hour from every other slot, 60 to 180 minutes past a 4 h bar boundary); a reboot blanks evaluation for its duration and D17's ordering keeps it from paging. The node joins the hosts that reboot by hand wherever they are listed: `infra/scripts/count-list.sh attended-hosts-with-automatic-reboot`, `tests/test_infra_unattended_upgrades.py` and `docs/reference/fleet.md`'s Reboots lines. Grafana, Loki, Alloy and Caddy come from origins unattended upgrades do not cover, so they are upgraded by hand once a month, a procedure in the node's runbook that reads Grafana's security advisories first and re-runs phase 1's acceptance reads after a Grafana upgrade; the daily pass's reminders bring the pass due a month after the node's last full converge, which the pass's own re-converge is, and the pass reads the reboot flag itself, since until the cutover the pending-reboot rule reaches the shadow channel alone; an advisory exploitable without authentication is patched the day it is read, since the login is public. Widening the unattended origins to `apt.grafana.com` was set aside: a Grafana upgrade is a reviewed change while every provisioning endpoint the push script calls is marked deprecated. Backup is everything config-shaped from the repo (the role, the push, the vault) plus Linode Backups for the node's history; a pull channel to the NAS was set aside as a keypair, a user, an entrypoint block and a NAS apply for history no rule reads past 27 h. Linode Backups are file-based and can catch a running store mid-write, so the recovery that is proven is the rebuild from the repo (D21), and a restore is tried first only for the history it may save.

**D4. One public hostname on tcp/443, relying on Grafana's own authentication.** Caddy terminates TLS on 443 and serves everything on the one name: `POST /api/v1/write` to Prometheus and `POST /loki/api/v1/push` to Loki behind Caddy's basic auth, `/metrics`, `/metrics/*` and `/swagger*` answered 404 because Grafana serves `/metrics`, a metrics tree per plugin under it and its API browser unauthenticated by default, and every other path to Grafana, `/api/health` among them; Grafana's two static API descriptions, `/public/api-merged.json` and `/public/openapi3.json`, stay served without a login, since they describe the API and carry no instance data. The firewall opens 443 beside sshd's 10022 in both layers, nftables through `group_vars/mon_host/vars.yml` and the Linode Cloud Firewall by hand. Ingest has two users, `fleet` for the Alloys on both paths and `logship` for the applications' own log push on the Loki path alone, so the applications' push can be revoked without blinding fleet telemetry; Caddy holds their bcrypt hashes with `hash_cache` on, so only the first push after a Caddy reload pays the hash. The owner's reasoning for a public login: Grafana is widely adopted with solid authentication, a compromised node yields telemetry, the Slack webhook and the power to silence alerts but no key to another host, and it is the exposure Grafana Cloud has today. Superseded on the owner's word of 2026-10-01: the assessment's client certificates for the UI and API, a second hostname with a Caddy allow-list of API routes, and an API port opened to the owner's home address. Nothing about that address enters the tree or any firewall rule.

**D5. Grafana runs on its embedded SQLite, hardened so its own authentication can carry D4.** `grafana.ini` is the role's template: `[server]` on `127.0.0.1:3000` with `root_url = https://zcrypto-mon.zhaow.me/`, from which every Slack link is built; `[security]` with the admin login's name, the admin password and the secret key read through `$__file{}`, the name a generated one, since the lockout is by account name and a default name is one a stranger's guesses can keep locked, `cookie_secure = true`, `cookie_samesite = strict` and the built-in login lockout left on; `[auth.basic] enabled = false`, load-bearing, since the default lets a caller guess the admin password through the API; `[auth.anonymous] enabled = false` with `hide_version = true`, which takes the version out of `/api/health`; `[auth.proxy]` and `[auth.jwt]` off; sign-up, organisation creation, snapshots, public dashboards and plugin administration off, and the plugin preinstaller off, so the Prometheus and Loki datasource plugins are the copies the package bundles, change only with it, and a start downloads nothing; `[feature_toggles] sqlExpressions = false`, which no rule uses and two advisories of 2026 need; `[database] wal = true`; analytics and update checks off. The login form stays on: it is the role's admin path (D7) and the owner's. SQLite because the database holds Grafana's own state alone, 2.8 MB after a full push; a second Grafana instance, or a write that fails on `database is locked`, are the assessment's triggers for PostgreSQL, and the second is one of the node's own rules (D16).

**D6. The tools hold one Editor service-account token; no Admin token exists, and the admin password is used by the role on the node's loopback and by the owner in the UI.** `grafana-push.sh`, `grafana-query.py` and `ops_daily.py` read one token of the service account `zcrypto-tools`, role Editor: an Editor token makes every call the three make, where a Viewer token is refused the push, and it is refused datasource writes, admin settings, users, service accounts and token minting. An Admin token, the owner's first word, was set aside on the lab's finding and the owner's decision of 2026-10-01: it adds nothing over the admin password, which must exist anyway to mint the first token, and is worse, since it can mint tokens for itself and invite users. A Viewer token beside the Editor one was set aside for one credential, as the tools share one today. A leaked token reads every metric sample and every log line and can rewrite or delete rules, dashboards, contact points and the template and read the Slack webhook back through the contact-point export, the exposure the Cloud token carries today; recovery is one push from `develop` and a rotation. The token lives in a controller-side vault-encrypted cache, `~/.config/zcrypto/grafana-mon.vault.yml`, mode 0600 under the repo's vault password and outside the tree because it is machine-minted and re-mintable, so a rebuild needs no commit; `grafana_auth.vault_var` reads it unchanged through its `vault_file` parameter. No token is rendered on any managed host.

**D7. One converge after the VPS is bootstrapped leaves Grafana fully usable, with no UI step and no secret copied by hand.** The role renders the admin password and secret key files and the ini before Grafana's first start, which the deb's postinst leaves to the role; file-provisions the datasources and the folder (D8); starts Grafana and waits for `/api/health`; logs in on loopback through the login form, `POST /login` with the vaulted admin name and password, which works with basic auth off; finds the service account by exact name, creates it when absent and corrects a drifted role; keeps exactly one token, minting when the cached one is absent, malformed, refused by `/api/user`, another account's (that endpoint answers 200 with `id: 0` for a service-account token, so the role compares its `login`), not the account's only token, or when the rotation key `-e mon_grafana_token_rotate=true` is passed, and deleting every other; writes the token into the cache from a task delegated to the controller; and logs out. The skeptic's five corrections are part of the design. (1) The writer strips the trailing newline before encrypting (`stdin_add_newline: false`) and a token is matched against `^glsa_[A-Za-z0-9]{32}_[0-9a-f]{8}\Z`, anchored at the end of the string because `$` also matches before a trailing newline, before it is ever placed in a header, a mismatch meaning mint: a cached token with a newline made a later task fail and print the token despite `no_log`. (2) A 401 at login is first treated as password drift, repaired by the CLI reset from the vault, and a second 401 fails the converge with a message naming the login lockout, never retried: six failed logins lock the account for about five minutes, and the owner mistyping in the UI is enough. (3) The three files `$__file{}` reads are `root:grafana 0640`, since the unit runs as `grafana` and an unreadable `$__file{}` stops Grafana at start. (4) The reset on the deb's layout passes `--configOverrides cfg:default.paths.data=/var/lib/grafana`: the unit hands the data path on its command line, and without the override the CLI reports success against a new database elsewhere. (5) The preview on a fresh VPS passes: every task that calls Grafana's API is skipped in check mode, and a service start that follows an apt install takes `when: not (ansible_check_mode and <install> is changed)`, the fail2ban role's pattern, because `converge.sh` always runs the preview first. Beside them: every controller-delegated task carries `become: false`; the admin login's name, the admin password and the secret key live in `host_vars/zcrypto-mon/vault.yml`, generated once by script and stable across rebuilds, so the reset works and the name is the one each database is created with, Grafana reading it at no other time; and the first `grafana-push.sh` stays a workstation command under the push skill's conditions, not a converge task.

**D8. The datasource uids and the alert folder uid are reused.** The role file-provisions two read-only datasources with `prune: true` under the uids `grafanacloud-prom` and `grafanacloud-logs`, pointing at loopback, and anchors the folder `bfrxdfoybx98gb` with a dashboards provider, so the push script's defaults, about 415 dashboard literals, the two tools' hard-coded uids and six test asserts do not move. The price is names that say Grafana Cloud for things that are not; renaming them is mechanical and left for after retirement. Dashboards, rules, contact points, the policy and the template stay with `grafana-push.sh` and are not file-provisioned: a file-provisioned resource cannot be edited through the API, which would break the push, its read-backs and its prune.

**D9. Alerting stays Grafana-managed on its built-in Alertmanager; alert history goes to the node's own Loki, with a stated gap.** Grafana OSS 13 provides every alerting function the rule file and the push script use, and Grafana Cloud itself notifies through the same built-in Alertmanager, so no Prometheus Alertmanager, vmalert or Loki-ruler rule is installed: substituting one would rewrite 106 rules and lose the per-rule error state, the measured value, the panel link and the silence link. No image renderer is installed: it asks for 16 GiB, no notification uses an image, and its one consumer, the push skill's render check, becomes at the cutover a read of the panel's query by value and a look at the panel. History is `[unified_alerting.state_history] backend = loki` against `http://127.0.0.1:3100`, because `infra/scripts/ops_daily.py` reads history across rules and the default annotations backend refuses that read with HTTP 500. The gap: history is written to the store it describes and a failed write is dropped, not retried, so every transition during a Loki outage on the node is missing from the daily pass's fired-in-window list and from a drill's history read; the node's runbook says so under the store-down rule, and a second copy in annotations was set aside because the daily pass does not read it. Silences and the notification log are saved every 15 minutes and at a clean stop, so the runbook's step after an unclean Grafana restart re-reads the silences.

**D10. One Prometheus is the remote_write receiver, kept 90 days.** Debian's `prometheus` 2.53.3 on `127.0.0.1:9090` with no scrape job: `--web.enable-remote-write-receiver`, `--storage.tsdb.retention.time=90d`, `--storage.tsdb.retention.size=8GB` (8 GiB in 2.53's units, three to four times the 90-day estimate, so time governs), and an 8 h out-of-order window so a shipper's WAL replays after an outage. Ninety days is the owner's word of 2026-10-01: the disk would hold the 400 days first designed, and nothing reads that far, the rules' widest window being 27 h and the free tier's 14 days being what bit. Sized for the unfiltered fleet of D12 from the lab's rates: 156–176 samples/s, 110–140 MB resident, and 2.1–2.5 GB for 90 days at a measured 1.7–1.8 bytes a sample, at most about 2.7 GB with the nine-day block that is deleted whole; more than 70 GB of the disk stays free and memory does not grow with retention. The figures count the fleet and not the node's own unfiltered self-scrape, which the plan's lab measured after this sizing; the open questions carry it. Two of the node's own rules (D16) replace the keep-lists as the budget's fence. Mimir is the assessment's rejection; Prometheus 3 was set aside because Debian main carries 2.53.3 under Debian security and upstream ships a tarball, which leaves the range-selector boundary a trap to prove (D20).

**D11. Loki is the single binary on the local filesystem, kept 90 days.** `loki` 3.7.8 from `apt.grafana.com` on `127.0.0.1:3100`: one process, filesystem storage, the tsdb index at schema v13, no authentication of its own, and the compactor's retention enabled with its delete-request store, since without it Loki keeps logs forever. The period is Prometheus's, on a volume of 3–5 MB a day, under half a gigabyte of raw text in 90 days. Its memory at this scale is not measured and is read in phase 1.

**D12. The self-hosted leg ships unfiltered; the Cloud endpoint keeps its filter until retirement.** Alloy applies `write_relabel_config` per endpoint, so the new endpoint carries none and the Cloud endpoint keeps its drop and keep pair untouched: no keep-list guard changes during dual-shipping, and the keep-lists, the REQUIRED sets and their tests are deleted at retirement (D23). Unfiltered, the fleet is about 9,400–10,600 active series against 1,413 today, which Cloud's 10k cap could not take and the node takes with room (D10). Two limits stay at the source. `set_collectors` keeps its six collectors: with Alloy's defaults ops publishes 1,561 series where the six publish 451. And the unix exporter gains `netdev { device_exclude = "^(veth|br-)" }` on ops, the capture pair and the NAS, for dashboard hygiene rather than size: ops went through 395 network devices in 14 days at 16 series each, no rule reads them, and the network panels plot every device but `lo`. The redis exporter's client-list and key options stay off. The filter's removal ends T0051's trap, published but not admitted and so absent, on the node; during dual-shipping a family present on the node and missing on Cloud is that trap seen directly. This supersedes the assessment's second filtered endpoint and its guard rewritten to "every endpoint carries the identical pair".

**D13. Dual-shipping is a second endpoint and a second `loki.write` in each of the five configs, under new names only.** Each `prometheus.remote_write "grafana"` gains a second `endpoint` block for the node, which has its own queue, so a dead endpoint does not hold the other. Logs take a separate `loki.write "mon"` component added to the parse stage's `forward_to`, never a second endpoint in the existing component, whose endpoints are fed in succession and can stall each other; the bridgehead ships no logs and gains none. The new blocks read `MON_*` environment names rendered from new values, the `fleet` user and password vaulted in `group_vars/observed/vault.yml`, the `logship` pair beside them for D22, and the two URLs plain. `grafana_prom_url` and `grafana_loki_url` are never repointed: `logship-secrets.env` re-renders on every capture-role converge and the engine reads it at its next start, so a repointed value would silently move the engine's log push at an engine restart inside the box and blind Cloud's `zcrypto-engine-error-logs`. During dual-shipping each Alloy carries about 107 more series of its own and 5–13 MB more resident memory; the tightest are the cache nodes and `zcrypto`.

**D14. A name reaches an Alloy process before the config that reads it, and a shared config file merges only when every host it serves can be converged.** A reload does not re-read the secrets file: on ops, the cache nodes and the capture pair the role's handler posts `/-/reload` and the process keeps the environment it started with, so a config that reads `MON_*` before the container is recreated reads empty strings. Those three roles therefore take two tree states, each converged with the host's running Alloy digest, which gates the secrets file's render as it gates the config's copy. The first renders the new names into the role's secrets template, and each host's Alloy is then recreated with `docker compose up -d` in the Alloy project, the bump-alloy skill's step. The second delivers the config, and the handler's reload loads it. `tests/test_infra_alloy_series.py::test_the_cache_secrets_template_renders_every_name_the_config_reads` holds `read == rendered`, so the cache role's first state widens it to the config's names plus exactly the new ones and the second restores the equality, each a guard change with its `infra/scripts/mutate-probe.sh` verdict. The bridgehead and the NAS take one state: there one converge lands both files and restarts Alloy after them, through the access role's `restart alloy` handler and the NAS role's apply. That is fourteen converges. The workstation proof that would collapse the two states is run before phase 2's plan is written: Alloy v1.19.2 reloaded with a config that reads unset names, reading whether the first endpoint keeps shipping and what the reload returns against the handler's accepted `[200, -1]`; if the reload is harmless that plan takes one state per role, converge then recreate, with no guard change and eight converges. Merging a `config.alloy` arms its role's drift assert, `assert the deployed alloy config matches the repo`, on every host the file serves until each is converged with its Alloy digest: the cache file serves three nodes and the capture file serves `zcrypto-red` and `zcrypto`, so inside the box the ops and access changes merge first and the cache role's only after the node drills of D15, when its three nodes are next to be converged, and the NAS and capture changes, secrets templates included, merge only after the box.

**D15. Inside the box the dual-ship set is the bridgehead, ops and the three cache nodes; the NAS and both capture hosts follow it.** The order: `zaccess` (`--tags access`), then `zcrypto-ops`; then the three node drills of D21 while only those two ship, so the engine's cache path joins only after a dark destination is proven harmless to the Cloud leg; then the cache nodes, one node per run (`--tags cache` with the running Alloy digest), outside the day's plan window and away from an engine restart, with a day's read of the first node's Alloy headroom, the Go-runtime measure its rule reads, before the second. After the box: the NAS in one pass (`-e nas_apply_compose=true`, which also restarts `archive-pull`), then `zcrypto-red`, then `zcrypto`, the last an attended converge in the bump-alloy skill's primary form, `--skip-tags engine -e converge_primary=true` with both running digests, under `.claude/rules/fleet-deploys.md`: the primary's capture is unbackfillable and a wrong capture digest restarts it. The Kraken maintenance feed is read whole at planning and again immediately before every converge of `zcrypto`, `zcrypto-red` and `zcrypto-ops`, the ops converges inside the box included. The assessment recommended the bridgehead and ops alone inside the box; the owner widened the set to the cache nodes. Converging the primary's Alloy inside the box as `--tags capture` was set aside: no skill prescribes that form and it buys only an earlier second evaluator.

**D16. The node ships to itself, carries its own rule group, and its death pages through healthchecks.io.** A native Alloy with a sixth config, `infra/ansible/roles/mon/files/config.alloy`, writes on loopback with no credential and no filter: the unix exporter's six collectors, Alloy's own metrics, the `/metrics` of Grafana, Prometheus and Loki, and the journals of the node's units, under `host="zcrypto-mon"`. Its rules are a tenth group, `zcrypto-mon`, each with a section in a new `infra/runbooks/mon.md` and a panel in a new row of the Fleet health dashboard: `zcrypto-alloy-dark-mon`; `zcrypto-mon-disk-low`; `zcrypto-mon-reboot-pending`; `zcrypto-mon-store-down`, a store down or not ready; `zcrypto-mon-sqlite-locked`, a write Grafana gave up on with `database is locked` in its journal, the retries it logs with the same text left out; `zcrypto-mon-ingest-dark`, every fleet host absent at once, which is the node's edge or certificate and not the fleet, and which the exposure page's runbook reads first; `zcrypto-mon-series-high`, head series above 20,000, about twice the expected count; and `zcrypto-mon-retention-by-size`, the size cap having fired, so time no longer governs. A rule cannot page the death of the node it runs on, so a role-written timer runs a self-check every five minutes and pings a healthchecks.io check, `zcrypto-mon`, with the `zcrypto-grafana-watchdog` check's 600 s timeout and 600 s grace, only when rule evaluation is fresh, a fleet sample is fresh and Loki answers ready; the node pings out, so nothing is whitelisted. The check is minted when the power-off drill is scheduled and not at node-up, the ping URL empty until then and the timer pinging nothing, the ops role's own semantics, because Cloud's `zcrypto-hcio-watchdog` counts every down check and a teething fault must not page critical. At the cutover the ops watchdog's probe is re-pointed at the node's `/api/health`, a second prober off the node, and `zcrypto-hcio-watchdog` keeps mirroring healthchecks.io into Grafana from the ops Alloy's scrape. No heartbeat rule is added to Grafana Cloud for the box.

**D17. The evaluator never starts ahead of its stores, and a store is not restarted under it unproven.** 104 of the 106 rules page on an evaluation error and 22 have `for: 0s`, so a store restart on the node can reproduce September's pages. `grafana-server` takes a drop-in that orders it after `prometheus` and `loki` and waits in `ExecStartPre` for Prometheus's `/-/ready` and Loki's `/ready`, since systemd's `After=` does not wait for readiness; the role's handlers restart a store with Grafana stopped around it, and the runbook's hand procedure does the same; and `prometheus`, the one package here that Debian security can upgrade unattended, is on this host's unattended-upgrades blacklist until the store-restart drill (D21) shows that a bare restart pages nothing, and stays there if it pages. The drop-in also lowers Grafana's OOM score below the stores', since a killed Grafana loses up to fifteen minutes of silences and may repeat notifications.

**D18. One tree feeds two stacks until retirement: the tools address a stack by name, and Cloud never receives the node's group.** `infra/scripts/grafana_auth.py` turns its one URL constant into a table of two stacks, each a URL, a token name and the vault file holding it; `grafana-query.py` and `ops_daily.py` take the stack as an argument and default to `cloud` until the cutover flips the default. `grafana-push.sh` is already driven by its environment and gains one variable, `GRAFANA_SKIP_RULE_GROUPS`: it pushes none of the named groups' rules and reports one found live as an orphan. The variable defaults to `zcrypto-mon` beside the Cloud URL default, so a push that names no stack keeps the node's rules off Cloud, where they have no data and their dead-men would page the main channel; the node's invocation overrides both. That default holds only while the variable is unset, and the shell that pushed the node still holds it empty, so the script also refuses, before any call, a push addressed to Grafana Cloud that does not skip the group. Every push in the dual period goes to both stacks from one checkout under the push skill's existing conditions; the skill takes its two-stack wording with phase 2's first dual push. In phase 1 it takes two sentences, so that its preflight and its verify step leave the skipped group's rules and the node's dashboard row, which read no series on Cloud by construction, to the node; and the node is pushed by its own runbook procedure and may trail the tree, since it pages the shadow channel alone. The node's contact points are minted with the shadow webhook, `slack_shadow_webhook_url`, a new value beside `slack_webhook_url`, and Cloud's keep the main one. The assessment's committed exclude list of rules the node has no data for yet was set aside: every rule is pushed to the node, the shadow channel absorbs the noise of hosts not yet shipping, and D19 names what is comparable.

**D19. The cutover is gated by seven days of comparison by value: every rule's query, on both stacks.** No test reaches a live Grafana, so the suite stays green through a wrong migration, and matching alert states for a week proves only the rules that changed state. A new script, `infra/scripts/grafana-compare.py`, runs every query node of `infra/grafana/alerts.yaml`, the 96 PromQL and 13 LogQL nodes of today, through each stack's datasource proxy at the same instants, 24 hourly instants across the preceding day, and compares the result sets: the same label sets, values equal within a relative 1e-6, an empty result equal to an empty result alone. A difference is a finding, fixed or explained in the cutover pull request. The seven days are consecutive daily runs with no unexplained difference; they start once the last host has 26 h of data on the node, the rules' widest window, and a rebuild of the node restarts them. Three things are outside the comparison, each by name. The `zcrypto-mon` group exists on the node alone. Rows whose `host` is `zcrypto-mon` exist on the node alone. **D22. The cutover: the node pages the main channel first, each direct-shipped stream is handed over in its own sitting, and Cloud's receivers move last.** Its gate is D19's seven days, the four drills passed and the boundary reading recorded. (2) One push to the node with the main webhook moves its two contact points; from here both stacks page the main channel and duplicates are accepted. (3) The logship templates' change to the new names merges, after the box only, and each stream is handed over: the poller on ops by an ops converge that recreates it; the capture daemon on `zcrypto-red` and, an hour later, on `zcrypto`, each by a capture-role converge that renders the file and an attended restart of the capture unit; the engine by an engine-tagged converge inside an inter-cycle gap, under the engine's restart rules in `infra/runbooks/engine-procedures.md`. **D25. Rollback, by phase.** Phase 1: nothing in the fleet points at the node, so it is deleted and the role stays inert. Phase 2: Cloud was never changed and the node's leg has its own queue and its own `loki.write`, so rollback is to stop looking; removing the leg is a revert and one converge per host. **D26. Alloy's remote configuration is not adopted.** Measured on Alloy v1.19.2: with the config server unreachable at start Alloy exits, cache on disk or not; a remote fragment cannot attach to a local pipeline; and no packaged self-hosted server exists. A remote source would make every shipper's cold start depend on the one node and would change Alloy on `zcrypto` without an attended converge; Grafana Cloud's Fleet Management, free, was considered and rejected for the same two reasons. The simplicity is taken instead from D12 and from D14's proof. Re-evaluate at an Alloy release whose cold start with the server unreachable loads the cache, proven by re-running that lab.
