# The engine's cache: a Valkey replica set behind a Sentinel-aware proxy

## Problem

The engine holds nothing across a restart but its ledger and what the venue answers at boot. On the pinned `nautilus-trader` (`2.0.0rc6.dev20260921`) a Kraken margin position report carries no entry price, so a restart with a margin position open either fails startup reconciliation or books the position at 0; the owner's operating rule of 2026-09-23 therefore forbids an engine converge or restart while a margin position is open, and every engine converge first closes positions. Rung 1 holds margin positions across rollovers by design, so the rule taxes every converge from Rung 1 on.
The library's documented answer is a cache-database backing: with one attached, a live restart restores the engine's own orders, fills and positions from the database before venue reconciliation runs (upstream `docs/concepts/execution/policies.md`, `docs/concepts/cache.md` at `70d887545790`). The estimate of 2026-09-24 (`.local/estimates/2026-09-24-engine-cache.md`) read that path, sized it for a Redis inside the engine's compose, and recommended entering Rung 1 without it. The owner's decision of 2026-09-24 supersedes the topology, not the recommendation: three dedicated Linode nodes, Valkey for its license, high availability required, sharding and load balancing not, and the engine-side landing held to Rung 2.
Two facts shape everything below. The library's Redis backing connects to exactly one `host:port`: its config has no Sentinel field, its binary carries no master lookup, and after a failover its connection manager keeps reconnecting to the address it was given. And its TLS mode takes no CA file, so a private wire is simpler than certificates on three nodes.

## Decisions

**D1. Purpose: the library's cache-database backing, for the engine's own orders, fills and positions, and nothing else.** The executor's ledger, the journal and the venue read at boot stay as they are; the cache is a recovery mechanism under them, the library's own words (`cache.md`: "a recovery mechanism, not a complete event archive or a synchronized distributed cache"). Success is one reading: an engine restarted inside an inter-cycle gap with a Kraken margin position open boots with that position and Kraken's entry price, logs no `Unresolved positions during startup reconciliation`, and leaves `.RestartCount` unchanged. That reading lifts the operating rule from the pages that carry it: `infra/runbooks/engine-procedures.md` (the `engine-restart-margin-position` paragraph and each step linking to it), `infra/runbooks/engine.md` (the restart and converge steps), `infra/runbooks/drills-order-path.md` (the standing rule, A2, drill D, F2 step 4, G's induce step), `infra/runbooks/order-semantics-verification.md` (§1.7, §6, §8) and the Reboots section of `docs/reference/fleet.md`. No other reason shapes this build: no research store, no engine state moving out of the ledger.

**D2. The store is Valkey 9.1.2 on three dedicated Linode nodes.** Valkey over Redis for its license, at a Redis-compatible interface the library's client speaks; over Postgres because the library's Postgres backing has no strategy state and loads unscoped (the estimate's reading of `crates/infrastructure/src/sql/cache.rs`, upstream #5050). 9.1.2 is upstream's latest stable; the `9.2` image tag is a release candidate. The nodes are `zcrypto-valkey1`, `zcrypto-valkey2` and `zcrypto-valkey3` (`<name>.zhaow.me`), Debian 13, 1 GB each, hosting Valkey and its observability and nothing else. valkey1 and valkey2 share the engine host's region; valkey3 is in another, kept there deliberately as the copy that survives a regional outage, which takes the engine with it, so it serves recovery, not continuity.

**D3. High availability is a replica set under Valkey Sentinel: one primary, two replicas, three Sentinels, quorum 2.** valkey1 is the first primary; `replica-priority` is 100 on valkey1 and valkey2 and 250 on valkey3, so promotion prefers the engine's region and takes the remote copy only when both local nodes are gone. `min-replicas-to-write 1` with `min-replicas-max-lag 10`: a primary cut off from every replica refuses writes rather than accepting ones a failover would lose; the cost, cache writes refused during a double-replica outage, is a state the alerts of D12 name. Sentinel per node monitors `zcache` with `down-after-milliseconds 5000`, `failover-timeout 60000`, `parallel-syncs 1`, `resolve-hostnames no`, and `announce-ip` the node's mesh address of D5. Sentinel's discovery breaks under Docker port mapping, so Valkey and Sentinel run with host networking (`network_mode: host`). Sentinel is the chosen shape, not a hard constraint: the owner's requirement is a Redis-compatible interface with HA, and a manual-failover replica set and a resolve-at-start design were read and set aside (a primary outage would drop cache writes silently until an operator or an engine restart acted; the second turns a cache failover into an engine restart the operating rule confines to a gap).

**D4. The engine reaches one stable endpoint: an HAProxy container in the engine's compose project, addressed as `cache-proxy:6379`.** The engine container sits on its compose network and cannot reach the host's loopback, which is why the proxy is a service beside it and not an apt package bound to a Docker-assigned bridge address; the official `haproxy` image, digest-pinned with a pins row, a 32m memory cap (HAProxy in TCP mode with nine checks uses 10–20 MiB), so a package upgrade never restarts the engine's cache link mid-cycle. Routing is `ha-valkey`'s pattern: three backends, one per node, each carrying three server lines whose health check goes to one Sentinel (`AUTH`, `PING`, `SENTINEL master zcache`, expect that node's mesh address), so a node is routed when at least two Sentinels name it primary; checks every second; `on-marked-down shutdown-sessions` cuts the engine's connections at a failover so its client reconnects and lands on the new primary. The backends are the nodes' mesh addresses of D5, routed through the host's tunnel so the nodes see the engine host's mesh address. A Prometheus endpoint on `127.0.0.1:9104`, published on loopback like the app ports, feeds the engine host's Alloy (D12). The proxy's rendered config lives in the engine role's compose project, so the change stays under the engine role, a Fable path.

**D5. The wire is a WireGuard mesh, `zcache0`, private by construction; no TLS.** Four peers: the engine host `zcrypto` at `10.98.0.1` and the nodes at `10.98.0.11`, `10.98.0.12`, `10.98.0.13`; the bridgehead's `zaccess0` keeps `10.99.0.0/24`. Full mesh, each host listing the other three, `AllowedIPs` one `/32` per peer, endpoints the public IPv4s, `PersistentKeepalive 25`, port `51821/udp` fleet-wide. Four keypairs: private halves in `group_vars/all/vault.yml` beside the bridgehead's, public halves plain beside those. A new role `cache_link` renders `/etc/wireguard/zcache0.conf` and enables `wg-quick@zcache0` on all four hosts; on `zcrypto` it runs under its own tag and restarts no container, and it is still a converge of the primary under the primary's rules. Valkey and Sentinel bind `127.0.0.1` and the host's mesh address only, so no database port exists on a public address; replication and client traffic alike travel inside the tunnel. TLS was set aside: the library's TLS mode takes no CA file, so certificates would have to be publicly trusted and renewed on three nodes, and the proxy would verify them; the mesh removes the whole class.

**D6. The firewall gains interface-scoped ports; every layer is opened by hand where the fleet already does.** The nftables role takes an optional list of ports accepted only on a named interface, rendered as `iifname` rules, empty by default so every existing host renders unchanged. The nodes accept `10022/tcp` and `51821/udp` on the public side and `6379`, `26379` on `zcache0` alone; the engine host adds `51821/udp`. The Linode Cloud Firewall, managed by hand as for the bridgehead, mirrors `10022` and `51821`, with `22` only during bootstrap. `tests/test_infra_firewall_template.py`, which today admits extra-port declarations only in the access group's vars, widens to the cache group and the engine host.

**D7. Durability, memory and the 1 GB budget.** `appendonly yes` with `appendfsync always`, plus periodic RDB snapshots for replica resyncs; data under `/var/lib/zcrypto-cache/`. `maxmemory 128mb` with `noeviction`: the cache must never drop a key silently, and the dataset is megabytes. The library never deletes keys (every key TTL −1 in the estimate's probe), so growth is alerted at 70% of `maxmemory` rather than trimmed; at one engine's order rate that is years away. Container caps on a 1 GB node: Valkey 256m (the gap above `maxmemory` is for the AOF-rewrite child's copy-on-write), Sentinel 64m, Alloy 256m with `GOMEMLIMIT 230MiB` (the fleet's 0.88–0.92 ratio); 576 MiB of ceilings against an expected working set near 150 MB, leaving about 400 MiB for the kernel, dockerd, sshd and the page cache. Every new Alloy cap takes a leg under the fleet's memory-headroom rule; the Valkey and Sentinel caps take none, since that rule parses `process_resident_memory_bytes`, which neither daemon publishes, and Valkey's memory is watched against `maxmemory` instead.

**D8. Authentication is ACL users; five secrets, one path each.** The `default` user is disabled. Users: `engine` (every key, no admin commands), `replica` (`masteruser`/`masterauth`), `sentinel` (the commands Sentinel needs on the data instances), `exporter` (read-only, the exporter's documented ACL). Sentinel itself takes `requirepass`, which the proxy's checks and the Sentinel exporter present. The five passwords live in `group_vars/cache_host/vault.yml`; the role renders them into `users.acl` at mode 0600 owned by the container's uid; the engine's copy of `engine`'s password reaches the engine as `ZCRYPTO_CACHE_PASSWORD` in `engine.env`, the trade key's path (root 0600, `no_log`, `diff: false`). A password shorter than five characters is refused by the role: the library logs a shorter one unredacted at DEBUG.

**D9. The daemons own their config files after first render.** Valkey rewrites `replicaof` and Sentinel rewrites its known replicas, sentinels and epoch into the files they were started with, so the role renders `valkey.conf` and `sentinel.conf` only when absent; a routine converge never resets a node's replication state. A deliberate change takes `-e cache_config_reset=true`, whose effect the runbook's config-reset procedure states (stop the node's containers, replace the files, start, confirm `master_link_status:up` and the Sentinel's view); a changed password is applied to the three nodes in one stop, since the nodes authenticate to each other and a node reset alone to a new password fails against the others. The role asserts the rendered template's hash against a recorded copy so drift is visible without being applied.

**D10. The library wiring: attached at node build, fail-closed at start, bounded retries.** `cli/engine/node.py` attaches `CacheConfig(use_instance_id=False, flush_on_start=False)` (`True` on the first reloads an empty namespace, on the second issues `FLUSHDB`, both from the estimate's probes) and `RedisCacheConfig(host="cache-proxy", port=6379, username="engine", password=<env>, ssl=False, connection_timeout=5, response_timeout=5, number_of_retries=6)`, a retry budget of about a minute so an unreachable cache fails the start inside the gap rather than hanging past it (the library's defaults, 100 retries and 20 s timeouts, block `run()` for hours). `load_cache` stays at its default, True. New fields `enabled`, `host`, `port`, `username` under `[zcrypto.engine.cache]` in `zcrypto.toml`, through `EngineConfig` and its strict loader, rendered by the engine role's template; `enabled` false renders no cache and changes nothing. Policy: cache enabled and unreachable at start means the node refuses to run, the unit restarts it and the engine-dark alert fires; mid-run, a write the library cannot deliver is logged by its Rust side only, which never reaches Loki (`infra/runbooks/engine.md`), so the external signals of D12 stand in, and the engine logs at each boot how many orders and positions it restored. Keys land under `trader-SHADOW-001:` in database 0; the set is dedicated to this engine.

**D11. The executor's startup pass learns that the cache may already hold this engine's own orders and positions.** From the estimate's code items: the startup venue read widens to any non-terminal cached order rather than the ledger's open rows alone; a restored order's terminal event reaching the engine takes the detached-event path, never the unknown-order trip; a pre-start guard refuses to run when the cache is enabled, loaded empty, and the ledger holds open rows, since that is a cache that lost its data, not a first boot; the realized-PnL gauge is scoped to fills this process saw, so a position restored at its entry price shows no phantom realization; the probe plan refuses spot inventory beside a margin lot on one pair, a shape the restore does not distinguish; and the executor and node docstrings that a persistent cache makes false are rewritten.

**D12. Observability: each node ships like a capture host; one new dashboard; one rule group.** Alloy as a digest-pinned container in its own compose project per node, host networking, D7's cap, a pins row per node, and a new `roles/cache/files/config.alloy` carrying the unix exporter (cpu, load, memory, filesystem, netdev, textfile), Alloy's self-exporter, and Alloy's built-in Redis exporter twice, against the local Valkey with the `exporter` user and against the local Sentinel; logs from the journal for the two containers and Alloy. The `host` label is the hostname (`constants.hostname`, the capture pattern), so the three read `zcrypto-valkey1/2/3`; a textfile probe on each of the four mesh members, the engine host included, publishes each peer's WireGuard handshake age, the bridgehead's pattern, and the engine host's capture Alloy admits that family. The engine host's Alloy gains one scrape job for the proxy's `:9104`. Keep-lists: a per-host list for the cache nodes in `tests/test_infra_alloy_series.py`, and the topology map in `tests/test_dashboards_cover_metrics.py` gains the three hosts so the fleet's unscoped node rules are admitted there; `redis_*` and `haproxy_*` are the fleet's first third-party families, unseen by the `zcrypto_*` source sweeps and held by the every-alerted-family-is-charted rule. The Logs dashboard's host list and the Slack template's display names gain `Cache 1/2/3`, `fleet.md`'s telemetry labels with them; the Fleet health dashboard is untouched. One new dashboard, `infra/grafana/cache-dashboard.json`, uid `zcrypto-cache`, title `Cache`, in rows: hosts (vitals, disk, handshake age, reboot pending); Valkey (role per node, connected replicas, replication lag, memory against `maxmemory`, commands and clients, AOF and RDB status); Sentinel (the primary as each sees it, quorum, known peers, failovers); the proxy (backend status, the routed node, sessions, check failures), placed here and not on Fleet health by the owner's word; and a logs panel for the engine's restore lines. Rules, one group, each with an anchor in a new `infra/runbooks/cache.md`: Alloy dark per node; primary count not exactly one; fewer than two replicas on the primary; the proxy with no UP backend; the engine holding no session through the proxy while it runs; memory past 70% of `maxmemory`; an AOF write or rewrite not `ok`; a peer's handshake older than three minutes; and headroom legs for the new Alloy caps (D7). No hc.io checks: nothing on these nodes pings, and the Alloy-dark rule is each node's dead-man.

**D13. Joining the fleet.** Inventory group `cache_host` with the three, a child of `observed`. `group_vars/cache_host/vars.yml` on the access group's shape: `zcrypto-deploy` on 10022, `AllowUsers` without `zcrypto-data`, the firewall's UDP port and D6's interface-scoped list. `host_vars/<host>/vars.yml`: the hostname, a distinct unattended-reboot slot each, staggered so no two nodes share an hour, the deploy key lookup, and a plaintext `ansible_host` as the bridgehead has; the base role's reboot-slot collision assert widens to the group, and its `zcrypto-data` user stays gated to `capture_host`. Bootstrap: the capture play in `bootstrap.yml` widens its hosts to `capture_host:cache_host`, its guards keyed on group membership as they are; per node, the Cloud Firewall opens 22 and 10022, `bootstrap.yml --limit <host> -e ansible_user=root -e ansible_port=22` runs with the owner's master key in the agent, `site.yml --limit <host>` runs through `converge.sh`, then 22 is dropped. Three deploy keypairs, `files/deploy_zcrypto-valkey{1,2,3}_ed25519`, private halves vault-encrypted, public halves plain, listed in `run.sh`; on the workstation the aliases `db1`, `db2`, `db3` on the fleet's alias shape, recorded in `fleet.md`'s Hosts table. The hand-enumerated lists each gain the three: `converge.sh`'s hosts, tags (`cache`, `cache-link`, `cache-proxy`) and extra-var keys; `run.sh`; `prune-host-images.py`; `deploy-log-audit.py`'s no-venue-exposure set; `ops_daily.py`'s telemetry hosts; the run.sh, converge.sh, unattended-upgrades, pins-converged and firewall-template tests; and `fleet.md`'s Hosts, Services, Storage, Reboots and Telemetry labels. Roles: `cache_link` (D5, on the four hosts), `cache` (Valkey, Sentinel and Alloy, on the nodes), `cache_proxy` (D4, rendered into the engine role's project); each follows the capture role's guards: the digest pre-staged, the pins row recorded, config drift asserted. Site plays: a `cache_host` play (base, hardening, firewall, fail2ban, chrony, docker, cache_link, cache), and `cache_link` and `cache_proxy` added to the engine host's play under their own tags.

**D14. One node per converge; replicas first; the primary last, after a failover on our schedule.** `converge.sh` takes one host per run and refuses a group, and a re-pin restarts the container, so the set is rolled: the restarted node's replication link up (`master_link_status:up`) and its offset caught up before the next, seconds, not a bake, since two copies stay up throughout and nothing here is unbackfillable. Re-pins go replicas first, then a deliberate `SENTINEL failover zcache`, then the old primary, so the engine's one reconnect happens when we choose rather than on the detection timer; by preference inside an engine gap, a preference and not a gate. The first converge, with no data, goes valkey1 (the primary Sentinel is told to monitor), then 2, then 3. The engine host's `cache-link` converge restarts nothing; the proxy and D10's wiring ride an image build through the canary rollout (`.claude/skills/zcrypto-rollout-image/SKILL.md`), the engine's first boot with the cache inside a gap while flat.

**D15. Verification and sequencing: steps 1–4 now, 5–6 at Rung 2.** First, a compatibility probe on `db1` once it runs Docker: the pinned library's client against Valkey 9.1.2, reading the `INFO` version line the library parses and writing then reading back an order; the one library-side unknown, settled before anything is built on it. Second, the offline two-process restart harness of the estimate against a real Valkey: a resting order and a margin position restored across a restart; an empty cache beside open ledger rows refused by D11's guard; the cache unreachable at start failing inside D10's budget; the cache killed mid-run with the engine carrying on. In CI a Valkey service container runs it on every push; locally it runs when `ZCRYPTO_CACHE_URL` names a server and skips otherwise, on the data-gated family's shape, since a database is not a venue; the plan review reads that gate against the skip-gate contract. The rollout: (1) bootstrap and base-converge the three nodes; (2) the mesh, the nodes then the engine host under `cache-link`; (3) Valkey and Sentinel, valkey1 first, replication verified, one forced `SENTINEL failover` with no engine attached and failed back; (4) Alloy on the nodes, the dashboard and the rules pushed, each rule's first sample verified by value; (5) the proxy and D10's wiring through the canary rollout, the cache enabled from the first boot; (6) the live proof of D1: the fixture mint opens a margin position, the engine restarts inside a gap, its boot shows the position with Kraken's entry price, and the operating rule lifts. Steps 1–4 touch nothing the engine depends on and proceed while Rung 1 runs; steps 5 and 6 are held to Rung 2's design point on the owner's word, the operating rule standing until the proof reads clean. If upstream #5065 lands first, the margin half of the restart problem is fixed at the venue read and the cache's remaining value is recovery of orders and positions without depending on the venue at boot.

## The measured basis

Every reading below was taken on 2026-09-24 from the workstation or the engine host, no venue reached and no order sent; the library is the checkout's `.venv` at `2.0.0rc6.dev20260921`.

- **The library's client has one address and no Sentinel lookup.** The shipped stub declares `RedisCacheConfig.__init__` with exactly eleven fields, `host, port, username, password, ssl, connection_timeout, response_timeout, number_of_retries, exponent_base, max_delay, factor`; the compiled extension carries no `get-master` text and names Sentinel only in its error kinds (`MasterNameNotFoundBySentinel`), while `rediss` and the insecure-TLS refusal are present. The estimate's source reading at `70d887545790` agrees: `get_redis_url` builds one `redis://` or `rediss://` URL, `create_redis_connection` opens a single-node connection manager, and a username without a password panics.

```
awk '/class RedisCacheConfig/{p=1} p&&/def __init__/{q=1} q{print} q&&/\) -> None/{exit}' $STUB
SO=$(ls .venv/lib/python3.14/site-packages/nautilus_trader/_libnautilus*.so)
for s in get-master sentinel MasterNameNotFoundBySentinel rediss insecure; do printf '%-30s %s\n' "$s" "$(strings -n 5 "$SO" | grep -c -F -- "$s")"; done
```

## Out of scope

- Off-node backups: valkey3 is the copy outside the engine's region, and the venue and the ledger remain the truth.
- TLS on the wire: the mesh carries it.
- Sharding, load balancing and any read path beside the engine's.
- Sentinel or a resolver on the engine host: the proxy is the engine's only view.
- hc.io checks for the nodes: the Alloy-dark rules are their dead-men.
- Trimming keys: growth is alerted, not pruned.
- Postgres, read at the estimate and not revisited.

## Spec amendments

- **D7, amended 2026-09-25.** "Every new cap takes a leg under the fleet's memory-headroom rule" now covers the Alloy caps alone. That rule parses `process_resident_memory_bytes`, which neither daemon publishes (Valkey's exporter reports its memory as `redis_memory_used_rss_bytes`, and Sentinel's no memory family), so their caps carry no leg, and Valkey's memory is watched against `maxmemory` by D12's 70% rule. D12's headroom legs follow.
- **D9, amended 2026-09-25.** The reset's effect is stated by the runbook's config-reset procedure; its rejoin procedure restarts a node and renders nothing. A changed password is applied to the three nodes in one stop: a replica authenticates to its primary and each Sentinel to each Valkey and to the other Sentinels, so a node reset alone to a new password fails against the two still holding the old one.
- **D12, amended 2026-09-25.** The handshake-age probe runs on all four mesh members, the engine host included, so each link is watched from both ends, and the engine host's capture Alloy admits its family; the headroom legs are the Alloy caps' (D7).
