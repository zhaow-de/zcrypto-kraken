# Runbooks — what to do when something demands action

You are here because an alert fired in Slack, because a guard in the code pointed you here, or because you mean to do something to the fleet. An alert names its section `Runbook: infra/runbooks/<file>.md#<anchor>`, a guard names it by the same file and anchor, and a procedure is found by its file and heading: `grep -n '^## ' infra/runbooks/*.md`. This file holds the scope below and nothing else.

## Scope — what belongs here, and what does not

- **Procedures** for a signal that fires at an operator, procedures an operator opens on purpose, and **accepted limitations** an operator may run into while debugging. Nothing else.
- **This is not a backlog.** If acting on a section produces work, put it where work lives: something needing a *decision* opens a `T<NNNN>` under `docs/open-topics/` through the `topic-ops` skill; something needing *doing* goes in the memo queue. Deferrals do not accumulate here — a runbook nobody can finish reading is a runbook nobody reads.
- **Four parts, in this order**: *What you are seeing* · *What it means* · *What to do* · *Retire when* — for ALERT, KNOWN LIMITATION and SCHEDULED REMINDER sections. A PROCEDURE carries those four, a drill's seven spec `00105` names, or, for a run an operator performs end to end, its numbered steps. The same order each time, so a cold reader can skim.
- **Four kinds, marked in the heading, and the kind is the section's trigger**: `— ALERT` is named by a rule's `Runbook:` link in `infra/grafana/alerts.yaml`; `— KNOWN LIMITATION` and `— SCHEDULED REMINDER` by the guard, comment, test or reminder that sends the reader here — a tracked file under `cli/`, `infra/`, `tests/` or `.claude/`, naming the section by file and anchor; `— PROCEDURE` by the intent its heading states — nothing fires it. A section with no kind, or a kind nothing names, has no trigger (set: the `## ` sections of `infra/runbooks/*.md`, this file aside; count: `infra/scripts/count-list.sh runbook-sections-without-a-trigger`).
- **A step names the sanctioned program that executes it.** A step with no such program is a credential-handling improvisation waiting for an operator — write the program's invocation, or do not write the step.
- **A drill's output is a runbook section, never a report** (no count command: nothing in the tree records a report that was not written).
- **A universal in a page's bullets is counted or declared uncountable** — a bullet whose prose outside code spans carries *every*, *never*, *always*, *only*, *any* or *cannot* names its set and a count command from `infra/scripts/count-list.sh`, or declares `(no count command: <why>)`: the test the corpus and the contracts take, extended to the pages on the owner's ruling of 2026-09-11 — the count reads 0, so the pages are in the commit guard's contract set and a new uncounted universal is refused where it is written (set: the bullets of `infra/runbooks/*.md`, this file aside; count: `infra/scripts/count-list.sh runbook-universals-without-a-count`).
- **An internal token never sits inside a bullet or a numbered step** — `Phase <N>`, `T<NNNN>`, `iter-<N>`, `spec <NNNNN>`, `WP<N>` or a spec decision number like `D4`: an operator who reached this page from an alert description cannot resolve one, so the step states the fact and names the operand — the module, the command, the record — instead. A paragraph and a table row may carry one, where provenance for a claim the tree cannot otherwise re-derive is worth keeping, and a token inside a real path stays, being the operand you need to open the file; a declaration's `why` is inside its bullet and takes the rule with it (set: the bullets of `infra/runbooks/*.md`, this file aside; count: `infra/scripts/count-list.sh runbook-bullets-with-an-internal-token`; the classes and the path exemption are `tests/test_internal_terms_not_operator_visible.py`'s, read over the same bullet reader as the universal rule above — the owner's ruling of 2026-09-12).
- Every ALERT, KNOWN LIMITATION and SCHEDULED REMINDER section carries a **Retire when** naming something checkable — a metric that stops existing, a rule absent from `infra/grafana/alerts.yaml`, a line no longer in the code. A retirement condition you have to *judge* is one nobody will act on (set: those sections; count: `infra/scripts/count-list.sh runbook-sections-without-a-retire-when`).

**A new section joins the subsystem file that already covers its signal, or mints a new `infra/runbooks/<subsystem>.md`.** Split a subsystem file when it exceeds ~12 sections, or gains a second subsystem's worth of material. Keep the explicit `<a name=…>` anchors byte-identical through any move, and update every citation in the same change: alert summaries, dashboard panel descriptions and code comments cite a section by **file and anchor**, so a section that moves without them leaves a paged responder holding a fragment and no next step. `tests/test_infra_alert_rules.py` is what fails when a citation and its anchor fall out of step. The anchors are explicit rather than heading-derived because the kind marker would otherwise become part of the slug.
