# Branch & PR workflow

- **`develop` is the integration branch.** Every branch — bug fixes, features, iterations, doc updates — is cut from `develop` and opens a GitHub pull request **into `develop`**.
- **`main` is release-only.** It advances solely by merging `release/<timestamp>` branches (cut from `develop` by the `/release` skill), and each such merge is tagged `v<major>.<minor>.<patch>`. Never branch off `main`, never open a PR into `main` for feature work, and never commit to `main` directly. After a release merges, `main` is back-merged into `develop` so the two stay in lock-step.
- **GitHub is the remote** — use `gh`.
- **One PR delivers ONE component, and the component must be nameable from durable repo state** — a memo queue item / `T<NNNN>` topic, a spec serial, or the defect a fix kills. Its spec, plan, implementation, fixes found along the way, and closeout all land in the **same** PR; a branch living for days with many commits is correct. The **PR-open gate**, checkable from repo state alone so a freshly compacted context RECOMPUTES the decision instead of improvising it:
  1. **Name the component** (spec / memo item / topic / the defect a fix kills). Cannot name it → not ready — report the branch's state instead of opening.
  2. **The component is complete**: its topic `resolved`, or `partial` with the remainder registered; nothing further on this subject is planned for this branch.
  3. **The word — in the multi-session setup it is `zcrypto-main`'s, by delegation** (`docs/reference/multi-agent-protocol.md`): a payload session sends main the component and its branch state and main opens the PR; a single attended session opens one only when the user explicitly says so — finish the branch, report ready, wait. Three standing exceptions. **The `ops-journal` branch**: the daily pass commits to it every run and, at a month change, opens and merges the finished month's PR on CI green with no review and no word — a month of all-clear entries has nothing to review, and a gate there is a place the routine stalls. **The daily pass's fix PR**: bounded to fixes off the capture write path, the live trade path, canonical data, and anything a host converges; merged on CI green. **And** a `/zcrypto-auto-exec` run opens and merges its own PRs at *item completion* — completion only: its prep for a parked attended step stays a reviewed, pushed branch with **no PR** (the skill's landing rule), and the attended session opens that component's single PR.
- **Both failure modes are equally wrong.** *Micro-PRs*: a green commit is never by itself a reason to open a PR — one-commit-one-file PRs on a subject that will be touched again strip reviewers of context. *Omnibus PRs*: a different component is never a reason to reuse an open branch — two queue items ⇒ two branches, however small each is.
- **An owner-directed fold-in rides the open PR** — named in the PR body under `## Changes` with the owner's word — never under `## Out of scope`, which holds only registered topics and explicit drops; the one case a second component shares a PR.
- **A trivial, already-verified one-liner while a related PR is open**: fold it into that PR as a small extra commit instead of a separate branch/PR; subagent review may be skipped for such fold-ins (see `commit-messages.md`). When unsure it qualifies, ask.
- Cut releases with the `/release` skill (commitizen; bump rules in `.cz.toml`). See `pull-requests.md` for PR titles.
